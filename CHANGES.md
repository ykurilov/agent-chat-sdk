# Что нового по версиям

## 0.93.0

Swift-ответы Одуванчика показывают картинки Markdown с подписью, включая картинки внутри абзацев. Приложение может загрузить файл с Mac своим авторизованным способом; ожидание и ошибка сохраняют высоту блока.

**Как обновить приложение:** обновить Swift-пакет до тега `v0.93.0`, затем передать `.agentChatImageLoader { address in ... }` на `AgentChatView` или `AgentChatMarkdown`. Загрузчик `@Sendable (String) async throws -> Data` получает исходный адрес без преобразования. Без него HTTP(S) загружается штатно, локальные пути остаются подписью. При собственном exhaustive switch по `ChatMarkdownBlock` добавить `.image`. [Контракт и ограничения](docs/swift-markdown-images.md). Сервер, веб-скины и база не меняются.

## 0.92.0

При открытии чата совпавший снимок истории больше не скачивается второй раз после подключения watch. Изменения между запросами и во время сверки сохраняются; при несовпадении и со старым сервером работает прежняя перезагрузка. Серверное чтение для сверки остаётся.

Появились лёгкие входы Одуванчика `/text` (статический SSR Markdown) и сценариев `/labels` (словари без доски). У хранилищ есть дешёвая проверка наличия сообщений; PostgreSQL получил индекс расходов по дате.

**Как обновить приложение:** все пакеты SDK одной версией, сервер и клиент вместе. Для сохранённого текста заменить импорт на `@ykurilov/agent-chat-skin-oduvanchik/text`; при необходимости подключить `/text/styles.css`. Интерактивные схемы/демо и копирование кода остаются у прежнего компонента. Подписи сценариев брать из `@ykurilov/agent-chat-flows/labels`. Вместо `listMessageLinks(chatId).length > 0` использовать `hasChatMessages(storage, chatId)` из core после проверки владельца. Индекс PostgreSQL добавляется штатной миграцией. Запрос каталога из настроек самого приложения SDK не объединяет. [Контракт и границы](docs/loading-performance.md).

В расширенном поле Одуванчика появился режим фишки рассуждений «только значок»: мозг и стрелка без обрезанной подписи. Подсказка и доступное имя сохраняют выбранный уровень; меню и смена уровня работают прежним путём.

**Как обновить приложение:** все пакеты SDK одной версией, затем `composerOptions={{ variant: "extended", reasoningChip: "icon" }}`. Стирать подписи через `ChatLabelsProvider` не требуется. По умолчанию подпись остаётся. [Настройка](skins/oduvanchik/README.md#три-вида-поля). Миграций нет.

## 0.90.0

Для модели доступны только актуальные версии выбранных карточек через `agent.contextBlocksHistory.latest`; сырая история сохраняется. `flow.reopen({ allowFinal: true })` позволяет приложению явно открыть тестовый разговор после `final`, не обходя `deadline`/`blocked` и срок программы. Вложения получили `unsentRetentionMs` (сутки по умолчанию, `null` отключает автоудаление по возрасту); PDF resolver совместим с обычной сборкой Next.js без вынесения всего пакета из неё.

**Как обновить приложение:** все пакеты SDK одной версией. Вместо обёртки истории включить `contextBlocksHistory: { latest: ["flow:state"] }` в `agent`; для нужных карточек добавить их ключи. Прямой вызов `FlowStore.reopenChat` тестового чата заменить на `flow.reopen({ ownerId, chatId, allowFinal: true })`, сохранив проверку права эксперта и снятие собственных бизнес-итогов приложения. Для ожидающих фото настроить срок `unsentRetentionMs` на всех обработчиках общего файлового хранилища. Убрать обход `serverExternalPackages` для всего пакета вложений, добавленный только ради `import.meta.resolve`. [Карточки](docs/context-blocks-refresh.md), [сценарии](docs/flows.md), [вложения](packages/attachments/README.md).

### Быстрый запасной провайдер при недоступности сети и 5xx

**Как обновить приложение.** Обновить пакеты SDK одной версией. Миграций нет, быстрый режим включён автоматически
при доступном запасном. Для немедленного перехода после ошибки добавить в существующий `providerFallback`

Настройка сокращает паузы повторов, но не гарантирует общий срок ответа: время соединения и генерации тоже входит
в ожидание. Полное молчание без ошибки по-прежнему ограничивается `modelSilenceTimeout`.

## 0.68.0 (19.10.2026) — flow.reopen: вернуться в брошенный разговор

### Брошенный разговор можно открыть заново: `flow.reopen`

Для приложения-генератора: человек бросил разговор и вернулся через несколько дней — агент продолжает тот же разговор
с памятью, а не начинает с нуля.

- **`flow.reopen({ ownerId, chatId, reason?, endedAfter? })`.** Открывает разговор, законченный `abandoned` или своей
  причиной приложения. `final`, `deadline`, `blocked` не открываются — ответ `{ reopened: false, reason }`.
- **Та же нода, история и память.** `admit` снова `answer`, `readRun` — живой разговор, в пути запись `reopen`.
- **Касания и часы ноды — от открытия**, как будто человек только что вошёл в ноду: «в ноде 20 мин» не уводит его
  сразу. Дни и срок программы — от исходного старта. Срок уже вышел —
  `deadline_passed`: иначе разговор тут же закончился бы сроком и ушло бы прощание.
- **Сколько дней ждать — решает приложение.** `endedAfter` — удобная проверка: закончился раньше — `ended_too_long_ago`.
- **`onReopen`** — событие, чтобы вернуть статус «идёт». Повтор безопасен, из двух копий приложения открывает одна.

Подробно — [docs/flows.md](docs/flows.md), «Открыть законченный разговор».

**Как обновить приложение.** Обновить `@ykurilov/agent-chat-flows`. В хранилище сценариев новое поле `reopened_at`:
миграции SQLite и PostgreSQL применяются сами при старте. Своё хранилище (`FlowStore`) — добавить метод
`reopenChat(chatId, { endedAt, at })` и поле записи `reopenedAt`. Статус «идёт» после открытия — в `onReopen`.

## 0.67.0 (19.10.2026) — потолок сообщений первым по дням программы, частые касания ноды до дня N

### Потолок «пишет первым» по дням программы и свои касания ноды до N-го дня программы

Для приложения-генератора: молчуну в первый день — как сейчас, со второго дня — не больше двух сообщений первым в
день. Дополнение к формату v2, старые сценарии работают как раньше.

- **`schedule.firstMessages.maxPerDayByDay`.** Список потолков по дням программы: `[3, 2]` — в день 1 не больше
  трёх, со дня 2 не больше двух (последнее значение — на все следующие дни). Задан — главнее `maxPerDay`.
  «Пишет первым» — только когда агент пишет сам (касание, утреннее, переход по сроку, прощание). Ответ человека
  счёт не обнуляет: день 2, утреннее и 12:00, человек ответил в 13:01 — касание в 16:01 при потолке 2 не уходит.
- **Почему у Игоря ушло третье в 16:01.** Ответ человека счёт не сбрасывал и раньше, это проверено тестом. В
  сценарии не был задан `maxPerDay`, поэтому действовал потолок по умолчанию — 3 в день. Утро, 12:00 и 16:01 — как
  раз три. Теперь потолок «2 со второго дня» задаётся прямо в сценарии.
- **`nudges.untilProgramDay` у ноды.** Частый ряд ноды действует, пока идёт день программы не позже N. Человек
  дошёл до ноды на день N+1 и позже — частого ряда нет, сразу общий. `nudges.days` по-прежнему считает от входа в
  ноду; заданы оба — конец по тому, что раньше.
- **Доска.** В «Днях и времени» поле «Не больше в день по дням программы» («3, 2»). У своих касаний ноды третий
  режим — «до дня программы включительно». Подписи ru/en. Договор скина: `FlowStateTimingProps` получил
  `nudgesUntilProgramDay` и `onNudgesUntilProgramDayChange`. Из `@ykurilov/agent-chat-flows/react` выгружены
  `parseCapsByDay` и `capsByDayText`.
- **Проверка.** `checkFlow`: `untilProgramDay` не целое или меньше 1 — ошибка `nudges_until_day_invalid`, больше
  срока программы — предупреждение `nudges_until_day_after_end`. Список потолков длиннее программы —
  предупреждение `max_per_day_by_day_after_end`.

**Как обновить приложение.** Обновить `@ykurilov/agent-chat-flows` и `@ykurilov/agent-chat-skin-tandem` вместе.
Сценариям ничего менять не нужно. Нужен потолок по дням — задать `maxPerDayByDay` на доске или в JSON. Свой скин
доски должен показать новый режим касаний: в `FlowStateTimingProps` есть `nudgesUntilProgramDay` и
`onNudgesUntilProgramDayChange`.

## 0.66.0 (19.10.2026) — починка JSON внутри строкового поля и лишней скобки, короткая ошибка аргументов, repairToolInput

### Кривые аргументы инструментов: чинится больше, ошибка короткая, у приложения есть своя точка входа

Продолжение починки из 0.46 и 0.63. Ничего не ломает.

- **Что чинится теперь.** Лишняя `}` или `]` посреди объекта (`{"a": {"b": 1}}, "c": 2}`). Поле-список или поле-объект,
  пришедшее строкой с JSON внутри (`"changes": "[{…}]"` вместо `[{…}]`), разбирается по схеме, и скобки в этом JSON
  чинятся тем же правилом. Это настоящие вызовы из прогона оценки приложения-генератора 2026-10-19: лишняя `}` перед
  `]`, лишняя `}` после `]`, забытая `]` в конце. Чинится, только если результат проходит схему инструмента.
- **Короткая ошибка модели.** Раньше при отказе модель получала `AI_TypeValidationError` со своими аргументами целиком
  (до десятков тысяч знаков). Теперь 1–2 строки: «аргументы не разбираются как JSON: лишняя `}` около позиции N
  (…кусок 30 знаков…); пришли вызов заново» или «аргументы не подходят по схеме — changes.0: …». Это экономит
  токены и не даёт модели повторять ту же простыню.
- **Своя починка приложения.** Опция `agent.repairToolInput({ toolName, text, error })` зовётся после встроенной
  починки и до отказа; возвращает починенный JSON-текст или `undefined`. Результат проверяется схемой. Встроенный
  починщик доступен как `repairToolArguments(text)`.
- **Журнал.** В строке `[аргументы починены]` в `правка=` появились `JSON из строки` и `правка приложения`.
  В `ToolInputRepair` новые поля `nestedJson` и `byApp`.

### «Агент написал первым — человек молчал 1 ч 7 мин»

- Ядро: право чата `appNotices` (по умолчанию `false`, как `errorDetails`; `modelDetails: false` выключает и его,

- React: `noticeLines` у `AgentChat` (и `ChatWorkspace`, `AgentPanel`) — имя пометки → строка. Механизм общий: свои

- Тандем рисует `ServiceLine`.

1. На сервере откройте право тестовым чатам (и экрану проверки, если он есть):

2. В подключении тестового чата передайте строки в чат:
   `renderChat: (chatId, { noticeLines }) => <AgentChat … noticeLines={noticeLines} />`.
3. Свой экран проверки: `<AgentChat … noticeLines={flowNoticeLines()} />` (английские подписи —
   `flowNoticeLines(englishFlowNoticeLabels)`).
4. Свои надписи `FlowLabels`: добавьте `notices` (готовые — `russianFlowNoticeLabels`, `englishFlowNoticeLabels`).
5. Свой скин (не Тандем): нарисуйте `ServiceLine` — без него строк не видно, остальное как раньше.
6. Свои литералы `Required<ChatCapabilities>` (полный набор прав) — добавьте `appNotices`.
7. Свои пометки приложения на экран: `createChatService({ appNoticeViews: { my_notice: (data) => ({ … }) } })` —
   без функции пометка не покажется. С `flow.withChat` сценарные функции добавляются к вашим.

- Скин: у `FlowTestChatFrameProps` новые необязательные `onNextFirstMessage`, `nothingScheduled`, `onAdvanceText`;
  надписи `nextFirstMessage`, `nothingScheduled`, `customTime`, `customTimePlaceholder`, `customTimeInvalid`.
  Тандем их уже рисует.

**Как обновить приложение.**

1. На сервере в адрес перемотки тестового чата пропустите `to: "next_first_message"` и отдайте код ошибки:
   `catch (error) { if (error instanceof FlowTestClockError) return c.json({ code: error.code }, 409); }`.
2. В подключении тестового чата добавьте

### Админ видит, почему не ответила модель

**Что было.** Сбой провайдера человек видел мягкой надписью вроде «На счёте провайдера закончились деньги». Админу
этого мало: какой провайдер, что именно сказал, когда снова заработает — было только в журнале сервера.

**Что стало.** Упавший ответ хранит подробности: провайдер, модель, код ответа, причину одной строкой и дату, когда
провайдер снимет предел (если сообщил). Пример: у ключа OpenRouter кончился месячный бюджет — причина «Key limit exceeded
(monthly limit)…», `resetsAt` — 1 ноября. Дата берётся только из сообщения о пределе, только в будущем и не дальше
двух лет; время без пояса — UTC.

Что вычищается из причины: ключи провайдеров из окружения сервера; `Bearer …` в любом регистре; значения после `key=`,
`token`, `api-key`, `secret`, `password` (если похожи на ключ: от 8 знаков, буквы и цифры); маски ключей со звёздочками
(`sk-proj-****abcd`); параметры адресов (`?token=…`); id организации и проекта (`org-…`, `proj_…`) и e-mail. Ответ
модерации может повторять текст человека — его увидит только тот, кому открыто право.

Всё, что попало в браузер, видно любому через инструменты разработчика. Поэтому подробности уходят на экран только
тому, кому приложение разрешило: новое право `errorDetails` в `chatCapabilities`. По умолчанию оно выключено, обычный
человек видит то же, что раньше.

**Как обновить приложение.**

1. Ничего не делать — всё как раньше: надписи прежние, подробностей в браузере нет.
2. Открыть подробности админу: `chatCapabilities: ({ userId }) => (isAdmin(userId) ? { errorDetails: true } : {})`.
   При `modelDetails: false` право выключено и так — служба один раз напишет об этом в журнал.
3. Показать их в надписи: `labels.errorText: (error, plain) => …` — `error.details` (`providerId`, `modelId`,
   `statusCode`, `reason`, `resetsAt`), `plain` — прежний текст. Без функции надпись прежняя. Функция бросила
   исключение — тоже прежняя, плюс одна запись в консоль.
4. Если сравниваете права целиком (`toEqual`) — в них теперь есть `errorDetails: false`. Если ждёте в `afterTurn` или
   хранилище ровно `error: { kind }` — там может быть и `details`.

Миграций базы нет: подробности лежат в той же колонке `error`.

## 0.62.0 (15.10.2026) — судья сценария смотрит только текущий этап, журнал входа судьи

### Судья после хода не берёт реплики прошлого состояния и пишет журнал

**Что было.** В приложении сценарий перевёл человека из «Доработки» в «Курс». Условие выхода: «человек сам
спросил про свой домен… или про курс». Человек про курс не спрашивал. Судья дал 0,92. Причина нашлась в старой реплике.

них. По нему судья и решил, что человек спросил про домен. Вживую тот же вход давал 0,80–0,93 пять раз из пяти. Без
этой одной реплики — 0,01. Значит, дело не в случайном разбросе судьи, а в старой реплике на входе. Был и второй

судье, нигде не записывалось.

- Судья после ответа смотрит реплики с ответа агента, на котором чат вошёл в состояние, до ответа этого хода. Место
  чата помнит этот ответ (`enteredAfterAnswer`). На этом случае — 0,01 вместо 0,9.
- Окно считается по истории ветки, а не по счётчику ходов. Человек уже написал дальше, пока судья читал историю, — это
  в окно не попадает. Сообщение, легшее в ветку без хода, — попадает.
- Ответ агента этого хода судья видит всегда: если история его ещё прячет, судья берёт его из итога хода.
- Журнал судьи: что ушло (цель, реплики, условия, усечённо, без ключей) и что ответил. По умолчанию тексты пишутся
  только в тестовом чате редактора. Боевой переход по судье пишется без текстов реплик: выход, вероятность, число
  реплик и их длины. `judge.journal: "transitions"` — боевые переходы с текстами, `"always"` — каждый вопрос с
  текстами, `"off"` — никогда. Приёмник — `logJudge`, по умолчанию `console.info`.
- Заявки агента (`flow_exit`) не менялись: судья видит последние реплики.

**Как обновить приложение.**

- Обновите `@ykurilov/agent-chat-flows`. Новое поле в месте чата появится после первого же перехода. До него судья
  видит последние реплики, как раньше.
- В журнале сервера появятся строки `[сценарий] судья: {…}` при переходах по судье, без текстов реплик. Нужен другой
  приёмник — передайте `logJudge`. Не нужен журнал — `judge: { journal: "off" }`.
- Для разбора спорных переходов поставьте `judge.journal: "transitions"` на время проверки. Тексты реплик тогда попадут
  в журнал сервера, до 300 знаков на реплику.

## 0.59.0 (15.10.2026) — вырезка поддельных служебных блоков в ответе модели

### Поддельные служебные блоки вырезает ядро

**Что было.** Модель видит в запросе служебные блоки: память `<agent_memory>`, место на экране `<screen_place>`,
служебные пометки, строки сценария. Иногда она повторяет такой блок в конце своего ответа. Человек видел на экране
кусок памяти в JSON, а блок оставался в записи и уходил модели в следующих ходах. Общей вырезки в SDK не было никогда.
обучающее приложение вырезал блоки сам: своим списком тегов, обёрткой хранилища и фильтром потока.

**Что теперь.** У ядра один список служебных форматов. В нём форматы ядра (`CORE_SERVICE_BLOCKS`), пакетов и приложения:

- память добавляет `<agent_memory>`, вложения — `<attachment>`, `withSkills` — `<skill>` и список навыков,
  `flow.withChat` — строки перехода, «скажи ровно это» и карточку клиента;
- свои форматы приложение передаёт в `agent.serviceBlocks`: тег `{ tag: "lesson_step" }` или строку
  `{ name, line, match?, until? }`. Ошибка в формате — `TypeError` при создании службы.

Блок, который начинается с начала строки, вырезается в потоке: до экрана, записи и следующего шага он не доходит.
Незакрытый тег режется только до первой пустой строки. Тег с пояснением в той же строке («`<agent_memory>` — это…»),
закрывающий тег без открывающего, блок после «Формат такой:» или «Например:» и ответ на вопрос о тегах и форматах не
трогаются. Агенту, который должен показывать служебные блоки, лучше показывать их в блоке кода.
В прошлых ответах — только в запросе к модели, запись не меняется, запрос байт в байт тот же (кэш). Код, цитаты и
упоминания посреди фразы не трогаются. Если кроме блока в ответе нет ни слова, блок остаётся: пустой ответ хуже.
Каждая вырезка — строка в журнал ошибок: `[служебный блок вырезан] тег=… чат=… ответ=… модель=… провайдер=…`.

**Как обновить приложение.**

1. Обновите `@ykurilov/agent-chat-core` и пакеты, которые подключены (`memory`, `attachments`, `skills`, `flows`).
2. Если у приложения своя вырезка служебных блоков — уберите её. Для обучающего приложения:
   - удалите `src/lib/lesson-chat/service-blocks.ts` и `src/lib/lesson-chat/hidden-service-blocks.ts` с их тестами;
   - в `chat-foundation.ts` уберите обёртку `hideServiceBlocksInStorage`, в `lesson-chat-handler.ts` —
     `hideServiceBlocksInResponse`;
   - `agent_memory` и `screen_place` теперь знает SDK. `conversation_summary` и `answer_progress` — тоже: это форматы ядра.
3. Свои теги, которых нет в SDK, передайте в `agent.serviceBlocks: [{ tag: "мой_тег" }]`.
4. Журнал: строка теперь `[служебный блок вырезан] тег=… чат=… ответ=… модель=… провайдер=…` — без `время=`,
   с `ответ=` и `провайдер=`. Поправьте поиск по журналу, если он был.

## 0.58.0 (15.10.2026) — запасной провайдер при нехватке денег и плохом ключе, брошенная пачка своей службе, PostgreSQL на пустой базе

### Брошенная пачка — службе своей версии

**Что было.** `answerAfterRestart` не годился, когда в приложении несколько служб чата на одном хранилище. Например,
своя служба на каждую опубликованную версию продукта (у каждой своя инструкция) плюс служба восстановления. Брошенную
при перезапуске пачку брала та служба, которая первой проверила брошенные. После рестарта мог ответить консультант без
инструкции или с чужой версии. Поэтому такие приложения держали свою очередь пачек.

**Что теперь.** У службы есть параметр `abandonedBursts: { serviceFor }`. Обход брошенных пачек (при старте,
регулярный, `tickBursts`) спрашивает `serviceFor({ ownerId, chatId, chat })` и отдаёт пачку той службе, которую она
вернула. Нужной службы ещё нет — `serviceFor` может создать её на лету (можно асинхронно). Вернула `null` или упала —
никто не отвечает, строка в журнал, пачка ждёт следующего обхода через 30 секунд. Чужая служба её не возьмёт, пачка не
теряется. Отвечает по-прежнему одна копия.

Почему не фильтр «мои ли это чаты» у каждой службы: службы старых версий создаются по требованию. С фильтром пачка
старой версии ждала бы, пока кто-то случайно создаст её службу. `serviceFor` создаёт её сам.

**Как обновить приложение.**

1. Обновите `@ykurilov/agent-chat-core` (и `@ykurilov/agent-chat-server`, если службы создаёт он).
2. Заведите одну функцию выбора службы по чату и передайте её всем службам на этом хранилище:

   ```ts
   const abandonedBursts = {
     serviceFor: async ({ chat }) => serviceForVersion(await versionOfChat(chat)), // создаёт службу, если её нет
   };
   const service = createChatService({ storage, agent, abandonedBursts /* , … */ });
   ```

   `createChatServer` принимает тот же параметр. Чат не относится ни к одной версии — верните `null`: пачка подождёт.
3. Перед `recoverInterruptedAnswers` подпишитесь на события каждой службы (`service.subscribeEvents`). Ход без вызова
   приходит событием `turn-started` с `unattended: true`.
4. Включите `answerAfterRestart: true` в `sendBurstMessage`.
5. Уберите свою очередь пачек (таймер окна, свою таблицу ждущих пачек и её разбор при старте). Окно, ожидание и ответ
   после перезапуска теперь делает SDK.

### Кончились деньги у провайдера — ходы идут через запасной

**Что было.** 14.10 на счету DeepSeek кончились деньги. Ученики 8 раз получили «у провайдера модели кончились
средства», хотя запасной OpenRouter был настроен и работал. Запасной брался только при перегрузке и лимите, а пустой
счёт (402) и непринятый ключ (401/403) сразу давали ошибку.

**Что теперь.** Пустой счёт или непринятый ключ — без повторов сразу следующий провайдер из списка запасных. Так в
любом шаге хода и у помощников. Отказавший провайдер 5 минут на паузе: новые ходы всей службы сразу идут к запасному,
не стуча в пустой счёт. После паузы основного пробует один ход, а не все разом. Запасных нет или они тоже не ответили —
прежняя ошибка. Человек видит причину у основного, если тот отказал в этом ходе, а если запасной лишь перегружен —
«попробуйте позже». На паузу ставят только явные отказы: 402, 401 и 403 со словами о ключе или деньгах. 403 по региону
или доступу к модели — переход к запасному без паузы. 403 модерации — ошибка без перехода. 429 со словами «quota
exceeded» (лимит в минуту у Gemini) — снова лимит запросов с повторами, а не пустой счёт. В журнале — строка
`[запасной провайдер] … причина=insufficient_funds` (или `invalid_key`). Владельцу — громкая строка не чаще раза в 15
минут на провайдер: `[ВНИМАНИЕ провайдер] deepseek: кончились деньги — ходы идут через запасной openrouter`. Подробно —
в [getting-started](docs/getting-started.md), раздел «Что делает сервер сам».

**Как обновить приложение.**

Обновите `@ykurilov/agent-chat-core`. Новых настроек нет: переход работает с тем же `providerFallback`. Запасные
выключены (`providerFallback: false`) — всё по-прежнему, только в журнале появится строка `[ВНИМАНИЕ провайдер]`.
Настройте поиск по ней в своих оповещениях (например, grep журнала контейнера), чтобы узнавать о пустом счёте сразу.

### PostgreSQL: пакеты стартуют разом на пустой базе

**Что было.** Приложение с навыками и серверами MCP запускали на совсем пустой базе PostgreSQL. Оба пакета
одновременно создавали одну и ту же схему `agent_chat`. Один успевал, второй падал с ошибкой «Failed query: CREATE
SCHEMA IF NOT EXISTS», и его хранилище не работало до перезапуска. То же могло случиться с любой парой пакетов на
PostgreSQL. Если схему заранее создавало хранилище чатов, беды не было.

**Что теперь.** Схему `agent_chat` создаёт тот пакет, кто успел первым, остальные коротко ждут. Потом каждый пакет
применяет свои миграции и других не ждёт. Если два пакета всё же столкнулись на «такое уже есть», шаг повторяется
сам. Касается всех пакетов с PostgreSQL: хранилища чатов, песочницы, фона, сценариев, навыков, MCP, мессенджеров и
картинок. Проверено одновременным стартом всех восьми хранилищ на пустой базе: на встроенном PostgreSQL и 15 раз
подряд на настоящем.

**Как обновить приложение.** Обновите пакеты, больше ничего делать не нужно. Порядок открытия хранилищ и заранее
созданная схема больше не нужны. Для своих пакетов на той же схеме в core есть помощник `migratePostgresSchema`.

### Окно тишины пачки: по часам службы и через перезапуск

**Что было.** `sendBurstMessage` считал окно тишины по часам службы (`now`), а ждал по настоящим. В тестах и прогонах
с остановленными часами ход так и не начинался. А ждущая пачка жила только в памяти: перезапустился сервер посреди
окна — ответа нет, пока канал сам не повторит вызов. Без своей очереди повторов сообщение терялось.

**Что теперь.** Окно ждётся по тем же часам. Сдвинули подменённые часы, вызвали `service.tickBursts()` — ход начался
сразу. С флагом `answerAfterRestart: true` пачка записана в хранилище до ответа. После перезапуска ей ответит

после окна. Живая копия, пока ждёт, продлевает удержание пачки — чужая её не возьмёт. Отвечает всё равно одна копия.
Такой ход приходит событием `turn-started` с `unattended: true`. Упёрся в предел одновременных ходов — пачка ждёт
следующего обхода, а не теряется. Отказ приложения или лимит расходов — строка в журнал, а `beforeTurn` и
`turnNotStarted` получают `unattended: true`: приложение может само сказать человеку. Без флага всё как раньше:
мессенджеры SDK повторяют вызов сами.

То же — между репликой сотрудника и следующим вопросом человека. Агент мог решить, что сломался, и извиняться.

**Что теперь.** В запросе модели реплика сотрудника идёт в одном сообщении с соседними словами человека, через пустую
строку. Заглушка остаётся только там, где ход и правда оборвался. Запрос по-прежнему зависит только от истории: кэш модели цел.

**Как обновить приложение.**

1. Обновите `@ykurilov/agent-chat-core` и пакет хранилища (`storage-sqlite` или `storage-postgres`). Таблица ждущих
   пачек создастся сама при открытии хранилища.
2. Не используете пачки (`sendBurstMessage`) — код менять не нужно.
3. Тесты и прогоны с подменёнными часами (`now`): после сдвига часов вызывайте `await service.tickBursts()` вместо
   настоящего ожидания.
4. Своей очереди повторов у канала нет — передавайте `{ answerAfterRestart: true }` в `sendBurstMessage`. Подпишитесь на
   события (`service.subscribeEvents`) до `recoverInterruptedAnswers`. На `turn-started` с `unattended: true` заберите
   ответ через `service.subscribe(userId, chatId)`, а если он вернул `null` (ход уже кончился), — из истории чата, и
   отправьте человеку. Отказы такого хода ловите в `turnNotStarted` и `beforeTurn` по `unattended: true`. Своё
   хранилище — добавьте методы `savePendingBurst`, `takeAbandonedBursts`, `renewPendingBurst`, `removePendingBurst`
   (проверка — `describeChatStorageContract` с `pendingBursts: "required"`). Канал, который сам повторяет вызов, флаг
   не ставит.

### Ответ, сорвавшийся в кашу, обрезается

**Что было.** Изредка модель теряет конец своего хода: после ответа пишет «userНу…» за человека, снова думает вслух,
отвечает себе и даже вызывает инструмент. Всё это сохранялось как ответ, человек видел кашу, а модель на следующих ходах
видела её в истории и повторяла.

**Что теперь.** Ядро распознаёт срыв по месту срыва и ещё одному признаку. Место срыва — строка с ролью с начала строки
сразу после законченной фразы. Второй признак — служебные метки, новый ход после места срыва или вызов инструмента после
`userНу…`. Правило общее для всех моделей. Код, цитаты, метки прозой, `</think>` в начале шага у DeepSeek, диалог и
шаблоны чатов (ChatML, Llama 3, DeepSeek) с ролями за обоих не трогаются.
- При сохранении текст отрезается с места срыва, ответ сохраняется законченным. Выполненные вызовы остаются в записи.
  Если без хвоста не осталось бы текста, ответ не режется. В журнал ошибок — `[хвост обрезан] … признаки=… знаков=…
  вызовов_не_запущено=…`.
- В потоке — то же правило, только на целых строках. Сработало — хвост перестаёт идти на экран, вызовы после места
  срыва не запускаются (и подтверждения не просят), следующего шага нет; в конце хода экран показывает обрезанный ответ.
- Старые ответы с кашей режутся перед отправкой модели, только в запросе: база не меняется, запрос от хода к ходу тот же.

Подробно — [docs/getting-started.md](docs/getting-started.md), «Ответ, сорвавшийся в кашу».

**Как обновить приложение.** Обрезка включена сама, менять в коде ничего не нужно. У чатов, где в истории уже есть
ответ с кашей, кэш модели один раз сбросится: запрос теперь уходит с обрезанным ответом. Если у вас свой разбор журнала
ошибок, новые строки начинаются с `[хвост обрезан]` и `[хвост не обрезан: ответ остался бы пустым]`.

### Навыки агента: указания для отдельных задач, которые агент грузит сам

**Что было.** Научить агента новой задаче («разработка игр», «оформление договора») можно было только инструкцией.
Инструкция росла с каждой задачей, модель читала её целиком в каждом запросе, а правка одной задачи сбрасывала кэш
модели во всех чатах.

**Что теперь.** Новый пакет `@ykurilov/agent-chat-skills`. Админ пишет навык на экране приложения: имя, «когда брать»
(1–2 фразы) и указания в markdown. Агент видит только список включённых навыков: имя и «когда брать». Подходит
задача — сам загружает указания инструментом `use_skill`. Пример: «сделай змейку» — агент грузит `game-dev`, «поправь
цвет кнопки» — не грузит ничего.

- **Кэш модели.** Список лежит в блоке контекста хода, а не в инструкции и не в описании инструмента. Инструкция и
  инструменты одни на все чаты, у админа и у человека. Пока навыки не правят, запрос к модели от хода к ходу
  начинается одинаково. Правка навыка меняет только новый вопрос, старая часть запроса остаётся байт в байт.
- **Повторная загрузка.** Те же указания ещё видны модели в переписке или уже отданы в этом ходе — короткий ответ «уже
  загружен выше». После сжатия истории, на другой ветке, после правки навыка или если его удалили и создали заново с
  тем же именем — указания приходят заново.
- **Кому виден.** Статус навыка: выключен, только админам, всем. «Только админам» видны по `viewer.isAdmin` ядра
  (права из базы приложения, раз в начале хода; см. раздел про `agent.viewer` ниже), в группе — никогда. В копии
  чата человека у сотрудника права человека, как у серверов MCP, если `viewer` считает права по `ownerId`. Чужой не узнает, что такой навык есть: ответ тот же,
  что про несуществующий. `isAdmin` пакета решает только доступ к экрану навыков.
- **Экран.** `SkillsAdmin` и скин `@ykurilov/agent-chat-skin-tandem/skills`: список со статусом и числом загрузок,
  правка с предпросмотром (HTML не исполняется), история версий с разницей и откатом, удаление, последние чаты, где
  навык загружали. Не админу — 404 и в API, и на экране. Одновременная правка не затирает чужую: 409 и «загрузить свежую».
  Уход к другому навыку или откат при несохранённых правках сперва спрашивает; закрытие вкладки предупреждает.
- **Учёт.** Каждая загрузка записывается (навык, версия, чат, человек, ход) и пишется строкой в журнал сервера.
- **Хранилища.** SQLite, PostgreSQL и память; таблицы `skills`, `skill_versions`, `skill_loads` создаются сами.
  Список для вопроса модели и экрана читается без тел (`listBrief`).
- **Скин Тандема.** Клик по обезвреженной ссылке (`javascript:`) в ответе агента больше не перезагружает страницу, а
  средняя кнопка мыши не открывает её в новой вкладке: ничего не происходит. Обычные ссылки работают как раньше.

Подробно — [packages/skills/README.md](packages/skills/README.md) и [docs/getting-started.md](docs/getting-started.md),
«Навыки агента». Пример — `apps/demo`, страница `/skills`.

#### Как обновить приложение

- Ничего делать не нужно, если навыки не нужны: без пакета ничего не меняется.
- Подключить: `pnpm add @ykurilov/agent-chat-skills`; на сервере `createSkills({ store, isAdmin, chatStorage })`,

### Ядро: права человека на ход — `agent.viewer`

**Что было.** Права человека (админ ли, какой тариф) часто лежат в базе приложения. А набор инструментов строится
синхронно, и пакеты вроде MCP могли спросить «админ ли» только синхронной функцией.

**Что теперь.** Необязательное `agent.viewer: async ({ userId, ownerId, chatId, … }) => ({ isAdmin, … })`. Ядро зовёт его
один раз в начале хода, до блоков контекста и сборки инструментов. Повтор хода и запасной провайдер его не зовут снова.
Ответ приходит полем `viewer` в `contextBlocks` и в `AgentToolsModel`; инструменты сжатия и фонового помощника
получают его так же — с каналом и группой чата (в группе — без админских инструментов) и сроком ответа 10 с. В запрос к модели он не попадает: кэш модели от него не зависит. `isAdmin` — общий признак для
пакетов (MCP, навыки). Функция бросила или вернула не объект — ход кончается ошибкой, в `logError` строка
`[agent.viewer] …`; молча «не админом» человек не станет. В песочнице права считаются по владельцу чата: в копии чата
человека — по человеку. Подробно — [docs/in-product-agent.md](docs/in-product-agent.md), раздел 15.

#### Как обновить приложение

- Ничего, если `viewer` не нужен: без него всё как раньше.

### Серверы MCP от админа — новый пакет `@ykurilov/agent-chat-mcp`

**Что было.** Чтобы дать агенту чужой сервис (документацию библиотек, задачи, CRM, поиск по коду), приложению нужно
было писать инструмент под каждый сервис.

**Что теперь.** Админ на экране «Серверы MCP» вставляет адрес сервиса, видит его инструменты и включает нужные — агент
пользуется ими сам. Проверено вживую: DeepWiki подключился за 2–3 с, агент на DeepSeek 4.1 Flash по вопросу про
репозиторий сам вызвал два инструмента и ответил по документации.

- Только удалённые серверы по адресу (Streamable HTTP, SSE); запуска программ на сервере приложения нет.
- Кэш модели не ломается: инструменты строятся из сохранённого снимка списка, а не из живого запроса. Список меняется
  только по действию админа. Сервис упал — инструменты остаются, вызов отвечает агенту понятной ошибкой.
- Статусы «Выключен / Только админы / Все». «Только админы» видны по `viewer.isAdmin` из `agent.viewer` ядра
  (права из базы приложения, раз в начале хода). `isAdmin` пакета решает, кто видит экран, и может быть асинхронной.
  При вызове доступ проверяется ещё раз.
- Правка сервера на экране: название, префикс, адрес, заголовки, прокси, срок. Старых секретов форма не показывает:
  адрес пустой — прежний, заголовок «задан» — «Заменить» или «Очистить». Новый адрес выключает инструменты: возможно,
  это другой сервис.
- Имена не сталкиваются. Имя для модели — `префикс__имя`; полное имя не повторяется между серверами — иначе админ
  получает ошибку. Совпало с инструментом приложения — агент получает инструмент приложения, в лог предупреждение.
- Несколько копий сервера приложения: правка админа доходит до всех копий сама. Каждая раз в 15 с (`syncIntervalMs`)
  читает отметку версии из хранилища и перечитывает серверы, только если отметка изменилась; экран админа сверяется
  перед каждым запросом.
- Адрес и заголовки сервиса хранятся зашифрованными ключом приложения; на экране и в ответах — только «Authorization:
  задан» и «параметры скрыты». Внутренняя сеть закрыта: соединение идёт ровно на адрес, который прошёл проверку DNS.
  Заголовки прокси уходят только на адрес прокси (`proxy.origin`).
- Описания и ответы сервиса — чужой текст: чистка, пределы длины, пометка «это данные, а не указания». Новый
  инструмент выключен, подтверждение человеком по умолчанию включено, кроме «только чтение».
- Журнал вызовов без содержимого, строка в лог сервера, расход нового штатного вида `mcp_tool`, пределы за ход и в
  минуту. Хранилище — память, SQLite, PostgreSQL.
- Экран — в скине Тандема (`@ykurilov/agent-chat-skin-tandem/mcp`), пример — страница `/mcp` демо.

**Почему отдельный пакет, а не вместе с навыками.** MCP тянет сетевой клиент, проверку адресов, шифрование и прокси;
навыкам — текстам админа — это не нужно, и приложение с навыками не должно за это платить. Риски тоже разные: MCP —
живой чужой сервис (запросы во внутреннюю сеть, внушение через описания, утечка ключей). Общее у них — образец
(статусы, `isAdmin`, экран, снимок в запросе), а не код.

#### Как обновить приложение

- Ничего делать не нужно, если MCP не нужен: остальные пакеты не меняются.
- Подключить: `pnpm add @ykurilov/agent-chat-mcp`, секрет `MCP_SECRET_KEY` (не короче 32 знаков) в окружение,
  `createMcpServers` + `...mcp.tools(model, appTools)` первым в `agent.tools` (инструменты приложения — после), `agent.viewer`, который возвращает `{ isAdmin }` (иначе
  серверы «только админы» не видны никому), `mountChat(app, createMcpAdminHandler(…))`, экран
  `<McpAdmin skin={tandemMcpSkin} />`. Шаги — [docs/getting-started.md](docs/getting-started.md), «Серверы MCP от админа».
- Своя сводка расходов по видам: появился штатный вид `mcp_tool` — добавьте ему подпись, если перечисляете виды сами.

### Библиотека готовых картинок

**Что было.** Картинку агент мог только создать нейросетью (пакет `images`). Показать готовую схему из материалов
приложения было нечем. К тому же в чате мог быть только один источник картинок: `images={…}` принимал одного клиента.

**Что теперь.** Новый пакет `@ykurilov/agent-chat-image-library`. Приложение даёт каталог: id, название, `alt`
(обязательно), адрес, ширина и высота, по желанию описание, понятия и теги. Агент ищет через `find_images` и показывает
через `show_image` только картинки из каталога. Чужой id или адрес — отказ. Картинка встаёт по ширине ответа с подписью,
по нажатию открывается окно просмотра. Она хранится в истории: видна после перезагрузки и в песочнице.

- Каталог — массив (библиотека берёт замороженную копию), функция (меняется без перезапуска) или
  `source: { search, get }` для большой базы. Функциям каталога — 5 с на ответ, дольше — «каталог недоступен».
- Адрес — путь своего сайта или `https` на доменах из `allowedHosts`.
- Описания инструментов постоянные, модель после показа видит только «показано: название»: кэш модели цел.
- `images` у `AgentChat`, `ChatWorkspace`, `AgentPanel` и в `chatProps` песочницы принимает и список клиентов.
  Генерация и библиотека работают в одном чате, окно просмотра листает все картинки ответа.
- Договор скина версии 26: у `GeneratedImages` необязательные `wide` и `caption`. Тандем рисует картинку по ширине
  ответа с подписью. Скин версии 25 работает без правок: картинка будет плиткой ближайшей обычной пропорции (1:1, 3:2, 2:3, 16:9, 9:16) без подписи.

Подробно — [docs/image-library.md](docs/image-library.md).

**Смена поведения: отказ `show_video` и `find_videos` — ошибка инструмента.** Раньше на чужой id видео, начало за концом
или недоступный каталог инструмент возвращал `{ отказ }`, и лента показывала зелёную галочку «готово». Теперь он бросает `VideoLibraryError` (`kind`:
`not_in_catalog`, `catalog_unavailable`, `start_after_end`). В ленте строка «show_video: ошибка», модель получает тот же
текст. «Ничего не нашлось» в поиске — по-прежнему обычный результат. `find_images` и `show_image` устроены так же
(`ImageLibraryError`). Старые сообщения с `{ отказ }` показываются как раньше.

**Как обновить приложение.**

Ничего делать не нужно: одиночный клиент в `images` работает как раньше. Чтобы включить библиотеку:

1. `pnpm add @ykurilov/agent-chat-image-library`.
2. На сервере: `const library = createImageLibrary({ images })` и `...library.tools(model)` в `agent.tools`.
3. На странице: `images={imageLibraryClient}` или вместе с генерацией `images={[imagesClient, imageLibraryClient]}`.
   Картинки с CDN — `createImageLibraryClient({ allowedHosts })` с теми же доменами, что на сервере.
4. Свой скин: поддержите `wide` и `caption` (договор 26) — или оставьте как есть, будет плитка.
5. Если ваш код читал `{ отказ }` из результата `show_video` или `find_videos`, ловите вместо него `VideoLibraryError` или смотрите
   на `state: "output-error"` у части сообщения.

### Сценарии: таймер «наступил день N программы»

**Что было.** Из таймеров по дням был только «нода длится N дней» — от дня входа в ноду. Быстрый человек проходил
«Знакомство» в первый день, «Доработка» длилась 1 день, и «Продажа» начиналась уже во второй день, а не в третий.
Сутки по 24 часа (`since_start`) в начало дня не попадают: поздний старт и ночь их сдвигают.

**Что теперь.** `{ "type": "timer", "from": "program_day", "day": 3 }` — выход в начале третьего дня программы, когда бы
человек ни пришёл в ноду. Номер дня тот же, что в `readRun().day`: поздний старт, ночь, смена пояса в первый день,
`dayStart`. Пришёл в ноду уже в день 3 или позже — выход сразу, в том же ходе: человек получает один ответ, уже из новой ноды.
Тишина, `in_state`, `state_days`, `time_of_day` не меняются. До первого утра идёт день 0: «с дня 1» при ночном старте —
утром. Переход идёт таймером на сервере, без хода приложения: в начале дня одним сообщением с утренним и ответом на
ночные. При «писать первым нельзя» (`canWriteNow` → `"never"`) — без сообщения, но в свой срок: запись чата,
`onTransition` с днём, `readRun` и следующие таймеры уже от новой ноды. Тестовый чат «К началу следующего дня» тоже его включает. На доске: «Длится» → «до дня программы», подпись
условия — «с дня N». `checkFlow`: день больше `lengthDays`, меньше 1 или не целый — ошибка, сценарий без «Дней и
времени» — предупреждение. Подробно — [docs/flows.md](docs/flows.md), «Таймеры».

**Смена поведения: `since_start` при входе.** Человек вошёл в ноду, а срок её `since_start` уже прошёл. Раньше выход
срабатывал отдельным ходом сервера через 15 с — два сообщения подряд. Теперь — в том же ходе, один ответ уже из новой
ноды. Проверьте сценарии, которые рассчитывали на отдельное сообщение.

**Смена поведения: таймер ноды при «never».** Переход по любому таймеру ноды, когда писать первым нельзя совсем, теперь
наступает в срок, а не ждёт хода человека: `onTransition` приходит в момент срока, а не при следующем сообщении.
Такой переход не теряется при «Переделать» и смене ветки: `onTransition` — ровно один раз. Переход, который ход дотянул
поверх него (наступил уже другой срок), получает свой `onTransition`.

**Своё хранилище `FlowStore`.** Договор уточнён, его проверяет общий тест памяти, SQLite и PostgreSQL. `addPending` с
тем же ключом не дублирует запись, но дописывает `appliedAt`, если его не было. `takePending` возвращает всё, но
переходы с `appliedAt` оставляет в очереди. Встроенные хранилища уже так работают; своё — доработайте так же.

**Формат.** Дополнение к версии 2, номер версии тот же: старые сценарии читаются как раньше. SDK до 0.55 сценарий с
этим таймером не откроет (ошибка формы «Неизвестное значение поля «from»»). Поэтому сначала обновите SDK на всех копиях
сервера, потом сохраняйте такие сценарии.

**Скин.** `DurationUnit` и `labels.statePanel.durationUnits` получили `"program_day"`, у подписей редактора новое поле
`programDay(day)`. Свой скин «Длится» без этого варианта работает как раньше. Свои подписи редактора целиком — добавьте
`programDay` и `durationUnits.program_day`.

#### Как обновить приложение

- Ничего делать не нужно, если таймер не нужен.
- Своё событие «наступил день N» (например, `program_day_N`, которое приложение подаёт в начале хода через
  `flow.signal`) можно заменить таймером: при загрузке сценария выход `{ "type": "event", "event": "app", "name":
  "program_day_3" }` → `{ "type": "timer", "from": "program_day", "day": 3 }`. После этого хук хода, который подавал
  событие, и свой расчёт дня для тестового чата не нужны: сдвиг часов тестового чата SDK учитывает сам.
- Разница с событием: переход наступает в начале дня, даже если человек молчит и писать первым нельзя, а не со
  следующим его сообщением.

### Сценарии: свои касания ноды — только на первые дни

**Что было.** Свои касания ноды («15 мин · 1 ч · 4 ч») действовали всё время в ноде. Ряд кончался в день входа, и
на следующий день молчун получал только утреннее: общий ритм сценария («через 3 ч и ещё через 3 ч») в эту ноду не
приходил.

**Что теперь.** У своих касаний ноды есть срок: `"nudges": { "afterSilence": […], "days": 1 }` — действуют столько
дней сценария, считая день входа (1 — только день входа). Потом — касания сценария (`schedule.nudges`, затем `nudges`
в корне): утреннее и общий ряд с начала, тишина не раньше начала дня. Ночь, правило трёх часов и `maxPerDay` — как
раньше. Пример: вошёл в 10:00 → 10:15, 11:15, 15:15; на второй день — утреннее в 09:00, потом 12:00, 15:00, пока не
кончится потолок дня. Без `days` — как раньше, всё время в ноде. Без «Дней и времени» дни календарные, по поясу
человека. `checkFlow`: `days` не целое или меньше 1 — ошибка `nudges_days_invalid`.

Утреннее выключено — шаг своего ряда, отложенный ночью, уходит утром обычным касанием, а после него общий ряд — с
начала.

На доске: панель ноды, «Касания» → «Свои» → «Свои касания действуют»: «всё время в ноде» или «N дн., считая день
входа». На карточке — «касания 15 мин · 1 ч · 4 ч в день входа». Подробно — [docs/flows.md](docs/flows.md), «Касания».

**Формат.** Дополнение к версии 2: SDK до 0.55 сценарий с `days` у касаний не откроет. Сначала обновите SDK на всех
копиях сервера, потом сохраняйте такие сценарии.

**Свой скин.** `FlowStateTimingProps` получил `nudgesDays` и `onNudgesDaysChange`; без них скин работает как раньше,
срок просто не настраивается. Свои подписи редактора целиком — добавьте `board.nudgesDays`, `statePanel.nudgesDays`,
`statePanel.nudgesDaysModes`, `statePanel.nudgesDaysHint`.

#### Как обновить приложение

- Ничего делать не нужно: старые сценарии работают как раньше.
- Нужен частый ритм только в день входа — включите на доске «Свои касания действуют: 1 дн.» или допишите `"days": 1`
  в `nudges` ноды. Общий ритм для следующих дней задайте в «Днях и времени» (`schedule.nudges`).

### Сценарии: каждый день молчания — утреннее и ряд касаний заново (смена поведения)

**Что было.** Ряд касаний (`afterSilence`) шёл один раз за всё молчание. Утреннее его не перезапускало: когда ряд
кончался, молчун получал на следующие дни только утреннее.

**Что теперь.** Утреннее — новая точка отсчёта ряда. Человек молчит — каждый день утреннее, потом ряд с первого шага,
пока не кончится дневной потолок `maxPerDay`. Пример: общий ряд 3 ч · 3 ч, потолок 3 — каждый день 09:00, 12:00, 15:00.
Шаг ряда, отложенный ночью или потолком, утром не уходит: утреннее его заменяет, и модель видит только «доброе утро»
(плюс переход ноды и ночные сообщения, если они есть). «Не завершил» (`giveUpAfter`) по-прежнему
считается от последних слов человека.

**Смена поведения.** Касается сценариев, где включено утреннее (`firstMessages.morning` или задан `lengthDays`) и есть
ряд `afterSilence`. Молчун теперь получает ряд каждый день, а не один раз. Это касается и своих касаний ноды без
`days`: их ряд тоже идёт заново каждое утро. Утреннее выключено — всё как раньше.

#### Как обновить приложение

- Ничего делать не нужно, если вам подходит новый ритм.
- Нужно меньше сообщений молчуну — уменьшите `maxPerDay`, укоротите ряд или задайте `giveUpAfter`.
- Нужен прежний ритм «ряд один раз» — выключите утреннее: `firstMessages.morning: false`.

### DeepSeek 4.1 Flash не пишет за собеседника: обрезка хвоста `min_p`

**Что было.** Изредка видимый ответ DeepSeek 4.1 Flash превращался в кашу: после ответа модель писала «user…» за
собеседника, новые рассуждения, иногда вызывала инструмент. Причина — в словаре модели есть склеенное слово «?» с
пустой строкой. Together по умолчанию изредка выбирает маловероятные слова и берёт его вместо «?» и конца ответа:
модель не останавливается. Каша остаётся в истории и провоцирует повтор (с такой историей у Together ≈5 % ответов).

**Что теперь.**

- В профиле модели DeepSeek 4.1 Flash `sampling: { minP: 0.05 }`: слова с шансом меньше 5 % от самого вероятного не
  выбираются. Уходит полем `min_p` к Together и OpenRouter; DeepSeek напрямую и Fireworks его не получают. Проверка в
  приложении обучающее приложение: 35 учеников, каши 0 из 1036 ответов (было 2 случая «пишет за ученика»).
- Новое в каталоге: `ModelProfile.sampling` (параметры выбора слов, пока `minP`) и `ProviderDescription.samplingRequest`
  — провайдер сам переводит их в запрос и не шлёт то, чего не принимает.
- Опции профиля (`providerOptions` и `sampling`) теперь несёт сама модель из каталога. Их получают все вызовы:
  ход, сжатие истории, помощники, `askModel` (судья, проверки) и склейка памяти после ответа — она раньше шла без
  опций профиля, в том числе без запрета хозяев OpenRouter.

**Как обновить приложение.**

- Ничего делать не нужно.
- Приложение само добавляло DeepSeek 4.1 Flash `min_p` (`addModels` с `providerOptions.togetherai.min_p` или
  `providerOptions.openrouter.min_p`) — эту правку можно убрать: SDK делает то же. Оставленная не мешает: значение то же.
- Выключить: профиль без `sampling` через `addModels`. Своё значение: `addModels: [{ ...профиль, sampling: { minP: 0.1 } }]`.
  Одному провайдеру — `providerOptions: { togetherai: { min_p: … } }` в профиле: она главнее `sampling`. Пример —
  [docs/getting-started.md](docs/getting-started.md), «Параметры выбора слов в профиле модели».

### Голос: расход в лимитах, причина отказа, Next.js, язык записи

По опыту конструктор приложений. Без ломающих изменений, кроме одного: код закрытия 4401 («не вошёл») браузер теперь показывает
как «Нет доступа к диктовке», а не «Сервис распознавания речи недоступен». Миграций нет.

- **Свои виды расхода.** `UsageSource` принимает любую строку: приложение пишет `"font_download"` без приведения типа,
  подсказки редактора для штатных видов остаются. Список штатных — `BUILT_IN_USAGE_SOURCES`. Новые штатные виды:
  `voice_input` (распознавание, в `inputTokens` — секунды) и `voice_polish` (чистка текста моделью). Хранилища пишут вид
  строкой, поэтому миграций нет; лимиты считают все виды вместе.
- **Голос в лимитах.** `createVoiceRelay({ spending: { service: chatService, recognitionUsdPerHour } })`: исчерпан лимит —
  диктовка не начинается, человек видит «Лимит расходов исчерпан». Секунды звука пишутся в журнал расхода на чат из
  `?chat=` (его ставит `AgentChat`), если это чат вошедшего; чужой — без чата (`"voice"`). Чистка текста учитывается тоже: `polish: { askModel: chatService.askModel, model }`,
  у Together — цена `pricing`, у своей чистки — `usage` в ответе.
- **Почему отказали.** Сервер закрывает соединение кодом причины (`RELAY_CLOSE`): лимит, нет доступа, слишком длинно,
  слишком часто, сервис недоступен. Отказ приложения `resolveUser → { refused: { code: "limit" } }` превращается в
  нужный код сам. В браузере новые виды ошибок `limit`, `forbidden`, `too_long` со своими подписями (ru/en,
  переопределяются в словаре).
- **Next.js.** `@ykurilov/agent-chat-voice/node`: `createVoiceUpgrade` вешается на `upgrade` своего HTTP-сервера Next.js
  с теми же проверками, что у Hono. Кривой путь (`GET //`) получает 400, обрыв сети во время проверки входа не роняет
  процесс, зависшая проверка входа — 503 через 10 с (`authorizeTimeoutMs`). `shareVoiceRelay` / `sharedVoiceRelay` — мостик между кодом Next.js и `server.ts`.
  Пример — в [README голоса](packages/voice/README.md#nextjs-свой-сервер-custom-server).
- **Язык записи.** `AgentChat` передаёт язык словаря (`labels.locale`), своё — `createVoiceInput({ languageHints })`.
  Сервер берёт только годные коды языков, `allowedLanguageHints` сужает выбор.
- **Сроки и пределы ретранслятора.** Браузер, который не прислал приветствие за 10 с, закрывается кодом 4400 и не
  держит место (`helloTimeoutMs`). Предел одного сообщения `maxFrameBytes` (1 МиБ, закрытие 1009) теперь проверяет сам
  ретранслятор — он одинаков у Hono и у node-входа. Относительный `relayUrl` (`"/voice/stream"`) достраивается от адреса
  страницы.
- **Предел записи из настройки.** «Запись остановлена: предел 3 минуты» — число из `maxSessionSeconds` сервера.
  Подпись `time_limit` в словаре — строка или функция от секунд.

#### Как обновить приложение

1. Поднимите пакеты `@ykurilov/agent-chat-*` до 0.55.0 вместе. Миграций нет.
2. Свой вид расхода: уберите приведение `as UsageSource` (`source: "font_download"` и так проходит). Голосу свой вид
   больше не нужен: штатные `voice_input` и `voice_polish`. Старые записи с вашим видом `voice_input` совпадают по имени
   и остаются в отчётах.
3. Учёт голоса в лимитах: передайте `spending: { service: chatService, recognitionUsdPerHour: <цена Soniox за час> }`
   в `createVoiceRelay` и уберите свой подсчёт секунд и свою запись расхода. Чистку переведите на
   `polish: { askModel: chatService.askModel, model: { providerId, modelId } }` — или оставьте Together и добавьте `pricing`.
   Если передаёте не всю службу, а свой объект, в нём нужны `assertWithinLimit`, `recordUsage` и `assertOwnChat`.
4. Свой код отказа «лимит» (`limit_reached` и закрытие 4401): проверку лимита сделает `spending`; если отказываете
   сами — `resolveUser` → `{ refused: { code: "limit", message } }`, сервер закроет соединение кодом 4402.
5. Next.js с custom server: свой `server.ts` с ручным подъёмом WebSocket на `ws` и мостик через `globalThis` замените на
   `createVoiceUpgrade({ path, relay: sharedVoiceRelay })` и `shareVoiceRelay(relay)` (пример в README голоса). Нужен
   пакет `ws`. Next.js подвесьте на отдельный сервер: `next({ …, httpServer: nextUpgrades })`, а соединения, которые
   не голос, передавайте `nextUpgrades.emit("upgrade", …)`. Без этого при маршруте вида `app/[...slug]` Next.js после
   первой страницы закрывает соединение голоса.
6. Свои `languageHints: ["ru", "en"]` в `createVoiceRelay` можно оставить подсказкой по умолчанию: язык экрана придёт
   сам. Если нужен выбор только из своих языков — `allowedLanguageHints: ["ru", "en"]`.
7. Свой `?chat=` в `relayUrl` уберите: `AgentChat` добавляет его сам. Свой `VoiceInput` (не `createVoiceInput`):
   `start(listener, context)` получает `{ chatId, language }`.
8. Свой словарь подписей целиком: подписи `limit`, `forbidden`, `too_long` можно добавить, без них возьмутся по
   умолчанию. Свой тест на 4401 → `service_unavailable` поправьте на `forbidden`.

## 0.54.0 (15.10.2026) — несколько сообщений подряд — один ответ, один ход между копиями сервера, место на доске сценария, лента без потерь, забытые скобки

### Несколько сообщений подряд — один ответ

**Что было.** Человек в мессенджере пишет «привет», «у меня вопрос», «вот ссылка» — и получает три ответа. Пишет, пока
агент ещё отвечает, — после ответа агент отвечает на каждое сообщение по очереди.

**Что теперь.** Агент ждёт, пока человек замолчит на окно тишины (3 секунды), и отвечает одним ходом на всё. Пришедшее
во время ответа — тоже одним ходом после него. В истории сообщения отдельные, модель видит их одним сообщением. Кэш модели
цел. Подробно — [docs/getting-started.md](docs/getting-started.md), раздел «Несколько сообщений подряд».

- **Ядро.** `service.sendBurstMessage(userId, chatId, message, { page, quietMs })` → `{ messageId, turn }`. Сообщение
  записано сразу. `turn` — поток ответа у вызова последнего сообщения пачки, у остальных `null`. `beforeTurn` один на
  пачку, с `burstMessageIds`. Касания сценария не начинаются, пока ждёт пачка. Перезапуск посреди окна — повтор вызова с
  тем же `message.id`.
- **Мессенджеры.** Личные сообщения склеиваются сами. `messageBursts: { quietMs }` — своё окно, `messageBursts: false` —
  как раньше. Группы и кнопки не склеиваются.
- **Сценарии.** Рамки дня считают каждое сообщение пачки: готовая фраза — одна на пачку. Пачка после жёсткой рамки
  отложена до утра, как одиночное сообщение. `flow.admit({ messages })` — для своих ворот.
- **«Стоп» во время окна** отменяет ход на пачку: сообщения остаются в истории, после них — пустой остановленный ответ.
  Следующее сообщение получит ход на всё, «Повторить» ответит на отменённую пачку. В мессенджере — `/stop` → «Остановил.».
- **Веб-вкладка** видит ждущее сообщение сразу: новое событие `message-added`, вкладка перечитывает историю.
- **Проверки — при начале хода.** Пауза сотрудника за секунды окна действует, лимит расходов отказывает из `turn`.
  Копия с ждущей пачкой упала или ворота промолчали (`{ hold: true }`) — касания ждут ещё до 2 минут.
- **Одна пачка — сообщения в окне тишины друг друга.** Отложенное ночью и утреннее модель видит двумя сообщениями, как и
  считают ворота. Правка сообщения пачки оставляет его в пачке.
- **Сообщения во время ответа** записываются после него: до конца ответа их нет ни в базе, ни во вкладке.

### Один ход за раз — и между копиями сервера

**Что было.** Две копии сервера на одной базе могли в одну и ту же долю секунды начать два хода в одном чате: каждая
проверяла «ответа нет» раньше, чем другая успевала записать свой.

**Что теперь.** Копия, начинающая ход, берёт в базе аренду хода чата и продлевает её, пока ход идёт. Вторая копия получает
«чат занят» (`ChatBusyError`), пачка — ждёт конца чужого хода. Ответ на виджет и подтверждение аренду не ждут: их и
так принимает одна копия. `flush` снимает аренды сразу. Упала копия — чат занят до 15 с: веб получает 409 `busy`, пачка
в мессенджере дождётся сама. Копия одна — `recoverInterruptedAnswers({ soleServer: true })` снимает аренды упавшего
запуска при старте, и чаты свободны сразу.

- **Хранилища.** У `ChatStorage` три необязательных метода: `claimChatTurn(chatId, holder, leaseMs)`,
  `releaseChatTurn(chatId, holder)` и `clearChatTurnLeases()`. Есть у памяти, SQLite (таблица `chat_turn_leases`, миграция 0017) и PostgreSQL
  (миграция 0016). Общий тест хранилищ проверяет их с опцией `chatTurnLease: "required"`, включая гонку десяти копий.

### Доска сценария: больше места графу

Приложение встраивает `FlowEditor` во вкладку своей страницы — над ним уже есть шапка с названием, и графу мало места.
Теперь доску можно «освободить». Без ломающих изменений, одно изменение поведения по умолчанию: **легенда «Условий
выхода» теперь свёрнута в кнопку «Легенда»** (раньше висела поверх графа слева внизу).

Новые необязательные свойства `FlowEditor`:

| Свойство | Значения (по умолчанию первое) | Что делает |
|---|---|---|
| `header` | `"full"` / `"compact"` | `compact` — одна узкая строка кнопок, без логотипа и названия сценария |
| `legend` | `"collapsed"` / `"open"` / `"hidden"` | Легенда: кнопка «Легенда» / открыта / нет совсем |
| `minimap` | `"open"` / `"collapsed"` / `"hidden"` | Мини-карта: открыта / свёрнута в кнопку / нет совсем |
| `inspector` | `"open"` / `"collapsible"` | Правая панель «Сценарий». `open` — открыта, сворачивается кнопкой. `collapsible` — свёрнута, пока ничего не выбрано; выбор ноды или стрелки раскрывает, клик в пустое место сворачивает |
| `fullscreen` | `true` / `false` | Кнопка «На весь экран» в шапке |
| `storageKey` | строка / `null` | Где в localStorage помнить свёрнутое. По умолчанию общий ключ `agent-chat-flow-board`; `null` — не помнить |

Как это работает:

- Кнопки «Скрыть/Показать панель «Сценарий»» и «Скрыть/Показать мини-карту» стоят на доске, «Легенда» — слева внизу.
  Что человек свернул или развернул, запоминается (общее для всех сценариев приложения). При `inspector="collapsible"`
  панель не запоминается: она следует за выбором. Проверка и прогон держат панель открытой.
- Полный экран: редактор встаёт поверх страницы (`position: fixed`), страница под ним не прокручивается, Esc и та же
  кнопка выходят (Esc при открытом окне JSON закрывает только окно), Tab ходит по кругу внутри, фокус возвращается на
  кнопку. На телефоне панель уходит под доску, как и раньше. Тёмная тема берётся из токенов Тандема. Свои `className` и
  `style` в полном экране не действуют. Не оборачивайте `FlowEditor` в элемент с `transform`: из него `fixed` не вырвется.
- Без localStorage (сервер, закрытое хранилище) — всё работает, просто без памяти.

### Исправления

- **Лента во время ответа.** Пока ответ рос, лента ехала вниз за ним, и окно ленты на это время убирало запас над экраном.
  Через 150 мс тишины оно возвращало запас, и готовые сообщения над экраном рисовались заново. Это повторялось при каждой
  паузе в ответе. Теперь, пока лента прилипла к низу, запас держится, и готовые сообщения не перерисовываются.

### Лента не теряет сообщение, записанное сервером сразу после своего ответа

**Что было.** Тестовый чат доски иногда не показывал «Доброе утро!» после «К началу следующего дня» (примерно 1 из 5
раз, чаще под нагрузкой). Экран перечитывал историю дважды подряд: при открытии подписки после своего ответа и по
событию «ход начался». Если старое чтение приходило первым, новое с утренним сообщением выбрасывалось как «лента
изменилась». Так же мог пропасть любой ход сервера: касание, ход из мессенджера, итог фона.

**Что теперь.** Ленту, сменённую другим чтением, более новое чтение всё равно показывает; запоздавшее старое новое не
стирает. Правка в `@ykurilov/agent-chat-react`, приложению делать ничего не нужно.

**Пояс после `flow.adopt`.** Проверено тестом: чат закреплён без хода (`defaultTimeZone` Москва), в первый день агент
узнал город — первый день, сроки нод, утреннее, срок программы и «День N из M» пересчитаны по поясу человека. Ошибки
не было, тест остался защитой.

### Забытые закрывающие скобки в аргументах инструментов

Продолжение починки из 0.46. Ничего не ломает.

- **Что было.** DeepSeek 4.1 Flash иногда забывает закрыть массив или объект: `{"facts": ["a", "b"}` или
  `{"fields": [{…}`. Вызов падал с `AI_JSONParseError`, модель видела ошибку и звала инструмент ещё раз.
- **Что теперь.** Ядро само дописывает недостающие `]` и `}` в правильном порядке — для всех моделей, по тому же
  правилу. Только если JSON оборван на законченном значении. Обрыв внутри строки, ключа, числа или слова `true`,
  после запятой или двоеточия, а также больше трёх недостающих скобок не чинятся: иначе получилась бы правка без хвоста.
- **Проверка схемой и журнал.** Починенный вызов, как и раньше, проходит схему инструмента; не прошёл — ошибка модели
  и повтор. Каждая починка — строка `[аргументы починены]` с видом правки: `дописаны скобки ×N` (рядом с
  `лишние скобки …`, `записи в строках`, `типы по схеме`). В `ToolInputRepair` новое поле `missingClosers`.

**Как обновить приложение.** Ничего делать не нужно. Если в приложении стоит свой обход (обёртка модели, которая
дописывает скобки до разбора), его можно убрать: ядро делает то же и осторожнее.

### Как обновить приложение

1. Поднимите пакеты `@ykurilov/agent-chat-*` до 0.54.0 вместе. Миграции SQLite 0017 и PostgreSQL 0016 (новая таблица
   `chat_turn_leases`) применяются сами при открытии хранилища.
2. Мессенджеры SDK: ничего делать не нужно, склейка включится сама. Ответ начинается на 3 секунды позже. Не нужно —
   `messageBursts: false` в `createMessengers`.
3. Свои боты (Telegram, ВК, MAX своими силами): вместо `sendMessage` зовите `sendBurstMessage` и печатайте поток из
   `turn`, если он не `null`. Считайте обновление мессенджера обработанным, когда `turn` закончился. После перезапуска
   повторите необработанные с тем же `message.id`.
4. Свой `beforeTurn`, который считает сообщения, — учтите `burstMessageIds`: ход на пачку — это несколько сообщений.
5. Своё хранилище (свой `ChatStorage`) и несколько копий сервера — добавьте `claimChatTurn`, `releaseChatTurn` и
   `clearChatTurnLeases` (см.
   [docs/getting-started.md](docs/getting-started.md), «Своё хранилище») и включите в общем тесте
   `chatTurnLease: "required"`. Без них всё работает, как раньше: один ход за раз держится только внутри копии.
6. Свой разбор событий чата (`ChatEvent`, `ChatWatchEvent`) с исчерпывающим `switch` — добавьте `message-added`.

7. Если у вас своя шапка над доской и вам тесно:

```tsx
<FlowEditor
  skin={tandemFlowEditorSkin}
  value={flow}
  onChange={setFlow}
  catalog={catalog}
  header="compact"      // убрать логотип и название
  inspector="collapsible" // панель появляется, когда выбрана нода
  minimap="collapsed"   // мини-карта по кнопке
/>
```

8. Нужна прежняя картина с открытой легендой — `legend="open"`. Кнопка полного экрана не нужна — `fullscreen={false}`.
9. Свой скин редактора: в договор добавлены необязательные `compact` и `fullscreen` у `FlowHeader`, `compact` у
   `FlowEditorFrame` (при `panel === null` рамка не должна оставлять пустую колонку) и необязательная часть
   `FlowBoardToggle` (без неё доска рисует простые кнопки). Подписи — `labels.board.space` (ru и en).

## 0.53.0 (14.10.2026) — сценарии: конец разговора без сбоев, «не сейчас», пояс по умолчанию, реплика сотрудника, тихое утро

Поверх 0.52.0. Без ломающих изменений: новые настройки необязательные. Изменилось поведение в трёх местах — это
исправления ошибок: конец разговора, `canWriteNow` и правило «человек писал недавно».

### Конец разговора наступает, даже если касание не ушло

**Что было.** Человек молчит, агент касается его по расписанию. После 5 ходов сервера подряд без человека ядро
переставало начинать ходы (защита от петли), а сценарий на отказ хода снимал все сроки чата. Итог: «срок вышел» и «не
завершил» не наступали, прощания не было, трёхдневка висела вечно. Так же действовали ворота приложения
(`beforeTurn` → `{ hold: true }`) и исчерпанный лимит расходов.

**Что теперь.**

- Касания сценария идут по его расписанию, и потолок ядра их не режет: молчащий человек получает все положенные
  касания. Свой потолок у `deliverNotices` — `maxServerTurnsInRow` (число или `false`); по умолчанию прежний (5).
- Ход касания не начался — касание переносится (через час, у лимита — на утро), а «срок вышел», «не завершил» и
  переход ноды по сроку наступают в своё время. Время конца пишется по сроку, а не по последнему касанию.
- Вместо потолка ядра у сценария свой мягкий потолок: 50 ходов сервера подряд без сообщения человека
  (`createAgentFlow({ timers: { maxServerTurnsInRow } })`, `false` — без потолка). Это страховка от петли переходов по
  коротким таймерам (A → B → A), особенно при `firstMessages: false`. Дошли — строка в журнал, касания и переходы по
  таймерам ждут сообщения человека, а «срок вышел» и «не завершил» наступают в свой срок.
- Срок наступил, а писать не о чем (упёрлись в предел переходов подряд) — срок встаёт на ближайшее настоящее: касание,
  переход ноды, конец разговора. Ничего впереди нет — срок снимается, а не повторяется каждый час.

### `canWriteNow`: «не сейчас» вместо «никогда»

**Что было.** `canWriteNow` → `false` снимал все сроки чата. Аварийная остановка рассылки навсегда ломала конец
разговора: даже после снятия остановки касаний и прощания не было.

**Что теперь.** `false` — «не сейчас»: касание повторится через час. `"never"` — молчать до сообщения человека:
касаний и повторов нет (так — отписавшийся человек). `{ retryAt: Date }` — повторить в этот момент; негодная дата —
как `false`, дата в прошлом — через минуту, а не каждый обход. Конец разговора и переходы нод по сроку от ответа не
зависят. `true` — как раньше. Подробно — [docs/flows.md](docs/flows.md), «Правила «писать первым»».

### Пояс по умолчанию: `createAgentFlow({ defaultTimeZone })`

**Что было.** Пока пояс человека неизвестен (до первого хода, мессенджер без страницы), дни, тихие часы и касания
считались по `agent.timeZone`, а без него — по поясу сервера.

**Что теперь.** `defaultTimeZone: "Europe/Moscow"` — пояс на этот случай. Порядок: человек → страница →
`defaultTimeZone` → пояс службы (`agent.timeZone`) → сервер. Не пояс IANA — `TypeError` при создании. Ядро теперь
говорит `prepareTurn` прямо, прислала ли страница пояс (`pageTimeZone`), поэтому пояс страницы, совпавший с поясом
службы, не путается с «пояса нет». Нет своего `agent.timeZone` — `flow.withChat` подставляет туда `defaultTimeZone`, и
дата в запросе к модели («Сегодня: …») совпадает с днём сценария.

### Реплика сотрудника в истории: `service.appendStaffMessage`

**Что было.** Приложение клало ответ эксперта в историю обычным сообщением собеседника. Проверки ответа и
`person_link_view` считали его словами человека: ссылка из ответа эксперта становилась «законной», и агент мог открыть
её как ссылку человека. `flow.noteStaffReply({ text })` с 0.49 писал реплику служебным сообщением, но экран её не
показывал, а имени сотрудника не было.

**Что теперь.** Подробно — [docs/flows.md](docs/flows.md), раздел «Пауза: отвечает сотрудник», и
[packages/core/README.md](packages/core/README.md).

- `service.appendStaffMessage({ ownerId, chatId, text, staffName?, wakeAgent?, deliveryKey? })` кладёт реплику в конец
  ветки. Модель видит «Живой сотрудник «Ольга» ответил человеку вместо тебя: «…»»; начало запроса не меняется, кэш цел.
- Словами человека она не считается: `person_link_view` ссылку из неё не откроет. А проверки ответа агента её текст
  знают: повторит агент ссылку или телефон сотрудника — проверка не вырежет ([docs/reply-check.md](docs/reply-check.md)).
- Ход сама не начинает; `wakeAgent: true` — агент отвечает сразу. Занятый чат — `busy`, пустой текст — `TypeError`.
- Экран: новый необязательный компонент скина `StaffMessage` (договор скина 25, [docs/skin-v25.md](docs/skin-v25.md)).
  Скин без него показывает реплику ответом агента с подписью «Сотрудник Ольга» (`labels.notices.staffSaid`).
- `flow.noteStaffReply` пишет тем же путём и принимает `staffName`. Его реплики теперь видны на экране сообщением
  сотрудника (раньше — только модели).

### Человек писал недавно — утром первым не писать

**Что было.** Правило «человек писал меньше 3 часов назад — утреннее не нужно» действовало только на утреннее
сообщение. Человек написал в 07:00, агент ответил, касание тишины через 15 минут попало в ночь и перенеслось на 09:00 —
и ушло, хотя человек писал два часа назад.

**Что теперь.** Правило касается любого касания в начале дня: утреннего, касания тишины или по часам, перенесённого
ночью на утро. Они ждут, пока пройдут 3 часа (`skipMorningIfHumanWithinMin`). Переход ноды по сроку и ответ на
сообщения, оставленные ночью без ответа, уходят в свой срок: это дело программы и ответ человеку, а не напоминание.

### Ответ на сообщения после жёсткой рамки приходит утром всегда

**Что было.** После жёсткой рамки дня (`dayFrame.hardAt`) агент молчит до утра, а утром отвечает на накопленное. Но
срок на утро ставился, только если у сценария было своё дело утром: утреннее или касание. Касания кончились, утреннего
нет — человек писал в 07:00 и ответа не получал вовсе. А сценарий с утренним в 09:00 ещё и здоровался: отложенные
сообщения правило «писал меньше 3 часов назад» не видело.

**Что теперь.** Отложенное сообщение само ставит срок чата на начало следующего дня. Ответ на накопленное уходит в
`dayStart` при любых настройках касаний и не ждёт 3 часов. Время отложенного сообщения лежит в данных чата
(`Chat.data`, ключ `flowHeldHuman`). Для сроков сценария оно — обычное сообщение человека:
- правило 3 часов: утреннее и касания в начале дня ждут;
- «не завершил» (`giveUpAfter`): молчание человека считается от отложенного сообщения, а не от последнего отвеченного;
- переход ноды «человек молчит» (`from: "silence"`) не срабатывает: человек писал после агента.

Касания `afterSilence` считают тишину от слов агента и пока сообщения ждут ответа стоят — для них ничего не изменилось.
Хранилищу нужен `updateChatData`; без него ответ утром всё равно придёт, а сроки не узнают о позднем сообщении.

### Касание с карточкой ролика доходит целиком

**Что было.** Своя доставка приложения (`attach({ deliver })`) получала только текст касания. Показал агент в касании
карточку ролика, картинку или файл — до человека доходил один текст.

**Что теперь.** `deliver` получает ещё `parts` — все части ответа, которые надо доставить: текст, файлы, вызовы
инструментов с результатом (`tool-show_video`, картинки, виджеты). Рассуждений модели и служебных частей там нет.
`text` остался прежним. Касание только карточкой, без текста, тоже уходит. Повтор доставки отдаёт те же части. Так же
`deliverNotices({ awaitAnswer })` возвращает `answer.parts`, а для своих нужд есть `deliverableParts(parts)` из ядра.

### Сумма расхода по списку чатов одним запросом

**Что было.** Чтобы показать расход в списке разговоров, приложение звало `storage.sumUsage({ chatId })` на каждый чат:
сто чатов — сто запросов.

**Что теперь.** `storage.sumUsageByChat({ chatIds, ownerId?, source?, since? })` — один запрос. Ответ — строки по чату и
паре «модель × провайдер», как у `sumUsage`, плюс `chatId`. Чатов без расхода в ответе нет. Метод есть у хранилищ в
памяти, SQLite и PostgreSQL; у своего хранилища он необязательный, общие тесты хранилищ его проверяют.

```ts
const sums = await storage.sumUsageByChat!({ chatIds, source: "first_message" });
const costByChat = new Map<string, number>();
for (const sum of sums) costByChat.set(sum.chatId, (costByChat.get(sum.chatId) ?? 0) + sum.costUsd);
```

### Мелочи для приложений

- `flow.tick()` — в публичном типе сценария: один обход таймеров сейчас, для тестов и своего планировщика.
- `factId(text)` — из пакета: id факта карточки по тексту.
- Перемотка `advanceTestClock({ to: "next_day_start" })` работает и у тестового чата, закреплённого через `adopt` без хода.

## 0.52.0 (2026-10-14) — редактор сценариев: только просмотр, отказ в сохранении, высота

Поверх 0.51.0. Без ломающих изменений: без новых настроек редактор ведёт себя как раньше, кроме высоты (ниже).

### Редактор сценариев: `readOnly`, отказ в `onSave`, `className` и `style`

**Что было.** Приложение, поставившее доску в кабинет эксперта, обходило редактор само. Пока агент правит черновик, доску
закрывали обёрткой «inert» (и она глушила просмотр с прогоном). Отказ сервера при сохранении без исключения редактор не
видел и писал «Сохранено». У `FlowEditor` не было `className` и `style`, а высоту родителя редактор не занимал: в
родителе без своей высоты, особенно на телефоне, холст схлопывался.

**Что теперь.** Подробно — [docs/flows.md](docs/flows.md), раздел «Подключение: редактор».

- **`readOnly`.** Нельзя двигать, соединять и удалять узлы, править панели, сохранять, загружать JSON и переводить чаты.
  Можно открывать узлы, проверять граф, прогонять, смотреть JSON; тестовый чат работает. В шапке плашка «Только
  просмотр» (`labels.header.readOnly`).
- **Отказ в `onSave`.** `onSave` может вернуть `{ ok: false, issues?: [{ path, message }] }`. Ничего (`void`) и
  `{ ok: true }` — успех, как раньше. При отказе шапка пишет «Не сохранено», `issues` встают у нод и выходов и видны в
  «Проверить граф». Исключение из `onSave` — такой же отказ, в консоль необработанная ошибка не уходит.
- **`className` и `style`** у `FlowEditor` идут на корень. По умолчанию корень занимает высоту родителя, но не меньше
  60% экрана (не меньше 420 px), на телефоне — экрана целиком (не меньше 640 px).
- **Скин.** Договор редактора: необязательные `saveFailed` и `readOnly` у `FlowHeaderProps`, `readOnly` у
  `FlowJsonDialogProps`, `className` и `style` у `FlowEditorFrameProps`. Свой скин без них работает: редактор сам не
  даёт сохранять и править в `readOnly`, но плашки не будет. Скин Тандема рисует всё.

### Как обновить приложение

1. Поднимите пакеты `@ykurilov/agent-chat-*` до 0.52.0 вместе. Миграций нет.
2. Вместо обёртки «inert» на время правок агента передайте `readOnly={agentIsEditing}`. Обёртку уберите: она глушила и
   просмотр с прогоном.
3. Если сервер при сохранении отказывает, верните это из `onSave`: `{ ok: false, issues: [{ path, message }] }` вместо
   «успеха» или исключения. `path` — как у `checks` (`states[2]`, `states[intro].exits[0]`).
4. Ручную высоту у родителя редактора (`height: 100%`, `min-height` для телефона) можно убрать: редактор занимает
   высоту родителя сам. Нужна своя — `style` или `className` у `FlowEditor`.
5. Свой скин редактора: по желанию нарисуйте `saveFailed` и `readOnly` в шапке, `readOnly` в окне JSON, примените
   `className` и `style` в раскладке.

## 0.51.0 (2026-10-14) — проверка ответа, исправления сценариев и фоновых задач

Поверх 0.50.1. Без ломающих изменений: проверки без новых настроек ведут себя как раньше, кроме одного исправления ниже.

### Проверка ответа: тексты приложения, проверка текста вне хода, слова только от человека

**Что было.** Проверки «выдуманные ссылки» и «чужие слова» знали только инструкцию, контекст хода и реплики человека.
Первое сообщение, прощание, тексты нод сценария, попутные задачи и названия роликов в этот набор не попадали: ссылка
из первого сообщения вырезалась, а латинские слова оттуда считались чужими. Свой текст приложения (итог его
инструмента) проверить тем же набором было нечем. А служебные сообщения и реплики живого сотрудника считались «виденным»:
чужая ссылка в ответе сотрудника становилась законной.

**Что теперь.** Подробно — [docs/reply-check.md](docs/reply-check.md).

- **Тексты приложения.** В `replyChecks` появилось `knownTexts: ({ ownerId, chatId }) => string[] | Promise<string[]>`.
  Слова и ссылки из этих текстов законны для всех проверок. Сбой функции — строка в журнал, проверки идут без них.
- **Сценарий отдаёт свои тексты сам.** Если `replyChecks` передан в `flow.withChat(…)`, к вашим `knownTexts`
  добавляются общая часть, ноды (название, инструкция, первое сообщение), прощание, текст рамки дня и попутные задачи.
- **Проверка текста вне хода.** `service.checkReply({ ownerId, chatId, text })` → `{ text, notes }`: те же проверки и тот
  же набор «виденного» (инструкция чата, блоки контекста, реплики человека, выводы инструментов, `knownTexts`).
  Хвоста шага (`stepContext`) вне хода нет: его тексты назовите в `knownTexts`.
- **Слова человека — только из сообщений человека.** Служебные сообщения приложения (`app`, «напиши первым») и реплики
  сотрудника больше не делают ссылку законной. Итоги фоновых задач остаются «виденным»: это выводы инструментов.

### Как обновить приложение

1. Поднимите пакеты `@ykurilov/agent-chat-*` до 0.51.0 вместе. Миграций нет.
2. Если в служебных сообщениях приложения были ссылки, которые агент должен повторять, назовите их в `knownTexts`: из
   самих служебных сообщений они больше не считаются виденными.
3. Тексты приложения вне инструкции (первое сообщение вне сценария, прощание, названия роликов) — в `knownTexts`.
   Если у вас была обёртка `withKnownTexts` вокруг проверок, её можно убрать.
4. Свой текст вне хода — `service.checkReply(…)` вместо своего цикла по проверкам.


### Исправления

- **Проверка сценария:** нода, в которую ведёт только «срок вышел» (например, отдельная нода «Срок вышел»), считалась недостижимой, и сервер не запускал чат. Теперь такая нода достижима.
- **Фоновые задачи на двух копиях сервера выполняются один раз.** Две копии сервера на одной базе. Сервер под нагрузкой, база отвечает медленно. После перезапуска копия
подбирает брошенные задачи, и это идёт секунды. За это время одна задача могла запуститься дважды: второй раз — той
же копией или соседней. Например, отчёт, который шлёт письмо, ушёл бы два раза. Тест двух копий изредка падал именно
из-за этого, а не из-за медленной машины. Задача выполняется один раз и под нагрузкой.

- Копия подбирает брошенные задачи одним обходом за раз.
- Срок аренды задачи считается с момента, когда копия её взяла, а не с начала обхода.
- Продление аренд не ждёт доставки итогов и подбора задач.


## 0.50.0 (2026-10-14) — сценарии: перенос чатов и факты о человеке

Сценарий без новых полей и настроек ведёт себя как в 0.49.

### Перенос идущих чатов, конец извне, причина «пишет первым», общие касания

**Что было.** Чат из старой системы закреплялся за сценарием только на ходе человека. Молчащий человек не получал
оставшихся касаний, а потолок дня и рамки начинались с нуля. Закончить разговор снаружи было нечем. Причину касания
приложение не видело. Касания без «Дней и времени» приходилось писать в каждую ноду.

**Что теперь.** Подробно — [docs/flows.md](docs/flows.md).

- **Перенос идущего чата.** `flow.adopt` закрепляет чат сразу: нода, последние реплики обеих сторон, шаг касаний,
  счёт за сегодня, пояс. Срок следующего касания ставится тут же и переживает перезапуск. Пример с рядом «15 минут,
  час»: человек молчит с 10:00, касание в 10:16 уже было — следующее придёт в 11:16, а вечернее — только если потолок
  дня не исчерпан.
- **Конец снаружи.** `flow.end({ reason: "switched", outcome })`: человек ушёл в другой продукт — `onFinish`, как у
  остальных концов, сроки сняты.
- **Причина касания в хвосте приложения.** `stepContext` получает `firstReasons`: «тишина, шаг 2», «утро», «прощание».
  Постоянная инструкция не меняется, кэш цел.
- **Касания на весь сценарий** без «Дней и времени» — `nudges` в корне.
- **Исправлено описание ночи.** В 0.49 документация писала, что ночью сообщения копятся до утра. На деле агент отвечает
  человеку и ночью: тихие часы — только для сообщений первым. Молчит он только после жёсткой рамки дня. «Утром отвечу!»
  уходит один раз за день — это теперь проверено тестом.

### Как обновить приложение

1. Поднимите все пакеты `@ykurilov/agent-chat-*` до 0.50.0 вместе. Миграций нет.
2. Ничего больше не нужно, если вы не используете новое.
3. Переносите чаты из своей системы — `flow.adopt` после `createChat` для каждого идущего чата («Перенос идущего чата»
   в [docs/flows.md](docs/flows.md)).
4. Исчерпывающий `switch` по причине конца с `never` в `default` — добавьте ветку для своих причин: `FlowEndReason`
   теперь принимает любую строку.

### Факты о человеке в карточке клиента и просмотр ссылки

**Что было.** У модели два места «запомнить»: карточка со строгими полями и память SDK. «Ведёт блог» в поле не влезает,
и модель писала такое в память, а карточку держала для другого. Люди и приложение видели две картины одного человека.

**Что теперь.** Включите `clientFacts: true` — карточка хранит ещё и свободные факты.

- Агент пишет факт тем же инструментом: `flow_note { fact: "ведёт блог" }`. Одна короткая фраза, до 30 на человека, повтор
  с другим регистром — та же запись.
- Список «Факты о человеке» в блоке `flow:client` идёт по порядку записи: начало запроса не меняется, кэш цел.
- «Что ты обо мне знаешь» показывает поля и факты. «Забудь» стирает факт по id или словами, «забудь всё» — и поля, и
  факты (даже если потом выключили `clientFacts`).
- С памятью SDK: факты о человеке — в карточку, правила общения («отвечай на ты») — в память. Правило входит в инструкцию.
  При «забудь обо мне» модель стирает в обоих местах.
- Свои таблицы фактов у приложения — необязательное `clientCard.facts: { read, add, forget }`. Нет — факты лежат в таблице
  модуля записями `fact:<id>` (миграций не нужно). Экран «Что агент знает о вас» показывает факты строками (`factName`).
- **Просмотр ссылки** (`person_link_view`): правила «страница не открылась — сказать один раз и не просить ссылку снова»
  и «расход пишется в журнал» работали и раньше, но не были описаны. Теперь описаны в `docs/flows.md` и README
  web-tools, а тестами закреплены и неоткрывшаяся страница: она считается просмотром, расход пишется и за неё, модель не
  видит подробностей сбоя.

## 0.49.0 (2026-10-14) — сценарии для приложений

Номер версии появится при выпуске. Сценарий без новых полей ведёт себя как в 0.48. Три оговорки для кода приложения —

**Что было.** Сценарий 0.48 жил одним разговором в веб-чате SDK. Программа «на три дня», утреннее сообщение, ночная

  сообщением. Чат, начатый до сценария, встаёт на нужную ноду и день. Судья ходит через прокси с заголовками. У каждого

- **Пауза сотрудника.** `flow.pause`, `resume`, `noteStaffReply`: отвечает живой человек — агент молчит, а потом
  продолжает, не противореча ему.
- **Конец разговора.** `onFinish` с причиной (`final`, `deadline`, `abandoned`, `blocked`), днём, нодой, метками и
  путём — всё, чтобы передать человека дальше. После конца агент отвечает по «Общему» (`afterEnd: "reply"`) или молчит
  (`"silent"`).
- **Карточка в базе приложения** (`clientCard`), пояс человека в базе приложения (`people`), поле «да/нет».
- **Попутные задачи** — «предложи подписаться на канал»: между делом, по 2 попытки. Встроенная «узнать город»: пока

- **Проверка ответа.** Новый пакет `@ykurilov/agent-chat-reply-check`: «чужие слова» и «выдуманные ссылки».

  ждёт проверки; мессенджеры шлют только проверенный текст. Ответ был целиком выдуманной ссылкой — уходит запасная

- **Касание, которое не дошло, не засчитывается.** `failed` и `window_closed` — и от своей доставки, и от каналов
  SDK. Тот же шаг повторится через свой срок от момента отказа. Пока ждёт повтор доставки, новых ходов нет. «Окно
  закрыто» снимает любое сообщение человека, даже без ответа агента. «Не завершил» считает тишину и от конца паузы
  сотрудника.
- **Несколько копий сервера.** Обход таймеров идёт до 5 ходов одновременно. Копия продлевает право на чат перед ходом
  и во время него: две копии не шлют одно касание дважды.
- **Мессенджеры.** `onAnswerDelivery` — исход доставки каждого ответа. Закрытое окно ВК (ошибка 950) — отдельный исход
  `window_closed`.
- **«Не доставлено».** Ответ, который не дошёл, остаётся в истории с серой отметкой, модель его больше не видит. Договор
  скина версии 24 ([docs/skin-v24.md](docs/skin-v24.md)), скин версии 23 работает без правок.
- **Редактор.** Панели «Дни и время», касания, рамки, попутные задачи, режим после конца. Поля приложения из
  `catalog.fields`, свои проверки (`checks`) — те же на сервере: `checkFlow(flow, catalog, { checks })`. В тестовом чате
  кнопка «К началу следующего дня».
- **Кэш цел.** Живой замер на трёх днях: 14 шагов, постоянная инструкция одна во все дни, ни одного промаха кэша.
  Ночь, жёсткая рамка и «срок вышел» модель не зовут. 17 запросов — $0,0032.
- **Тесты приложения.** `now` у службы чата и сценария, `flow.settled()`, `advanceTestClock({ to: "next_day_start" })`.

## 0.47.0 (2026-10-12)

Для конструктора приложений. Ничего не ломает.

### «Максимум» больше не съедает ответ

**Что было.** Claude Haiku 5.5 на уровне «Максимум» думал 275 секунд: из 71 803 токенов вывода 69 621 ушли на
рассуждения. Файлов нет, ответ «оборван по длине». В запросе не было предела вывода, и OpenRouter брал свой, меньше
настоящего потолка модели.

**Что теперь.**

- **Потолок вывода в профиле.** Новое поле `maxOutputTokens` в профиле модели. Оно уходит в каждом запросе как
  `max_tokens`, если приложение не задало свой предел. У Claude Haiku 5.5 — 128 000.
- **«Максимум» — самый глубокий уровень с запасом на ответ.** Ответу остаётся пятая часть предела и не меньше 16 тысяч.
  У Claude через OpenRouter сила рассуждений — доля предела: `xhigh` отдаёт на рассуждения 95 %. Новое поле профиля
  `reasoning.effortShareOfOutput` выбирает самую глубокую силу, после которой запас остаётся. У Haiku 5.5 при пределе
  128 000 «Максимум» и «Высокий» уходят как `high` (ответу 25 600), при пределе приложения 64 000 и меньше — как
  `medium`.
- **Жёсткий бюджет рассуждений.** Новое поле `reasoning.tokenBudget` для моделей, которые держат бюджет числом
  (Claude до 4.6, Gemini 2.5): уровень уходит числом токенов с тем же запасом. У стандартных моделей не стоит.
- **Честно про Haiku 5.5.** Долю предела модель держит нестрого: на `high` с пределом 8 000 рассуждала все 8 000.
  Понижение уровня делает рассуждения мельче, а главная защита — предел 128 000. Живая проверка на трудной задаче — в
  журнале выпуска.
- **Кэш цел.** Уровень и числа зависят только от выбора и предела: запрос от хода к ходу байт в байт тот же. У GPT,
  Gemini 3, GLM и DeepSeek запрос прежний.

### Как обновить приложение

- Своя копия профиля `claude-haiku-5.5` (как у конструктора приложений) — добавьте в неё `maxOutputTokens: 128_000` и
  `reasoning.effortShareOfOutput: true`. Профиль из `standardCatalog` получит их сам.
- Своя модель Claude через OpenRouter — те же два поля. Модель, которая держит бюджет числом (проверьте вживую), —
  `maxOutputTokens` и `reasoning.tokenBudget: true`.
- Задан малый `agent.maxOutputTokens` — он главнее потолка модели: уровень станет мельче, а модель, которая долю не
  держит, может истратить его на рассуждения. Давайте с запасом или уберите.

Подробности — в [getting-started](docs/getting-started.md) («Потолок вывода и бюджет рассуждений»).

### Claude через OpenRouter: не больше 4 меток кэша

**Что было.** Claude Haiku 5.5 через OpenRouter падал посреди хода с инструментами: «A maximum of 4 blocks with

### Заметка хода после ответа на виджет

**Заметка хода — у последнего входа.** Заметка хода — служебные сведения для модели: место на экране, день, блоки
приложения (`contextBlocks`). Раньше после ответа на кнопку виджета или «Разрешить» она оставалась в давнем вопросе
человека, а новое место модель не видела. Например, интерфейс переключили на английский, человек нажал кнопку плана — а
модель ответила по-русски. Теперь:

- **Ответ на виджет и подтверждение.** Свежая заметка встаёт сразу после ответа человека — последним сообщением запроса.
  Ничего не поменялось — заметки нет. Страница не прислала `place` — место прежнее. У подтверждения заметка идёт после
  результата разрешённого инструмента.
- **Кэш цел.** Всё, что раньше последнего входа, — байт в байт прежнее: и на этом ходе, и на следующих. Прошлые заметки
  со своих мест не переезжают.
- **Остальные входы — как были.** Сообщение человека, поправка на лету, сообщения из мессенджеров и продолжение после
  фоновой задачи — заметка в конце этого сообщения. «Переделать» — в конце вопроса. «Повторить» — тот же запрос, заметки
  на своих местах.

**Как обновить приложение.** Ничего делать не нужно. Читаете ответы из хранилища сами — пропускайте все части `data-frozen-context`: теперь их в
ответе бывает несколько.

### Битые аргументы инструментов

Битые аргументы инструментов чинятся без повтора. Ничего не ломает.

- **Лишняя скобка.** DeepSeek иногда присылает вызов инструмента с лишней `}` или `]`: в конце (`…]}}`) или после
  элемента списка (`…"}}, {…`). Раньше вызов падал, модель видела ошибку и звала инструмент ещё раз — лишний шаг,
  время и деньги. Теперь ядро убирает такую скобку само. Скобка без пары данных не несёт: содержимое не угадывается.
- **Только очевидное.** Чинится не больше двух лишних скобок. Не хватает скобки, после конца JSON идут не скобки,
  строка не закрыта — не чинится. Починенный вызов SDK заново проверяет схемой инструмента. Не прошёл — ошибка модели
  и повтор, как раньше.
- **В истории — починенный вызов.** Модель видит верный JSON и не учится на своей опечатке. Кэш не страдает: свой ответ
  модель и так получает в следующем запросе новым текстом.
- **Журнал.** Каждая починка — строка `[аргументы починены]`: чат, инструмент, модель, провайдер, что поправлено, длина.
  Самих аргументов в строке нет. Туда же теперь пишутся и прежние починки (переводы строк, `"2"` вместо числа).
  Строка идёт в `logError` (по умолчанию `console.error`), как `[результат обрезан]`.

Строгий режим вызовов DeepSeek (`strict`) не взят: он только на бета-адресе и требует, чтобы каждое поле каждого
инструмента было обязательным, без `minLength` и `maxItems`. Это переделка схем всех инструментов приложений.

**Как обновить приложение.** Ничего делать не нужно: починка работает сама у всех провайдеров.

Приложение на старой версии SDK (например, 0.25.0): поднимите все пакеты `@ykurilov/agent-chat-*` до `^0.46.0`, затем `pnpm install`.
Ломающие изменения между 0.25 и 0.46 — в «Как обновить» версий [0.31.0](#0310), [0.35.0](#0350), [0.36.0](#0360-2026-10-11)
и [0.37.0](#0370-2026-10-11). В прогоне оценки ошибка «Нет ошибок и упавших вызовов» с `AI_JSONParseError` уйдёт,
в журнале сервера появится `[аргументы починены]`. Ошибки схемы (`AI_TypeValidationError`, лишние поля) по-прежнему
идут модели на повтор.

### Наблюдения приложения с формами

- **Сервер упал посреди инструмента — вызов не теряется.** Раньше вызов попадал в базу не сразу: если сервер падал,
  пока инструмент работал, в истории не было и следа вызова, хотя бронь уже могла пройти. Теперь вызов записан ещё до
  того, как инструмент начал работу. После перезапуска он виден прерванным, а «Повторить» продолжает с него.
- **На последнем шаге агент ничего не делает.** На последнем шаге хода модели запрещено звать инструменты, но
  модель могла позвать всё равно — и инструмент выполнялся. Теперь такой вызов не выполняется: модель получает отказ, а
  история остаётся правильной для следующего хода. То же у помощников и у вызовов с подтверждением: на последнем шаге
  подтверждения не спрашивают.
- **Приложение знает, что ход упёрся в предел шагов.** `afterTurn` получает `stepLimit: true`, в журнале SDK — строка
  `[предел шагов]`. Флаг значит «дошли до потолка шагов», а не обязательно «недоделали»: модель могла закончить дело как
  раз на последнем шаге. Человеку на экране ничего не показывается: показать своё — по этому полю.
- **«Повторить» сообщает, какой ответ заменяется.** `beforeTurn` и `turnNotStarted` получают `previousAnswerId` и
  `abandonedAnswerIds`, как у «Переделать» и правки вопроса.
- **«Ответа уже нет» — экран сразу показывает правду.** Человек выбрал время в виджете, а сервер ответил, что ответ уже
  ушёл дальше: лента сразу перечитывает историю. Если сервер под нагрузкой и чтение сорвалось, лента пробует снова, а не
  застывает. То же у подтверждения и у действия на странице.
- **Тандем: набранный текст не пропадает.** Раньше поле ввода пересоздавалось, когда загружалось меню моделей, и текст,
  набранный до этого, исчезал. Теперь поле то же самое: текст и курсор на месте. Так же при появлении вложений, голоса,
  кнопок приложения и лимита.

**Как обновить приложение.** Обновление само по себе ничего не требует. Обходы в приложении с формами, которые можно убрать:

1. **Ожидание кнопки «Модель» в тестах** (`tests/support/test-chat-ready.ts`): текст, набранный до меню, не пропадает.
2. **Ожидание `status: complete` перед обрывом сервера** в тесте восстановления: сервер можно обрывать посреди
   инструмента — вызов уже в базе.
3. **Свои проверки «последний ли шаг» в инструментах с последствиями** (бронь, оплата): SDK сам не выполнит вызов на
   последнем шаге.
4. **Свой подсчёт шагов в `afterTurn`**: вместо него `turn.stepLimit`.
5. **Своё вычисление прежнего ответа для «Повторить»**: вместо него `previousAnswerId` в `beforeTurn` / `turnNotStarted`.
6. **Читаете ответы из хранилища сами** — в ответе на пределе шагов есть служебная часть `data-step-limit` (как
   `data-length-cut`): пропускайте её.

### Вложения: картинки для моделей без зрения

Зрение модели теперь считается для пары «модель + провайдер», модель без зрения может смотреть картинку инструментом
приложения, а типы файлов можно сузить.

- **Зрение по паре.** В профиле модели `acceptsImagesByProvider: { together: false }` — отметка провайдера главнее
  `acceptsImages`. `modelAcceptsImages(profile, providerId)` из ядра; по нему меню моделей и вложения.
- **Исправлен каталог.** DeepSeek 4.1 Flash и GLM 5.3 Flash через Together картинок не видят (в каталоге Together они только
  текстовые): раньше SDK отправлял туда байты картинки, теперь модель получает пометку, а меню говорит «не видит».
  Через DeepSeek, Fireworks и OpenRouter они видят, как раньше.
- **Плашка для модели без зрения.** `createAttachments({ imagesForBlindModels: { toolName } })`: вместо картинки —
  постоянная плашка `[Картинка «shot.png», вложение <id>. Посмотреть: <toolName>.]` (свой текст — `marker`, всем моделям —

  Без `always` смена пары «модель + провайдер» между зрячей и слепой меняет историю (плашка ↔ картинка), и кэш модели

  картинки, приложение сверяет `authorId` в своём инструменте.
- **Только нужные типы.** `createAttachments({ acceptedMediaTypes: [...] })`: чужой тип — отказ `unsupported_type` до

  при `["image/png"]` проходит (запись хранит его в новом поле `sourceMediaType`; своё хранилище должно его сохранять,

  ошибка `unsupported_type` с текстом «Такой файл прикрепить нельзя: подойдут только PNG, JPEG, WebP.» (по списку).
  Импорт чата вместо картинки неподходящего типа пишет «[картинка: имя]», а не падает целиком.

- **`isAttachmentId`** — из публичного входа `@ykurilov/agent-chat-attachments`.

- **Скрытый провайдер.** `hiddenFromMenu: true` у фабрик провайдеров (или в описании) убирает провайдера и его модели из

  с `details`, и экран показывает его текущей моделью.

- **Остановка сервера ждёт ответы** (`flush({ waitForAnswersMs })`). Новые ходы не начинаются, идущие ответы
  дорабатывают до срока. Не успевшие закрываются как «Стоп», без обрывков. `flush` возвращается после записи и
  `afterTurn`.

### Как обновить приложение

1. В остановке сервера: `await chat.flush({ waitForAnswersMs: 20_000 })` вместо `await chat.flush()`, затем закрыть
   хранилище. Без опций ответы останавливаются сразу. Раньше после остановки ответ был `interrupted`, теперь `stopped` со
   `stopReason: "shutdown"`.
2. Если `beforeTurn` что-то резервирует — снимайте резерв в `turnNotStarted` (по `messageId`).
3. По желанию: `agent.turnTimeoutMs` и `agent.maxOutputTokens` (число или `{ default, byModel }`).
4. Проверка: `pnpm typecheck`; остановка посреди ответа даёт `stopped` и `stopReason: "shutdown"`.

Подробно — в [журнале core](packages/core/CHANGELOG.md).

Панель агента в приложении: боковая панель поверх страниц (`AgentPanelProvider` и `AgentPanel` из `@ykurilov/agent-chat-react/panel`, скин Тандема уже готов). Агент знает, где человек (`useAgentPlace`), делает действия на странице (браузерные инструменты: `agent.browserTools`, функции у провайдера) и сообщает странице об изменённых данных (`notifyDataChanged`, `useAgentDataChanges`). Инструменты агента получают в `model` ещё и `place`. Работает на одном сервере. Раздел «Панель агента в приложении» в `docs/getting-started.md`. Ломает только мелочи: полный словарь надписей, написанный вручную, — нужна `agentPanelToolUnavailable` (и `agentPanel…`); тесты, собирающие `AgentToolsModel` вручную, — поля `place` и `notifyDataChanged`; свои реализации `ChatService` — метод `answerBrowserCall`, а `retry`, `regenerate` и `answerApproval` получили необязательный последний аргумент `page`, `sendMessage` и `editMessage` — поле `page` в настройках (свои обёртки, которые пересылают аргументы или поля поштучно, его потеряют — место и вкладка не дойдут); `HandlerErrorKind` получил вид `not_pending` (исчерпывающий `switch` по нему перестанет собираться); в сжатии истории `tools(...)` получает `model.place: null`; `useChatList` при смене `rememberKey` сбрасывает список. Договор скина версии 12 — по желанию, только для своего скина панели.

Надёжность хода агента (022). Что работает само: тихие повторы и запасной провайдер той же модели; «Повторить» продолжает оборванный ход, а не начинает заново; оборванный посреди ответа текст дописывается сам (до двух раз); переполнение окна модели лечится сжатием; зависший инструмент или молчащая модель больше не держат ход вечно (`agent.toolTimeoutMs`, `agent.modelSilenceTimeout`); опасные инструменты можно пускать по одному (`agent.sequentialTools`, очередь одна на чат); расход оборванных ответов не теряется и помечен «примерно», у OpenRouter он потом сверяется с настоящим. Дата в запросе по часовому поясу человека, в журнале сервера строки про повторы, сбои и промахи кэша. Защита: запись с чужой страницы получает 403 (`allowedOrigins`, фронт и API на разных адресах — шаблон `https://*.example.com`, за nginx передайте `Host`), не больше трёх одновременных ответов на человека, тело запроса не больше 1 МиБ, секреты вычищаются из ошибок инструментов, большие фото уменьшаются (`sharp`), внешние картинки в ответе модели Тандем показывает ссылкой. Нужен Node 22. Можно несколько копий сервера на одной базе. Миграции SQLite 0011–0012 и PostgreSQL 0010–0011 применяются сами.

Что ломает: вид ошибки `context_overflow` (исчерпывающий `switch`, полный словарь надписей — добавьте `context_overflow`, `signed_out`, `too_many_turns`, `forbidden_origin` и ключи правок `signedOut`, `tooManyTurns`, `forbiddenOrigin`, `approvalTooManyTurns`; поверх `{ ...russianLabels }` ничего делать не нужно); по умолчанию не больше трёх одновременных ответов на человека (`maxConcurrentTurnsPerUser`, `Infinity` — без предела); запись с чужой страницы без `allowedOrigins` отклоняется; вложениям нужен `sharp`, а `react` у них стал необязательным peer. Для своих хранилищ: `FinishedMessagePatch.providerId` (необязательно), фильтры `messageId` и `source` в `sumUsage`, а для нескольких копий сервера — `markAnswerAlive`, `listSilentAnswerIds` и поле `alive` (без них работает только одна копия). Первое обновление до этой версии — остановите все старые копии сервера, потом запускайте новые.
