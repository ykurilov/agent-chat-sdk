# Contract: HTTP-адреса — дополнения 003

Дополняет [002](../fast-feed-and-liveness/http-api.md) и 001. Общие правила
те же: без пользователя `401`, чужой чат `404`, тело ошибки `{ "error": { "kind": … } }`.

## Настройка обработчика

```ts
createChatHandler({
  …как в 001/002,
  // resolveModel УДАЛЁН
  defaultChoice?: { modelId: string; providerId: string; reasoning?: ReasoningLevelId },
})
```

Если `defaultChoice` не задан — первая модель каталога у первого провайдера с ключом. Если задан, но
его нет в каталоге, — сообщение в `logError` при создании обработчика и первая доступная модель.

## Новые адреса

| Метод и путь | Что делает | Ответ |
|---|---|---|
| `GET {base}/models` | Список для меню ([data-model.md](./data-model.md)) | `200 ModelMenu` |
| `PUT {base}/:chatId/model` | Записать выбор чата | `200 { modelId, providerId, reasoning }` |

`PUT {base}/:chatId/model`, тело `{ "modelId": "…", "providerId": "…", "reasoning": "medium" }`
(`reasoning` необязателен: без него уровень по умолчанию модели).

- Проверки: модель в каталоге; провайдер её обслуживает и у него есть ключ на сервере; уровень есть у
  модели (профиль без уровней — уровня быть не должно). Иначе `400 { error: { kind: "invalid" } }`,
  ничего не сохранено.
- Можно в любой момент, в том числе пока идёт ответ: идущий ответ дописывает прежняя модель.
- В ответе — уровень, как он сохранён (при отсутствии в теле — уровень по умолчанию модели).

## Изменения существующих ответов

- `GET {base}/:chatId`: `chat` несёт эффективный выбор (`modelId`, `providerId`, `reasoning`): сохранённый,
  если он доступен, иначе замена (выбор по умолчанию). Сообщения не меняются.
- `POST {base}` (создание) сохраняет в чате выбор по умолчанию; ответ `201 { id }` прежний.
- Ход агента идёт на эффективном выборе чата на момент запуска.
- `GET {base}/models` не содержит ключей, имён переменных окружения и адресов провайдеров (SC-006).
