# Конечные сбои очереди картинок

`createImageQueue` принимает необязательный `onFailed(event, context)` и `failureRetryMs` (по умолчанию 30 000 мс). Те же параметры доступны в `createImageGeneration` с `delivery: "background"`.

`ImageFailureEvent` содержит `id`, `run`, `job` и `failure`. `failure` имеет поля `kind`, `reason` и необязательный `providerCode`. Поле `job.failure` возвращается также из `queue.get()` и `queue.list()`.

## Классификация

- `transient`: сетевой сбой, срок ожидания, HTTP 408/429/5xx либо распознанный временный код провайдера.
- `content`: явный отказ фильтра содержания в ответе провайдера. Исходный prompt не используется для классификации.
- `limits`: HTTP 402 либо распознанный отказ из-за баланса.
- `configuration`: параметры, ключ или адрес подключения требуют исправления.
- `delivery`: приёмник готовой картинки не смог её принять.
- `unknown`: данных недостаточно. Это не разрешение на автоматический повтор.

Классификация консервативна, форматы ответов провайдеров меняются. Для своего провайдера `ImageGenerationError` принимает `kind` и `providerCode`; у результата `queue.check()` со статусом `failed` есть необязательные `failureKind` и `providerCode`. Учёт стоимости и `refusedBeforeWork` независимы от категории: отказ фильтра сам по себе не доказывает отсутствие расходов.

`queue.retry()` отклоняет повтор того же запроса с `failure.kind === "content"`, не обращаясь к провайдеру. Приложение скрывает соответствующую кнопку. Исправленный сюжет оформляется отдельным заказом после проверки правил и бюджета приложения. Косметическая переформулировка для обхода фильтра не является восстановлением технического сбоя. После исправления ключа или баланса ручной повтор разрешён.

Для старых окончательно проваленных задач явный safety-маркер из сохранённого `reason` показывается как `content`, прочие причины - `unknown`. Исторические события автоматически не создаются.

## Сохранение и подтверждение события

При конечном сбое событие записывается в ту же запись задачи до вызова `onFailed`. Его id `image-failed:<job.id>:<run>` не меняется при повторной доставке. `onFailed` должен только идемпотентно записать событие в очередь приложения с уникальным ключом `event.id` и завершиться. Генерацию, вызов агента и другую долгую работу выполняет отдельный worker приложения.

Успешное завершение callback подтверждает событие. Если callback бросил исключение или процесс завершился до подтверждения, очередь повторит доставку после `failureRetryMs` и перезапуска. Повтор уведомления не вызывает провайдера и не расходует попытки генерации. Неподтверждённая запись остаётся активной и не удаляется штатной чисткой. Повторы доставки продолжаются до подтверждения; при недоступном приёмнике приложение контролирует рост очереди и журнал ошибок. Отключение callback не подтверждает сохранённые события.

Подтверждение после внешней записи не атомарно с базой приложения. При падении между ними callback придёт повторно с тем же id. Гарантии exactly-once для внешних действий нет. Встроенные хранилища используют существующую аренду и CAS версии задачи; пока callback жив, аренда продлевается. При потере аренды приложение всё равно обязано подавлять дубли по `event.id`.

`context.signal` позволяет остановить работу при завершении очереди или смене запуска. `context.isCurrent()` проверяет событие этого запуска и его аренду. Потеря актуальности события прерывает обработчик и не подтверждает событие; перед подтверждением SDK проверяет актуальность ещё раз. Актуальность места картинки, владельца приложения, нового заказа с другим id и бизнес-ограничения проверяет приложение перед созданием recovery и перед новым заказом. Передаваемые объекты отделены от сохранённой записи; правки callback не изменяют хранилище.

`order()` возвращает сохранённый сбой, не ожидая завершения callback. Для задачи с `lateUntil` провал ещё не конечный: событие появляется только после истечения окна позднего результата. Успех, отказ приёмника с `false` (discarded), вытеснение заказа и синхронный отказ без создания задачи не создают событие конечного сбоя.

## Ограниченное восстановление

Лимиты повторов генерации SDK остаются в силе. Для отказов содержания, баланса и настройки автоматического нового заказа нет. У приложения отдельный сохранённый бюджет восстановления, атомарное разрешение одного нового заказа на событие, проверка владельца и актуальности места. Временный сбой допускает технический повтор в пределах этого бюджета. Отказ содержания передаётся агенту как ограничение: разрешённый иной сюжет или готовый asset, либо сообщение человеку об ограничении.

## Обновление

Параметры необязательны. Встроенным SQLite и PostgreSQL хранилищам не нужны новые SQL-колонки или ручная миграция. Своё `ImageJobStore` сохраняет и возвращает `failure` и `failureNotification` вместе с остальными JSON-полями записи и исполняет существующий CAS/lease-договор. `active: true` у законченной задачи может означать неподтверждённое событие, а не продолжающуюся генерацию.

Все установленные пакеты SDK обновляются одной версией. Приложение добавляет durable приёмник до включения callback; старые задачи не воспроизводятся массово.

## Условный технический повтор

Worker события вызывает `queue.retry({ ownerId, key, expectedJobId: event.job.id, expectedRun: event.run })`. Оба условия передаются вместе. Если выбранная задача или её запуск сменились, возвращается `null` без нового запроса провайдеру. Условие запуска проверяется повторно после проигранного CAS; вызов не подхватывает новый запуск. Вызовы с разными условиями не объединяются с обычным ручным повтором. Ручной `retry({ownerId,key})` сохраняет прежнее поведение.

Это CAS конкретной записи job/run, а не общая транзакция с таблицами приложения или запрет последующих заказов другого job.id. Проверка актуальности места и условная запись файла остаются обязанностью приложения.
