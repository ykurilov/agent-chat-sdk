# Аудит: сеть и фоновые задачи (ветка audit-network)

Исправления по четырёхмодельному аудиту: зона веб-инструментов, картинок, MCP и фоновых задач.

## Что изменилось

### Подмена DNS при скачивании снимков и картинок (C-05, kimi-1, kimi-2)

Раньше снимок страницы проверял имя по DNS, а потом `fetch` разрешал его ещё раз. Злоумышленник мог ответить на
проверку публичным адресом, а на соединение — внутренним (DNS rebinding). Скачивание картинок провайдера проверяло
только запись адреса, без DNS.

Теперь у `@ykurilov/agent-chat-web-tools` есть серверный вход `./network`: проверка адреса и закреплённый `fetch`
(`createPinnedFetch`). Имя разрешается один раз, в момент соединения; этот же ответ проверяется и идёт в соединение.
Адрес-число (`127.0.0.1`, `[::1]`) проверяется там же, при соединении: и в первом адресе, и после переадресации, в том
числе обычной (`redirect: "follow"`). Без `allowPrivateNetwork` закреплённый `fetch` во внутреннюю сеть не ходит;
встроенный транспорт MCP с `allowPrivateNetwork` по-прежнему открывает свои частные адреса.
Им пользуются три места, копий нет:

- `page_screenshot` без своего `fetch` приложения;
- скачивание картинок провайдера без своего `fetch` (`createImageGeneration`, `createImageQueue`);
- встроенный транспорт MCP (перенесён из `@ykurilov/agent-chat-mcp`, тексты ошибок прежние).

Вход `./network` не тянет инструменты, службы поиска, ядро и `ai`. Пакет `undici` грузится при первом запросе.
Соединения общие на процесс; `PinnedFetch.close()` их закрывает.

**Сайт подключения провайдера (`baseURL` из настройки)** остаётся доверенным: с него картинку можно скачать по http и
с localhost. Доверие действует, пока адрес на этом точном сайте (`origin`). Переадресация на другой сайт снова
проверяется при соединении и разрешения на внутреннюю сеть не наследует.

**Свой `fetch` приложения** (`createWebTools({ fetch })`, `createImageGeneration({ fetch })`,
`createImageQueue({ fetch })`, MCP `fetch`) — граница доверия приложения. SDK проверяет адрес и, где было, DNS до
запроса. Закрепить соединение за проверенным адресом такой `fetch` должен сам. Полной защиты от подмены DNS со своим
`fetch` SDK не обещает. Нужен прокси и защита — оберните `createPinnedFetch` из `@ykurilov/agent-chat-web-tools/network`.

### Предел задач человека для нескольких копий сервера (codex-3, kimi-5)

`maxRunningPerUser` проверялся подсчётом и отдельной записью под замком одной копии. Две копии на одной базе могли
вместе запустить больше. Второй вход того же предела — ответ на подтверждение: пауза отдаёт место, а ответ продолжал
задачу без проверки, и после ответа задач у человека становилось больше предела.

Теперь место занимается одним действием хранилища: новый метод `TaskStore.admitWithinLimit(admission, maxActive)`.
`admission` — новая задача (`{ create: task }`) или продолжение с паузы (`{ resume: { ownerId, taskId, patch, when } }`,
условная правка как у `update`). В памяти — синхронно; в SQLite — транзакция `immediate`; в PostgreSQL — транзакция с
замком на человека (`pg_advisory_xact_lock`). Запуски и ответы на двух копиях делят одно место честно.

Что получает приложение, когда мест нет:

- запуск — как и раньше, ответ инструмента `too_many_tasks` для модели;
- ответ на подтверждение (`answerApproval`, и «Разрешить», и «Запретить») — отказ `TurnRefusedError` с кодом
  `too_many_tasks`. Обработчик чата отдаёт его как `403 turn_refused` с этим кодом и текстом; плашка на экране
  показывает обычное «ответ не принят» (`approvalFailed`) с теми же кнопками, мессенджер — текст отказа.
  Ничего не записано: задача на паузе, тот же вопрос ждёт, кнопки те же. Место освободилось — тот же ответ продолжает
  задачу один раз. Задачу на паузе можно отменить.

Места освобождают законченные, упавшие, остановленные и вставшие на паузу задачи, как и раньше. Подхват идущей задачи
после падения копии новой записи не создаёт и места не досчитывает: задача уже занимает своё место и отдаёт его, когда
закончится.

### `person_link_view`: отказ проверки адреса не считается просмотром (gemini-5)

Адрес, который не прошёл проверку безопасности до обращения к службе, раньше оставался «просмотром в работе» и после
перезагрузки истории считался настоящим просмотром. Теперь это отказ: текст начинается с «Отказ:», в счёт трёх
просмотров он не идёт ни в этом ходе, ни из истории. Оборванный «Стопом» просмотр по-прежнему считается: запрос мог уже
уйти, а «Стоп» заканчивает ход, поэтому бесконечных настоящих попыток нет.

### Экран админа MCP: битая %-кодировка в адресе (gemini-6)

Адрес вроде `/api/mcp/servers/%E0%A4%A` давал 500. Теперь 404. Не-админ по-прежнему получает 404, запись с чужой
страницы — 403.

### Не подтверждено: C-06 (`takeAbandonedBursts` в PostgreSQL)

Проверено на настоящем PostgreSQL 18.4. План запроса на 10, 1000 и 100 000 строк, по умолчанию и с навязанными
вариантами (без hash, merge, material, hashagg, memoize): подзапрос `IN (… for update skip locked)` всегда выполняется
один раз. Гонка восьми соединений, 200 раундов, предел 3: 1600 захватов, превышений предела 0, двойных захватов 0.
Двойной захват исключён и устройством запроса: строку обновляет только тот, кто держит её замок, а внешнее условие
проверяется заново. Запрос не менялся.

## Что сделать при обновлении

- **Ломающее для своего хранилища фоновых задач.** `TaskStore.admitWithinLimit` обязателен: без него
  `createBackgroundTasks` сразу падает с ошибкой, а TypeScript не соберёт хранилище. Тихой замены отдельными подсчётом
  и записью нет: она держала бы предел только внутри одной копии. Реализуйте: подсчёт как у `countActive` и запись
  (вставка для `create`, условная правка как у `update` для `resume`) одним действием базы — транзакция с замком на
  человека. Встроенные хранилища менять не нужно.
- Ответ на подтверждение фоновой задачи теперь может получить отказ `too_many_tasks` (`403 turn_refused`). Плашка на
  экране показывает «ответ не принят» с теми же кнопками, мессенджер — текст отказа; ответить можно позже.
- Свой `fetch` приложения для снимков, картинок или MCP — проверьте, закрепляет ли он соединение за проверенным
  адресом. Нет — оберните `createPinnedFetch` из `@ykurilov/agent-chat-web-tools/network`.
- Картинки провайдера теперь качаются закреплённым `fetch`, если своего `fetch` нет. Склад провайдера во внутренней сети
  (кроме сайта `baseURL` из настройки) больше не откроется.
- SQL-миграций и новых обязательных настроек нет.
