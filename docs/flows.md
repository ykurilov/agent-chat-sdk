# Сценарии поведения агента

Обычно агент ведёт разговор по одной большой инструкции. Хочешь «сначала познакомься, потом найди проблему, потом
предложи разбор, а замолчал человек на 3 часа — напомни» — пишешь это абзацами и надеешься, что модель не перескочит
шаг. Сценарий решает это по-другому: разговор идёт по карте шагов.

Пример — «Разбор продаж курса»:

- **Знакомство.** Агент спрашивает тему курса и продажи. Человек ответил — переход дальше.
- **Поиск затыка.** Вместе с человеком ищут, что мешает продажам. Нашли — дальше.
- **Предложение разбора.** Агент предлагает 30 минут с наставником. Засомневался человек — «Работа с сомнениями».
- Спросил человек «а сколько стоит?» в любой момент — агент отвечает из «Общего для всех состояний» и продолжает с того
  же места.
- Замолчал на 3 часа — «Напоминание». Молчит до утра — в 10:00 «Утреннее касание». Ответил — агент возвращается туда,
  где шёл разговор.

Каждый шаг — **состояние** со своей короткой инструкцией. Из состояния ведут **условия выхода**. Сработало условие —
агент переходит и ведёт себя уже по новому состоянию. Не сработало ни одно — остаётся, где был.

Это отдельный пакет `@ykurilov/agent-chat-flows`. Без него ничего не меняется.

## Подключение: сервер

```bash
pnpm add @ykurilov/agent-chat-flows
```

```ts
import { createAgentFlow } from "@ykurilov/agent-chat-flows";
import { sqliteFlowStore } from "@ykurilov/agent-chat-flows/sqlite";
import { createChatServer } from "@ykurilov/agent-chat-server";

const flow = createAgentFlow({
  // Какой сценарий у нового чата. Чат закрепляется за версией и дальше идёт по ней.
  loadFlow: async ({ ownerId, chat }) => ({ flowId: "sales-review", versionId: "3", flow: await myFlows.published("sales-review") }),
  store: sqliteFlowStore("./data/chat.db"), // тот же файл, что у чатов; или postgresFlowStore(pool)
  judge: { fallback: { modelId: "deepseek-4.1-flash", providerId: "deepseek" } },
  onTransition: async (event) => {
    if (event.tags.includes("человек")) await callOperator(event.chatId);
  },
});

const { handler, service } = createChatServer(
  flow.withChat({ basePath: "/api/chat", storage, resolveUser, catalog, agent: { instructions: "…", tools: myTools } }),
);
flow.attach(service); // после createChatServer
flow.start(); // таймеры; при остановке сервера — await flow.stop()
```

- `withChat` дописывает к настройкам чата то, что нужно сценарию: инструкцию, служебные инструменты, блоки, шаги до и
  после хода. Свои настройки передавайте как обычно.
- Проверки ответа (`replyChecks` в `withChat`) получают тексты сценария как «известные»: общая часть, ноды, первые
  сообщения, прощание, текст рамки дня, попутные задачи. Ссылка из первого сообщения не вырезается.
  Подробно — [docs/reply-check.md](reply-check.md).
- `loadFlow` вернул `null` — чат идёт без сценария, как раньше.
- В групповых чатах мессенджеров сценарий выключен: там агент ведёт себя как без него.
- Место чата в сценарии (ключ `flow` в состоянии чата) посетитель не видит: SDK сам прячет его от браузера
  (`privateStateKeys`). Где чат и какой путь прошёл, сервер читает через `flow.readRun`.
- Сценарий с ошибками сервер не запустит: строка в журнал, чат идёт без сценария.
- Хранилище: `memoryFlowStore()` (тесты), `sqliteFlowStore(path)`, `postgresFlowStore(pool)`. Таблицы создаются сами
  при первом обращении: `flow_chats`, `flow_versions`, `flow_client_cards`, `flow_first_messages`, `flow_people`,
  `flow_side_tasks`.
- Ключ судьи — `OPENROUTER_API_KEY` в окружении сервера (или `judge.openrouter.apiKey`).

Что ещё есть у `flow`: `signal` (событие приложения), `admit` (как поступить с сообщением человека), `pause`, `resume` и
`noteStaffReply` (отвечает сотрудник), `reportDelivery` (исход доставки), `readRun` (где чат и какой путь прошёл),
`chatsByState` и `migrateChats` (перевод на новую версию), `readClientCard` и `forgetClientCard`, `advanceTestClock`
(тестовый чат), `tick` (один обход таймеров сейчас — для тестов и своего планировщика вместо `start()`), `settled`
(дождаться фоновой работы).

`withChat` добавляет к `agent.serviceBlocks` служебные тексты сценария (`FLOW_SERVICE_BLOCKS`): строку перехода
«Сработало: … → «…».», строку смены состояния из ответа `flow_exit`, «скажи ровно это: «…»» и карточку клиента. Если
модель повторит их в ответе, ядро вырежет их до экрана и записи. Карточки состояния в списке нет: у неё нет надёжной
последней строки.

## Привязка к приложению

Простой случай — одна служба чата на всё приложение: `flow.attach(service)`, как выше. Приложению с несколькими
продуктами и своими каналами (Телеграм-бот, ВК, свой мессенджер) нужно больше.

```ts
const flow = createAgentFlow({
  loadFlow: async ({ ownerId, chat }) => {
    const lead = await leads.byChat(chat.id);
    // Чат, начатый до сценария, встаёт на нужное место: нода, начало программы, вход в ноду.
    return { flowId: "first-result", versionId: "7", flow: await flows.published("first-result"),
      stateId: lead.stage, startedAt: lead.startedAt, enteredAt: lead.stageAt };
  },
  store: postgresFlowStore(pool),
  judge: {
    fallback: { modelId: "deepseek-4.1-flash", providerId: "deepseek" },
    // Судья через свой прокси: адрес и заголовки.
    openrouter: { baseUrl: "https://proxy.example.com/openrouter/v1", headers: { "X-Proxy-Token": proxyToken } },
  },
  onFinish: async (end) => crm.close(end.chatId, end.reason, end.tags),
  clientCard: appCardStore, // карточка в вашей базе, см. ниже
  people: appPeople, // пояс человека в вашей базе
});

flow.attach({
  // Служба чата этого разговора: у разных продуктов — разные службы со своей инструкцией.
  portFor: ({ chatId }) => servicesByProduct[productOf(chatId)],
  // Своя доставка ответов, которые агент пишет первым. Нет — доставляют каналы SDK.
  deliver: async (message) => myBot.send(message), // → { status: "delivered" | "blocked" | "window_closed" | "retry" | "failed" }
});
```

- **Что получает `deliver`.** `{ ownerId, chatId, messageId, text, parts, reasons, attempt }`. `text` — текст ответа.
  `parts` (с 0.53) — все части, которые надо доставить человеку: текст, файлы, вызовы инструментов с результатом.
  Показал агент в касании карточку ролика (`tool-show_video`), картинку или виджет — они в `parts`, доставьте их так
  же, как в обычном ответе. Рассуждений модели и служебных частей там нет. Ответ без текста, но с карточкой, тоже
  уходит в `deliver`. Повтор доставки отдаёт те же `text` и `parts`.

- **Причина перехода.** У каждого шага пути (`readRun().path`) и в `onTransition` есть `reason: { kind, text }` — почему
  агент перешёл, словами: у заявки агента — его объяснение, у остальных — условие («нода длится 1 день», «узнали
  «Цель»», «срок вышел»). `kind` — кто решил, как `decidedBy`.
- **Перенос чата.** `loadFlow` может вернуть `stateId`, `startedAt` и `enteredAt`: чат, который шёл у вас до сценария,
  продолжается с нужной ноды и нужного дня, а не с начала. Идущий чат переносится целиком — см. «Перенос идущего
  чата».
- **Конец снаружи.** `flow.end({ ownerId, chatId, reason, outcome })` — см. «После конца разговора».
- **`settled()`** ждёт всю фоновую работу: судью после хода, доставку, `onTransition`, `onFinish`. Нужен в тестах и
  перед остановкой сервера. В тестах вместе с `now` у `createAgentFlow` и `createChatService` часы подменяются целиком.

### Перенос идущего чата

Человек молчит в старой системе, а ему ещё положены касания. Ждать его хода нельзя: напоминаний не будет. `flow.adopt`
закрепляет чат сразу и ставит срок следующего касания.

```ts
await flow.adopt({
  ownerId, chatId, flowId: "first-result", versionId: "7", flow: await flows.published("first-result"),
  stateId: "polish", startedAt, enteredAt,
  lastHumanAt: lead.lastHumanAt, // от неё «не завершил» (giveUpAfter)
  lastAgentAt: lead.lastAgentAt, // от него тишина и касания
  nudgeStep: 1, // одно касание ряда afterSilence уже было
  today: { firstMessages: 2, humanMessages: 12, dayClosed: false },
  timeZone: lead.timeZone, // пояс человека, если знаете
});
// → { adopted: true }; уже закреплённый чат — { adopted: false }, ничего не меняется
```

- Чат должен быть в службе чата (`createChat`). Сценарий с ошибками или нет такой ноды — исключение.
- `today.firstMessages` — сколько агент уже написал первым сегодня: идёт в дневной потолок, второй вызов его не удваивает.
- `today.humanMessages` и `today.dayClosed` — для рамок дня и «на сегодня всё». Работают только с «Днями и временем».
- Без пояса ночь и «сегодня» считаются по `defaultTimeZone`, иначе по поясу приложения или сервера, пока человек не
  напишет со страницы.
- Тестовый чат (`flowTestChatData()`), закреплённый так без хода, перематывается и до утра (`to: "next_day_start"`).
- Перенос лежит в записи чата и переживает перезапуск. Таймеры, `admit` и `readRun` видят перенесённое место сразу,
  первый ход кладёт его в состояние чата.
- Те же поля может вернуть `loadFlow`: тогда чат закрепится на первом ходе человека. Молчащий чат так касаний не
  получит, поэтому для переноса — `adopt`.

### Исходы доставки

Канал приложения отвечает, как прошло:

| Исход | Что делает сценарий |
|---|---|
| `delivered` | сообщение засчитано в дневной потолок |
| `retry` | тот же текст с тем же `messageId` уходит снова: через `afterMs` или 1 мин · 5 мин · 30 мин. Пока ждёт повтор, новых ходов нет и его срок ничто не затирает |
| `window_closed` | канал не пускает писать первым (окно ВК): агент молчит, пока человек не напишет сам. Любое сообщение человека снимает запрет, даже если агент на него не ответил |
| `blocked` | человек заблокировал канал: конец разговора `blocked`, `onFinish` |
| `failed` | не доставлено насовсем: ответ помечен «Не доставлено», модель его больше не видит, в счётчик не идёт |

Недоставленное касание (`failed`, `window_closed`) не засчитывается. Это правило одинаково для своей доставки и для
каналов SDK. Тот же шаг касаний повторится через свой срок, считая от момента отказа. Пример: касание «через час» не
дошло в 16:00 — следующая попытка того же касания в 17:00, а не переход к «через 4 часа». Для этого в `FlowRun` есть
поле `touch`; записи без него, сделанные до 0.49, читаются как раньше.

Каналы SDK (`@ykurilov/agent-chat-messengers`) сообщают исход сами — одной строкой:

```ts
createMessengers({ …, onAnswerDelivery: (report) => flow.reportDelivery(report) });
```

### Входящее сообщение: `admit`

Свой канал перед ходом спрашивает сценарий, что делать с сообщением человека. Каналы SDK делают это сами.

```ts
const decision = await flow.admit({ ownerId, chatId, text });
// answer — ход как обычно; reply — отправить decision.text без модели (жёсткая рамка дня);
// hold — записать и молчать до decision.until (после жёсткой рамки — до начала следующего дня); paused — отвечает сотрудник;
// ended — разговор закончен, см. «После конца»
```

**Несколько сообщений подряд.** Свой бот, где человек пишет короткими сообщениями, зовёт вместо `sendMessage`
`service.sendBurstMessage` (см. [getting-started](./getting-started.md), «Несколько сообщений подряд»): один ход на
пачку. Ворота сценария работают сами: `admit` зовётся один раз на пачку, касания ждут, пока пачка не решена, пауза
сотрудника — пачка записана, агент молчит. Решаете пачку сами — передайте её размер:
`flow.admit({ ownerId, chatId, text, messages: 3 })`. В рамки дня идёт каждое сообщение (ниже).

## Подключение: редактор

Редактор — управляемый компонент: сценарий хранит и сохраняет ваше приложение.

```tsx
import { FlowEditor } from "@ykurilov/agent-chat-flows/react";
import { tandemFlowEditorSkin } from "@ykurilov/agent-chat-skin-tandem/flows";

<FlowEditor
  skin={tandemFlowEditorSkin}
  value={flow}
  onChange={setFlow}
  onSave={(flow) => api.saveFlow(flow)}
  // Что приложение умеет: из этих списков автор выбирает, а не пишет имена руками.
  catalog={{ tools: ["give_booking_link", "call_expert"], events: ["booking_link", { name: "paid", label: "Оплачено" }], widgets: [] }}
/>;
```

**Подписи событий.** Событие или кнопка в `catalog.events` — строка-имя или `{ name, label }`. С подписью доска, прогон и
карточка условия показывают «Событие приложения «Оплачено»» вместо «paid»; в JSON сценария остаётся имя. Без подписи — имя,
как раньше. Подпись даёт приложение на своём языке, отдельного перевода нет. `describeCondition(flow, when, catalog)` с
каталогом тоже пишет подпись; без каталога — имя. Имена из каталога — `catalogEventNames(catalog)`, подпись —
`catalogEventLabel(catalog, name)` (из `@ykurilov/agent-chat-flows/format`).

### Только просмотр, отказ в сохранении, высота

**`readOnly`.** Пока сценарий правит внешний агент, передайте `readOnly`: доска только для просмотра. Нельзя двигать,
соединять и удалять узлы, править панели (поля и кнопки выключены), сохранять, загружать JSON и переводить чаты. Можно
открывать узлы, «Проверить граф», «Прогон», смотреть и копировать JSON; тестовый чат (`FlowTestChat`) работает как
обычно. В шапке плашка «Только просмотр» (`labels.header.readOnly`, ru и en). Снимите `readOnly` — редактор снова обычный.

**`onSave` может отказать без исключения.** Ответ `onSave`: ничего или `{ ok: true }` — сохранено; `{ ok: false, issues?:
[{ path, message }] }` — отказ. Шапка вместо «Сохранено» пишет «Не сохранено» (`labels.header.saveFailed`), а `issues` встают у
нод, выходов, полей и попутных задач и видны в «Проверить граф». `path` тот же, что у `checks`: `states[2]`,
`states[intro].exits[0]`, `anyState.exits[0]`, `clientCard[1]`, `sideTasks[0]`. Исключение из `onSave` — такой же отказ без
списка: в консоль необработанная ошибка не уходит. Любая правка снимает отказ, повторное сохранение идёт как обычно.

```tsx
<FlowEditor
  skin={tandemFlowEditorSkin}
  value={flow}
  onChange={setFlow}
  readOnly={agentIsEditing}
  onSave={async (flow) => {
    const result = await api.saveFlow(flow);
    return result.ok ? { ok: true } : { ok: false, issues: result.errors }; // [{ path, message }]
  }}
  catalog={catalog}
/>
```

**Место доски.** Встраиваете редактор во вкладку своей страницы, и графу тесно — освободите место (все свойства
необязательные, подробности и таблица — в `CHANGES.md`, 0.54.0):

```tsx
<FlowEditor
  skin={tandemFlowEditorSkin}
  value={flow}
  onChange={setFlow}
  catalog={catalog}
  header="compact"          // одна узкая строка кнопок, без логотипа и названия
  legend="collapsed"        // по умолчанию: «Легенда» — кнопка; "open" / "hidden"
  minimap="open"            // "collapsed" / "hidden"
  inspector="collapsible"   // панель «Сценарий» свёрнута, пока ничего не выбрано; "open" по умолчанию
  fullscreen                // кнопка «На весь экран» в шапке (есть по умолчанию), Esc выходит
  storageKey="my-app:flow-board" // где помнить свёрнутое; по умолчанию общий ключ, null — не помнить
/>
```

Свёрнутое запоминается в `localStorage` и работает без него (сервер, закрытое хранилище). В полном экране редактор
стоит поверх страницы (`position: fixed`), страница не прокручивается, Tab ходит по кругу внутри, Esc выходит; свои
`className` и `style` в нём не действуют. Не оборачивайте редактор в элемент с `transform`.

**Высота.** `className` и `style` у `FlowEditor` идут на корень. Корень занимает высоту родителя (`height: 100%`), но
не меньше разумной: 60% высоты экрана, не меньше 420 px, на телефоне — экрана целиком, не меньше 640 px. Родителю не нужна
ни своя высота, ни обёртка. Нужна другая высота — `style={{ height: 720, minHeight: 0 }}` или `className="min-h-0 h-[720px]"`.

При сохранении проверяйте сценарий на сервере той же функцией, что в редакторе:

```ts
import { parseFlow, checkFlow } from "@ykurilov/agent-chat-flows/format";

const parsed = parseFlow(body); // объект или строка JSON
if (!parsed.ok) return error(parsed.errors); // [{ path: "states[0].exits[1].when.amount", message: "…" }]
const errors = checkFlow(parsed.flow, catalog).filter((issue) => issue.level === "error");
```

Надписи — русские и английские (`FlowLabelsProvider`, `russianFlowLabels`, `englishFlowLabels`).

## Формат сценария

Свой JSON. Связи — только по `id`, поэтому переименование состояния ничего не рвёт. Значения по умолчанию можно не
писать. Раскладка доски (`layout`) лежит отдельно от поведения: движок её не читает. JSON Schema для внешних редакторов
и агентов: `@ykurilov/agent-chat-flows/agent-flow.schema.json`.

```json
{
  "format": "agent-flow",
  "version": 2,
  "id": "sales-review",
  "name": "Разбор продаж",
  "start": "intro",
  "common": "Ты — помощник Анны. Разбор бесплатный, 30 минут. Цены платных программ не называй.",
  "clientCard": [{ "id": "course_topic", "name": "Тема курса", "about": "О чём курс, одной фразой." }],
  "chatNotes": [{ "id": "main_block", "name": "Главный затык", "about": "Что мешает продажам." }],
  "anyState": {
    "except": [],
    "exits": [{ "id": "any_silence", "when": { "type": "timer", "from": "silence", "amount": 3, "unit": "h" }, "to": "remind" }]
  },
  "states": [
    {
      "id": "intro",
      "title": "Знакомство",
      "instructions": "Понять тему курса и продажи.\nПо одному вопросу, на «вы».",
      "learn": ["course_topic"],
      "exits": [{ "id": "intro_clear", "when": { "type": "judge", "text": "Понятны тема курса и продажи" }, "to": "block" }]
    }
  ]
}
```

- У состояния: `title`, `instructions` (первая строка — цель, её видно на доске), `firstMessage` (точный текст при
  входе, уходит без модели), `learn` (что узнать здесь), `tools`, `tags`, `noSideQuestions`, `exits`.
- Состояние без `exits` — **конечное**: общие переходы и таймеры в нём не действуют, а агент отвечает по его инструкции.
- Цель `"@return"` — «назад»: в последнее основное состояние. Состояния, из которых есть «назад» (напоминания,
  касания), при возврате пропускаются.
- `anyState` — общие переходы: действуют из любого состояния, кроме конечных и перечисленных в `except`.
- С 0.49 формат — версия 2: добавились `schedule` («Дни и время»), `nudges` у состояния, таймер `state_days`, тип поля
  `boolean`, `sideTasks`, `afterEnd`. Сценарий версии 1 читается и молча переводится во вторую. Версия 0.48 JSON
  версии 2 не откроет.
- С 0.55 к версии 2 добавился таймер `program_day` («наступил день N программы»). Номер версии тот же: старые сценарии
  читаются как раньше. Сценарий с этим таймером SDK до 0.55 не откроет: `parseFlow` вернёт ошибку «Неизвестное значение
  поля «from»», а `loadFlow` такой версии упадёт так же, как на любом негодном JSON.

Полные примеры — в [packages/flows/tests/fixtures](../packages/flows/tests/fixtures): разбор продаж, поддержка
магазина, урок по таблицам. Программа на три дня со всеми новыми частями —
[packages/flows/demo/three-day-program.json](../packages/flows/demo/three-day-program.json).

## Общее для всех состояний

Поле `common`: кто агент, тон, цены, условия, ссылки, ответы на частые вопросы. Агент видит его всегда. Отдельного
состояния «ответ про цену» не нужно: спросили посреди разговора — агент ответит отсюда и вернётся к теме состояния.

## Условия выхода: четыре вида

| Вид | Пример | Кто проверяет |
|---|---|---|
| Словами `judge` | «Понятны тема курса и продажи» | судья |
| По данным `data` | поле `sales` заполнено; «Тип вопроса» = «возврат»; сумма больше 1000 | код, сразу как агент записал |
| Событие `event` | пришло сообщение (`message`), нажата кнопка (`button`), инструмент выполнился (`tool`), сигнал приложения (`app`) | код |
| Таймер `timer` | время в состоянии, тишина человека, прошло N с начала, наступило время суток, нода длится N дней, наступил день N программы | код по часам сервера |

Сработало несколько сразу — побеждает первое по порядку, свои условия раньше общих.

## Судья

Условие словами проверяет отдельная дешёвая модель — судья. По умолчанию это `microsoft/microsoft-decision-1` через
OpenRouter: модель выбора из вариантов, отвечает вероятностью. Порог «выполнено» — 0,7 (`judge.threshold`).

Когда он зовётся:

- **Агент заявил выход** служебным инструментом `flow_exit`. Судья подтвердил — агент в том же ответе ведёт себя по
  новому состоянию. Не подтвердил — агент остаётся и слышит «продолжай разговор»; тот же выход можно заявить снова после
  следующего сообщения человека.
- **После каждого ответа агента**, где перехода не было: судья смотрит все условия словами одним запросом. Человек его
  не ждёт: переход применится в начале следующего хода.

Судья видит только цель состояния, условия и последние 6 реплик. Весь чат и карточку не видит.

Перед каждым обращением к судье проверяется лимит расходов. Лимит исчерпан — запроса нет, условие «не проверено», агент
остаётся в состоянии.

**Запасная модель** (`judge.fallback`, обязательна) — модель из каталога приложения. Она нужна, пока decision-1 в
предварительной версии: основной не ответил за 5 секунд или упал — спрашивается запасная. Не ответили обе — перехода
нет. Расход судьи пишется в журнал с назначением `judge` и входит в лимиты.

## Агент пишет первым

Таймер сработал — агент пишет сам: точным текстом состояния или ходом модели. В веб-чате ответ виден в открытой
вкладке, в привязанном мессенджере приходит сообщением.

Чтобы агент не писал ночью и не заваливал человека, есть правила. Общие — в настройке приложения. У сценария с «Днями и
временем» его ночь и дневной потолок главнее (см. ниже).

```ts
createAgentFlow({
  …,
  firstMessages: {
    quietHours: { from: "21:00", to: "09:00" }, // по умолчанию; срок в тихие часы переносится на 09:00
    maxPerDay: 3, // по умолчанию
    canWriteNow: async ({ ownerId }) => !(await isUnsubscribed(ownerId)),
  },
  // firstMessages: false — писать первым без тихих часов и дневного потолка
});
```

`canWriteNow` отвечает «можно ли сейчас»:

| Ответ | Что будет |
|---|---|
| `true` | писать |
| `false` | не сейчас: касание повторится через час. Так работает аварийная остановка: сняли её — касания пошли дальше |
| `"never"` | молчать до сообщения человека: касаний и повторов нет (спросят снова только в срок перехода ноды). Человек написал — касания снова идут. Так — отписавшийся человек |
| `{ retryAt: Date }` | повторить в этот момент. Негодная дата — как `false`; дата в прошлом — повтор через минуту, а не каждый обход |

Переходы нод по сроку и конец разговора («срок вышел», «не завершил») от ответа не зависят и наступают в свой срок. До
0.53 `false` снимал все сроки чата, и конец разговора не наступал. С `false` у сценария без `lengthDays` и
`giveUpAfter` приложение будут спрашивать раз в час без конца — для «больше не писать» отвечайте `"never"`.

Прощание (`farewellOnDeadline`) спрашивает те же правила один раз: нельзя писать в момент срока (тихие часы, `false`,
`"never"`) — прощания нет, разговор всё равно кончается.

Тихие часы и потолок касаются только сообщений первым. Человек написал сам в 23:00 — агент отвечает.

**Почему агент пишет первым — в хвосте приложения.** В ходе касания `agent.stepContext` получает `firstReasons`: все
причины этого хода списком. Ход на сообщение человека их не получает. Хвост стоит в конце запроса, постоянная
инструкция от причины не меняется — кэш цел.

```ts
import type { FlowStepContextInput } from "@ykurilov/agent-chat-flows";

stepContext: (input) => {
  const { firstReasons } = input as FlowStepContextInput;
  // [{ kind: "silence", step: 2 }], [{ kind: "morning" }, { kind: "transition", stateId: "offer" }], [{ kind: "farewell" }] …
  return firstReasons?.some((reason) => reason.kind === "morning") ? "Утро: можно напомнить о курсе." : null;
},
```

Время — по поясу человека. Пояс приходит со страницы. Пока он неизвестен (до первого хода, мессенджер без страницы),
берётся `createAgentFlow({ defaultTimeZone: "Europe/Moscow" })`, без него — `agent.timeZone`, без него — пояс сервера и
предупреждение в журнал. Порядок: человек → страница → `defaultTimeZone` → пояс службы → сервер. Не пояс IANA в
`defaultTimeZone` — `TypeError` при создании.

Дата в запросе к модели («Сегодня: …») считается ядром: пояс страницы, иначе `agent.timeZone`. Нет своего
`agent.timeZone` (и пояса лимитов) — `flow.withChat` подставляет туда `defaultTimeZone`, и «сегодня» в запросе совпадает
с днём сценария. Задан свой `agent.timeZone` — дата в запросе по нему, а дни сценария по `defaultTimeZone`: держите их
одинаковыми.

**Срочный сигнал.** Событие приложения с `wakeAgent: true` будит агента сразу, мимо тихих часов и счётчика. Пример:
платёжная система прислала «оплачено» в 23:00, человек сейчас на странице.

```ts
await flow.signal({ ownerId, chatId, name: "paid", data: { amount: 4900 }, wakeAgent: true });
// без wakeAgent переход применится в начале следующего хода
```

## Таймеры

| Таймер | Что считает |
|---|---|
| `in_state` | время в состоянии. При возврате «назад» отсчёт продолжается с места ухода: пока агент был в напоминании, часы стояли |
| `silence` | тишину человека с последнего ответа агента. Человек написал — отсчёт заново |
| `since_start` | время с начала сценария |
| `time_of_day` | время суток по поясу человека, например `"10:00"` |
| `state_days` | нода длится N дней сценария: срок — начало дня «день входа + N» (`schedule.dayStart`). Только с «Днями и временем» |
| `program_day` | наступил день N программы (`{ "type": "timer", "from": "program_day", "day": 3 }`): срок — начало дня N, как его считает `readRun().day`. Только с «Днями и временем» |

**«Нода длится N дней» или «наступил день N».** Быстрый человек прошёл «Знакомство» в первый день и сразу попал в
«Доработку». У «Доработки» «длится 1 день» — «Продажа» начнётся во второй день. У «Доработки» «с дня 3» — в начале
третьего дня, когда бы человек в неё ни пришёл. Нужна привязка к программе, а не к ноде — берите `program_day`.

- Дни считаются так же, как номер дня в `readRun` и хвосте запроса: поздний старт, ночь — к ближайшему утру, смена
  пояса в первый день, `dayStart`, пояс человека или `defaultTimeZone`.
- До первого утра идёт день 0: «с дня 1» при ночном или позднем старте наступает утром.
- Человек вошёл в ноду уже в день N или позже — выход срабатывает сразу, в том же ходе, как цепочка переходов по
  данным. Человек получает один ответ, уже из новой ноды.
- Так же при входе срабатывает `since_start`, если его срок уже прошёл: оба срока не зависят от момента входа.
  Тишина, `in_state`, `state_days`, `time_of_day` при входе не проверяются — их отсчёт идёт от входа или по часам.
  Предел переходов подряд общий с переходами по данным. Наступили несколько — выигрывает самый ранний срок, при
  равенстве — порядок выходов в ноде.
- В начале дня один ход на всё: переход по этому таймеру, утреннее, ответ на ночные сообщения. Причина хода —
  `{ kind: "transition", stateId }`. Правило «человек писал меньше 3 ч назад» переход не задерживает.
- Писать первым нельзя совсем (`canWriteNow` → `"never"`, потолок ходов сервера подряд) — переход наступает в свой срок
  без хода: запись чата, `onTransition` с номером дня, `readRun` с новой нодой и путём, следующие таймеры — уже от новой
  ноды. Сообщения агента нет; ход человека переносит переход в состояние чата и не сообщает о нём второй раз.
- Сообщение лишь отложено (ночь, потолок в день, лимит денег, повтор хода) — переход придёт вместе с ним, одним ходом.
- Тестовый чат: «К началу следующего дня» срабатывает так же.
- `checkFlow`: день не целый или меньше 1 — ошибка; день больше `lengthDays` — ошибка; сценарий без «Дней и времени» —
  предупреждение (таймер не пойдёт).
- На доске: «Длится» → «до дня программы» и номер дня; подпись условия — «с дня N». Модель и журнал видят «наступил
  день N».

- Таймеры лежат в базе и переживают перезапуск. Сервер был выключен в момент срабатывания — сработает один раз сразу
  после старта, пропущенные не догоняются пачкой.
- Несколько копий сервера — срабатывание одно: копия берёт таймер в аренду (60 секунд) и продлевает её перед ходом и во
  время него. Долгий ход не отдаёт чат другой копии, и одно касание не уходит дважды.
- Обход идёт до 5 ходов одновременно: один медленный ход не задерживает остальные чаты.
- Своё хранилище (свой `FlowStore`) должно реализовать `renewLease()` (продлить аренду; `false` — чат взяла другая
  копия) и `setDue(chatId, due, { unlessDelivery })` (не затирать срок повтора доставки).
- Из двух таймеров срабатывает наступивший раньше, при равенстве — таймер самого состояния.
- Сервер смотрит таймеры раз в 15 секунд (`timers.tickMs`).
- Защита от зацикливания: не больше 5 переходов подряд без ответа агента или человека.
- Касания идут по расписанию сценария, поэтому общий потолок ядра «5 ходов сервера подряд без человека» их не режет:
  молчащий человек получает все положенные касания.
- Свой мягкий потолок у сценария (с 0.53): 50 ходов сервера подряд без сообщения человека (`timers.maxServerTurnsInRow`,
  `false` — без потолка). Это страховка от петли переходов по коротким таймерам (A → B → A каждую минуту), особенно при
  `firstMessages: false`. Дошли — строка в журнал, касания и переходы по таймерам ждут сообщения человека; «срок вышел» и
  «не завершил» наступают в свой срок.
- Срок наступил, а писать не о чем (упёрлись в предел переходов подряд) — срок переносится на ближайшее настоящее:
  касание, переход ноды, конец разговора. Ничего впереди нет — срок снимается до сообщения человека.
- Конец разговора не зависит от того, начался ли ход касания. Ход не начался (ворота приложения `{ hold: true }`,
  лимит расходов, `canWriteNow` → «не сейчас») — касание переносится, а «срок вышел», «не завершил» и переход ноды по
  сроку наступают в своё время.

## Дни и время

Блок `schedule` превращает разговор в программу по дням: «за 3 дня соберём первый результат».

```json
"schedule": {
  "dayStart": "09:00",
  "nightFrom": "21:00",
  "lengthDays": 3,
  "deadlineState": "wrap",
  "firstMessages": { "maxPerDay": 3 },
  "nudges": { "afterSilence": [{ "amount": 2, "unit": "h" }], "dailyAt": ["19:00"], "giveUpAfter": { "amount": 2, "unit": "d" } },
  "dayFrame": { "softFrom": 12, "hardAt": 15, "hardText": "На сегодня всё — утром обязательно отвечу!" }
}
```

- **День сценария** начинается в `dayStart` по поясу человека. Пришёл поздно, меньше чем за `lateStartHours` (3) до
  ночи — первым днём считается завтра.
- **Ночь** — с `nightFrom` до `dayStart`. Ночью агент не пишет первым: касания и утреннее ждут `dayStart`. Человек
  написал сам — агент отвечает и ночью.
- **Одно утреннее сообщение.** В начале дня все причины написать склеиваются в один ход: переход по сроку ноды, утреннее,
  ответ на сообщения, оставленные без ответа после жёсткой рамки. Касание тишины или по часам, наступившее к утреннему,
  утреннее заменяет (с 0.55). Человек получает одно сообщение, а не три. Утреннее пропускается, если человек
  писал за 3 часа до него (`skipMorningIfHumanWithinMin`).
- **Человек писал недавно — первым не писать.** Человек написал до начала дня (например, в 07:00) меньше чем за
  `skipMorningIfHumanWithinMin` (3 часа) — касания в начале дня ждут, пока эти 3 часа пройдут: утреннее, касание
  тишины, перенесённое ночью на утро, касание по часам (`dailyAt`). Переход ноды по сроку и ответ на сообщения, оставленные
  без ответа ночью, не ждут: это не «напомнить о себе», а дело программы или ответ человеку. Касания, склеенные с ними в
  один ход, уходят вместе с ними.
- **Срок.** Через `lengthDays` дней в `dayStart` — «срок вышел»: переход в `deadlineState` без хода модели и конец
  разговора `deadline`. Прощание — `farewellOnDeadline` (модель пишет) или `farewellText` (готовый текст).
- **День в хвосте запроса.** Агент видит «День 2 из 3. Сейчас …» и «сегодня последний день» в конце запроса, а не в
  постоянной инструкции: кэш не ломается от смены дня.
- `flow.readRun` отдаёт `day`: номер дня, всего дней, последний ли, начало этого и следующего дня.

### Касания

Касание — агент пишет в той же ноде, когда человек молчит. Правило общее (`schedule.nudges`) или своё у ноды
(`nudges` у состояния; `"off"` — без касаний).

Касания нужны и без «Дней и времени» — с 0.50 их можно задать на весь сценарий, `nudges` в корне:

```json
{ "format": "agent-flow", "version": 2, …, "nudges": { "afterSilence": [{ "amount": 15, "unit": "min" }], "giveUpAfter": { "amount": 3, "unit": "d" } } }
```

Порядок: своё у ноды → `"off"` → `schedule.nudges` → `nudges` сценария. Заданы оба общих — действуют касания «Дней и
времени», проверка предупреждает (`nudges_shadowed`). Ночь и потолок без «Дней и времени» — из `firstMessages`
приложения.

- `afterSilence` — ряд сроков тишины от последнего ответа агента: 15 минут, час, 4 часа. Человек написал — ряд сначала.
  Утреннее сообщение — тоже новая точка отсчёта (с 0.55): после него ряд идёт с первого шага. Человек молчит много
  дней — каждый день утреннее и ряд заново, пока не кончится дневной потолок. Утреннее выключено
  (`firstMessages.morning: false`) — ряд один раз за молчание, как раньше.
- `dailyAt` — после ряда пишет в эти часы каждый день.
- `giveUpAfter` — столько тишины, и разговор кончается «не завершил» (`abandoned`) без сообщения. После паузы
  сотрудника тишина считается от конца паузы, а не от последнего ответа агента.
- `days` — только у своих касаний ноды (с 0.55): свой ряд действует столько дней сценария, считая день входа (1 —
  только день входа). Потом — касания сценария (`schedule.nudges`, затем `nudges` в корне), их ряд с начала, тишина
  не раньше начала дня; своего `giveUpAfter` нет — общий. Нет `days` — свой ряд всё время в ноде. Без «Дней и
  времени» дни календарные, по поясу человека.

Пример: у «Знакомства» `{ "afterSilence": [15 мин, 1 ч, 4 ч], "days": 1 }`, общий ряд — 3 ч · 3 ч · 3 ч, потолок 3 в
день. Человек вошёл в 10:00 и молчит: 10:15, 11:15, 15:15. Второй день: утреннее в 09:00, касания в 12:00 и 15:00,
дальше потолок. Третий, четвёртый день — так же: 09:00, 12:00, 15:00. Шаг ряда, попавший на ночь или за потолок,
не уходит: утреннее его заменяет, модель видит только «доброе утро», а ряд после него — с начала. Человек ответил на второй день — ряд с начала, и
он общий. «Не завершил» (`giveUpAfter`) считается от последних слов человека: ежедневный ряд его не отодвигает.

Касания подчиняются ночи и дневному потолку, как всё, что агент пишет первым.

### Рамки дня

Человек разговорился и пишет без остановки — день мягко сворачивается. Считаются его сообщения за день сценария.

- С `softFrom`-го сообщения в хвосте запроса строка «пора сворачиваться»: агент отвечает коротко и предлагает
  продолжить завтра.
- На `hardAt`-м — готовая фраза `hardText` без модели, один раз за день. Дальше до начала следующего дня агент молчит,
  сообщения записываются (`admit` → `hold`). Утром в `dayStart` он отвечает на них одним ходом — при любых настройках
  касаний и не дожидаясь 3 часов. Время последнего такого сообщения лежит в данных чата (`Chat.data`, ключ
  `flowHeldHuman`): для сроков оно — сообщение человека. Утреннее и касания ждут 3 часа, «не завершил» и переход
  «человек молчит» считают молчание от него.
- Пачка сообщений (`sendBurstMessage`) считается по сообщениям: три подряд — три в счёт дня. Пачка дошла до `hardAt` —
  готовая фраза один раз на всю пачку. Пачка начинается уже за рамкой — отложена до утра, как одиночное сообщение.
- Человек сам сказал «на сегодня всё» — агент зовёт `flow_close_day`: сегодня он первым больше не пишет. В последний
  день инструмент день не закрывает, а агент прощается с итогом.

## Пауза: отвечает сотрудник

Живой сотрудник взял разговор — агент молчит, таймеры и касания стоят.

```ts
await flow.pause({ ownerId, chatId }); // до until или на staffSilenceHours (2 ч) от сейчас
await flow.noteStaffReply({ ownerId, chatId, text: "Добавил вас в группу", staffName: "Ольга" }); // продлевает паузу
await flow.resume({ ownerId, chatId });
```

Пауза снимается сама после `pause.staffSilenceHours` молчания сотрудника. Агент видит, что сотрудник написал, и
продолжает, не противореча ему.

С 0.53 реплика ложится в историю тем же путём, что `service.appendStaffMessage` ядра: сообщением сотрудника, а не
человека. Модель видит «Живой сотрудник «Ольга» ответил человеку вместо тебя: «…»», экран — сообщение сотрудника
(`StaffMessage` скина). Словами человека она не считается: агент не откроет ссылку сотрудника как ссылку человека
(`person_link_view`). А проверки ответа агента её текст знают: повторит агент ссылку или телефон сотрудника — проверка
не вырежет. Без сценария — сразу
`service.appendStaffMessage({ ownerId, chatId, text, staffName })`.

## После конца разговора

Разговор кончается: конечная нода (`final`), срок вышел (`deadline`), человек пропал (`abandoned`), заблокировал канал
(`blocked`), приложение закончило его само (`flow.end`). Тогда один раз зовётся `onFinish({ reason, day, state, tags, run, … })`.

```ts
// Человек пришёл по ссылке другого продукта: старый разговор закончен.
await flow.end({ ownerId, chatId, reason: "switched", outcome: "перешёл на «Курс масла»" });
// → { ended: true }; уже законченный или чат не по сценарию — { ended: false }
```

Причина — любая строка: придёт в `onFinish.reason`, `admit` (`ended`) и `readRun().endReason`. `outcome` — в
`onFinish.outcome`. Место остаётся в своей ноде, сроки и повтор доставки снимаются.

Человек написал после конца — решает `afterEnd` сценария:

- `"reply"` (по умолчанию) — агент отвечает по «Общему» и инструкции «Программа закончилась»: не ведёт по шагам, новых
  сроков нет.
- `"silent"` — агент молчит. Свой канал получает от `admit` решение `ended` и может передать сообщение сотруднику.

Сценарий с `afterEnd` или «Днями и временем» закрывает разговор при входе в конечную ноду. Без них, как в 0.48,
конечная нода только сообщает `onFinish`.

**Конец как точка передачи.** В `onFinish` есть всё, чтобы передать человека дальше: нода и её метки (итог), путь и
заметки чата (`run`), а карточка — `flow.readClientCard(ownerId)`. Сейчас передачу делает приложение. Передачу в
следующий сценарий SDK возьмёт на себя позже.

## Попутные задачи

Дела между делом: «предложить подписаться на канал», «спросить, откуда узнал».

```json
"sideTasks": [
  { "id": "subscribe", "text": "Предложить подписаться на канал @first_result", "when": "когда человек доволен результатом", "field": "subscribed" }
]
```

- Агент берётся за задачу в общем темпе вопросов о человеке: не чаще раза в 5 сообщений.
- `field` — поле карточки или заметки: задача решена, когда оно известно. Без поля агент отмечает её сам
  (`flow_side_task`).
- Попыток не больше `maxAttempts` (2). Считаются на человека или, с `perConversation`, заново в каждом разговоре.
- **Встроенная «узнать город».** У сценария с «Днями и временем», пока пояс человека неизвестен, агент в первый день
  до ночи узнаёт город и записывает пояс (`flow_time_zone`). Эта задача первая по важности и идёт вне общего темпа.
  Пояс хранится в `flow_people` или у приложения (`people: { readTimeZone, writeTimeZone }`).

## Ссылка человека

Человек прислал ссылку на свою страницу — агент может её посмотреть. Инструмент из `@ykurilov/agent-chat-web-tools`:

```ts
import { createPersonLinkTool } from "@ykurilov/agent-chat-web-tools";

const personLink = createPersonLinkTool({ storage, screenshots, reader, appDomains: ["apps.example.com"] });
// agent.tools: (model) => ({ ...myTools, ...personLink(model) })
```

- Открывает только адреса, которые человек сам написал. Голое имя («sveta-nails») — на доменах `appDomains`. Адрес
  из почты человека («olga@studio.ru») ссылкой не считается.
- Не больше трёх просмотров за разговор (`maxPerChat`). Отказы в счёт не идут, а страница, которая не открылась, — идёт:
  попытка сделана, служба вызвана.
- Страница не открылась — инструмент отвечает: «Страница не открылась. Скажи человеку об этом один раз и не проси ссылку
  снова: двигайся дальше без неё». Подробностей сбоя («таймаут», адрес сервера) модель не видит. То же сказано в правилах
  сценария. Это указание модели, а не запрет в коде: если она всё же вызовет инструмент ещё раз, вызов пройдёт и
  посчитается просмотром, пока не вышел лимит.
- Расход каждого просмотра пишется в журнал расходов чата как `web_tools` (`pricePerViewUsd`), и когда страница не
  открылась тоже: службе платим за вызов. Отказ по правилам (чужой адрес, лимит) расходом не пишется.
- Страница приходит как данные, а не команды: просьбы на ней агент не выполняет.
- В сценарии включается как обычный инструмент: `person_link_view` в `tools` ноды. Тогда в инструкции появляются
  правила просмотра.

## Версии и перевод чатов

Граф хранит приложение. Чат закрепляется за версией, с которой начался. SDK держит копию этой версии: приложение её
потеряло — чат не сломается. Под тем же `versionId` другой граф — чат идёт по сохранённому, строка в журнал.

Вышла новая версия — идущие чаты можно перевести:

```ts
await flow.chatsByState("sales-review", { exceptVersionId: "4" }); // [{ versionId, stateId, chats }]
await flow.migrateChats({ flowId: "sales-review", toVersionId: "4", map: { old_block: "block" }, flow: version4 });
```

- `map` — куда отправить чаты из состояний, которых в новой версии нет.
- Путь, заметки и место в разговоре сохраняются. Ни один разговор не начинается заново.
- Чат применяет перевод в начале своего следующего хода. Один промах кэша на чат — у новой версии другое «Общее».

**Каких чатов перевод не касается.** По умолчанию закончившиеся разговоры (`flow.end`, итог, срок вышел) и тестовые
чаты редактора (`FlowTestChat`, `flowTestChatData()`) не считаются и не переводятся. Вернуть их — `includeEnded: true`
и `includeTestChats: true`. Свой отбор приложения — `chatIds` (только эти чаты) и `filter` (решение по каждому чату):

```ts
const selection = {
  // chat: { chatId, ownerId, flowId, versionId, stateId, ended, endReason, test, data } — data это Chat.data
  filter: (chat) => chat.data.leadMagnetCheck !== true,
};
await flow.chatsByState("sales-review", { exceptVersionId: "4", ...selection });
await flow.migrateChats({ flowId: "sales-review", toVersionId: "4", map, flow: version4, ...selection });
```

Отбор в обоих вызовах работает одинаково: передайте один и тот же — и переведутся ровно те чаты, что посчитаны. Цель в
`map` нужна только для удалённых состояний, где есть отобранные чаты. `filter` может быть асинхронным: зовётся по разу
на чат, пачками по 100.

В редакторе это кнопка «Перевести идущие чаты» (`migration` у `FlowEditor`: `chatsByState` и `migrate` через ваш API).
Счётчик окна — это ответ `chatsByState`; после перевода окно перечитывает его и показывает, кто остался.

## Карточка клиента и заметки чата

**Карточка клиента** (`clientCard`) — что агент помнит о человеке между чатами. Одна на человека и общая для всех
сценариев приложения: Ольга записалась на разбор, потом купила курс — сценарий продажи тоже знает её имя.

- Порядок полей — что узнать раньше. Типы: текст, число, выбор из вариантов, «да/нет» (`boolean`, хранится
  `true`/`false`; условия «заполнено», «равно», «не равно»).
- `refreshAfterMonths` — «может устареть»: через столько месяцев агент мягко сверит («Всё ещё в основном Инстаграм?»).
- `learn` в состоянии — спросить здесь прямо. Остальное агент узнаёт между делом, не чаще раза в 5 сообщений
  (`pace.sideQuestionEveryMessages`). В состоянии с `noSideQuestions` не спрашивает.
- Агент записывает поле инструментом `flow_note`; значение проверяется по типу.
- Человек спрашивает «что ты обо мне знаешь?» или «забудь, где я работаю» — агент показывает или стирает поле
  инструментом `client_card`. Работает везде, и в мессенджерах тоже.
- Сотрудник в песочнице (копия чата человека) карточку только читает: записать или стереть поле он не может.
- Экран «Что агент знает о вас» — по желанию, рядом с экраном памяти:

```tsx
import { ClientCardPanel } from "@ykurilov/agent-chat-flows/react";
import { tandemClientCardSkin } from "@ykurilov/agent-chat-skin-tandem/client-card";

<ClientCardPanel skin={tandemClientCardSkin} fields={flow.clientCard} read={() => api.readCard()} forget={(id) => api.forgetCard(id)} />;
// на сервере: flow.readClientCard(ownerId), flow.forgetClientCard(ownerId, fieldId | "all")
```

**Карточка в базе приложения.** У приложения своя карточка клиента (CRM, своя таблица) — передайте её:

```ts
createAgentFlow({
  …,
  clientCard: {
    read: (ownerId) => crm.fields(ownerId), // [{ fieldId, value, updatedAt, chatId, flowId }]
    write: ({ ownerId, fieldId, value }) => crm.setField(ownerId, fieldId, value), // ошибка — агент услышит «не записано»
    forget: (ownerId, fieldId) => crm.clear(ownerId, fieldId),
  },
});
```

Нет `clientCard` — карточка в таблице модуля `flow_client_cards`, как в 0.48. Поля, которые у приложения есть, редактор
предлагает из `catalog.fields`.

**Заметки чата** (`chatNotes`) нужны только в этом разговоре: «главный затык», «номер заказа». Они живут в ветке чата:
человек отредактировал старое сообщение — заметки откатываются вместе с состоянием.

### Свободные факты о человеке

Поля карточки заранее известны, а людей всегда узнаёшь больше: «ведёт блог», «живёт в Тбилиси». Включите факты — агент
запишет такое тем же инструментом, без отдельной памяти:

```ts
createAgentFlow({ …, clientFacts: true });
```

- Запись: `flow_note { fact: "Ведёт блог про акварель" }`. Одна короткая фраза (до 200 знаков), не больше 30 фактов на
  человека. Тот же факт другими буквами регистра и пробелов — та же запись, а не две. У факта есть `id` (`f` и восемь
  цифр), по нему и стирают.
- Агент видит их в блоке `flow:client` отдельным списком «Факты о человеке», по порядку записи: старое выше. Начало блока
  не меняется, пока не записали новое, так что кэш запроса цел.
- «Что ты обо мне знаешь» — `client_card { action: "show" }` показывает и поля, и факты. «Забудь, что я веду блог» —
  `forget` по id или словами. «Забудь всё» стирает факты тоже, даже если `clientFacts` потом выключили: записанное
  нельзя оставить без «забудь».
- Сотрудник в песочнице факты только читает.
- Без `clientFacts` всё как в 0.49: в `flow_note` нет `fact`, в инструкции нет правила, в блоке нет списка.

**Где лежат факты.** По умолчанию — в таблице модуля `flow_client_cards`, записями с `fieldId` вида `fact:<id>`
(миграций не нужно). Не называйте так свои поля. Если приложению нельзя мешать факты с полями (на полях строятся
фильтры и рассылки), дайте им отдельное хранилище, договор `clientCard` расширяется без ломки:

```ts
clientCard: {
  read, write, forget, // как раньше
  facts: {
    read: (ownerId) => db.facts(ownerId), // [{ id, text, updatedAt, chatId, flowId }]
    add: ({ ownerId, fact: { id, text }, chatId, flowId, at }) => db.addFact(ownerId, id, text, chatId, flowId, at), // тот же id — тот же факт
    forget: (ownerId, factId) => db.forgetFact(ownerId, factId), // factId — id факта или "all"
  },
},
```

Свои id фактов считайте `factId(text)` из пакета (с 0.53): тот же текст с точностью до регистра и пробелов — тот же id.

«Забудь всё» зовёт `forget(ownerId, "all")` и у полей, и у фактов. `flow.readClientCard(ownerId)` отдаёт факты записями
`{ fieldId: "fact:<id>", value: <текст> }`: так человека передают дальше, и так их рисует экран «Что агент знает о вас»
(название строки — `factName` хука или `labels.clientCard.fact`, по умолчанию «Факт»). `flow.forgetClientCard(ownerId, "fact:<id>")` стирает один.

### Карточка и долгая память SDK

Если подключены и карточка, и память (`@ykurilov/agent-chat-memory`), у модели два места «запомнить» и она путается.
Делим по смыслу, правило входит в инструкцию сценария при `clientFacts: true`:

| Что | Куда |
|---|---|
| Поля сценария («Имя», «Чем занимается») | карточка, `flow_note { field, value }` |
| Любой другой факт о человеке («ведёт блог») | карточка, `flow_note { fact }` |
| Как с человеком общаться («отвечай на ты», «без эмодзи») | память, `manage_memory` |

«Забудь обо мне» модель стирает в обоих местах: `client_card` и `manage_memory`. Но экран приложения «забудь обо мне»
должен звать оба: `flow.forgetClientCard(ownerId, "all")` и стирание записей памяти.

Приложению, которому правила общения не нужны, память подключать не надо: тогда карточка — единственное место, где
агент помнит человека, и дублей нет. Отдельной настройки «факты вместо памяти» нет: SDK не может убрать у модели чужой
инструмент `manage_memory`, а правило в инструкции делит работу надёжнее, чем запрет.

## Метки и onTransition

Метки (`tags`) — подписи состояния: «продажа», «успех», «касание», «человек». SDK их не толкует. Они приходят в
`onTransition` и лежат в истории переходов (`flow.readRun(ownerId, chatId).path`).

```ts
onTransition: async ({ ownerId, chatId, from, to, exitId, decidedBy, tags }) => {
  if (tags.includes("успех")) await analytics.track("booked", { chatId });
  if (tags.includes("касание") && !(await isOnline(ownerId))) await sendPush(ownerId);
},
```

`decidedBy` — кто решил: агент с судьёй (`claim`), судья после хода (`judge`), код по данным (`data`), событие
(`event`) или таймер (`timer`).

## Редактор и тестовый чат

- **Доска.** Состояния — карточки, стрелки — переходы четырёх видов. Тянете стрелку из условия в состояние — переход.
  Отпускаете на пустом месте — новое состояние.
- **Проверить граф.** Нет старта, недостижимое состояние, условие без цели, имя инструмента или события, которого
  приложение не объявило. Клик по ошибке ведёт к месту.
- **Прогон.** Автор выбирает «что произошло» и видит путь по доске, что агент знает о человеке и какой вопрос задал бы
  следующим. Модель не вызывается.
- **JSON.** Показать, скопировать, скачать, загрузить с проверкой.
- **Тестовый чат.** Автор пишет агенту прямо в редакторе, на доске подсвечено текущее состояние. Кнопки «Промотать»
  проверяют напоминания без ожидания. «К началу следующего дня» проматывает до утра сценария с «Днями и временем»
  (`advanceToNextDay` у подключения, на сервере `flow.advanceTestClock({ ownerId, chatId, to: "next_day_start" })`).
- **Свои проверки приложения.** `checks` у `FlowEditor` и `FlowTestChat` — функция `(flow) => [{ path, message }]`.
  Те же проверки на сервере: `checkFlow(flow, catalog, { checks })`. Тип `FlowAppChecks` — из
  `@ykurilov/agent-chat-flows/format`.

```tsx
import { FlowTestChat, type FlowTestChatConnection } from "@ykurilov/agent-chat-flows/react";

const testChat: FlowTestChatConnection = {
  start: (flow) => api.post("/flow-test/start", { flow }), // сервер: service.createChat(userId, { data: flowTestChatData() })
  advance: (chatId, ms) => api.post("/flow-test/advance", { chatId, ms }), // сервер: flow.advanceTestClock({ ownerId, chatId, ms })
  readRun: (chatId) => api.post("/flow-test/run", { chatId }), // сервер: flow.readRun(ownerId, chatId) — место для доски
  renderChat: (chatId) => <AgentChat api="/api/chat" chatId={chatId} skin={tandemSkin} />,
};

<FlowTestChat skin={tandemFlowEditorSkin} value={flow} onChange={setFlow} catalog={catalog} testChat={testChat} />;
```

Посетитель места чата не получает, поэтому доска читает его отдельно — методом `readRun`. Адреса тестового чата
(перемотка и место) приложение закрывает правами само: только редактору и только для тестовых чатов. Перемотка
работает только у тестового чата. У рабочего чата `advanceTestClock` — ошибка. Рабочий пример:
[apps/demo/flow-test-chat](../apps/demo/flow-test-chat).

## Кэш модели

Переход не ломает кэш провайдера: начало запроса от хода к ходу то же самое.

- Постоянная инструкция одна на весь чат: правила сценария и «Общее для всех состояний».
- Набор инструментов одинаков во всех состояниях. Инструмент чужого состояния не выполняется, а модель получает «в
  этом состоянии недоступно».
- Карточка текущего состояния приходит новым блоком в конце разговора — только при переходе. Переход посреди ответа —
  карточка в результате `flow_exit`.
- День, местное время, рамки дня и попутная задача — строки в хвосте запроса. Смена дня кэш не ломает.

Промах кэша бывает один раз — при переводе чата на новую версию.
