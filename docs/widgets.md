# Виджеты агента

Агент умеет спросить человека не текстом, а кнопками, звёздами или короткой формой. Ход ставится на паузу, человек нажимает,
ответ уходит модели, и она дописывает ответ в то же сообщение. Есть пять готовых виджетов и свои, которые пишет приложение.

Без настройки `agent.widgets` ничего не меняется: ни новых инструментов, ни новых строк в запросе модели.

## Включить готовые

```ts
createChatHandler({
  …,
  agent: {
    instructions: appInstructions,
    widgets: { basic: true }, // все пять; или список: basic: ["ask_choice", "suggest_replies"]
  },
});
```

| Виджет | Что делает | Ответ, который видит модель |
|---|---|---|
| `ask_choice` | один вариант из 2–8 кнопок | `{"выбрано":"Про"}` |
| `ask_multi_choice` | несколько вариантов (`min`, `max`) | `{"выбрано":["А","Б"]}` в порядке вариантов |
| `ask_rating` | звёзды 1–5 или шкала от 0/1 до 2–10 с подписями краёв | `{"оценка":4}` |
| `ask_form` | форма из 1–5 полей: текст, число, дата, выбор из списка | `{"поля":{"имя":значение}}`, пустые необязательные поля не приходят |
| `suggest_replies` | до 4 кнопок-подсказок под ответом, ход не ждёт | модель сразу получает «показано»; нажатая подсказка уходит обычным сообщением |

На экране отдельных настроек не нужно: виджеты рисует скин. Тандем уже умеет.

## Свой виджет

Виджет описывается один раз в общем файле, который читают и сервер, и страница. В нём нет серверного кода.

```ts
// widgets/pick-slot.ts
import { defineWidget } from "@ykurilov/agent-chat-core";
import { z } from "zod";

export const pickSlot = defineWidget({
  name: "pick_slot", // латиница, цифры и «_»; не начинается с ask_ и suggest_
  description: "Предложить человеку выбрать время встречи",
  inputSchema: z.object({ slots: z.array(z.string()).min(2).max(6) }),
  answerSchema: z.object({ slot: z.string() }),
  question: (input) => `Выберите время: ${input.slots.join(", ")}`, // текст для запасного вида и голоса
});
```

```ts
// сервер
agent: { widgets: { basic: true, custom: [pickSlot] } }
```

```tsx
// страница: компонент по имени виджета
import type { CustomWidgetProps } from "@ykurilov/agent-chat-react";

function PickSlotWidget({ input, state, answer, onAnswer, pending, failure }: CustomWidgetProps<{ slots: string[] }, { slot: string }>) {
  return (
    <div>
      {input.slots.map((slot) => (
        <button key={slot} disabled={!onAnswer || pending} onClick={() => onAnswer?.({ slot })}>{slot}</button>
      ))}
      {state === "answered" && <p>Выбрано: {answer?.slot}</p>}
      {failure && <p>{failure}</p>}
    </div>
  );
}

<AgentChat … widgets={{ pick_slot: PickSlotWidget }} />
```

- `chatId` и `toolCallId` — чат и вызов виджета: по ним компонент сам читает и пишет данные приложения, без своего
  React-провайдера. В `AgentChat` они есть всегда; в типе необязательные, чтобы старые свои вызовы компонента не сломались.
- `state`: `pending` (ждёт), `answered` (ответ есть), `answered_by_message` (человек ответил сообщением), `closed` («Стоп», сбой или вопрос из другой ветки).
  `onAnswer` есть только у ждущего виджета в последнем ответе ветки.
- Негодный ответ сервер не запишет: проверка идёт по `answerSchema`. Ответ больше 16 КБ тоже отклоняется.
- Нет компонента на странице — покажется запасной вид «Ответьте сообщением».
- Имена виджетов не должны совпадать с именами ваших `agent.tools` и `browserTools`: это ошибка при создании службы.
- Описание виджета постоянное: оно стоит в начале запроса и не ломает кэш модели.

## Проверка ответа на сервере (`checkAnswer`)

Схема ловит неверную форму ответа. А «это время уже заняли» знает только ваша база. Для этого у виджета есть проверка с
доступом к базе: она зовётся после схемы, пока чат удержан за этим ответом, и решает, что делать с ответом.

```ts
// только на сервере: файл виджета читает и страница, база в него не попадает
agent: {
  widgets: {
    custom: [
      {
        ...pickSlot,
        checkAnswer: async (answer, ctx) => {
          const hold = await bookings.tryHold({ key: ctx.toolCallId, chatId: ctx.chatId, start: answer.slot });
          if (!hold) return { refuse: "Это время уже заняли. Выберите другое." };   // виджет остаётся открытым
          ctx.state.set("booking.holdId", hold.id);                                  // ляжет вместе с ответом виджета
          return { answer: { ...answer, holdId: hold.id } };                         // можно подменить ответ
        },
      },
    ],
  },
}
```

- **Три исхода.** `undefined` — принять как есть. `{ answer }` — принять с заменой: её видят и модель, и экран. Замена
  схемой не перепроверяется, только должна быть JSON до 16 КБ. `{ refuse: "текст" }` — отказать: текст до 300 знаков
  (длиннее режется, пустой текст — ошибка приложения).
- **Отказ.** Ничего не записано, ход не идёт, виджет остаётся открытым, под ним показывается текст отказа. Сервер отвечает
  `409 { error: { kind: "widget_answer_refused", code: "widget_answer_refused", message } }`, служба бросает
  `WidgetAnswerRefusedError`. Человек выбирает снова: проверка зовётся с тем же `toolCallId`, ключ записи стройте и по ответу.
- **`ctx`:** `ownerId`, `chatId`, `messageId` (ответ с виджетом), `toolName`, `toolCallId`, `input` (вход вызова),
  `subject`, `chatData`, `state`, `signal`, `emitAppEvent`. Ничего из этого не уходит к модели.
- **`ctx.state`** — состояние чата на ветке, как `model.state` у инструмента: читает свёртку до ответа, пишет записи. Принятые
  записи ложатся в ответ вместе с результатом виджета одной записью, `getChatState` и следующий ход их видят. Отказ и
  исключение их отбрасывают. После конца проверки запись не принимается (строка в `logError`). Записала проверка хоть
  что-то — `onStateChanged` зовётся сразу после записи ответа с причиной `widgetAnswer` (`previousState` — до ответа,
  `atMessageId` — ответ с виджетом), в канал наблюдения уходит `state-changed`. Копировать состояние в свою базу из
  самой проверки больше не нужно. Записи `data-app-state` из проверки теперь идут клиенту и потоком: первыми кусками
  продолжения ответа, вместе с событиями.
- **`ctx.emitAppEvent(event)`** — событие приложения, как `model.emitAppEvent` у инструмента: `{ type, data? }`, неверная
  форма — `TypeError` сразу. Все события одной проверки — не больше 16 КБ в JSON: сверх — `RangeError` сразу, событие
  не записано (кладите ссылку, а данные читайте из своей базы). Событие ложится в ответ вместе с результатом виджета (после записей состояния). Отказ и
  исключение его отбрасывают, после конца проверки — строка в журнал. На странице `onAppEvent` получает его живым
  (`live: true`) один раз: при продолжении ответа — первым куском потока, до слов модели; если ответ ещё ждёт другого
  решения человека — страница сама перечитывает историю после ответа сервера (канал наблюдения тоже сообщает о нём,
  второго срабатывания нет). Модели событие не уходит. «Повторить» после сбоя копирует событие в новый ответ с `id`
  вида `copied:<ответ>:<номер>`: страница показывает его, но `onAppEvent` получает его с `live: false` — так со всеми
  скопированными событиями, и от инструментов тоже.
- **Исключение.** Ответ 500, ничего не записано, виджет открыт, в журнале строка `[виджет] ошибка проверки чат=… вызов=…`
  только с именем ошибки (`Error`, `TypeError`…): текст ошибки в журнал не идёт, в нём могут быть данные ответа или базы.
- **Срок.** `agent.widgets.checkAnswerTimeoutMs` (по умолчанию 5 000 мс): проверка держит чат занятым, зависшая не держит
  его вечно. Вышел срок — это не исключение приложения: служба бросает `WidgetAnswerCheckTimeoutError`, сервер отвечает
  `504 { error: { kind: "widget_check_timeout", code: "widget_check_timeout", message } }`, ничего не записано, виджет
  открыт, повторить можно; в журнале строка `[виджет] отказ answer_check_timeout …`, а не ошибка. Страница показывает под
  виджетом подпись `widgets.answerCheckTimeout` («Не удалось проверить ответ, попробуйте ещё раз»). Срок хода (`turnTimeoutMs`) проверка не расходует. Держите его заметно меньше
  срока запроса на странице (`requestTimeoutMs` у `AgentChat`, по умолчанию 10 000 мс): иначе страница сдастся раньше сервера и
  человек увидит «нет связи» вместо отказа или ошибки проверки. Поднимаете срок проверки — поднимите и срок запроса.
- **Отмена (`ctx.signal`).** Это `AbortSignal`. Он срабатывает, когда вышел срок проверки или человек нажал «Стоп» в этом
  чате. Служба после отмены сразу отпускает чат и ничего не пишет: ни ответ, ни `ctx.state`, виджет остаётся открытым.
  «Стоп» — не сбой: служба бросает `WidgetAnswerCheckAbortedError`, сервер отвечает
  `409 { error: { kind: "widget_answer_cancelled", code: "widget_answer_cancelled", message } }`, страница молча оставляет
  виджет открытым, в журнале строка `[виджет] отказ answer_cancelled …`, а не ошибка.
  Остановить вашу работу она не может: приложение слушает `ctx.signal` само и бросает то, что уже не нужно
  (`fetch(url, { signal: ctx.signal })`, запрос в базу с отменой). Не слушаете — проверка доработает впустую, а её побочное
  действие (бронь) останется сиротой, см. ниже.
- **Закрытие чата.** Чат могли закрыть (`closeChat`), пока шла проверка. Тогда после проверки ответ не пишется, служба
  бросает `ChatClosedError`, а ждущий виджет закрывается отказом, как при обычном закрытии чата.
- **Сироты.** Проверка могла что-то записать в вашу таблицу (бронь), а ответ не лёг (другая копия сервера ответила раньше,
  сбой базы). Такие записи снимайте по ссылке из состояния: запись, на которую состояние больше не ссылается, лишняя.
- **Общая проверка.** `agent.widgets.checkAnswer(call, answer, ctx)` — для всех виджетов без своей `checkAnswer`: базовых
  (`ask_choice` и др.) и своих. `call` — `{ toolName, toolCallId, input }`. Своя проверка виджета главнее общей.
- **Порядок.** Свой чат → ждущий виджет → схема (`InvalidWidgetAnswerError`) → `checkAnswer` → запись. `beforeTurn`,
  закрытие чата и лимиты проверяются раньше. Без `checkAnswer` всё как прежде. Запрос к модели проверка не меняет:
  результат вызова — принятый (возможно, заменённый) ответ.

## Свой набор виджетов в каждом чате (`enabledFor`)

Разным чатам — разные виджеты: в анкете «а» только выбор варианта, в анкете «б» только запись на время. Набор
выбирает функция по чату:

```ts
agent: {
  widgets: {
    basic: ["ask_choice", "ask_rating"],
    custom: [pickSlot],
    enabledFor: ({ chat }) => (chat.data?.form === "b" ? ["pick_slot"] : ["ask_choice", "ask_rating"]),
  },
}
```

- **Вход:** `chat.id`, `chat.ownerId`, `chat.data` (данные чата к началу хода), `chat.subject` (у чата объекта). Ответ —
  имена базовых и своих виджетов. Нет `enabledFor` — включены все, как раньше.
- **Модель выключенных не видит вовсе:** их нет среди инструментов запроса. Инструкцию под набор пишет приложение
  (`chatInstructions`): ядро текст инструкции не меняет, и упоминать там выключенные виджеты не надо.
- **Старые вызовы.** Вызов виджета, который потом выключили, идёт модели текстом («прошлый вызов, сейчас выключен», вход
  и ответ), а не вызовом инструмента: строгие провайдеры (Anthropic, Bedrock) не принимают вызов инструмента, которого
  нет в запросе. Экран и хранилище видят вызов как был.
- **Кэш модели.** Набор зовётся на каждый запрос: ход, повтор, продолжение после ответа на виджет, сжатие истории. Функция
  должна быть синхронной и без побочных действий: те же данные чата — тот же набор, и кэш модели цел. **Смена набора
  сбрасывает кэш модели** (меняется список инструментов в начале запроса): меняйте данные чата, от которых он зависит,
  редко — например, раз при открытии анкеты, а не на каждом ходе.
- **Ошибки.** `enabledFor` не функция — ошибка при создании службы. Неизвестное имя — одна строка в журнал на имя, имя
  пропускается. Исключение в функции — ошибка хода.

## Что видит человек и что делает сервер

- **Статус «ждёт человека».** Пока виджет без ответа, ответ агента хранится со статусом `awaiting_approval`, как запрос подтверждения.
  Ждать можно сколько угодно: состояние лежит в базе, переживает перезагрузку страницы и перезапуск сервера, ответить можно с другого устройства.
- **Один вопрос за раз.** Если модель вызвала несколько ждущих виджетов в одном шаге, показан первый, остальные получают
  ошибку «Задавай один вопрос за раз».
- **Ответ сообщением.** Человек может не нажимать, а написать. Тогда виджет закрывается пометкой «Ответ дан сообщением»,
  модель видит `{"ответ":"сообщением"}` и само сообщение.
- **«Стоп» и сбой** закрывают висящий виджет так же, как вызов инструмента без результата: модель увидит «ответа не было». Экран делает то же сразу, без перезагрузки.
- **Другая ветка.** Вопрос из неактивной ветки не нажимается: ответить на него можно только там.
- **Голос.** Голосовой режим произносит вопрос и варианты («Базовый, Стандарт или Про?»), для формы и своего виджета — «ответьте на экране или голосом». Голосовая реплика — обычное сообщение и закрывает виджет.
- **Лимит расходов.** Ответ на виджет проверяет лимит, как ответ на подтверждение: при исчерпанном лимите (429) виджет остаётся на месте.

## Маршрут ответа

Страница вызывает его сама. Нужен только тем, кто пишет свой клиент.

`POST {api}/:chatId/widgets/:toolCallId`, тело `{ "answer": <JSON> }`: до 64 КБ целиком, сам ответ до 16 КБ.

| Ответ | Когда |
|---|---|
| `200 { "resumed": boolean }` | ответ принят. `true` — ход продолжился, его поток читается обычным `GET {api}/:chatId/stream`. `false` — ответ записан, но в сообщении ждёт ещё виджет |
| `400 invalid_answer` | ответ не прошёл схему, больше 16 КБ, тело не JSON, длиннее 64 КБ или без поля `answer`; ничего не записано |
| `404 not_found` | чата нет или он не этого человека |
| `409 widget_answer_refused` | приложение отказало в ответе (`checkAnswer`): тело `{ error: { kind, code, message } }`, слова — человеку; ничего не записано, виджет ждёт |
| `409 widget_answer_cancelled` | человек нажал «Стоп», пока шла проверка ответа (`checkAnswer`): тело `{ error: { kind, code, message } }`; ничего не записано, виджет ждёт, показывать нечего |
| `504 widget_check_timeout` | проверка ответа (`checkAnswer`) не уложилась в срок `checkAnswerTimeoutMs`: тело `{ error: { kind, code, message } }`; ничего не записано, виджет ждёт, повторить можно |
| `409 widget_not_pending` | вызова нет, он уже отвечен, закрыт сообщением, не в последнем ответе ветки, или виджет убран из настроек (тогда ответить можно только сообщением) |
| `409 busy` | в чате идёт ход |
| `429 spending_limit_reached` или `too_many_turns` | лимит расходов или число одновременных ответов |

Каждый отказ пишется в журнал сервера строкой `[виджет] отказ <вид> чат=… вызов=…` без содержимого ответа.

Служба: `chatService.answerWidget({ chatId, ownerId, toolCallId, answer })`. Своя реализация `ChatService` должна получить этот метод.

## Свой скин

Скин версии 13 получает необязательные части `Widget` (готовые виджеты), `SuggestedReplies` (подсказки). Проверку формы и выбора
(пределы, обязательные поля) делает слой поведения: неверные значения скину не доходят, он получает только текст ошибки поля.
Скин без этих частей работает: виджеты показаны запасным видом «Ответьте сообщением». Подписи — группа `widgets` словаря надписей.
Подробности — [договор скина](contracts/agent-widgets/react-and-skin.md).

Пример — `apps/demo` (сценарии `apps/demo/e2e/widgets.spec.ts`).
