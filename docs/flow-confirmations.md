# Подтверждённая веха и актуальный вопрос

Серверная проверка сценария может сохранить достигнутую веху независимо от перехода. Например, человек опубликовал своё приложение, а о домене спросил через десять сообщений. Судья подтверждает публикацию один раз; guard выхода требует это подтверждение и отдельно проверяет актуальный вопрос. Окно истории судьи не увеличивается.

Это оценка диалога зарегистрированным судьёй SDK. Она не доказывает право собственности на домен, доступ к аккаунту или фактическую доступность сайта. Критерий приложения по-прежнему должен требовать именно свою ссылку, результаты её просмотра и отсутствие сомнений в атрибуции. Один URL или слова «опубликовал» сами по себе не заменяют проверку.

## Новый объединённый этап

Настройки передаются в серверный `createAgentFlow`. Они не входят в JSON редактора, карточку клиента или инструменты модели.

```ts
const ownPublished = { key: "ownPublished", revision: "own-app-v1" };

const flow = createAgentFlow({
  loadFlow,
  store,
  judge,
  confirmations: [{
    flowId: "first-app",
    ...ownPublished,
    states: ["publish"],
    judge: "Человек прислал ссылку на apps.example.com на то самое приложение, которое " +
      "он собирал в этом разговоре. Если помощник сомневается, что это его " +
      "приложение, или сказал, что по ссылке не то, условие не выполнено.",
  }],
  exitGuards: [{
    flowId: "first-app",
    state: "publish",
    exitId: "polish_done",
    requires: ownPublished,
    judgeWindow: "current-human-turn",
  }],
});
// Как обычно: createChatServer(flow.withChat(...)), затем flow.attach(service).
```

В JSON у `polish_done` остаётся judge об интересе: явный вопрос человека про собственный домен, ИИ-агента, заявки или обучение. Публикация остаётся обязательной через серверный guard. Независимый `publish_day3` с `program_day: 3` не получает этот guard и продолжает работать без публикации.

Проверка вехи выполняется после полного ответа в перечисленных неконечных состояниях, даже когда интереса к курсу нет. При положительном результате SDK сохраняет квитанцию в `FlowRun.confirmations`. В ней есть человек, чат, сценарий, `key`, `revision`, SHA-256 критерия, время проверки, исходная версия сценария, id ответа и сообщения человека, вероятность судьи. Свободные факты, `flow_note`, `learn` и текст модели такую квитанцию не устанавливают. Поля `flow.confirmations`, `flow.confirmationCheck` и `flow.checkedTransition` записывает только серверный путь SDK. Запись или удаление этих полей через `model.state`, в том числе заменой всего `flow`, отклоняются; обычные заметки и другие поля приложения сохраняют прежние правила. `get` возвращает копию, поэтому изменение прочитанного объекта не меняет состояние.

Подтверждение действует в своём чате и ветке. Правка или перегенерация до доказательства не наследуют подтверждение из будущей ветки. Оно не переносится другому человеку, чату или сценарию. При смене семантики критерия измените `revision` и выпустите новую immutable версию сценария. Несовпадение revision или хеша означает неизвестный результат, а не подтверждение. В пределах одной версии сценария несовместимый серверный конфиг не переписывает уже записанные receipt/revoke: без порядка строковых revisions SDK не угадывает, какой конфиг новее. Сохранённый интерес/decision прежней версии не применяется к новому графу.

`current-human-turn` проверяет последнее текстовое сообщение человека перед данным ответом и сам ответ. Предыдущие вопросы не передаются этой проверке. Возобновление ответа после approval/widget использует прежний human message id; служебные сообщения и автоматические ходы не создают новый интерес. Отдельного сохраняемого флага интереса нет. Первичная проверка публикации использует прежнее ограниченное окно, а не всю переписку; ограничения судьи в шесть реплик и 600 знаков на реплику сохраняются. Критерий регистрации ограничен 800 знаками.

Guarded `flow_exit` не выполняет переход в середине генерации: SDK проверяет его после завершения ответа. Положительное подтверждение и решение о переходе пишутся одной служебной записью до применения перехода. Следующая подготовка хода повторно проверяет guard и применяет решение. После сбоя между записью и переходом решение остаётся в ветке для повторного применения. Если у целевого состояния есть `firstMessage`, SDK будит агента; указание сказать первый текст приходит только после реально выполненного перехода. Готовый `reply`, обходящий эту проверку, для guarded выхода не используется.

Стабильные `common`, инструменты и блок карточки состояния не получают квитанцию каждый ход. Служебные записи состояния не отправляются модели как новые реплики. Дополнительные вызовы судьи и запись состояния возникают только при включении этой возможности.

## Исправление атрибуции

Историческая веха не отменяется из-за последующего удаления приложения или HTTP 404. Если человек явно исправляет прежнее утверждение («та ссылка была чужая»), приложение обрабатывает это своим доверенным backend-путём и вызывает:

```ts
const snapshot = await service.getChatState(ownerId, chatId);
const result = await flow.revokeConfirmation({
  ownerId, chatId, flowId: "first-app",
  ...ownPublished,
  expectedAtMessageId: snapshot.atMessageId,
  idempotencyKey: correctionId, // стабильный id операции приложения
  reason: "Человек уточнил, что прежняя ссылка была чужой",
});
```

`applied` означает запись, `same` — повтор уже выполненной отмены. `busy` означает занятый ход; `stale` — изменившийся снимок или revision. Приложение обязано обработать эти результаты, перечитать актуальную ветку и решить, относится ли исправление к ней; молчаливо считать отмену успешной нельзя. Не публикуйте этот метод как незащищённый endpoint с произвольным JSON человека.

Отмена хранит границу доказательств и снимает ещё не применённое guarded решение. Запоздалый положительный ответ судьи старого снимка не переписывает её. Старое доказательство не подтверждается заново повтором того же хода. Новая положительная проверка после этой границы разрешена; это не постоянный запрет. SDK не обнаруживает опровержение самостоятельной модельной записью флага: семантика и маршрут вызова backend revoke принадлежат приложению.

## Строгая выборочная миграция

Существующий `migrateChats` без дополнительных опций переносит состояния, но не доказывает публикацию. Для сценария, где перенос требует сохранённой вехи, передайте `requiresConfirmation` и предварительно изучите read-only отчёт:

```ts
const migration = {
  flowId: "first-app",
  toVersionId: "first-app-four-states-v1",
  requiresConfirmation: ownPublished,
};
const preview = await flow.previewMigration(migration);
// preview.eligible: string[]
// preview.keepOriginal: { chatId, status: "ambiguous", reason }[]

await flow.migrateChats({
  ...migration,
  chatIds: preview.eligible,
  map: { first_version: "idea", polish: "publish" },
  flow: fourStateFlow,
});
```

Строгий отбор повторно проверяется при вызове миграции. Неподходящие чаты пропускаются и остаются на исходной immutable версии. Версия нового сценария применяется к новым чатам через `loadFlow`; мигрировать существующие необязательно. Поддерживаются прежние `chatIds`, `filter`, `includeEnded` и `includeTestChats`.

Проверяется квитанция SDK исходной ветки **до** `map`: scope, revision, хеш критерия, существование исходной immutable версии и наличие исходных сообщений в ветке. Квитанция сохраняется целиком, её исходная версия и id не переименовываются. Перенос не выдаёт новую квитанцию и не оживляет отозванную. Отмена после отбора по-прежнему блокирует guard целевого состояния; сам batch-перенос FlowStore и сообщения чата не образуют общую транзакцию.

`missing_receipt`, `revoked_receipt`, `incompatible_receipt`, `source_version_missing` и `source_not_on_branch` попадают в `keepOriginal`. Исторические `publish_done`, `currentState=polish` и поле карточки «опубликовал» без versioned receipt не импортируются. Старый `path` не хранил версию проверки, мог пережить административные переносы и обрезается до 50 записей. SDK не восстанавливает отсутствующее доказательство по названию состояния, совпадению id выхода или предположению о старом графе. Универсального `setConfirmed(true)` и legacy attestation API нет.

## Сохранение и границы

Квитанция и pending guarded decision сохраняются одной записью состояния ветки с compare-head под блокировкой хода чата. Повтор операции не дублирует запись; другой payload с тем же ключом отклоняется. Более свежий ответ, revision или revoke не перезаписываются старым снимком. Служебная запись не вызывает модель, не считается сообщением человека и не создаёт ACK.

Атомарность относится к записи квитанции и ожидающего решения о переходе, а не к внешним эффектам приложения. `afterTransitions`, `onTransition` и `onFinish` могут выполниться до устойчивой записи состояния хода: сбой между callback и записью оставляет окно для повторного вызова при восстановлении. SDK не гарантирует exactly-once для платежей, писем и других внешних действий из этих callbacks. Приложение обеспечивает их идемпотентность самостоятельно; новая квитанция эту существующую границу не меняет.

Новая SQL-схема не требуется. Для нескольких процессов серверов хранилище чатов должно поддерживать существующие `claimChatTurn`/`releaseChatTurn`. Без них действует только сериализация внутри одной службы, как у обычных ходов SDK. Lease не является бессрочной блокировкой при падении/зависании процесса.

Расширение подключается к настоящему `ChatService` совместимой версии SDK через `attach(service)` либо возвращает такую службу из `portFor`. Прокси, копирующие только отдельные методы в новый объект, не переносят внутреннюю capability записи flows. Несовместимый порт не подтверждает guard; ошибка попадает в журнал.
