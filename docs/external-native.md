# Внешний исполнитель и нативный клиент: первый срез

Это отдельный, включаемый приложением протокол бесед. Он не меняет существующий `ChatService`, React-чат или их API. Внешний исполнитель работает в своей системе; SDK хранит проекцию переписки, очередь исходящих, разрешения и журнал событий клиента. Модель через SDK при этом не вызывается.

В срез входят текст, список бесед, история, накопленный текст ответа, остановка, разрешения, повторное подключение и локальная очередь Swift. Вложения, виджеты, ветки и встроенный модельный исполнитель нативного протокола в этот срез не входят.

## Сервер

Публичные входы:

- `@ykurilov/agent-chat-core/external`: типы, `createExternalConversationService`, `createMemoryConversationStore`;
- `@ykurilov/agent-chat-storage-sqlite/external`: `createSqliteConversationStore(path)`;
- `@ykurilov/agent-chat-server/external`: `createExternalChatHandler`.

В серверном composition root создайте SQLite store и сервис. `resolveExecutor(definition)` возвращает адаптер нужного внешнего агента; `definition.execution.id` задаёт внутреннюю привязку, клиент её не получает. Для каждой разрешённой беседы вызовите `ensureConversation({id, ownerId, title, pinned, execution:{kind:"external",id}})`, затем `start(ownerId,id)`. Повторное создание не меняет владельца и исполнителя. При перезапуске приложения эти вызовы повторяются. Ждать первого пользовательского хода для восстановления не требуется.

Обработчик `createExternalChatHandler({service, resolveUser, basePath:"/api/conversations"})` возвращает `fetch(Request):Promise<Response>`. В Hono он монтируется через `app.all("/api/conversations/*", c => handler.fetch(c.req.raw))`; отдельный маршрут для `/api/conversations` тоже направьте этому обработчику. `resolveUser` проверяет авторизацию приложения и возвращает `{id}` либо `null`. Учётная запись и привязки агента берутся только на сервере, не из тела запроса. HTTPS, выдача и отзыв токенов, CORS и ограничения частоты запросов остаются приложению.

На shutdown: прекратите принимать запросы, дождитесь `service.close()`, затем закройте SQLite store. Не закрывайте store раньше сервиса. Таблицы `sdk_external_*` создаются в переданном SQLite-файле; существующие таблицы `ChatStorage` не меняются. `createMemoryConversationStore` предназначен для тестов, не переживает перезапуск. Свой `ConversationStore` обязан атомарно выполнять синхронный transaction callback вместе с журналом и исполнять `guarded:true`; Promise из callback запрещён.

## Исполнитель и обязанности Моста

Точный договор находится в `packages/core/src/external/types.ts`:

- `status()` возвращает `idle | thinking | waiting_approval | offline`;
- `send(text,messageId)` передаёт именно заданный ID и текст;
- `stopTurn()` прерывает ход, сохраняя соединение. Остановка должна вызывать прерывание исполнения, а не отключение транспорта;
- `respondToPermission(requestId,response)` отвечает конкретному открытому запросу; `agentId` захватывается в адаптере;
- `onConversation(asyncListener)` возвращает отписку. Источник ждёт успешного завершения listener **до** продвижения своего сохранённого курсора;
- `reconcile()` воспроизводит сообщения, открытые разрешения и статус через **тот же последовательный async listener**. Завершается только после их подтверждённой записи.

SDK подписывается до reconcile. Источник не должен терять сообщения между снимком и подпиской. Не вызывайте события параллельно и не ждите окончания нового хода внутри `send`: достаточно подтверждения приёма сообщения.

`delta {id,textSoFar}` содержит накопленный текст. `message` завершает запись, `turn_ended` задаёт исход `completed | canceled | failed | unknown`. Ошибка хода хранится в его состоянии, а не выдаётся за реплику агента. При сверке воспроизводите сообщения, текущий статус и разрешения; исторические `turn_started/turn_ended` повторно не проигрывайте. Текущие границы хода приходят живыми событиями. После успешной сверки авторитетный статус `thinking/waiting_approval` восстанавливает активный ход и кнопку «Стоп». Если прежде активный ход исчез, а источник уже `idle`, его итог становится `unknown`, а не выдуманным `completed`; открытые потоковые сообщения тоже помечаются `unknown`. Старая неподтверждённая остановка не блокирует кнопку после сверки. Поэтому `status()` по завершении reconcile должен отражать тот же свежий снимок источника, а не устаревший локальный кеш.

`permissions_snapshot {requests}` - авторитетный список открытых запросов, включая пустой. Отсутствующие запросы считаются закрытыми. Разрешения отдельны от текста и адресуются исходным ID. Нативная карточка показывает имя/описание и параметры запроса, чтобы решение не было вслепую. Адаптер приложения удаляет секреты из передаваемых пользователю параметров до их сохранения в SDK. Ответ пользователя сохраняется до вызова адаптера; состояние `responding` снимается подтверждением источника, не оптимистическим исчезновением карточки. Повторный ответ адресует тот же request ID: внешний источник обязан отклонять уже закрытый запрос без повторного действия. Для вопросов SDK передаёт исходные `questions` и пользовательские `answers` в `updatedInput`, не принимает произвольную подмену параметров инструмента.

После смены эпохи внешней системы перед rebuilt replay передайте `history_reset {epoch}`. Эпоха устойчива при перезапуске Моста. Пересобранные сообщения сверяются последовательно по роли, точному тексту и времени с допуском 2 секунды; каждое старое сообщение участвует один раз в эпохе. Это сохраняет две одинаковые реплики. Сверка неоднозначна вне этого временного допуска; адаптер должен сохранять исходные ID, когда они доступны. Удаление/редактирование внешней истории первым срезом не поддержано.

## Доставка и граница повторов

POST сообщения сначала атомарно сохраняет текст и `clientMessageId`, затем возвращает **202**. Недоступный исполнитель оставляет `queued`; активный сервис отправляет очередь после восстановления связи. Повтор ID с тем же текстом возвращает прежнюю запись; с другим текстом - 409. Импорт внешнего пользовательского сообщения никогда не вызывает `send`.

Перед удалённым вызовом записывается `sending`. Успех подтверждает приём. Потерянное подтверждение или перезапуск посреди вызова дают `unknown`: SDK сверяет исходный ID с лентой, **не делает слепую повторную отправку**. `ExternalDispatchRejected` допустим только когда адаптер доказал, что отправка не была принята; тогда запись снова `queued`. Обычная сетевая ошибка этим доказательством не является. Для копий пакета/адаптера предусмотрен явный `code:"external_dispatch_rejected"`; SDK распознаёт его без зависимости от `instanceof`. Только адаптер, доказавший неприём, выставляет этот код. Ошибка первой сверки при офлайн-старте сохраняет подписку; повторная сверка с ограниченным интервалом происходит после возвращения исполнителя. До успешной сверки отправка и ответы на разрешения не выполняются. Таймаут не запускает вторую физическую сверку поверх незавершённой первой: SDK ждёт её фактического окончания, затем запрашивает свежий снимок. Для навсегда зависшего I/O требуется восстановление или перезапуск адаптера. `close` отписывает источник и ограждает поздние записи, не ожидая бесконечно исходный Promise источника.

Reconcile должен находить принятый клиентский ID даже за пределами обычного хвоста ленты. Если источник не доказал ни приём, ни отсутствие отправки, `unknown` блокирует следующие исходящие, сохраняя порядок. Автоматического решения неопределённой доставки и exactly-once для внешних действий здесь нет. До production требуется договор источника о полном поиске ID и операционном разрешении неустранимой неопределённости.

Один сервис держит аренду беседы; соседняя копия получает `busy`. Все последующие записи ограждены holder и сроком. Потерявшая аренду копия не меняет проекцию; уже начатый удалённый вызов этим не отменяется. Адаптер/внешняя система по-прежнему отвечают за идемпотентность исходных команд. «Стоп» не ставится в офлайн-очередь, чтобы запоздалой командой не остановить другой ход.

## Протокол клиента

Все ответы имеют `version:1`. Адреса относительно `basePath`:

| Запрос | Результат |
|---|---|
| GET `/` | разрешённые владельцу беседы, закреплённые первыми |
| GET `/:id` | согласованный снимок с курсором |
| GET `/:id/events?after=N` | события после курсора, либо 409 для нового снимка |
| GET `/:id/events?after=N`, Accept `text/event-stream` | SSE `change`, `id` = seq, `data` = сохранённое событие |
| POST `/:id/messages` | `{clientMessageId,text}` → 202 |
| POST `/:id/stop` | `{commandId}` → 202, если исполнитель доступен |
| POST `/:id/permissions/:requestId` | `{commandId,decision}` → 202 |

Снимок и события содержат сообщения с ревизиями, разрешения и состояние хода. SSE построен из сохранённого журнала, а не из эфемерного сокета. Потеря курсора за окном хранения (по умолчанию 1024 изменения) требует нового снимка. Клиент сохраняет событие и курсор вместе. Лишние/повторные номера игнорируются, разрыв номеров требует сверки.

## Swift: локальный SPM

В корне SDK находится `Package.swift` с продуктами **AgentChatClient** и **AgentChatOduvanchik**. Минимум iOS 17 / macOS 14, Swift 6. Подключение первого среза - локальный SPM package из checkout SDK. Канонический YKDesign берётся из соседней папки `../YKDesignSystem/swift/YKDesign` или из абсолютного `AGENT_CHAT_YKDESIGN_PATH` в окружении процесса Xcode. Пакет дизайна не копируется внутрь SDK. Публичного SPM URL дизайна пока нет; установка SDK только по Git URL на произвольной машине этим срезом не обещается.

Создайте `AgentChatClient(endpoint:accountID:cacheURL:credential:)` на аутентифицированную учётную запись. Endpoint - полный basePath сервера. Credential - async closure, возвращающий действующий bearer; SDK его не сохраняет. Cache URL выбирает приложение в своём Application Support. При выходе остановите клиент и примените свою политику удаления кеша. Кеш другого accountID/endpoint не принимается. Защита файлов ОС и их резервного копирования остаётся приложению.

`AgentChatView(client:)` из AgentChatOduvanchik включает список бесед, текст, разрешения, поле сообщения и одновременные «Отправить»/«Стоп». Поведение соединения не находится в скине: свой SwiftUI экран использует `updates()`, `send`, `answer`, `stop`, `openConversation`, `connect/disconnect`. `send` возвращает после атомарной записи на устройство, а не после сети. Черновик и исходящие сохраняются; повтор транспорта использует тот же ID. HTTP 202 отмечает приём, но локальный текст остаётся на устройстве до сохранения соответствующей серверной записи вместе с курсором. Подтверждённая команда повторно не отправляется. При 401 приложение обновляет авторизацию и вызывает connect заново.

У каждой беседы собственные execution kind и modelChoice. Главный чат закрепляет приложение. Список и протокол не зависят от того, кто будет исполнять ход. `kind:"model"` зарезервирован для следующего среза; сервер явно отказывает его запуску/отправке вместо имитации модельного ответа. Селектор DeepSeek и его маршрутизация в этом выпуске не реализуются.

## До production

Нужны проверка на живом Мосте (включая полный поиск принятого messageId и подтверждаемый source cursor), iPhone-интеграция с авторизацией приложения и жизненным циклом, визуальная и accessibility проверка нативного экрана, публикация канонического дизайна для переносимого SPM, а также политика неопределённой доставки. Для больших историй требуется пагинация/компактизация: первый срез читает полную проекцию. Push делает приложение. Реестр бесед, создание/удаление чатов, права, блокировки и выбор привязок исполнителя также остаются приложению.

## Общий нативный экран и компоненты (0.85)

`AgentChatView(client:responderName:)` использует общий комплект `AgentChatOduvanchik`: шапку и состояние исполнителя, Markdown ответа, мягкий пузырь пользователя, отдельные карточки разрешений, индикатор работы и отметки доставки. «Остановить» остаётся рядом с отправкой, когда человек набирает сообщение. Состояния неопределённой доставки не получают слепой автоматический повтор.

Для своего shell экспортированы `AgentChatHeader`, `AgentChatResponderLabel`, `AgentChatMarkdown`, `AgentChatUserBubble`, `AgentChatThinkingRow`, `AgentChatDeliveryNote`, `AgentChatComposer`, `AgentChatApprovalCard` и `AgentChatPermissionCard`. Они используют канонический YKDesign; соединение и сохранение остаются в AgentChatClient/AgentChatScreenModel. Markdown поддерживает заголовки, абзацы, списки, цитаты, fenced code и строчное оформление/ссылки; незакрытый code fence допускается во время потока. Это не HTML и не полная реализация CommonMark.

Снимок и события содержат `sequence` первого сохранённого появления у сообщений и разрешений. У разрешения сохраняется `createdAt` источника, если он передан в request, иначе время первого приёма SDK. Повтор запроса/смена статуса позицию не меняют. `ChatSnapshot.timeline` объединяет сообщения и все карточки, включая закрытые. У записей из 0.84 этих метаданных может не быть: время старого запроса не выдумывается, неизвестный старый порядок не восстанавливается точно. Старые строки идут стабильной группой перед новыми, а локальное ещё не спроецированное сообщение - в конце.

`decision` в проекции/Swift - намерение, отправленное через SDK. Фактический ответ внешней системы - отдельное необязательное `resolution`. Адаптер передаёт его событием `permission_resolved {requestId, decision?: ExternalPermissionResponse}`: `behavior`, `selectedActionId?`, `updatedInput?`, у deny также `message?`. На сервере это сохраняется в `resolution`; Swift не отбрасывает ни одно из двух полей. При отсутствии фактического решения карточка показывает **«Выбор неизвестен»**, даже если есть локальное намерение. Это касается закрытия по окончании хода и ответа, пропущенного во время офлайна. Поздний закрывающий event без decision не стирает известное решение. Секреты из updatedInput/message также удаляет адаптер до передачи в SDK.

Публичные value-типы клиента получили `public init`, поэтому snapshot, permission, conversation, turn, action и события создаются в тестах без JSON. Новые поля необязательны при чтении старого кэша. SQL-схема, переменные окружения и контракт старого HTTP-ответа не меняются. Для живого порядка и фактического ответа обновите сервер и Swift checkout одной версией; адаптер добавляет decision только когда источник действительно сообщил resolution.

Replay не меняет сохранённые `stopped/error/unknown` обратно в `complete/streaming`. Отдельное продолжение внешнего ответа по-прежнему получает устойчивый новый ID сегмента. Одинаковые состояния соединения и хода не создают повторных status-записей. Захват занятой беседы бросает `ExternalConversationBusyError` с `code: "external_conversation_busy"` и прежним message `busy`; HTTP сохраняет `409 error.kind: "busy"` и добавляет тот же `error.code`.


## Голосовой ввод Swift (0.86.0)

Распознавание подключает приложение. SDK не запрашивает доступ к микрофону,
не записывает звук и не обращается к Soniox или другим провайдерам.
`AgentChatComposer` и готовый `AgentChatView` принимают необязательный
`speechRecognizer: (any AgentChatSpeechRecognizer)? = nil`. Без него микрофон скрыт,
существующие вызовы компонентов остаются совместимыми.

```swift
@MainActor public protocol AgentChatSpeechRecognizer: AnyObject {
    func start() throws -> AsyncStream<AgentChatSpeechEvent>
    func finish()
    func cancel()
}

public enum AgentChatSpeechEvent: Sendable, Equatable {
    case partial(String)
    case final(String)
    case finished
    case failed(String)
}
```

Все команды возвращаются сразу: длительную запись, запрос разрешения и сетевую
работу распознаватель выполняет в собственных задачах. `start` создаёт новую сессию
и новый поток. `partial` заменяет весь неподтверждённый хвост этой сессии;
`final` передаёт новый подтверждённый фрагмент ровно один раз, а не накопленный
текст всей сессии. Адаптер cumulative-провайдера сам выделяет новые final-фрагменты.
После `finish()` запись звука прекращается, но поток принимает последние final
и заканчивается событием `finished`. Пустой `finished` не превращает partial
в подтверждённый текст. Закрытие потока без terminal-события считается ошибкой.
`cancel()` немедленно освобождает микрофон/сетевую работу приложения и закрывает
поток; SDK отбрасывает запоздалые события старой сессии. Повторный start после
отмены допустим. `failed` и ошибки start содержат локализованное сообщение для
человека, без токенов и внутренних ответов поставщика. Приложение отвечает за
Info.plist/разрешения и собственную маршрутизацию звука.

Подтверждённый текст дописывается к **актуальному** черновику, включая правки
клавиатурой во время диктовки. С 0.86.1 SDK добавляет пробел только перед первым фрагментом сессии
после уже набранного текста (кроме пробелов и пунктуации на границе). Все дальнейшие
фрагменты склеиваются побайтно как пришли, включая подслова и ведущие пробелы.
Правка черновика клавиатурой начинает новую границу; исходные символы не нормализуются. Промежуточный хвост показан курсивом в области ввода и доступен
VoiceOver с подписью «Промежуточный текст»; в Binding/сохраняемый черновик он не входит.
С 0.86.1 отправка доступна и во время записи: она заканчивает диктовку, ждёт `finished`
и вызывает прежний `onSend` с итоговым черновиком. Повторное нажатие во время ожидания
не отправляет второй раз. При `failed`, отмене, обрыве без `finished` и пустом итоге
отправки нет. Отмена и ошибка сохраняют
подтверждённый текст; неподтверждённый хвост удаляется. Повторный тап по микрофону
заканчивает запись, отдельная кнопка отменяет её.

При самостоятельном использовании `AgentChatComposer` передавайте `speechContextId:
chatId`. Изменение контекста, распознавателя, отключение composer, исчезновение
экрана или уход приложения в background отменяют сессию. Готовый `AgentChatView`
передаёт выбранный chatId сам. Временный inactive (например системный запрос доступа
к микрофону) не отменяет запись. Экран `AgentChatView` скрывает клавиатуру тапом по
ленте и интерактивной прокруткой; кнопки разрешений и ссылки сохраняют свои действия.

В модели `AgentChatDictation` доступны `phase` (`idle`, `listening`, `finishing`,
`failed(String)`), `partialText`, `isActive`, `start(using:onFinal:)`, `finish()` и
`cancel()` для приложения, которое собирает собственную композицию. В готовом
composer модель создаётся внутри. Подтверждения записи черновика по-прежнему
принадлежат Binding приложения; отправки без нажатия кнопки нет.

### Как обновить приложение

Обновить Swift-источник SDK до v0.86.0 и при необходимости передать реализацию
`speechRecognizer`. Существующие потребители без распознавателя не требуют правок.
Новых обязательных env и SQL-миграций нет. При проверке: исходный текст + partial +
несколько final не теряют клавиатурный черновик; finish ждёт дорасшифровку; cancel
и переключение чата не дописывают старую речь в другой чат. Реальный микрофон и
Soniox проверяются в приложении: SDK тестирует контракт через управляемый распознаватель.


### Уточнения поведения в 0.86.1

API распознавателя не изменён. Подтверждённые фрагменты распознавателя могут быть
частями одного слова: после первого фрагмента SDK не вставляет разделители.
Общий composer делает это автоматически. При собственной композиции используйте
`dictation.appendFinal(fragment, to: currentDraft)` внутри `onFinal`.
Статический `AgentChatDictation.appending` теперь по умолчанию склеивает буквально;
его параметр `separating: true` относится только к границе сессии/внешнего текста,
а не к каждому сетевому фрагменту.

`finishAndSend(draft:onSend:)` модели ждёт успешный `finished`, читает свежий draft,
проверяет непустой итог и вызывает onSend один раз. `isSendPending` закрывает повторный
тап. После ошибки или отмены намерение отправить снимается, подтверждённый текст
остаётся в поле. Обычная кнопка окончания записи не отправляет сообщение.

Под полем больше нет подписей «Слушаю…», «Дорасшифровываю…» и текстовой ссылки отмены.
Отмена доступна кнопкой со значком и accessibility-label, состояния озвучиваются
через accessibility-value. Текст ошибки сохраняется. При активной сессии область
текста удерживает максимальную измеренную высоту; сокращение partial и перенос его
в final не сжимают её. После окончания сессии резерв высоты снимается. Для роста
используется движение Одуванчика; Reduce Motion отключает анимацию.

Для приложения с AgentChatComposer/AgentChatView достаточно обновить Swift-источник
до v0.86.1. Если приложение собирает поле само через AgentChatDictation, заменить
пофрагментное статическое склеивание на `appendFinal` и подключить `finishAndSend`
для новой отправки. Серверный протокол, SQL, env и API распознавателя прежние.
