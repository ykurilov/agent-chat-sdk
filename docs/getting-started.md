# Подключение чата с агентом к своему приложению

Инструкция ведёт от пустого приложения на Hono и React до работающего чата: собеседник пишет,
агент отвечает по частям, показывает рассуждения и вызовы инструментов, ответ можно
остановить, а переписка хранится в SQLite. Дальше — как взять PostgreSQL вместо SQLite и как
подключить чат к Next.js вместо Hono.

Рабочий пример всего, что здесь описано, — демо-стенд в `apps/demo` этого репозитория. Пример на Next.js — `apps/next-example`.

## 1. Что понадобится

- Node.js 22 и pnpm 10.
- Приложение: сервер на Hono 4, клиент на React 19 со сборкой Vite и Tailwind CSS 4.
- Ключ хотя бы одного провайдера: DeepSeek, Fireworks или Together AI.

## 2. Установка

Пакеты лежат в общем каталоге npm. Ключи и настройки `.npmrc` для установки не нужны.

```bash
pnpm add @ykurilov/agent-chat-core @ykurilov/agent-chat-server \
  @ykurilov/agent-chat-storage-sqlite @ykurilov/agent-chat-react \
  ai@7.0.122 zod hono @hono/node-server react react-dom
pnpm add -D tsx typescript @types/node @types/react @types/react-dom \
  vite @vitejs/plugin-react tailwindcss @tailwindcss/vite
```

Первая команда — то, что нужно приложению в работе, вторая — сборка клиента (Vite, React, Tailwind), запуск серверного
TypeScript (`tsx`) и типы. Если Vite, Tailwind и TypeScript в вашем приложении уже есть, вторую команду пропустите. Скин
Тандема ставится на шаге 5. Ещё два пакета нужны не всем:

- `lucide-react` — если в своих компонентах вы берёте иконки. Ставьте ту же версию, что у скина
  (`1.33.0`, см. `dependencies` скина), иначе в сборку попадут две копии.
- `@ai-sdk/provider` (в dev-зависимости, `4.0.19`, как у `ai@7.0.122`) — только для проверки сбоев модели на шаге 10.

Зависимости-«соседи» (peer): `react` и `react-dom` 19 (для `react`-пакета и скина), `hono` 4 (для
`@ykurilov/agent-chat-server/hono`), `vitest` 5 нужен только если вы берёте общие тесты хранилища из
`@ykurilov/agent-chat-core/storage-contract`.

**`better-sqlite3` собирать не нужно.** В его пакете лежат готовые сборки для macOS, Windows и Linux (в том числе
Alpine). pnpm 10 при установке всё равно напишет «Ignored build scripts: better-sqlite3»: это предупреждение можно
не трогать, хранилище работает. Разрешать сборку в `pnpm-workspace.yaml` (`onlyBuiltDependencies`) имеет смысл, только
если у вашей платформы готовой сборки нет: тогда `better-sqlite3` соберётся из исходников, и нужны компилятор C++ и Python.

`ai` ставьте той же версии, что закреплена в ядре (`7.0.122`). Иначе инструменты,
описанные через `tool()` из вашей копии `ai`, не совпадут по типам с ядром.

Пакеты приходят собранными: JavaScript и типы (`.d.ts`) лежат в `dist`, исходников TypeScript нет. Серверные
пакеты запускаются обычным `node`; `tsx` в примерах нужен только для вашего собственного серверного кода на
TypeScript (`tsx server/index.ts`).

## 3. Ключи провайдеров

Ключи живут только на сервере, в переменных окружения:

```ini
# .env — в .gitignore, в репозиторий не попадает
DEEPSEEK_API_KEY=…
FIREWORKS_API_KEY=…
TOGETHER_API_KEY=…
OPENROUTER_API_KEY=…
```

Нужен ключ хотя бы одного провайдера. Браузер ключей не получает и к провайдерам сам не ходит: все запросы
идут через ваш сервер. В меню выбора модели попадают только провайдеры, чей ключ есть на сервере.

Стандартный набор моделей (`standardCatalog`) и кто их отдаёт:

| Модель | `deepseek` | `fireworks` | `together` | `openrouter` |
|---|---|---|---|---|
| DeepSeek 4.1 Flash (`deepseek-4.1-flash`) | да | да | да | да |
| GLM 5.3 Flash (`glm-5.3-flash`) | | да | да | да |
| GPT 6 Luna (`gpt-6-luna`) | | | | да |
| Gemini 3.8 Flash (`gemini-3.8-flash`) | | | | да |
| Claude Haiku 5.5 (`claude-haiku-5.5`) | | | | да (кэш на час) |

| `providerId` | Переменная с ключом | Особенности |
|---|---|---|
| `deepseek` | `DEEPSEEK_API_KEY` | кэш ведёт сам поставщик |
| `fireworks` | `FIREWORKS_API_KEY` | чат получает свой ключ кэша, ответы привязываются к сессии |
| `together` | `TOGETHER_API_KEY` | кэш ведёт сам поставщик; ключ берётся в кабинете Together AI |
| `openrouter` | `OPENROUTER_API_KEY` | один ключ на много создателей моделей; среди хозяев модели выбирается самый быстрый |

Зашифрованные рассуждения (GPT 6 Luna) человеку не показываются: на экране только пересказ.

### Сервер в России: провайдеры через прокси и часовой пояс

С российского сервера зарубежные провайдеры напрямую недоступны: запросы идут через обратный прокси. Адрес прокси и его
заголовок задаются в каталоге, своего провайдера объявлять не нужно:

```ts
import { createChatHandler } from "@ykurilov/agent-chat-server";
import { extendCatalog, standardCatalog } from "@ykurilov/agent-chat-core";
import { createSpendingLimits } from "@ykurilov/agent-chat-limits";

const proxyHeaders = { "X-Proxy-Token": process.env.PROXY_TOKEN! };

const catalog = extendCatalog(standardCatalog, {
  connectProviders: {
    openrouter: { baseURL: "https://proxy.example.com/openrouter/api/v1", headers: proxyHeaders },
  },
});

const limits = createSpendingLimits({
  storage,
  catalog,
  budget: async () => ({ user: 1 }),
  period: "day",
  timeZone: "Europe/Moscow", // сутки обнуляются в полночь по Москве, а не в 03:00
});

const handler = createChatHandler({ /* … */ catalog, limits });
```

- **Всё идёт через прокси.** Ход агента, фоновые вызовы памяти и сжатия, сверка расхода OpenRouter
  (`GET …/generation`): все берут провайдера из каталога. Меню моделей, цены и учёт расходов те же, что без прокси.
- **Провайдер остаётся на своём месте** в каталоге и с прежними настройками, меняется только подключение. Так же
  можно собрать провайдера самому: `createOpenRouterProvider({ baseURL, headers, dataCollection })`,
  `createDeepSeekProvider`, `createFireworksProvider`, `createTogetherProvider` и `addProviders: […]`.
- **Ключ провайдера уходит как обычно** (`Authorization`), заголовки прокси добавляются к каждому запросу.
  Значения заголовков — секреты: они вычищаются из ошибок и журналов, как ключи.
- **Прокси должен пробрасывать заголовок ответа `x-generation-id`**, иначе расход OpenRouter останется оценкой
  (`proxy.example.com` его пробрасывает).
- **Ошибки настройки видны сразу.** Адрес не `http(s)://`, пустой заголовок (не задан `PROXY_TOKEN`), значение
  заголовка короче 8 знаков, заголовок `Authorization` (ключ провайдера задаётся отдельно), провайдер, которого нет
  в каталоге или собранный своей копией (`{ ...openrouterProvider, createLanguageModel }`), — ошибка при сборке каталога.
- **Часовой пояс** (`timeZone` у лимитов) — одна настройка для всего, где время режется на сутки и месяцы. По нему
  считаются сутки и месяцы лимитов, дата обновления на экране и сегодняшняя дата агента, если браузер человека свой
  пояс не прислал. `agent.timeZone` задавать не нужно; если задан, он должен совпадать с поясом лимитов (другое имя того же пояса,
  например `Asia/Calcutta` и `Asia/Kolkata`, — совпадение). Без
  `timeZone` всё как раньше: лимиты по UTC, дата агента по поясу сервера. Пояс не из базы IANA — ошибка при старте.
- **Голос через прокси**: чистка текста — `polish: { provider: "together", baseUrl, headers }`, звуки человека в
  голосовом режиме — `sounds: { baseUrl, headers }` (раздел «Голосовой ввод» и README голосовых пакетов).

**Выбор модели в чате.** В поле ввода есть меню моделей (провайдер → модель) и рядом выбор уровня рассуждений;
уровни зависят от модели: у DeepSeek «Выкл/Вкл», у GLM от «Низкий», у GPT и Gemini несколько уровней. Выбор
запоминается в чате, а последний выбор человека — ещё и за ним самим: новый чат открывается на модели, провайдере
и уровне, которые человек выбрал в последний раз, а не на `defaultChoice`. Если той модели больше нет в каталоге
или у её провайдера нет ключа, новый чат открывается на `defaultChoice`; уровень, которого у модели нет, заменяется
её уровнем по умолчанию. Выбор одного человека другой не видит, старые чаты с сообщениями не меняются, а пустой чат при открытии переходит на последний выбор. Запоминается именно последний выбор, в том числе сделанный в старом чате; при двух открытых вкладках побеждает позже пришедший запрос. Выбор хранится по человеку и общий для всех обработчиков на одной базе; недоступная модель заменяется моделью по умолчанию. Работает у встроенных
хранилищ (память, SQLite, PostgreSQL), у своего хранилища — если в нём есть `getUserModelChoice` и
`saveUserModelChoice`; без них всё как раньше. Модель можно сменить посреди чата: рассуждения прежней модели в запрос новой не уходят, но
в базе и на экране остаются. Чат, у которого сохранённой модели больше нет в каталоге, открывается на выборе по
умолчанию, сообщения не меняются. Ничего подключать не нужно: меню приходит с `AgentChat` и скином Тандема.

## 4. Сервер

```ts
// server/index.ts
import { serve } from "@hono/node-server";
import { standardCatalog } from "@ykurilov/agent-chat-core";
import { createChatHandler } from "@ykurilov/agent-chat-server";
import { mountChat } from "@ykurilov/agent-chat-server/hono";
import { createSqliteChatStorage } from "@ykurilov/agent-chat-storage-sqlite";
import { tool } from "ai";
import { Hono } from "hono";
import { z } from "zod";

process.loadEnvFile(".env"); // ключи провайдеров → process.env

const storage = createSqliteChatStorage({ filePath: "chat.sqlite" }); // таблицы создаются сами

const chat = createChatHandler({
  basePath: "/api/chat",
  storage,

  // Кто делает запрос. Модуль вход не реализует: берите пользователя из своей сессии.
  // null → 401. Чужой чат модуль сам отдаёт как 404, не раскрывая, что он существует.
  resolveUser: async (request) => {
    const userId = await currentUserId(request); // ваша функция
    return userId ? { id: userId } : null;
  },

  // Чем отвечать в новом чате; дальше пользователь выбирает сам в поле ввода.
  // Не задано — первая модель каталога у первого провайдера с ключом.
  defaultChoice: { modelId: "deepseek-4.1-flash", providerId: "deepseek" },

  catalog: standardCatalog,

  agent: {
    // Постоянный текст: без даты, времени и имени пользователя. Тогда начало запроса
    // одинаково от хода к ходу и провайдер берёт его из кэша — это в разы дешевле.
    instructions: "Ты — помощник магазина. Отвечай по-русски, коротко и по делу.",
    tools: {
      order_status: tool({
        description: "Статус заказа по номеру",
        inputSchema: z.object({ orderId: z.string() }),
        execute: async ({ orderId }) => findOrderStatus(orderId), // ваша функция
      }),
    },
    // Сколько раз подряд агент может звать инструменты; по умолчанию 20. Последний шаг — итог без инструментов:
    // вызов вопреки запрету не выполняется, afterTurn видит stepLimit: true.
    maxSteps: 20,
  },
});

const app = new Hono();
mountChat(app, chat); // все адреса /api/chat и /api/chat/*
// Заголовки и cookie, которые ваши app.use(...) выставили до next(), в ответ чата попадают.

// Брошенные ответы (сервер упал или выключился посреди ответа) помечаются «прерванными». До приёма запросов.
// Дальше сервер сам проверяет их раз в 5 с, до chat.flush(). После падения ответ ещё 15–20 с выглядит идущим.
// Копия сервера на этой базе одна — { soleServer: true }: оборванные прошлым запуском ответы прерываются сразу
// (только здесь, при старте; условия — «Одна копия сервера» ниже).
await chat.recoverInterruptedAnswers();

const server = serve({ fetch: app.fetch, port: 3000 });

// Штатная остановка: перестать принимать запросы → flush → закрыть хранилище → выйти.
// flush ждёт идущие ответы до waitForAnswersMs, не успевшие закрывает как «Стоп» (написанное цело), ждёт afterTurn.
async function shutdown() {
  server.close();
  await chat.flush({ waitForAnswersMs: 20_000 });
  storage.close();
  process.exit(0);
}
process.on("SIGINT", shutdown);
process.on("SIGTERM", shutdown);
```

Что стоит знать:

- **Модели.** `standardCatalog` — пять моделей и четыре провайдера (таблица в шаге 3). Список для меню собирается
  из каталога и ключей на сервере. Приложение правит каталог одной функцией:

  ```ts
  import { extendCatalog, standardCatalog } from "@ykurilov/agent-chat-core";

  const catalog = extendCatalog(standardCatalog, {
    removeProviders: ["together"], // провайдер уходит; модель, у которой не осталось провайдеров, уходит вместе с ним
    removeModels: ["glm-5.3-flash"], // модель уходит у всех провайдеров
    addProviders: [myProvider], // свой провайдер: id, displayName, apiKeyEnv, createLanguageModel, requestOptions
    addModels: [myModelProfile], // своя модель со своим профилем (уровни рассуждений, окно, картинки)
    pinModelVersions: { "gpt-6-luna": { openrouter: "openai/gpt-6-luna-2026-09-30" } }, // закрепить версию у провайдера
  });
  ```

  Порядок правок: убрать → добавить → закрепить. Несогласованная правка (убрать провайдера, которого нет;
  закрепить версию модели у провайдера, который её не отдаёт) — ошибка при создании каталога, а не при первом
  ответе. Новая версия модели приходит только с новой версией пакета: `standardCatalog` сам не меняется.
  Подробности — в [contracts/model-profile.md](contracts/models-and-picker/model-profile.md).
- **Потолок вывода и бюджет рассуждений.** В профиле модели `maxOutputTokens` — сколько токенов модель может выдать
  за один запрос (у Claude Haiku 5.5 — 128 000). Он уходит в каждом запросе, если приложение не задало свой предел
  `agent.maxOutputTokens`. Без него OpenRouter берёт свой предел по умолчанию, и на «Максимуме» рассуждения съедали
  его целиком: ответа нет, ход «оборван по длине».

  Ответу всегда остаётся запас: пятая часть предела, но не меньше 16 тысяч (у малого предела — половина). Как его
  оставить, зависит от модели:

  - `reasoning.tokenBudget: true` — модель держит жёсткий бюджет рассуждений (Claude до 4.6, Gemini 2.5). Уровень уходит
    числом: `reasoning.max_tokens` у OpenRouter.
  - `reasoning.effortShareOfOutput: true` — сила рассуждений у модели — доля предела. У Claude через OpenRouter
    `xhigh` — 95 %, `high` — 80 %, `medium` — 50 %, `low` — 20 %, `minimal` — 10 %. Уровень уходит самой глубокой
    силой, после которой ответу остаётся запас. Поэтому «Максимум» у таких моделей — не «95 % на размышления», а
    самый глубокий уровень с запасом на ответ. Стоит у Claude Haiku 5.5.
  - Ни того, ни другого (GPT, Gemini 3, GLM, DeepSeek) — сила уходит как раньше: эти модели решают сами, долю предела
    им не задают.

  | Предел вывода | Максимум | Высокий | Средний | Низкий | Минимум |
  |---|---|---|---|---|---|
  | 128 000, бюджет | 102 400 | 81 920 | 51 200 | 20 480 | 10 240 |
  | 128 000, доля | `high` | `high` | `medium` | `low` | `minimal` |
  | 64 000, бюджет | 48 000 | 38 400 | 24 000 | 9 600 | 4 800 |
  | 64 000 и меньше, доля | `medium` | `medium` | `medium` | `low` | `minimal` |
  | 16 000, бюджет | 8 000 | 6 400 | 4 000 | 1 600 | 1 024 |

  Ставьте `tokenBudget` только после живой проверки: Claude семейства 5 (и Haiku 5.5) бюджет не держит — OpenRouter
  переводит число в силу, 2000 дало 6082 токена рассуждений. Долю предела Haiku 5.5 тоже держит нестрого: на `high` с
  пределом 8 000 он рассуждал все 8 000. Понижение уровня делает рассуждения мельче, а главная защита — большой предел
  (128 000), до которого модель почти никогда не дорассуждает. Малый `agent.maxOutputTokens` такую модель всё равно
  может оборвать — давайте с запасом.

  Кэш: уровень и числа зависят только от выбранного уровня и предела, запрос от хода к ходу байт в байт тот же. Предел
  вывода в кэш Anthropic не входит. Смена уровня меняет параметры рассуждений: у Anthropic это может сбросить кэш
  переписки, как и раньше; включение и выключение рассуждений сбрасывает его всегда. OpenRouter заранее проверяет,
  хватит ли денег на весь предел вывода: на почти пустом счёте большой предел даёт ошибку 402 раньше, чем малый.
- **OpenRouter без хранения запросов.** По умолчанию хранение — по настройкам вашего аккаунта OpenRouter. Запретить
  его в коде: `extendCatalog(standardCatalog, { addProviders: [createOpenRouterProvider({ dataCollection: "deny" })] })`.
  Тогда запрос уходит только тем хозяевам модели, которые не хранят запросы; `zeroDataRetention: true` — ещё строже,
  без хранения даже ненадолго. Моделей, доступных так, меньше.
- **OpenRouter: потолок цены, сортировка, липкость, срок кэша.** Там же, в `createOpenRouterProvider`:
  - `maxPrice: { completionPerMillion: 1.3 }` — хозяева модели дороже 1,3 $ за миллион выходных токенов запрос не получат
    (ещё `promptPerMillion`, `requestUsd`, `imageUsd`). Нет хозяина дешевле — запрос не пройдёт;
  - `sort: "price" | "latency"` — выбирать хозяина по цене или по задержке; по умолчанию по скорости, `false` — как решит OpenRouter;
  - `stickyProvider: false` — не закреплять чат за одним хозяином. По умолчанию закрепляет (заголовок `x-session-id`),
    чтобы кэш модели не терялся.
  - Срок кэша (часовой кэш Anthropic, Claude через OpenRouter). Метки кэша с `ttl: "1h"` держат кэш час, без срока — 5 минут.
    Запись в часовой кэш дороже (у Anthropic 2× цены входа вместо 1.25×), чтение стоит столько же; выгодно, когда между
    ходами чата больше 5 минут. Срок один на все метки запроса (инструкция, последнее сообщение, конец шага): Anthropic не
    принимает часовую метку после пятиминутной. Кто главнее, сверху вниз:
    1. `cacheTtlByModel: { "claude-haiku-5.5": "5m" }` — срок отдельной модели;
    2. `cacheTtl: "1h"` или `"5m"` — срок всех моделей провайдера;
    3. `cacheTtl` в профиле модели — у Claude Haiku 5.5 в `standardCatalog` это `"1h"`;
    4. иначе 5 минут: метки без срока, запрос как раньше.
    Цена записи — по сроку: в `pricing` профиля `cacheWritePerMillion` (5 минут) и `cacheWrite1hPerMillion` (час). Каталог
    сам отмечает в цене, что модель пишет кэш на час (`cacheWriteTtl: "1h"`), и лимиты расходов считают запись по часовой
    цене. Часовой цены нет (у цены или у её ступени) — запись идёт по `cacheWritePerMillion`: так приложения до 0.43 клали туда
    часовую цену, и их расход не меняется. Об этом служба чата пишет предупреждение в журнал при запуске (`[цена кэша] …`;
    тот же список — `cachePriceWarnings(catalog)`), например когда `cacheTtl: "1h"` сделал часовой модель без часовой цены.
    Неверное значение — ошибка при создании провайдера или сборке каталога. Опечатку в id модели в `cacheTtlByModel`
    SDK не ловит: такой срок просто не сработает.
  - `ignore: ["venice"]` — этим хозяевам модели запрос не уходит. Складывается с запретом из профиля модели: у моделей
    стандартного набора там хозяева, которые не видят картинку в результате инструмента (`providerOptions.openrouter.provider.ignore`).
    Потолок цены, сортировка и свой запрет при этом сохраняются.
- **Несколько маршрутов OpenRouter.** Маршрут — отдельный провайдер каталога со своим `id` и выбором хозяев модели:
  ```ts
  addProviders: [
    createOpenRouterProvider({ id: "or-deepseek", displayName: "OpenRouter → DeepSeek", only: ["deepseek"], allowFallbacks: false }),
    createOpenRouterProvider({ id: "or-fireworks", displayName: "OpenRouter → Fireworks", only: ["fireworks"], allowFallbacks: false }),
  ]
  ```
  `only` — только эти хозяева, `order` — порядок хозяев, `allowFallbacks: false` — OpenRouter сам к другим хозяевам не
  уходит, `requireParameters: true` — только хозяева, которые умеют все параметры запроса. Маршрут обслуживает те же
  модели, что провайдер `openrouter`: id моделей, цены и закреплённые версии переходят на него сами. Своя запись модели
  для маршрута главнее. Провайдер `openrouter` должен остаться в каталоге. Маршруты попадают и в порядок запасных
  провайдеров по умолчанию. С `order` сортировка по скорости по умолчанию не ставится, чтобы не переставить хозяев.
  Явный `sort` вместе с `order` уходит как есть, но что из них главнее, OpenRouter не обещает. Один хозяин и в `only`,
  и в `ignore` — ошибка при создании. Все хозяева `only` запрещены профилем модели — ошибка запроса с объяснением.
- **Модель для нового чата.** `defaultChoice: { modelId, providerId, reasoning? }`. Если выбор не подходит
  (нет модели, провайдер её не отдаёт), обработчик пишет в журнал и берёт первую доступную модель.
  Это выбор для человека, который ещё ничего не выбирал; после первого выбора новые чаты идут на его
  последнем выборе (см. «Выбор модели в чате»).
- **Список для меню** отдаёт `GET /api/chat/models`, выбор чата записывает `PUT /api/chat/:id/model`
  ([contracts/http-api.md](contracts/models-and-picker/http-api.md)). Ключей и имён переменных в ответе нет.
- **Инструменты** — обычные инструменты AI SDK. Если `execute` бросает ошибку, модель видит
  её текст и продолжает ответ, а собеседник видит строку вызова «ошибка». Опасный инструмент можно пометить так, что
  без разрешения человека он не выполняется — раздел «Подтверждение опасных действий» ниже.
- **Сжатие истории.** Длинная переписка сжимается сама: когда модель видит больше 200 тысяч токенов, всё старое, кроме
  свежих ~20 тысяч, заменяется короткой сводкой. Настраивать ничего не надо; подробности и настройки — в разделе
  «Сжатие истории и поиск по старой переписке» ниже.
- **Ответ живёт на сервере.** Закрытая вкладка не останавливает ответ: он дописывается
  в базу, и при следующем открытии клиент подключается к нему с текущего места.
  Реестр идущих ответов живёт в памяти процесса, поэтому запросы одного чата должны попадать на одну копию сервера
  (несколько копий на одной базе — в разделе «Какое хранилище выбрать»).
- **Запросы с чужих страниц.** Браузер прикладывает куки человека и к запросу, который отправила чужая страница.
  Поэтому всё, что меняет данные (сообщения, новый чат, память, удаление), обработчик принимает только со своего
  сайта: чужая страница получает 403 `forbidden_origin`, а в журнале — строка с её адресом. Запросы не из браузера
  (сервер, curl) проходят. Чат встроен на чужой сайт и шлёт запросы прямо оттуда (например, со страницы GetCourse) —
  впишите эту страницу: `allowedOrigins: ["https://school.getcourse.ru"]`, а CORS и куки с `SameSite=None; Secure`
  настройте в своём приложении. Если чужой сайт показывает вашу страницу во фрейме (`iframe`), список не нужен:
  запросы идут с вашего сайта. Но куки входа тогда тоже должны быть `SameSite=None; Secure`.
- **Фронт и API на разных адресах.** Страница на `https://app.example.com`, а API на `https://api.example.com`
  (или на другом порту) — для сервера это чужая страница: чтение работает, а отправка сообщения получает 403.
  Клиент показывает «Сервер чата не принимает сообщения с этой страницы», а в режиме разработки пишет в консоль,
  какой адрес вписать. Впишите адрес фронта: `allowedOrigins: ["https://app.example.com"]`. Все свои поддомены
  разом — шаблоном `allowedOrigins: ["https://*.example.com"]`: он пускает `app.example.com` и `a.b.example.com`,
  но не сам `example.com` и не `evil-example.com`; схема и порт должны совпасть. Шаблон вроде `https://*.com` или `https://*.com.` —
  ошибка при запуске. Общие суффиксы вроде `*.co.uk` или `*.github.io` проверка не распознаёт и пропустит: в шаблон
  вписывайте только свой домен. В демо адрес фронта задаёт `DEMO_ALLOWED_ORIGINS` (например, `http://localhost:5627`), если
  открыть его без пересылки `/api` через Vite.
- **За прокси (nginx).** Старые браузеры и страницы по `http://` не присылают `Sec-Fetch-Site`. Тогда сервер сверяет
  `Origin` страницы со своим именем из `Host` или `X-Forwarded-Host`. Прокси, который подменяет `Host` на адрес
  приложения (`127.0.0.1:3000`), ломает сверку: запись получает 403, а в журнале — «Origin не совпал с Host…».
  Передайте имя сайта дальше:

  ```nginx
  location /api/ {
    proxy_pass http://127.0.0.1:3000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Host $host;
    # Голос идёт по WebSocket
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    # Ответ модели идёт потоком
    proxy_buffering off;
  }
  ```
- **Одновременные ответы.** У одного человека одновременно идут не больше трёх ответов во всех его чатах:
  четвёртый получает 429 `too_many_turns`, а клиент просит дождаться. Предел — `maxConcurrentTurnsPerUser`
  (`Infinity` — без предела). С лимитом расходов это значит: перерасход не больше трёх ходов сверх лимита.
- **Размер запроса.** Тело запроса больше 1 МиБ не читается: ответ 413 `too_large`. Самое длинное сообщение
  (100 000 знаков) помещается с запасом.
- **Своё хранилище.** Нужна другая база — реализуйте интерфейс `ChatStorage` из ядра.
  Проверить реализацию можно общими тестами `describeChatStorageContract` из
  `@ykurilov/agent-chat-core/storage-contract` (нужен `vitest`). Их же проходят память, SQLite и PostgreSQL.
  Для сжатия в интерфейсе три метода: `insertCompaction` (записать отметку), `listCompactions` (отдать отметки чата по порядку добавления)
  и `listMessageLinks` (id, родитель и время создания сообщений чата, в том же порядке, что у `listMessages`, но без текстов и выводов инструментов).
  Для подтверждения действий ещё два: `updateAwaitingMessage(messageId, patch)` (переписать части ответа, который ждёт решения, и при продолжении вернуть ему статус «пишется») и `getMessage(messageId)` (сообщение по номеру или `null`).
  Для веток ответов два метода: `insertBranchSelection` (дописать запись «выбран этот вариант») и `listBranchSelections` (отдать записи чата по порядку добавления).
  Журнал расхода: `sumUsage(filter)` принимает поля `ownerId`, `chatId`, `messageId`, `source` и `since`; свои хранилища обязаны учитывать все (общие тесты это проверяют).
  Для нескольких копий сервера — знак жизни идущего ответа: поле записи `alive` (`"now"` — время ставит само хранилище,
  `"released"` — ответ брошен штатной остановкой), лёгкая отметка `markAnswerAlive(messageId)` и
  `listSilentAnswerIds({ silentForMs, chatId? })` (идущие ответы без отметки дольше `silentForMs`). Без
  `listSilentAnswerIds` служба при старте прерывает все идущие ответы и пишет предупреждение в журнал: так можно только
  с одной копией сервера.
- **Без Hono.** `chat.fetch(request)` принимает стандартный `Request` и отдаёт `Response`.
  Его можно подключить к любому серверу, который умеет эти объекты. Для Next.js есть готовое подключение
  (раздел «Next.js» ниже).

### Какое хранилище выбрать

| Хранилище | Когда брать | Пакет |
|---|---|---|
| Память | тесты вашего приложения: ничего не пишется на диск, после остановки всё пропадает | уже в ядре: `createInMemoryChatStorage` |
| SQLite | один сервер, переписка в одном файле, отдельная база не нужна | `@ykurilov/agent-chat-storage-sqlite` |
| PostgreSQL | база уже есть, или серверов будет несколько, или нужны резервные копии базы | `@ykurilov/agent-chat-storage-postgres` |

Три способа создать хранилище. Всё остальное в `createChatHandler` одинаково:

```ts
// Память (для тестов)
import { createInMemoryChatStorage } from "@ykurilov/agent-chat-core";
const storage = createInMemoryChatStorage();

// SQLite
import { createSqliteChatStorage } from "@ykurilov/agent-chat-storage-sqlite";
const storage = createSqliteChatStorage({ filePath: "chat.sqlite" });
// при остановке: storage.close()

// PostgreSQL. Создание асинхронное: при запуске оно подключается к базе и применяет миграции
import { createPostgresChatStorage } from "@ykurilov/agent-chat-storage-postgres";
const storage = await createPostgresChatStorage({ connectionString: process.env.DATABASE_URL! });
// при остановке: await chat.flush(); await storage.close()
```

О PostgreSQL:

- **Адрес базы** — переменная окружения (например, `DATABASE_URL`), в код и в репозиторий он не попадает.
  Если база недоступна, `createPostgresChatStorage` бросает понятную ошибку без пароля.
- **Таблицы лежат в отдельной схеме `agent_chat`.** Ваши таблицы `chats` и `messages`, если они есть, чат не трогает.
  Миграции применяются сами при создании хранилища; два сервера, стартующих одновременно, друг другу не мешают.
  Нужен пользователь базы с правом создавать схему и таблицы.
- **Порядок остановки.** Сначала `await chat.flush({ waitForAnswersMs })`, потом `await storage.close()`. `flush` ждёт
  идущие ответы до срока (по умолчанию 0), не успевшие закрывает как «Стоп» с записью и возвращается, когда всё записано и
  `afterTurn` закончен. Ход, который после остановки 10 с не может записать итог (база висит), `flush` не ждёт: строка в
  журнал, ответ прервёт восстановление при следующем старте. Закрытие в обратном порядке потеряет хвост ответа.
- **Несколько копий сервера на одной базе.** Можно, и обновление с перекрытием (новая копия стартует, пока старая
  отвечает) безопасно. Идущий ответ раз в 5 с отмечает в базе «жив» (колонка `alive_at`). Прерванным считается
  только ответ без отметки дольше 15 с: его копия упала. Такие ответы ищет `recoverInterruptedAnswers` при старте и
  потом каждая копия раз в 5 с. Начатый вызов инструмента пишется в базу до выполнения: упади сервер посреди
  инструмента, восстановленный ответ показывает вызов прерванным, а «Повторить» продолжает с него, не запуская
  инструмент второй раз сам. Чужие живые ответы никто не трогает. Штатная остановка (`flush`) закрывает свои ответы
  как «Стоп»; если конечная запись не прошла, ответ помечен брошенным, и его прерывают сразу. После падения ответ ещё 15–20 с выглядит идущим. Экран человека в это время
  сам перечитывает историю раз в 3 с и показывает «Ответ прерван» с «Повторить», как только сервер его прервёт;
  обновлять страницу не нужно. Так и с одним сервером.
- **Одна копия сервера.** `recoverInterruptedAnswers({ soleServer: true })`: при старте все идущие ответы, кроме ответов
  этого процесса, прерываются сразу, а не через 15–20 с. Всё остальное как обычно: написанное цело, незаписанный расход —
  в журнал, хук итога и фон. Регулярная проверка тоже запускается. Условия:
  - только один раз при старте процесса, до приёма запросов. Вызов позже прервёт ход, который как раз запускается;
  - не с несколькими копиями на одной базе: новая копия прервёт живые ответы соседей (и при обновлении с перекрытием);
  - не там, где в одном процессе создаётся несколько служб чата на одной базе. Так бывает в dev-режиме Next.js: горячая
    перезагрузка создаёт обработчик заново, и новый прервёт ответы прежнего. Там вызывайте без опции.
- **Переход на эту версию — один раз без перекрытия.** Старые копии не отмечают «жив», и новая копия раз в 5 с
  прерывала бы их ответы старше 15 с. Поэтому при переходе сначала остановите все старые копии, потом запускайте
  новые. Дальше обновления с перекрытием безопасны.
- **Часы копий.** Время отметки «жив» и сравнение с ним берутся из часов самой базы PostgreSQL, так что часы машин
  с копиями сервера могут расходиться. SQLite живёт на одной машине с сервером, ему хватает её часов.
- **Ответ, прерванный другой копией.** Если копия сочла живой ответ соседа брошенным (например, сосед завис дольше
  15 с), сосед, узнав об этом при следующей записи, сам останавливает ход. Человек видит «прерван», расход не
  задваивается.
- **Запросы одного чата держите на одной копии** (липкая привязка по человеку или чату у балансировщика). Поток идущего
  ответа, «Стоп», ожидание браузерных инструментов и сжатие живут в памяти копии. Запрос на другую копию не увидит
  идущий ответ: «Стоп» не сработает, а поток не подключится. Пределы одновременных ходов и загрузок каждая копия
  считает сама. Ещё одно следствие: экран, чей запрос истории попал не на ту копию, через 30 с сам покажет «прерван»,
  хотя ответ на своей копии идёт. «Повторить» тогда откажет, пока ответ не кончится, а его итог человек увидит после
  обновления страницы.
- Свои настройки: `poolSize` (соединений в пуле, по умолчанию 10) и `logError` (куда писать ошибки соединений).

## Next.js

Подключение к Next.js (App Router) — один файл маршрута. Пакет `next` серверной части не нужен: он не
импортируется, версию Next выбираете вы. Проверено на Next 16 и React 19.

```ts
// lib/chat.ts — обработчик один на процесс; всё, что в шаге 4 после `createChatHandler`, здесь так же
import { createChatHandler } from "@ykurilov/agent-chat-server";
import { standardCatalog } from "@ykurilov/agent-chat-core";

export const chatHandler = createChatHandler({
  basePath: "/api/chat", // совпадает с адресом файла маршрута
  storage, // любое хранилище из раздела выше
  resolveUser: async (request) => currentUser(request), // ваша сессия; null → 401
  defaultChoice: { modelId: "deepseek-4.1-flash", providerId: "deepseek" },
  catalog: standardCatalog,
  agent: { instructions: "Ты — помощник магазина. Отвечай по-русски, коротко и по делу." },
});

// Брошенные ответы (сервер упал посреди ответа) помечаются «прерванными»: как в шаге 4, один раз при старте процесса.
void chatHandler.recoverInterruptedAnswers();
```

```ts
// app/api/chat/[[...path]]/route.ts
import { createNextRouteHandlers } from "@ykurilov/agent-chat-server/next";
import { chatHandler } from "@/lib/chat";

export const { GET, POST, PUT, PATCH, DELETE, OPTIONS, HEAD } = createNextRouteHandlers(chatHandler);
export const dynamic = "force-dynamic"; // ответы чата не кэшируются
export const runtime = "nodejs"; // хранилища работают только в Node.js, не в Edge
```

Клиент — тот же `AgentChat` (шаг 6), в клиентском компоненте (`"use client"`).

- **`basePath`.** Путь файла маршрута (`app/api/chat/[[...path]]`) и `basePath` обработчика должны совпадать.
  Если в `next.config` задан свой `basePath` приложения, укажите его и в `createChatHandler` (`/app/api/chat`) и в `api` у `AgentChat`.
- **Пользователь** берётся из вашей сессии внутри `resolveUser(request)`, как в шаге 4.
- **Нужен долгоживущий сервер** (`next start`, Docker, VPS), а не serverless. Ответ агента живёт в памяти процесса
  и после ответа функции не продолжится; ещё нужен один и тот же процесс между запросом «отправить» и «подключиться к ответу».
- **`next dev`** перезагружает модули при правках, а вместе с ними и обработчик: держите его в `globalThis`,
  как в `apps/next-example/lib/chat.ts`, иначе идущий ответ при правке потеряется (для хранилища в памяти — и вся переписка).
- Завершение сервера (`flush` и `close`) в Next обычно делают в обработчике сигналов вашего запуска (`SIGTERM`).
- Рабочий пример с проверкой потока, остановки и переподключения — `apps/next-example` (`pnpm test:next` в репозитории SDK).

Адреса, коды ответов и формат потока описаны в
[contracts/http-api.md](contracts/basic-agent-dialog/http-api.md); пинги в потоках —
в [дополнении к нему](contracts/fast-feed-and-liveness/http-api.md).

## 5. Скин Тандема

Скин — обычный пакет. Вместе с ним ставится дизайн-система Тандем (`@ykurilov/tandem-ui`); приложению её нужно
поставить и самому, под именем `@tandem/ui`: из CSS-файла приложения пакет скина не виден.

```bash
pnpm add @ykurilov/agent-chat-skin-tandem "@tandem/ui@npm:@ykurilov/tandem-ui@^0.7.0"
```

(имя `@tandem/ui` — псевдоним: пакет тот же `@ykurilov/tandem-ui`, скин использует то же имя, поэтому он один на приложение.)
Tailwind должен видеть классы скина и Тандема. В главном CSS-файле (пути даны от файла `src/styles.css` до
корня проекта, поправьте под своё место):

```css
@import "tailwindcss";
@import "@tandem/ui/styles.css";
@source "../node_modules/@tandem/ui/dist";
@source "../node_modules/@ykurilov/agent-chat-skin-tandem/dist";
```

`@import "@tandem/ui/styles.css"` подключает стили и шрифты Тандема; без него чат будет без цветов и шрифтов.
Компоненты Тандема и скина лежат в `dist`: с `@source` на другие папки пакета классы не попадут в CSS, и чат останется
без пузырей и кнопок.

**Цвета вокруг чата.** Свои элементы страницы красьте переменными Тандема: `--canvas` (фон страницы), `--surface`,
`--foreground`, `--border`. Переменной `--background` в Тандеме нет: `var(--background)` не даст цвета, и фон окажется
прозрачным. Тёмная тема включается классом `dark` на корневом элементе (`<html class="dark">`).

Если скин нужно поправить целиком, скопируйте исходники из репозитория `skins/tandem/src` в свой проект и
подключайте вместо пакета (тогда `@source` укажите на свою папку). Чаще достаточно заменить отдельный компонент:
`{ ...tandemSkin, ToolCallRow: MyToolCallRow }` (шаг 7).

## 6. Клиент

```tsx
// src/chat-page.tsx
import { AgentChat } from "@ykurilov/agent-chat-react";
import { useEffect, useState } from "react";
import { tandemSkin } from "@ykurilov/agent-chat-skin-tandem";

export function ChatPage() {
  const [chatId, setChatId] = useState<string | null>(null);

  useEffect(() => {
    // Новый чат: POST /api/chat → 201 { id }. Id держите у себя: в адресе страницы или в базе.
    void fetch("/api/chat", { method: "POST" })
      .then((response) => response.json() as Promise<{ id: string }>)
      .then(({ id }) => setChatId(id));
  }, []);

  if (!chatId) return null;
  return (
    <div style={{ height: "100dvh" }}>
      <AgentChat api="/api/chat" chatId={chatId} skin={tandemSkin} />
    </div>
  );
}
```

- В режиме разработки React (`StrictMode`) эффект срабатывает дважды, и пример создаст два
  чата. В настоящем приложении id обычно приходит из адреса страницы или из вашей базы.
- `AgentChat` занимает всю высоту родителя: лента прокручивается, поле ввода внизу.
- Сессия пользователя (cookie) уходит на сервер вместе с запросами чата: адреса чата должны
  быть на том же домене, что и страница. Для разработки проксируйте их в Vite:

  ```ts
  // vite.config.ts
  export default defineConfig({ server: { proxy: { "/api": "http://localhost:3000" } } });
  ```

  Прокси Vite ведёт себя иначе, чем прямое соединение, и это видно при сбоях:
  - Сервер не запущен или остановился — прокси отвечает браузеру `500`, а не обрывает соединение. Чат считает обрывом связи
    только сетевую ошибку, поэтому вместо «Нет связи с сервером» покажет «Что-то пошло не так». Это особенность
    режима разработки: в боевом приложении, где страница и адреса чата отдаются одним сервером, всё работает как описано.
  - Сервер упал посреди ответа — прокси держит соединение с браузером открытым, и вкладка молча ждёт. Чтобы вкладка
    увидела обрыв, как без прокси, рвите и её соединение:

    ```ts
    proxy: {
      "/api": {
        target: "http://localhost:3000",
        configure: (proxy) => {
          proxy.on("proxyRes", (proxyRes, _request, response) => {
            proxyRes.on("close", () => {
              if (!proxyRes.complete) response.destroy();
            });
          });
        },
      },
    },
    ```

  Проверять «Нет связи» и «Переподключаемся…» удобнее на собранном клиенте, который отдаёт сам сервер, либо по шагу 10.

- **Чужой или удалённый чат.** Сервер отвечает на него `404`, и `AgentChat` сам показывает
  «Чат не найден» (компонент скина `ChatNotFound`, надпись `chatNotFound` из словаря): без ленты,
  поля ввода и «Повторить». Проверять `chatId` заранее не нужно — можно передавать его прямо
  из адреса страницы.
- **Отказ своими словами.** Ваша обёртка над сервером чата может отказать ходу (отправке, «Повторить», «Переделать»,
  правке) ответом 4xx с текстом: `{ error: "Разговор завершён" }` или `{ error: { kind, message: "…" } }`. Чат покажет
  этот текст вместо «Что-то пошло не так»: только как текст, без разметки, не длиннее 300 знаков. После 408, 425 и 429
  повтор имеет смысл, и «Повторить» остаётся. После остальных 4xx (например, 403, 409, 422) повтор получит тот же отказ:
  кнопки нет, а отправленный текст возвращается в поле. Отказ правке показывает сам редактор. Отказы самого сервера чата
  (`{ error: { kind } }` без текста), 5xx и обрыв связи выглядят как раньше: общая надпись и «Повторить». Текст отказа
  хук отдаёт в `serverRefusal`, скин получает его в `ErrorNotice.text` (договор скина версии 16).

## 7. Замена одного компонента скина

Скин — объект из тринадцати обязательных компонентов (`Layout`, `UserMessage`, `BranchSwitcher`, `MessageEditor`,
`AgentMessage`, `AgentText`, `Reasoning`, `ToolCallRow`, `ErrorNotice`, `ConnectionNotice`, `CompactionDivider`,
`ChatNotFound`, `Composer`) и необязательных (виджеты, картинки, окно просмотра и другие). Любой можно заменить своим,
не трогая остальные:

```tsx
import type { ChatSkin } from "@ykurilov/agent-chat-react";
import { useChatLabels } from "@ykurilov/agent-chat-react";

const MyToolCallRow: ChatSkin["ToolCallRow"] = ({ toolName, state, output, errorText, open, onOpenChange }) => {
  const labels = useChatLabels();
  const title = state === "running" ? labels.toolRunning(toolName) : state === "done" ? labels.toolDone(toolName) : labels.toolError(toolName);
  return (
    <div className="my-2 font-mono text-xs">
      {/* Раскрыта ли строка, помнит чат, а не компонент: раскрытое не пропадает, когда сообщение уходит за край экрана. */}
      <button type="button" aria-expanded={open} onClick={() => onOpenChange(!open)}>
        {title}
      </button>
      {open && <pre>{errorText ?? JSON.stringify(output, null, 2)}</pre>}
    </div>
  );
};

const skin = { ...tandemSkin, ToolCallRow: MyToolCallRow };
<AgentChat api="/api/chat" chatId={chatId} skin={skin} />;
```

Если объект скина собирается внутри компонента, заверните его в `useMemo`. Поведение чата
от замены не меняется: переписка, набранный текст и идущий ответ остаются на месте.

Если строке раскрытие не нужно, `open` и `onOpenChange` можно просто не использовать.
То же у `Reasoning` (рассуждения агента).

Какие данные получает каждый компонент — в типе `ChatSkin` (`packages/react/src/skin-contract.ts`) и в описаниях
последних версий договора ([версия 24](./skin-v24.md), [23](./skin-v23.md), [22](./skin-v22.md), [21](./skin-v21.md), [20](./skin-v20.md), [19](./skin-v19.md), [18](./skin-v18.md)); `Composer.voice` появился в версии 5 ([contracts/voice.md](contracts/voice-input/voice.md)); `BranchSwitcher`, `MessageEditor` и свойства сообщений для веток — в версии 6 ([contracts/branches-and-edit.md](contracts/branches-and-edit/branches-and-edit.md)); `ChatWorkspace` и `ChatList` — в версии 7 (раздел «Список чатов»); `CompactionDivider` появился в версии 4 —
[contracts/compaction-and-search.md](contracts/compaction-and-search/compaction-and-search.md). Свой `Composer` получает `modelChoice`
(меню моделей и уровни рассуждений); если он его не рисует, выбора модели в чате нет.
Живой пример — `apps/demo/src/custom-tool-call-row.tsx` и переключатель «Свой ToolCallRow» в демо.

### Свой `Layout`

Лента рисует только те сообщения, что сейчас у экрана, поэтому длинный чат открывается сразу
внизу. Прокруткой управляет чат, а не скин. От вашего `Layout` нужно три вещи:

- Повесить `scrollRef` на элемент, который прокручивается (`overflow-y: auto`), и положить
  `feed` внутрь него. Отступы вокруг ленты можно: чат сам замеряет, где лента начинается.
- Обернуть `feed` в элемент с `role="log"` и `aria-live="off"`. Старые сообщения при прокрутке
  подгружаются заново, и диктор не должен зачитывать их вслух.
- Положить `announcement` в скрытый от глаз элемент с `aria-live="polite"`. Так экранный диктор
  слышит только новый законченный ответ.

Промежуток между сообщениями делайте внутренним отступом (`padding`) корня своих `UserMessage` и
`AgentMessage`, а не `gap` у контейнера и не `margin`: иначе лента считает высоты неверно и
прыгает. Ещё одно правило для своего скина: не ставьте стили, которые зависят от того, последний
ли элемент (`:last-child`, `:has()`), и не добавляйте элементы рядом с пузырём, когда ответ
дописан. Иначе браузер пересчитывает стили всего длинного ответа разом и чат подвисает.
Полный список правил — в [contracts/skin.md](contracts/fast-feed-and-liveness/skin.md).

## 8. Связь с сервером

Пока агент пишет, сервер шлёт в потоке тихие «пинги» — признаки жизни. Настройка
`heartbeatIntervalMs` у `createChatHandler` (по умолчанию 10 с; меньше 1 с — ошибка при запуске).
Если вкладка 30 с не получает ни байта, она считает связь зависшей и сама переподключается,
показывая «Переподключаемся…». Ответ при этом не повторяется и не теряется: вкладка снова
подключается к тому же ответу с текущего места. Когда три попытки подряд (сразу, через 2 и через
5 секунд) не удались, чат показывает «Нет связи с сервером» и кнопку «Повторить». Когда сеть
вернётся, вкладка подключится сама. Запросы без потока (загрузка истории, «стоп») ждут не дольше
10 с.

```tsx
<AgentChat
  api="/api/chat"
  chatId={chatId}
  skin={tandemSkin}
  liveness={{ silenceTimeoutMs: 30_000, reconnectDelaysMs: [0, 2000, 5000], requestTimeoutMs: 10_000 }}
/>
```

Это значения по умолчанию, обычно их не трогают. Меняйте, если:

- **Прокси между браузером и сервером рвёт тихие соединения быстрее 10 с.** Уменьшите
  `heartbeatIntervalMs` на сервере. Вкладка подстроится сама: она ждёт не меньше трёх пингов, даже
  если задать `silenceTimeoutMs` короче.
- **Модель может долго молчать между кусками.** Ничего менять не нужно: пока идут пинги,
  «тишины» нет, и минутное раздумье агента обрывом не считается.
- **Нужны другие паузы между попытками.** Поменяйте `reconnectDelaysMs`.

Своему скину нужен компонент `ConnectionNotice`: он получает `state` (`"reconnecting"` или
`"offline"`) и, у `"offline"`, обработчик `onRetry`. Подробности —
[contracts/liveness.md](contracts/fast-feed-and-liveness/liveness.md), формат пингов —
[contracts/http-api.md](contracts/fast-feed-and-liveness/http-api.md).

## 9. Надписи

Все надписи чата — в словаре. По умолчанию русский (`russianLabels`). Поменять любую:

```tsx
import { ChatLabelsProvider, russianLabels } from "@ykurilov/agent-chat-react";

<ChatLabelsProvider labels={{ ...russianLabels, retry: "Ещё раз", composerPlaceholder: "Спросите что-нибудь" }}>

```

Свои компоненты скина тоже берут надписи из `useChatLabels()`, а не пишут их в коде.
Список ключей — в [contracts/labels.md](contracts/basic-agent-dialog/labels.md); три новых ключа —
`reasoningLevels` (названия уровней рассуждений), `modelChoiceFailed` и `modelMenuFailed` — в
[дополнении 003](contracts/models-and-picker/labels.md); два новых ключа
версии 0.2.0 — `reconnecting` («Переподключаемся…») и `connectionLost` («Нет связи с сервером») —
в [дополнении к нему](contracts/fast-feed-and-liveness/labels.md). Четыре ключа голоса — `voiceStart`, `voiceStop`, `voiceConnecting`, `voiceErrors` (по видам ошибок, включая `rate_limited` и `time_limit`) — в
[contracts/voice.md](contracts/voice-input/voice.md). Если вы
написали словарь целиком, а не через `{ ...russianLabels, … }`, добавьте в него все новые ключи.

### Живая надпись «думает»

Пока модель думает и текста ответа ещё нет, фраза сменяется каждые 3–4 секунды, рядом идёт время: «Сверяю детали… 12 с»,
после минуты — «1 мин 5 с». Свои фразы — ключ `thinkingPhrases`, запись времени — `thinkingElapsed`:

```tsx
<ChatLabelsProvider labels={{ ...russianLabels, thinkingPhrases: ["Собираю экран…", "Подключаю базу…", "Проверяю сборку…"] }}>
```

Пустой набор — одна фраза `reasoningRunning` («Думает…»), время остаётся. Словарь со своей `reasoningRunning` (например, на другом
языке) без `thinkingPhrases` показывает только её, а время без `thinkingElapsed` — цифрами («0:12», «1:05»): русские слова не подмешиваются. Экранный диктор слышит одну постоянную
`reasoningRunning`, а не каждую фразу. Свой скин берёт фразу и время из хука `useThinkingStatus()`.

### Английский интерфейс

Полный английский словарь — `englishLabels`. Пакеты со своими надписями дают английские словари рядом с русскими:

```tsx
import { ChatLabelsProvider, englishLabels } from "@ykurilov/agent-chat-react";
import { createAttachmentsClient, englishAttachmentsLabels } from "@ykurilov/agent-chat-attachments/react";
import { englishWebToolTitles, withWebToolTitles } from "@ykurilov/agent-chat-web-tools/labels";

const attachments = createAttachmentsClient(englishAttachmentsLabels);

<ChatLabelsProvider labels={withWebToolTitles(englishLabels, englishWebToolTitles)}>
  <AgentChat api="/api/chat" chatId={chatId} skin={tandemSkin} attachments={attachments} />
</ChatLabelsProvider>;
```

- Названия инструментов: `withWebToolTitles(labels, englishWebToolTitles)`, `withHistorySearchTitles(labels, englishHistorySearchTitles)`,
  `withMemoryToolTitles(labels, englishMemoryToolTitles)`. Без второго аргумента — русские, как раньше. Словари памяти и
  поиска по истории есть и в корне пакета, и в `/labels` (для браузерной сборки — `/labels`):

  ```tsx
  import { englishMemoryToolTitles, withMemoryToolTitles } from "@ykurilov/agent-chat-memory";
  import { englishHistorySearchTitles, withHistorySearchTitles } from "@ykurilov/agent-chat-history-search";
  ```
- Мессенджеры и песочница: `englishMessengersLabels`, `englishSandboxLabels`, `englishChatReopenLabels`, `englishPeopleChatsLabels`.
- Свои поправки — поверх: `{ ...englishLabels, retry: "Try again" }`.

Надписи самой дизайн-системы Тандем (`@ykurilov/tandem-ui` 0.7.0 и новее: «Прикрепить», «Модель: …», «Закрыть» у диалогов,
«Таблица», «Скопировать код» и т. п.) скин Тандема берёт по языку словаря: у `englishLabels` поле `locale: "en"`, у
`russianLabels` — `"ru"`. Поле ввода, «Отправить», «Стоп» и копирование кода — из словаря чата, поэтому свои поправки
видны и в Тандеме. Другой язык: свой словарь чата с его `locale` и словарь Тандема вокруг чата —
`<TandemLabelsProvider labels={…}>` из `@tandem/ui`.

## Веб-инструменты (по желанию)

Пакет `@ykurilov/agent-chat-web-tools` даёт агенту три инструмента: `web_search` (поиск), `read_page` (текст страницы в Markdown)
и `page_screenshot` (снимок страницы). Приложению, которому они не нужны, ставить его не надо. Пример — `apps/demo/server/demo-web-tools.ts`.

```bash
pnpm add @ykurilov/agent-chat-web-tools
```

Ключ Firecrawl лежит только на сервере (`FIRECRAWL_API_KEY`), в браузер он не попадает. С российских серверов сервис
доступен через прокси: его адрес — `baseUrl`, токен прокси — в `headers`.

```ts
import { createWebTools, webToolsInstructions } from "@ykurilov/agent-chat-web-tools";
import { createFirecrawlServices } from "@ykurilov/agent-chat-web-tools/firecrawl";

const firecrawl = createFirecrawlServices({ apiKey: process.env.FIRECRAWL_API_KEY!, baseUrl: process.env.FIRECRAWL_BASE_URL });
const webTools = createWebTools(firecrawl);

createChatHandler({
  // …остальное как в шаге 4
  agent: {
    instructions: `${appInstructions}\n${webToolsInstructions}`,
    tools: (model) => ({ ...appTools, ...webTools(model) }),
  },
});
```

- `agent.tools` может быть функцией от выбранной модели (`{ profile, providerId }`): так скриншот достаётся только моделям, которые
  видят картинки. Инструкция и описания инструментов постоянны, поэтому кэш провайдера работает.
- `page_screenshot` выдаётся, только если у модели в профиле `acceptsImages: true` и её провайдер указан в `toolResultImageProviders`
  (провайдеры, через которые модель видит картинку в результате инструмента; проверено вживую). В стандартном наборе через
  OpenRouter видят все пять моделей, DeepSeek 4.1 Flash — ещё и у самого DeepSeek. Внутри OpenRouter модель обслуживают
  десятки хозяев, и несколько из них картинку не видят или отвергают запрос: такие запрещены в профиле модели
  (`providerOptions.openrouter.provider.ignore`, замер — `docs/research/openrouter-tool-images.md`). Через Fireworks и Together
  картинка в результате инструмента не проходит. Своей модели отметку добавляйте в профиль (`addModels`).
- Картинку в сообщении модель может видеть не у всех провайдеров: `acceptsImagesByProvider: { together: false }` в профиле
  главнее `acceptsImages`. Решение для пары даёт `modelAcceptsImages(profile, providerId)` из `@ykurilov/agent-chat-core`; по нему
  же меню моделей (`acceptsImages` у каждой модели внутри провайдера) и вложения.
- Поиск можно заменить (например, на Exa): реализуйте `WebSearchService` и передайте вместо `firecrawl.search`.
- **Траты в лимит расходов.** `createWebTools({ ...firecrawl, spending: { storage, pricePerCallUsd: { web_search, read_page, page_screenshot } } })`:
  каждый удачный вызов пишется расходом `web_tools` по вашей цене. Вызов, оборванный «Стопом» или сбоем после отправки запроса,
  тоже пишется: служба могла списать кредиты. Отказ до работы службы (неверный адрес, ключ, деньги, частота) не пишется. У Firecrawl поиск — 2 кредита за 10 результатов, страница и снимок —
  по 1 кредиту; цену кредита возьмите из своего тарифа. Без `spending` вызовы не учитываются.
- Подписи вызовов в ленте: `withWebToolTitles(russianLabels)` из `@ykurilov/agent-chat-web-tools/labels` (без кода Firecrawl):

  ```tsx
  <ChatLabelsProvider labels={withWebToolTitles(russianLabels)}>
    <AgentChat api="/api/chat" chatId={chatId} skin={tandemSkin} />
  </ChatLabelsProvider>
  ```

## Сжатие истории и поиск по старой переписке

**Сжатие.** Работает в ядре само, включено по умолчанию. После ответа, когда контекст (число токенов, которое назвал
провайдер) перешёл порог, в фоне модель пишет сводку: цель, решения, факты, файлы и результаты, незакрытые задачи,
где остановились. Дальше модель получает сводку и свежий хвост переписки; сами сообщения из базы не удаляются, в ленте
на месте сжатия появляется строка «История сжата», по клику открывается сводка.

- Порог, хвост и потолок сводки — настройка `compaction` обработчика (все поля необязательны; `compaction: false` выключает сжатие):

  ```ts
  createChatHandler({
    // …остальное как в шаге 4
    compaction: { thresholdTokens: 200_000, tailTokens: 20_000, summaryCeilingTokens: 20_000 },
  });
  ```

  У модели с маленьким окном порог не выше 80% окна. Вылезла сводка за потолок — она ужимается ещё раз.
- Сжимает та же модель, что отвечает; другую можно указать в `compaction.model`. Своё задание сжатия — `compaction.instruction`.
- Новое сообщение, пока идёт сжатие, ответа не ждёт: оно идёт с полным контекстом, а сводка подхватывается со следующего хода.
  Исключение — маленькое окно и контекст почти у предела: тогда ответ ждёт сжатия. «Стоп» такое ожидание обрывает сразу; начатое сжатие доделывается в фоне.
- Штатная остановка сервера (`chat.flush()`) ждёт идущие сжатия до `compaction.flushWaitMs` (по умолчанию 30 секунд). Что не успело, отменяется без записи: полусводок в базе не бывает, а вставка не падает после закрытия базы.
- Что сжатие уже идёт (и что второе запускать не надо), сервер помнит в памяти процесса — как и реестр идущих ответов. Если запросы одного чата попадают на разные копии сервера, каждая сжимает сама: возможно двойное сжатие и двойной расход токенов. Поэтому запросы чата держите на одной копии (раздел PostgreSQL).
- Префикс запроса (инструкция и инструменты) от сжатия не меняется, так что кэш модели теряется один раз, в момент сжатия.
- Экран сам спрашивает `GET /api/chat/:id/compactions` (ответ `{ compactions, compacting }`) после ответа и дальше, пока `compacting` истинно, но не дольше 12 минут. Сервер выставляет `compacting` до конца потока ответа, так что первая проверка не мажет мимо старта. Адрес лёгкий: читает связи сообщений, а не тексты.
  Свой скин рисует разделитель компонентом `CompactionDivider`; надписи — `historyCompacted` и `historyCompactedHint` в словаре.
  Кнопки «сжать сейчас» в экране нет; в ядре есть `service.compactNow(userId, chatId)`.

**Поиск по старой переписке (по желанию).** В сводке точные детали (число, адрес, слова человека) могут потеряться.
Пакет `@ykurilov/agent-chat-history-search` даёт агенту инструмент, который ищет их в оригиналах из базы. Приложению, которому
он не нужен, ставить пакет не надо. Пример — `apps/demo/server/demo-app.ts`.

```bash
pnpm add @ykurilov/agent-chat-history-search
```

```ts
import { createHistorySearchTools, historySearchInstructions } from "@ykurilov/agent-chat-history-search";

const historySearch = createHistorySearchTools({ storage });

createChatHandler({
  // …остальное как в шаге 4
  storage,
  agent: {
    instructions: `${appInstructions}\n${historySearchInstructions}`,
```

Подпись вызова в ленте — `withHistorySearchTitles(russianLabels)` из `@ykurilov/agent-chat-history-search/labels`

**Проверка на малом пороге.** В демо (`apps/demo`) порог задаёт переменная `DEMO_COMPACTION_THRESHOLD_TOKENS`
(например, `2000`): на заглушке модели два подробных ответа подряд дают разделитель, а вопрос «Какой код от сейфа?»
вызывает поиск. Сценарий — `apps/demo/e2e/compaction.spec.ts`.

## Голосовой ввод (по желанию)

Пакет `@ykurilov/agent-chat-voice` добавляет в поле ввода кнопку микрофона: слова появляются в поле по ходу речи,
человек правит и отправляет сам. Без пакета (или без свойства `voice`) кнопки нет.

Основной и рекомендуемый путь — **через ваш сервер**: браузер шлёт звук вам, вы пересылаете его в Soniox. Ключ Soniox
остаётся на сервере, работает из России, и только так доступна чистка текста моделью.

```bash
pnpm add @ykurilov/agent-chat-voice @hono/node-ws
```

```ts
// сервер (Hono на Node); главный ключ Soniox — SONIOX_API_KEY в окружении сервера
import { createNodeWebSocket } from "@hono/node-ws";
import { serve } from "@hono/node-server";
import { createVoiceRelay } from "@ykurilov/agent-chat-voice/server";
import { mountVoiceRelay } from "@ykurilov/agent-chat-voice/hono";

const { upgradeWebSocket, injectWebSocket } = createNodeWebSocket({ app });
const relay = createVoiceRelay({
  resolveUser: async (request) => currentUser(request), // тот же вход, что у чата
  polish: { provider: "together" },                     // по желанию: чистка текста; ключ TOGETHER_API_KEY
});
mountVoiceRelay(app, "/api/voice/stream", relay, upgradeWebSocket);
injectWebSocket(serve({ fetch: app.fetch, port: 8787 }));
```

```tsx
// браузер
import { createVoiceInput } from "@ykurilov/agent-chat-voice";

const voice = createVoiceInput({ api: "/api/voice", mode: "relay" });
<AgentChat api="/api/chat" chatId={chatId} skin={tandemSkin} voice={voice} />;
```

Если между браузером и сервером стоит прокси (Vite, Nginx), он должен пропускать WebSocket по пути `/api/voice/stream`
(в Vite — `ws: true` в `proxy`).

- Ключи Soniox и модели чистки в браузер не попадают.
- Язык по умолчанию русский (`languageHints`), модель `stt-rt-v5`, обе настраиваются в `createVoiceRelay`.
- По «стоп» сервер просит Soniox закрепить всё сказанное и ждёт метку конца; не ответил за 3 секунды — остаётся то, что пришло.
- Чистка (`polish`): после «стоп» модель убирает «э-э», повторы, расставляет знаки. Заменяется только надиктованное; набранное руками
  и правка во время чистки не теряются. Сбой, подозрительный ответ или тишина дольше 5 секунд — остаётся текст Soniox. Текст уходит в модель чистки (Together), ключ остаётся на сервере.
  Лимиты расходов чистку не учитывают; у неё свой лимит (`polishRateLimit`, 6 в минуту на человека).
- Со своим скином: `Composer` получает `voice` (`VoiceInputView`) — договор скина версии 5, необязательное `polishing` — признак чистки.
  Нет `voice` — кнопку не рисовать.
- Из России адрес и заголовок прокси задаются в `createVoiceRelay` (`websocketUrl`, `upstreamHeaders`).
- Route handlers Next.js WebSocket не держат: нужен отдельный маленький Node-сервер на Hono (README пакета).
- Частота ограничена по человеку (по умолчанию 10 диктовок в минуту, `rateLimit`; не больше 2 соединений сразу, `maxConnectionsPerUser`); общие лимиты приложения — ваши.
- Диктовка длится до 5 минут, потом запись останавливается с понятной надписью; отправка сообщения диктовку останавливает.
- Микрофону нужен `https` (или `localhost`). Отказ в доступе, нет связи, сервис недоступен — понятные надписи `voiceErrors`, чат работает.
- Чужая страница голос не откроет: соединение с другого сайта получает 403 ещё до подъёма сокета. Чат на чужом сайте (GetCourse) —
  `allowedOrigins: ["https://school.getcourse.ru"]` в `createVoiceRelay`, как у чата.
- **Напрямую (не рекомендуется).** `createVoiceHandler` выдаёт браузеру временный ключ Soniox, браузер соединяется с Soniox сам:
  `createVoiceInput({ api: "/api/voice" })`. Оставлено для уже работающих приложений; чистки текста в нём нет, а из России браузер до Soniox не достаёт.
- Пример — `apps/demo` (сценарий с подменённым микрофоном: `apps/demo/e2e/voice.spec.ts`). Подробнее — README пакета.

## Вложения к сообщению (по желанию)

Пакет `@ykurilov/agent-chat-attachments` даёт скрепку в поле ввода (а также перетаскивание и вставку из буфера), превью с удалением, миниатюры
картинок и плашки файлов в ленте. Без пакета (или без свойства `attachments`) чат текстовый.

```bash
pnpm add @ykurilov/agent-chat-attachments
```

Серверу без экрана React не нужен: `react` и `@ykurilov/agent-chat-react` у пакета необязательные. Приложению с экраном они и так стоят (чат на экране — это `@ykurilov/agent-chat-react`).

```ts
// сервер
import { createAttachments, createDiskAttachmentStorage } from "@ykurilov/agent-chat-attachments";

const attachments = createAttachments({ storage: createDiskAttachmentStorage({ directory: "./data/attachments" }) });
createChatHandler({ …, attachments, agent: { instructions: appInstructions } });
```

```tsx
// браузер
import { attachmentsClient } from "@ykurilov/agent-chat-attachments/react";
<AgentChat api="/api/chat" chatId={chatId} skin={tandemSkin} attachments={attachmentsClient} />;
```

- Картинки уходят только моделям, которые их видят у выбранного провайдера (`acceptsImagesByProvider` профиля, иначе `acceptsImages`;
  например, DeepSeek 4.1 Flash и GLM 5.3 Flash через Together картинок не видят); иначе человек видит пометку до отправки. Текст PDF
  и текстовых файлов достаётся на сервере и идёт любой модели.
- Модель без зрения может смотреть картинку инструментом приложения: `createAttachments({ imagesForBlindModels: { toolName } })`
  ставит вместо картинки постоянную плашку с номером вложения, а `attachments.readChatImage({ chatId, attachmentId })` отдаёт
  инструменту картинку только этого чата. Подробно — в README пакета.
- Только нужные типы файлов: `createAttachments({ acceptedMediaTypes: ["image/png", "image/jpeg", "image/webp"] })` — остальные
  отклоняются до разбора, поле ввода узнаёт список само.
- Лимиты по умолчанию: 10 файлов, 20 МБ на файл, потолок извлечённого текста; на человека — 30 неотправленных файлов и 200 МБ, 3 одновременные загрузки. Меняются в `createAttachments({ limits })`.
- Картинки при загрузке ужимаются по очереди: разом не больше половины ядер процессора (`limits.maxParallelImageFits`), остальные ждут. Много больших фото сразу не занимают весь процессор.
- Старые большие картинки (загруженные до того, как сервер стал их уменьшать) уменьшаются один раз и держатся в памяти сервера: до 128 МБ, настройка `limits.imageCacheBytes` (`0` — не хранить, уменьшать на каждом шаге). Инструкцию агенту про вложения ядро добавляет само.
- Файлы лежат в заменяемом хранилище (диск и память из коробки), схема базы чата не меняется. Своё хранилище проверяется
  набором `describeAttachmentStorageContract` из `@ykurilov/agent-chat-attachments/storage-contract`.
- Со своим скином: `Composer` и `UserMessage` получают необязательные `attachments` — договор скина версии 5. Нет свойства — вложений нет.
- Пока сервер принимает файлы сообщения, чат занят: второе сообщение в тот же чат в это время получит 409.
- Пример — `apps/demo` (сценарий `apps/demo/e2e/attachments.spec.ts`). Подробнее — README пакета.

## Подтверждение опасных действий

Агент не должен удалять, отправлять и оплачивать без спроса. Пометьте такой инструмент `needsApproval: true` — ход остановится, а в ленте появится карточка:
название действия, входные данные и кнопки «Разрешить», «Отклонить», «Всегда в этом чате».

```ts
import { tool } from "ai";
import { z } from "zod";

const clearNotes = tool({
  title: "Очистить заметки", // так действие называется в карточке; без названия покажется имя инструмента
  description: "Безвозвратно очищает заметки в папке.",
  inputSchema: z.object({ folder: z.string() }),
  needsApproval: true, // или функция от входных данных: ({ folder }) => folder !== "черновики"
  execute: async ({ folder }) => clearFolder(folder),
});
```

- Ждать можно сколько угодно: состояние лежит на сервере, переживает перезагрузку страницы и перезапуск сервера, ответить можно с любого устройства.
- «Разрешить» — инструмент выполняется, ответ дописывается в то же сообщение. «Отклонить» — модель получает «пользователь отклонил» и продолжает без него.
  «Всегда в этом чате» разрешает этот инструмент до конца чата (в других чатах спросят снова). Кнопка есть только у `needsApproval: true`;
  если там функция, «Всегда» не показывается и каждый вызов спрашивает заново.
- Сбой или «Стоп» после «Разрешить» не оставляют вызов висеть: он закрывается как прервавшийся. Ответ на карточку проверяет лимит расходов: при исчерпанном лимите (429) карточка остаётся на месте.
- Новое сообщение, написанное вместо ответа на карточку, считается отказом.
- Пока идёт ожидание, поле ввода свободно; «Повторить» для такого ответа не показывается.
- Кэш модели не страдает: инструкция и набор инструментов не меняются, решение попадает в конец запроса.
- Свой адрес: `POST /:chatId/approvals/:approvalId` с телом `{ "decision": "allow" | "deny" | "always" }` ([contracts/approvals.md](contracts/tool-approval/approvals.md)).
- Со своим скином: `ToolCallRow` получает необязательные `title` и `approval` — договор скина версии 9 (`canAlways` — показывать ли «Всегда», `failureText` — причина отказа). Нет `approval` — обычная строка вызова.
- Со своим хранилищем: реализуйте `updateAwaitingMessage` и `getMessage` (их проверяет `describeChatStorageContract`). Схема базы не меняется.
- Пример — `apps/demo` (инструмент `clear_notes`, сценарии `apps/demo/e2e/tool-approval.spec.ts`).
## Виджеты, схемы, картинки и видео в ответах агента (по желанию)

Агент может отвечать не только текстом. Каждая возможность включается отдельно, без включения всё работает как раньше.

- **Виджеты** — агент спрашивает кнопками, звёздами или короткой формой, ход ждёт ответа: `agent: { widgets: { basic: true } }`. Свой виджет — `defineWidget`. [Подробно](widgets.md).
- **Схемы** — блок ` ```mermaid ` в ответе рисуется на экране: `agent: { diagrams: true }` на сервере и `diagrams={diagramsClient}` на странице (пакет `@ykurilov/agent-chat-diagrams`). [Подробно](diagrams.md).
- **Живые демонстрации** — блок ` ```html-demo ` в ответе запускается в изолированной рамке: ползунки, кнопки, мини-игры. `agent: { liveDemos: true }` на сервере и `liveDemos` на странице, пакетов не нужно. [Подробно](live-demos.md).
- **Картинки** — агент делает картинки через Runware (пакет `@ykurilov/agent-chat-images`, нужны вложения). [Подробно](images.md).
- **Видео** — агент присылает видео из каталога приложения карточкой с плеером YouTube или Kinescope (пакет `@ykurilov/agent-chat-videos`, договор скина версии 14, часть `AgentVideo` необязательная). [Подробно](videos.md).
- **Песочница для админа** — страница, где админ говорит с боевым агентом и видит журнал обращений к модели и вызовов инструментов, правит любые сообщения и меняет модель и инструкцию на один чат (пакет `@ykurilov/agent-chat-sandbox`, договор скина версии 15). [Подробно](sandbox.md).
- **Окно просмотра** — картинки и схемы открываются на весь экран; в Тандеме уже есть, для своего скина — [описание](media-viewer.md) (договор скина версии 13, все новые части необязательные).

## Список чатов (по желанию)

Боковая панель со списком чатов пользователя: создать, переименовать, удалить. Чат сам получает название по первому сообщению.
Без `chatList` на сервере и без `ChatWorkspace` в браузере приложение работает как раньше, с одним чатом на страницу.

```ts
// сервер
createChatHandler({ …, chatList: true });
```

```tsx
// браузер: вместо AgentChat, свойства те же, кроме chatId
import { ChatWorkspace } from "@ykurilov/agent-chat-react";
<ChatWorkspace api="/api/chat" skin={tandemSkin} />;
```

- Что открыть первым: чат из `initialChatId` (например, из адреса страницы), иначе тот, что был открыт в прошлый раз, иначе самый недавний, иначе новый.
  `onChatChange(chatId)` сообщает, какой чат открыт: например, чтобы записать его в адрес.
- Три новых адреса под `basePath`: `GET` (список), `PATCH /:id` с `{ title }`, `DELETE /:id`. Чужой чат — 404, как и везде.
- Удаление настоящее и с подтверждением: сообщения, записи сжатия и файлы вложений исчезают навсегда. Идущий ответ и сжатие останавливаются.
- Название: первое сообщение (до 60 знаков), вручную можно до 100. Заданное вручную первое сообщение не перезаписывает.
- База: колонка `title` у чатов; SQLite и PostgreSQL обновляются сами при открытии, названия старых чатов заполняются по их первому сообщению.
  Свои хранилища должны реализовать `listChats`, `renameChat`, `deleteChat` (проверяется `describeChatStorageContract`); свои хранилища файлов — `removeAllOfChat`.
- Удаление не мешает идущему ответу: он останавливается. Пока чат удаляется, сообщение, сжатие и вложения в него получают `409`. Переименовать можно всегда.
- Свой полный словарь надписей (`ChatLabels`) получает 16 новых обязательных ключей `chatList*`; с `{ ...russianLabels, … }` ничего делать не нужно.
- Со своим скином: `ChatWorkspace` и `ChatList` (`ChatListSkin`) — договор скина версии 7. На узком экране список лежит в панели, которой управляет слой поведения.
- Пример — `apps/demo` (сценарии `apps/demo/e2e/chat-list.spec.ts` и `chat-list-phone.spec.ts`).

## Ветки ответов и правка сообщений

Работает само, отдельной настройки нет. Собеседник может переделать последний ответ агента («Переделать ответ») и исправить
любое своё отправленное сообщение (карандаш под ним). Прежний вариант никуда не девается: под сообщением появляется
переключатель «‹ 2/3 ›», и по нему можно вернуться к любому варианту.

- **Как хранится.** Каждый вариант — новое сообщение с тем же родителем (`parentId`), как и раньше у «Повторить». Переделка делает
  новый ответ на тот же вопрос, правка — новое сообщение с новым текстом на месте старого и новый ответ на него. Ничего не удаляется
  и не переписывается: журнал только дописывается. Выбранный вариант запоминается отдельной записью (таблица `branch_selections`),
  так что после обновления страницы или на другом устройстве открывается тот же вариант. Миграция базы применяется при открытии
  хранилища сама.
- **Что видит модель.** Только текущую ветку: после правки она не знает прежнего текста, после переключения — знает. Инструкция и
  инструменты в запросе не меняются, поэтому кэш модели от веток не страдает. Сжатие истории и поиск по старой переписке
  работают по текущей ветке; сводка действует на ветке, где она сделана, на другой ветке молчит.
- **Пока идёт ответ**, переключать варианты, переделывать и править нельзя (сервер отвечает 409 `busy`, кнопки в экране неактивны).
- **Адреса** (все с префиксом чата): `GET /:id/branches` — развилки `{ forks }` (у каждой id сообщений-соседей по порядку создания),
  `POST /:id/branch` `{ messageId }` — переключиться на вариант, `POST /:id/regenerate` `{ messageId }` — переделать ответ,
  `POST /:id/edit` `{ editedMessageId, message }` — правка. Развилки приходят и в `GET /:id`. Подробно —
  [contracts/branches-and-edit.md](contracts/branches-and-edit/branches-and-edit.md).
- **Свой скин** обязан иметь компоненты `BranchSwitcher` и `MessageEditor` (договор v6); сообщения `UserMessage` и `AgentMessage`
  получают новые свойства `branchSwitcher`, `onEdit`, `onRegenerate`. Надписи — `previousBranch`, `nextBranch`, `branchPosition`,
  `regenerate`, `editMessage`, `saveEdit`, `cancelEdit`, `editErrors` (`busy`, `offline`, `rejected`) в словаре; `MessageEditor` получает
  необязательное `error` — показать под полем.
- **Отказ при правке.** Поле правки закрывается, только когда сервер принял правку. Если он отказал (например, 409, потому что ответ уже идёт),
  сообщения возвращаются на место, поле остаётся с исправленным текстом и ошибкой. В своей ленте: `edit(messageId, text)` возвращает
  `Promise<EditOutcome>` (`started`, `not_started`, `refused`).
- **Своё хранилище** — два новых метода и общие тесты `describeChatStorageContract`.
- **Вложения при правке.** Файлы сообщения остаются как были: слова меняются, файлы переходят в новый вариант, над полем правки их видно
  (`MessageEditor.attachments`), убрать или добавить файл при правке нельзя. Сообщение из одних файлов можно отправить и с пустым текстом.
- **Проверка.** В демо (`apps/demo`) заглушка на «по-разному» отвечает новым вариантом при каждом повторе, а на «Как меня зовут?» —
  по тому, что ей передали в истории. Сценарий — `apps/demo/e2e/branches.spec.ts`.

## Поправка на лету

Работает само, отдельной настройки нет. Агент долго делает задачу, человек видит, что тот свернул не туда, и пишет поправку,
не останавливая его. Поле ввода во время ответа свободно, «Стоп» стоит рядом с «Отправить».

- **Что видит человек.** Поправка сразу встаёт в ленту под ответом с пометкой «Агент учтёт на следующем шаге». Агент берёт её
  на ближайшей границе шага (закончились очередные вызовы инструментов): ответ закрывается, сделанное в нём остаётся, и
  агент продолжает новым ответом с учётом поправки. Пометка уходит. Ответ кончился раньше — поправка просто запускает новый ход.
  Несколько поправок подряд агент берёт все, по порядку.
- **«Стоп» при ждущей поправке** останавливает текущий ответ, но поправку не теряет: агент сразу отвечает на неё.
- **Подтверждение опасного действия.** Если ход остановился на карточке «Разрешить?», а человек написал поправку, карточка
  закрывается отказом — как при обычном новом сообщении, — и агент отвечает на поправку.
- **Хранение.** Поправка пишется в базу сразу, обычным сообщением человека с отметкой `data-agent-steer` (модели отметка не уходит).
  После обновления страницы ждущие поправки приходят в истории отдельным полем `pendingMessages` и снова видны с пометкой.
  Ветки, сжатие истории и лимиты работают как с обычным сообщением: поправка проходит `beforeTurn` (действие `send`), лимит
  сообщений и расходов. Отказ — поправка уходит из ленты, текст возвращается в поле.
- **Для строгих провайдеров** (DeepSeek, Anthropic через OpenRouter) поправки подряд уходят модели одним сообщением человека,
  а закрытый ответ — перед ними. Кэш модели: начало запроса прежнее, один раз без кэша читаются только части закрытого ответа.
- **Несколько копий сервера.** Поправка принимается копией, на которой идёт ответ (как «Стоп»). Попала на другую — отказ
  `409 busy`, текст возвращается в поле. Держите запросы одного чата на одной копии (липкие сессии).
- **Выключить.** `<AgentChat steering={false} />` — поле во время ответа снова занято. Своя лента на `useAgentChat` включает
  поправки явно: `useAgentChat({ steering: true })` и рисует `corrections` после `messages`.
- **Адрес.** `POST /:id/steer` `{ message, place?, tabId? }` → `202 { status: "queued" | "started", messageId }`. В ядре —
  `service.steer(userId, chatId, message, { page })`. Продолжение после поправки получает `place` самой свежей поправки
  (а не начала хода): служебная заметка приложения (`serviceNote`, «Версия 7…») уже новая. Кэш цел — блок места ложится
  в хвост поправки.
- **Конец хода.** Ответ, закрытый ради поправки, — отдельный ход: `onTurnFinished` (на сервере и в `AgentChat`) приходит
  и для него, и для ответа на поправку, по порядку. Повтор с тем же `message.id` (клиент не дождался ответа) получает тот же итог,
  второй копии нет; `useAgentChat` после обрыва шлёт тот же текст с тем же id.
- **Свой скин** (договор v21, [docs/skin-v21.md](./skin-v21.md)): `Composer.canSteer` — рисовать «Отправить» рядом со «Стоп»;
  `UserMessage.pending` — пометка у ждущей поправки, текст — `labels.steeringPending`; признак `steering: true` в скине включает
  поправки. Скин без признака работает как раньше: поле во время ответа занято, поправок нет.
- **Проверка.** В демо заглушка на «Запусти долгую проверку» пять секунд вызывает инструмент, а на сообщение со слова
  «Поправка» отвечает «Учёл поправку: …». Сценарий — `apps/demo/e2e/steering.spec.ts`.

## Лимиты расходов (по желанию)

Бюджет в долларах на человека, на чат, на весь сервис — в любых окнах. Ядро записывает токены и стоимость в долларах (по ценам модели на момент хода) каждого ответа и фонового сжатия в журнал
расхода (он есть всегда и обновляется миграцией при открытии хранилища), а лимиты и суммы считает пакет `@ykurilov/agent-chat-limits`.
Ход и сжатие относятся к тому периоду, в котором начались.

1. `pnpm add @ykurilov/agent-chat-limits`.
2. На сервере: `const limits = createSpendingLimits({ storage, catalog, budget: async ({ userId }) => ({ user: 5 }) })` и `limits` в
   `createChatHandler({ …, limits })`. Хранилище и каталог — те же, что у чата. `budget` — ваша функция: сколько долларов можно
   потратить этому человеку и этому чату (`{ user }`, `{ chat }` или оба). Период — `period: "month"` (по умолчанию), `"day"`, `"none"`.
   Сутки и месяцы режутся по UTC, а с `timeZone: "Europe/Moscow"` — по Москве (раздел «Сервер в России»).
3. Цены берутся из профиля модели (`pricing`). Своя модель без цены — понятная ошибка при создании лимитов
   (или явно `unpricedModels: "ignore"`: такие ходы пишутся с нулевой стоимостью).
4. В браузере: `<AgentChat … spendingLimits />`. Чат покажет «Использовано 80% лимита на месяц», а при исчерпании — «Лимит на
   месяц исчерпан, обновится 1 ноября» и остановит отправку.
5. Свой скин: необязательный компонент `SpendingNotice({ id, state, text })` (`state` бывает `none`: область для диктора должна быть на странице всегда) и свойства
   `Composer.sendingBlocked` и `Composer.sendingBlockedReasonId` (договор v8); нет их — надписи не будет, а отправка всё равно остановится. Надписи — `spendingWarning` и `spendingExhausted` в словаре.

- **Отказ.** Исчерпанный лимит — `429 spending_limit_reached` до начала хода (для отправки, повтора, переделки и правки); адрес
  `GET /:id/spending` отдаёт `{ state, scope, period, share, resetsAt }` без сумм (с `timeZone`, если пояс задан). Сбой самой проверки тоже останавливает ход.
- **Ход, начатый в пределах бюджета, доводится до конца**: один ход может выйти за бюджет, следующий не начнётся. Проверка не
  резервирует деньги: ходы, начатые одновременно, могут вместе выйти за бюджет.
- **Веб-инструменты** считаются, если им передан `spending` (раздел «Веб-инструменты»).
- **Одновременные ходы.** Без резерва денег ходы, начатые одновременно, могли бы вместе сильно выйти за бюджет. Поэтому у человека
  одновременно идут не больше трёх ответов (`maxConcurrentTurnsPerUser`): перерасход — не больше трёх ходов сверх лимита.
- **Расход «примерно».** Шаг, оборванный «Стопом» или сбоем после первых слов модели, и шаг, по которому провайдер не прислал
  числа, прикидываются по длине текста с учётом письма (латиница — токен на 3 знака, кириллица и JSON — на 2, иероглифы — токен
  на знак, файл — 1600 токенов; прикидка скорее завышает). Ход, оборванный перезапуском сервера, записывается при следующем
  запуске (`recoverInterruptedAnswers`) или проверкой брошенных ответов: только то, чего ещё нет в журнале. Если база не
  приняла конечную запись ответа и после двух повторов (через 1 и 3 с), ответ остаётся для такой проверки. У таких записей `estimated: true` (колонка `estimated`,
  миграция SQLite `0011`, PostgreSQL `0010`), у итога ответа — `usage.estimated`.
- **Поправка до настоящего расхода.** У OpenRouter оборванный ответ сверяется в фоне: через несколько минут сервер узнаёт у
  OpenRouter настоящий расход генерации и дописывает запись `answer_correction` — разницу с оценкой (может быть меньше нуля).
  Сумма записей ответа становится точной. Перезапуск сервера во время сверки оставляет оценку. Свой провайдер подключает то же
  через `generationUsage` в описании провайдера.
- **Автопродолжение и запасной провайдер лимит не перепроверяют**: это продолжение того же хода, а ход, начатый в пределах
  бюджета, доводится до конца.
- **Часы пик** задаются в `pricing.peakHours`: `{ timeZone?, windows: [{ days: [1…7], from: "ЧЧ:ММ", to: "ЧЧ:ММ" }], multiplier,
  cachedInputMultiplier?, exceptDates? }`. Цены профиля — вне пика; запрос, ушедший в окно, стоит дороже в `multiplier` раз
  (вход из кэша — в `cachedInputMultiplier`, по умолчанию так же). Каждый шаг хода считается по времени своего запроса. Из коробки
  так у DeepSeek 4.1 Flash у DeepSeek: база 0,15 / 0,60 / 0,003, по будням 01–04 и 06–10 UTC вдвое. Праздники Китая не заданы
  (расход в них чуть завышен); добавить — `exceptDates`.
- **Ступени цены по длине контекста** задаются в `pricing.tiers`: `{ inputTokensAbove, inputPerMillion, outputPerMillion, … }`.
  Запрос, у которого вход больше порога, целиком идёт по ценам ступени; в ходе из нескольких шагов ступень выбирается у каждого шага.
  Из коробки так у GPT 6 Luna выше 272 тысяч токенов и у Claude Haiku 5.5 от 100 тысяч.
- **Запись в кэш на час** стоит дороже, чем на 5 минут: `cacheWrite1hPerMillion` рядом с `cacheWritePerMillion` (и в ступенях).
  По ней считается запись у моделей, которые пишут кэш на час (срок кэша — в описании OpenRouter выше).
- **Окна лимитов** (`windows`) вместо `budget`: любой набор одновременных окон — сутки, неделя, месяц по поясу, «N часов от
  первого запроса» или на всё время; область — человек, чат или весь сервис. Перерасход начатого хода можно перенести в следующее
  окно (`carryOverrun`). Правила хода (`turn`): запас на старт (`minRemainingUsd`), потолки хода по деньгам и вызовам инструментов
  (`maxCostUsd`, `maxToolCalls`) — на потолке ход заканчивается итогом. Человеку — свой лимит, блокировка и ручной сброс окна
  (`setUserSettings`, `resetWindow`), события порогов 80% и 100% (`onThreshold`). Браузер видит только доли и время сброса.
  Подробно — [README пакета](../packages/limits/README.md#окна-лимитов).
- **Лимит сообщений.** Окно может считать не доллары, а сообщения человека: `limitMessages: 20` вместо `limitUsd`. Считаются
  отправка и правка; переделка, «Повторить», служебные сообщения, импорт и песочница — нет. Удаление чата счёт не сбрасывает.
  Отказ — `429 spending_limit_reached` с `unit: "messages"`, экран пишет «Лимит сообщений исчерпан». `exemptUsers` снимает
  окна с сотрудников и тестеров. Подробно — [агент внутри продукта](in-product-agent.md#5-лимит-сообщений).
- **Расход для страницы «тариф»:** `await limits.getSpending({ userId, chatId })`. Ручное `compactNow` лимит не проверяет.
- **Своё хранилище** — для окон «N часов», личных настроек, сброса и порогов нужны ещё `getSpendingLimitState` и
  `saveSpendingLimitState` (запись по версии; общие тесты `describeChatStorageContract(…, { spendingLimitState: "required" })`).
  Для расхода — два метода (`insertUsageRecord`, `sumUsage`; запись и сумма несут `costUsd`) и общие тесты `describeChatStorageContract`.
- **Проверка.** В демо `DEMO_SPENDING_LIMIT_USD=0.0005` включает маленький бюджет; сценарий — `apps/demo/e2e/spending-limits.spec.ts`.
  Подробно — [пакет](../packages/limits/README.md) и [контракт](contracts/spending-limits/spending.md).

## Долгосрочная память (по желанию)

Агент запоминает устойчивое о человеке (предпочтения, правила общения, факты о работе) и помнит это в новых чатах. Что запомнить, решает
сам агент по ходу разговора: отдельного «извлечения» после чата нет. Человек видит записи на экране памяти, может добавить, исправить,
удалить запись или стереть всё. Записи у каждого человека свои; удаление чата их не трогает. Пример — `apps/demo`.

1. `pnpm add @ykurilov/agent-chat-memory`.
2. На сервере: `memory: createLongTermMemory({ storage })` в `createChatHandler({ … })`. Хранилище — SQLite, PostgreSQL или в памяти;
   своему хранилищу нужны пять методов памяти (список — в README пакета). Инструкция агента и инструмент `manage_memory` добавляются сами,
   адреса `/api/chat/memory` появляются сами. Без опции `memory` чат работает как раньше, адреса памяти отвечают `404`.
3. В браузере — экран памяти:

   ```tsx
   import { AgentMemory, createMemoryApi } from "@ykurilov/agent-chat-react";
   import { tandemMemorySkin } from "@ykurilov/agent-chat-skin-tandem";

   const memoryApi = useMemo(() => createMemoryApi({ api: "/api/chat" }), []); // один раз
   <AgentMemory api={memoryApi} skin={tandemMemorySkin} />
   ```

   Экран — обычный компонент: поставьте его на свою страницу или в окно (в демо — адрес `/memory`). Высоту и прокрутку задаёт страница.
4. Подпись вызова в ленте — `withMemoryToolTitles(russianLabels)` из `@ykurilov/agent-chat-memory/labels` («Работа с памятью: готово»).
   Можно вложить в другие: `withMemoryToolTitles(withHistorySearchTitles(withWebToolTitles(russianLabels)))`.

- **Чужой текст не записывается.** Инструкция велит записывать только сказанное самим человеком: «запомни» на веб-странице или в
  результате инструмента память не меняет.
- **Как записи попадают к модели.** Как файл правил в Claude Code: память читается один раз на чат. Блок `<agent_memory>`
  вписывается в вопрос первого хода и дальше не меняется. В идущем чате память не перечитывается: новые, изменённые и
  удалённые записи (и записанные самим агентом — он видит их в переписке) на каждом ходе не досылаются. Память читается
  заново: в новом чате; после сжатия истории; при смене начала истории — правке первого сообщения или «Переделать»
  первого ответа; в первом личном ходе после группового (групповой ход память не читает); в ходе после сбоя чтения.
  Начало запроса прежнее, кэш модели цел, хранилище не опрашивается на каждом ходе. В истории на экране и в сжатии
  блока нет.
- **Пределы.** 200 записей и 48 000 знаков на человека; в блок идёт не больше 12 000 знаков (самые недавно изменённые), остальное агент находит поиском,
  а экран пишет «Показано агенту: N из M». Запись, вытесненная из блока, не выдаётся за удалённую: модель видит «Не показано ради места, но по-прежнему действует». Свои значения — `maxNotes`, `maxTotalChars`, `maxBatch`, `maxBlockChars` в `createLongTermMemory`.
- **Склейка повторов.** После ответа раз в сутки та же модель предлагает слить повторные записи, код проверяет и применяет годные. На экране памяти раздел
  «Объединено» с кнопкой «Вернуть как было». Опция: `optimizer: { intervalHours }` или `optimizer: false` в `createLongTermMemory`; по умолчанию включена, если хранилище умеет
  (SQLite, PostgreSQL и память умеют). После сбоев пауза растёт: час, 6 часов, сутки; удачный запуск сбрасывает счёт. Новые адреса: `GET /api/chat/memory/merges`
  и `POST /api/chat/memory/merges/:runId/revert` (ответ `409` с `conflict`, `limit_reached` или `duplicate` — экран объяснит). Своему хранилищу склейка нужна не всегда: без шести методов она выключена (список — в README пакета).
- **Одновременные действия.** Пределы и дубли проверяются под замком на человека; при нескольких серверах — внутри транзакции хранилища (свои хранилища: два необязательных метода `…Checked`, см. README пакета).
- **Свой скин.** Экрану памяти нужен `MemorySkin` — договор скина версии 11 (`MemoryScreen`, `MemoryGroup`, `MemoryNoteRow`, `MemoryNoteEditor`,
  `MemoryConfirm`); `ChatSkin` не менялся. Надписи — в словаре (`memoryHeading`, `memoryAdd`, `memoryClearAll` и другие, все начинаются с `memory`).
- **Миграции** применяются сами при открытии базы: SQLite `0009` и `0010`, PostgreSQL `0008` и `0009`.
- **Проверка.** В демо `DEMO_MEMORY=1` включает память, а заглушка на «Запомни, что …» записывает, на «Что ты помнишь?» отвечает записями из блока.
  На задание проверки дублей заглушка отвечает слиянием: две записи об одном («…каждый день» и «…каждый день в компании Acme») склеиваются в одну.
  Сценарии, в том числе «Объединено → Вернуть как было», — `apps/demo/e2e/memory.spec.ts`; живая проверка на настоящих моделях — `pnpm test:live memory`.

## Панель агента в приложении (по желанию)

Агент живёт в боковой панели поверх вашего приложения: человек ходит по страницам, панель и идущий ответ остаются. Агент знает, где человек
сейчас, делает действия на странице (например, открывает карточку) и сообщает странице, что поменял данные. Пример — страница `/panel-app` в `apps/demo`.

Свой инструмент, от нуля до работы — тридцать строк (сервер чата уже настроен, роутер в примере — React Router):

```ts
// shared/browser-tools.ts — описание для сервера и страницы
import { tool } from "ai";
import { z } from "zod";
export const browserTools = { open_task: tool({ description: "Открыть задачу на экране", inputSchema: z.object({ taskId: z.string() }) }) };

// сервер: добавить в agent у createChatHandler({ …, chatList: true, agent: { instructions, … } })
import { tool } from "ai";
import { z } from "zod";
import { browserTools } from "./shared/browser-tools";
  browserTools,
  tools: ({ ownerId, notifyDataChanged }) => ({
    create_task: tool({
      description: "Создать задачу",
      inputSchema: z.object({ title: z.string() }),
      execute: async ({ title }) => {
        await tasks.create(ownerId, title); // права человека
        notifyDataChanged({ tag: "tasks" });
      },
    }),
  }),
```

```tsx
// корневой макет, выше страниц
import { AgentPanel, AgentPanelProvider } from "@ykurilov/agent-chat-react/panel";
import { tandemSkin } from "@ykurilov/agent-chat-skin-tandem";
import { useNavigate } from "react-router";
const navigate = useNavigate();
<AgentPanelProvider api="/api/chat" userKey={user.id} browserTools={{ open_task: ({ taskId }) => navigate(`/tasks/${taskId}`) }}>
  <Routes />
  <AgentPanel skin={tandemSkin} />
</AgentPanelProvider>;

// страница карточки и страница списка
import { useAgentDataChanges, useAgentPlace } from "@ykurilov/agent-chat-react/panel";
useAgentPlace({ description: `Карточка задачи «${task.title}»`, data: { taskId: task.id } });
useAgentDataChanges("tasks", () => reloadTasks());
```

На сервере нужен `chatList: true`. Провайдер ставится один раз в корневом макете: так панель не пересоздаётся при переходах.

- **Свой `fetch`** у провайдера (`fetch`) нужен только для списка чатов; сам чат ходит обычным `fetch`.
- **Страница под панелью.** `mode="overlay"` (по умолчанию): панель поверх страницы, страница кликается. `mode="push"`: отступ страницы приложение ставит само,
  по `pageInset` из `useAgentPanel()` (например, `padding-right`); на экране до 640 px панель на весь экран и `pageInset` равен 0.
- **Место человека.** `useAgentPlace({ description, data? })`: пока компонент на экране, агент знает место. Главнее компонент, появившийся на экране позже;
  вложенный всегда главнее внешнего: место страницы «Карточка задачи» перекрывает место макета «Раздел задач» и при первом показе, и после переходов.
  Ушла страница — снова действует место макета, ушли все — места нет. Модель видит только `description` (до `agent.placeMaxLength`, 1000 по умолчанию, длиннее обрезается с «…»); `data` до 4 КБ
  видят только инструменты (`model.place.data`), а модели не уходят. `data`, которая не превращается в JSON (цикл, `BigInt`), отбрасывается — сообщение всё равно уходит.
- **Где модель видит место.** В конце последнего входа хода: сообщения человека или поправки. Ответ на кнопку виджета и «Разрешить» продолжают
  тот же ответ, и новое место встаёт заметкой сразу после ответа человека, последним сообщением запроса. Начало запроса прежнее — кэш цел.
- **Изменения данных.** Инструмент после записи зовёт `notifyDataChanged({ tag, details? })`: метка 1–100 знаков, `details` — JSON до 4 КБ; страница узнаёт сразу, не дожидаясь конца ответа.
  Ловить: `useAgentDataChanges(tag | [метки], handler)` на странице или `onDataChanged` у провайдера (для всех меток). Обработчик зовётся один раз
  на сообщение, в том числе после перезагрузки страницы во время ответа: вкладка помнит последние 500 сообщений в `sessionStorage`.
  Повторно он сработает только в редком случае: хранилище вкладки недоступно (строгий приватный режим) и страницу перезагрузили во время ответа.
  Если чат с идущим ответом открыт в двух вкладках, каждая получает сообщение один раз. Совет: данные меняйте серверными инструментами, как `create_task`
  выше (права человека, запись в базе), а страницу только просите обновиться. Браузерная функция годится для действий на экране — открыть, подсветить, прокрутить.
- **Браузерные инструменты.** Описания (`tool({ description, inputSchema })` без `execute`) лежат в общем файле сервера и страницы; на сервере `agent.browserTools`,
  на странице функции с теми же именами в `browserTools` провайдера (типы входа — `BrowserToolImplementations<typeof browserTools>`). Функция получает `{ signal }`: он срабатывает
  по сроку, «стопу» и удалению чата. Срок ответа — `agent.browserToolTimeoutMs` (по умолчанию 30 с, от 1 с до 2³¹−1 мс). Нет функции на странице — модель получает «Инструмент недоступен на этой странице»
  (надпись `agentPanelToolUnavailable`). Вкладка отвечает на `POST {basePath}/:chatId/browser-tools/:toolCallId` (`204`, `400`, `401`, `404`, `409`; тело не больше 64 КБ).
  Чужой, повторный и поздний ответ — `409` (`BrowserCallNotPendingError`, вид ошибки `not_pending`).
- **Что получает модель.** Результат функции до 16 КБ, больше — «Слишком большой результат»; ошибка обрезается до 1000 знаков; пустой результат (`undefined`, `null`) — «готово»;
  нет вкладки — «Действие на экране недоступно: страница не подключена»; нет ответа в срок — «Страница не ответила за N с».
- **Ограничения.** Работает на одном сервере: ожидание ответа вкладки живёт в памяти процесса (как и продолжение идущего ответа). Перезагрузка страницы во время исполнения: вызов не повторится,
  модель получит ошибку по сроку. Инструмент с подтверждением («Спросить разрешения»): функция на странице запускается только после «Разрешить».
- **Свой скин.** Панели нужен `AgentPanelSkin` (`AgentPanelLauncher`, `AgentPanel`) — договор скина версии 12; в `tandemSkin` он уже есть. Надписи `agentPanel…` в словаре.
- **Проверка.** В демо страница `/panel-app`: сценарии — `apps/demo/e2e/agent-panel.spec.ts` и `agent-panel-phone.spec.ts`, замер открытия панели с историей (меньше 300 мс) — `perf-panel-open.spec.ts`.

## Агент внутри продукта (по желанию)

Агент работает с объектами вашего продукта — уроком, заказом, документом. Восемь независимых возможностей, каждую можно
включить отдельно; без них чат работает как раньше:

- приложение отказывает в ходе своими словами (`beforeTurn`, отказ из `resolveUser`);
- итог каждого хода надёжно доходит до приложения (`afterTurn`), свои события на экране (`appEvents`, `onAppEvent`);
- один чат на объект (`subjectChats` на сервере, `<AgentChat subject="lesson:42" />`);
- агент пишет первым заранее написанным текстом (`greeting`), без вызова модели;
- лимит по числу сообщений (`limitMessages`) и снятие лимитов с сотрудников (`exemptUsers`);
- перенос старой переписки (`service.importChat`);
- сотрудник смотрит чат человека и проверяет ответы в копии в своей песочнице (раздел «Чаты людей»);
- свои кнопки у поля ввода (`composerActions`).

Подключение и пример с уроком — [docs/in-product-agent.md](in-product-agent.md). Рабочий пример — страница `/lesson` в `apps/demo`.

## Надёжность хода

Ничего включать не нужно: всё ниже работает само. Настройки лежат в `agent` у `createChatHandler` и нужны, только если
вас не устраивают значения по умолчанию.

**Что делает сервер сам**

- **Повторы.** Временная ошибка провайдера (перегрузка, лимит, сбой сети) повторяется тихо, человек ничего не видит.
  Те же повторы у сжатия истории и у склейки памяти.
- **Запасной провайдер.** Если провайдер перегружен или упёрся в лимит, а ответ ещё не начался, ход один раз идёт к
  следующему провайдеру той же модели, чей ключ есть на сервере. Кэш при этом теряется, деньги считаются по цене
  запасного. Настройка `providerFallback`: не задана — включено; `false` — выключено; `{ byModel: { "gpt-6-luna": ["openrouter"] } }` —
  свой порядок или `false` для одной модели.
- **Переход посреди ответа** (по желанию). `providerFallback: { onSilence: "restart-step-on-next" }`: модель замолчала
  дольше `modelSilenceTimeout` — до первого куска или посреди ответа. Тогда шаг обрывается и начинается заново у
  следующего провайдера списка, без повтора у того же. Уже показанный текст шага стирается: в ленте, в мессенджере и в
  сохранённом ответе. Клиент получает часть `data-step-reset`: «убрать всё от последнего начала шага». `useAgentChat`
  и мессенджеры делают это сами. Своя лента на истории — `withoutResetSteps(parts)` из core или react. Шаг, где
  инструмент уже получил вход целиком, не стирается: ответ продолжается у запасного. `scope: "step"` — следующий шаг
  снова у основного провайдера, по умолчанию `"turn"` — запасной до конца хода. Возврат к основному — только после
  перехода при молчании: запасной, выбранный из-за перегрузки, остаётся до конца хода. Перегрузка у запасного ведёт к
  следующему за ним, а не обратно к нему же. `maxSwitches` — сколько переходов за ход, по умолчанию 1. Каждый переход
  съедает шаг из предела шагов. Стёртый шаг оплачен и есть в расходе хода. Срок хода (`turnTimeoutMs`) идёт и во время
  переходов. После начала `flush` или при «Стоп» перехода нет и показанное не стирается.
  Такой ход сразу после `start` присылает клиенту кусок `data-steps-may-reset` (в ответе его нет). По нему мессенджер
  не отправляет части идущего шага отдельными сообщениями до конца шага. Если стёрт весь показанный текст, живое
  сообщение показывает «Пишу ответ заново…».
- **«Повторить» продолжает.** После сбоя, «Стоп» или перезапуска сервера «Повторить» идёт дальше с уже выполненных
  вызовов инструментов: просили три задачи, оборвалось на третьей — после повтора их три, а не пять.
  Рядом с «Повторить» у такого ответа есть «Переделать ответ»: она пишет ответ с чистого листа, без прежних вызовов.
- **Автопродолжение.** Если связь с моделью оборвалась посреди ответа, ход через 2–5 с дописывает его у того же
  провайдера, не больше двух раз. Человек видит один ответ без ошибки.
- **Переполнение окна.** Переписка не влезла в модель — ход сам сжимает историю и продолжает. Ошибка `context_overflow`
  («Переписка не помещается в модель») — только если не помогло и это.
- **Вызов без результата.** Инструмент, прерванный «Стопом» или сбоем, закрывается ошибкой «действие могло выполниться»,
  и чат не ломается.
- **Последний шаг.** Когда шаги кончаются, модель получает запрос без инструментов с просьбой подвести итог.
- **Расход без дыр.** Оборванный ответ тоже попадает в журнал расхода, помечен «примерно» (`estimated`). У OpenRouter
  сервер потом сверяет цену с настоящей и дописывает разницу (`answer_correction`); не узнал за ~10 минут — остаётся оценка.
- **Часовой пояс.** Сегодняшняя дата в запросе — по поясу человека (браузер присылает его сам). Запасной пояс —
  `agent.timeZone` (например, `"Europe/Moscow"`) или пояс лимитов (`createSpendingLimits({ timeZone })`), без них —
  пояс сервера. Оба заданы и разные — ошибка при старте.

**Пределы ожидания**

| Настройка | По умолчанию | Что меняет |
|---|---|---|
| `toolTimeoutMs` | 120 000 мс | срок серверного инструмента; не ответил — отмена и ошибка для модели. `0` или `Infinity` — без срока; `{ default, byTool }` — свои сроки |
| `modelSilenceTimeout` | `{ firstChunkMs: 90000, betweenChunksMs: 120000 }` | молчание модели до первого куска (тихий повтор, затем запасной провайдер) и между кусками (автопродолжение); `false` — без пределов |
| `toolResultMaxLength` | 50 000 знаков | предел результата инструмента; `{ default, byTool }`, не меньше 1000 |
| `turnTimeoutMs` | без срока | общий срок хода до записи итога; вышел — ход останавливается как «Стоп», `afterTurn` видит `stopReason: "timeout"`. `afterTurn` записанного ответа срок не обрывает. `0` или `Infinity` — без срока; `{ default, byModel }` — свои сроки |
| `maxOutputTokens` | потолок модели из профиля, нет его — без предела | предел токенов ответа в каждом запросе к модели; упёрся — `afterTurn` видит `lengthCut: true`. `{ default, byModel }` — свои пределы |

```ts
agent: {
  toolTimeoutMs: { default: 60_000, byTool: { ask_user: 0 } }, // ask_user сам ждёт человека
  modelSilenceTimeout: { firstChunkMs: 120_000 },
  turnTimeoutMs: { default: 180_000, byModel: { "deepseek-4.1-flash": 120_000 } },
  maxOutputTokens: 4_000,
  toolResultMaxLength: { default: 30_000, byTool: { read_page: 80_000 } },
  providerFallback: { byModel: { "deepseek-4.1-flash": false } },
  timeZone: "Europe/Moscow",
},
```

Свой срок молчания у провайдера задаётся при его подключении тем же полем: заданные сроки перекрывают общие, пропущенные
берутся из общих. Срок действует на каждую попытку у этого провайдера, в том числе когда ход перешёл на него запасным.

```ts
extendCatalog(standardCatalog, {
  addProviders: [
    createOpenRouterProvider({ id: "or-together", only: ["together"], modelSilenceTimeout: { firstChunkMs: 3_000 } }),
    createOpenRouterProvider({ modelSilenceTimeout: { firstChunkMs: 30_000 } }), // запасной
  ],
});
```

**Скрыть провайдера из меню.** Поле `hiddenFromMenu: true` (в фабриках `create…Provider` и в описании провайдера) убирает
провайдера и его модели из `GET {base}/models` и из выбора в чате (React-хуки и список в экране берут меню оттуда). `PUT
/:id/model` на скрытого отказывает так же, как на неизвестного. Как `defaultChoice` и запасной в `providerFallback` скрытый
работает как обычный: меню, не маршрут (запасной по умолчанию и переход при молчании тоже могут идти на скрытого).

Одно правило: **скрытый выбор в чате равен выбору по умолчанию.** Чат с сохранённым скрытым провайдером идёт на выборе по
умолчанию, запись в базе не меняется. `importChat` с моделью скрытого провайдера не падает, а заводит чат без своего выбора
(на выборе по умолчанию); неизвестный провайдер в импорте по-прежнему ошибка. `openSubjectChat` и новый чат берут
запомненный выбор человека; если он скрытый, берётся выбор по умолчанию.

Если сам `defaultChoice` у скрытого провайдера, `GET /models` честно отдаёт его в `defaultChoice` (в `providers` его нет)
и добавляет `defaultChoice.details` с названиями, картинками и уровнями. `useModelChoice` показывает его как текущую
модель отдельным пунктом списка; выбрать его вручную нельзя. Без `details` пункт подписан id, уровней нет.
Подключение через прокси (`connectProviders`) флаг не теряет.

```ts
extendCatalog(standardCatalog, {
  addProviders: [createOpenRouterProvider({ id: "or-fastest", sort: "throughput", hiddenFromMenu: true })],
});
```

Время работы инструмента молчанием модели не считается. Инструменты с подтверждением ждут «Разрешить» без срока.

**Опасные инструменты по очереди.** `agent.sequentialTools: true` (или список имён, например `["charge"]`) пускает такие
вызовы по одному: «спиши деньги» не пойдёт, пока не кончился предыдущий. Очередь одна на чат: «Стоп» и сразу «Повторить»
не запустят второй вызов поверх первого, пока тот не закончился или не истёк его срок. Объявляйте такие инструменты как
`async function*`, если они выдают промежуточный вывод.

**Строки журнала сервера.** Текстов сообщений и ключей в них нет; ищите по первому слову в скобках.

| Строка | Когда |
|---|---|
| `[повтор]` | тихий повтор хода, сжатия или склейки памяти |
| `[сбой провайдера]` | ход упал: код, имя ошибки, до 4000 знаков тела (ключи заменены на `[скрыто]`) |
| `[запасной провайдер]` | переход к запасному, «кэш потерян» |
| `[переход при молчании]` | шаг начат заново у следующего провайдера: откуда, куда, номер перехода, стёрт ли шаг |
| `[автопродолжение]` | дописываем оборванный ответ: попытка, пауза, причина |
| `[переполнение]` | сжатие из-за переполнения окна: начато, готово, не вышло |
| `[результат обрезан]` | результат инструмента длиннее предела |
| `[аргументы починены]` | модель прислала битые аргументы инструмента (лишняя скобка, перевод строки, `"2"` вместо числа), ядро починило их без повтора: инструмент, модель, провайдер, что поправлено, длина |
| `[инструмент не ответил]` | сработал `toolTimeoutMs` |
| `[молчание модели]` | сработал `modelSilenceTimeout` |
| `[промах кэша]` | начало запроса то же, а провайдер почти не взял из кэша: сколько токенов и примерная переплата. Выключается `cacheMissLog: false` |

Для OpenRouter каждый запрос несёт заголовок `x-session-id` с номером чата: запросы одного чата идут на один сервер,
кэш не теряется. Номер чата уходит в OpenRouter как идентификатор сессии.

**Что ещё защищено.**

- Секреты (`password=`, `token=`, `Authorization`, ключи сервисов, значения секретных переменных окружения) вычищаются из
  ошибки инструмента, прежде чем текст уйдёт человеку, в базу и модели.
- Большие фото уменьшаются при загрузке (библиотека `sharp`, нужен Node 22), память под старые копии — `limits.imageCacheBytes`
  (128 МБ), раздел «Вложения».
- Картинки из ответа модели скин Тандема показывает ссылкой и не грузит: надпись `externalImageLink` (по умолчанию «картинка»).
- Чужие страницы, лимит тела и предел одновременных ответов — в шаге 4.

**Своему `ErrorNotice`.** Покажите `text`, если он есть, вместо `labels.errors[kind]` (договор скина версии 16). Без этого
скин работает, но вместо причины отказа сервера покажет общую надпись.

**Своим словарям надписей.** Добавьте `errors.context_overflow`, `errors.signed_out`, `errors.too_many_turns`,
`errors.forbidden_origin`, `editErrors.signedOut`, `editErrors.tooManyTurns`, `editErrors.forbiddenOrigin`
и `approvalTooManyTurns`. Словарь на основе `{ ...russianLabels }` получает их сам.

**Несколько копий сервера.** Можно, если запросы одного чата идут на одну копию. Идущий ответ раз в 5 с отмечает
«жив»; чужие живые ответы никто не трогает. Первое обновление до этой версии — один раз остановите все старые копии,
потом запускайте новые. Подробности — в разделе «Какое хранилище выбрать». Если пишете своё хранилище, нужны
`markAnswerAlive`, `listSilentAnswerIds` и поле `alive` (шаг 4, «Своё хранилище»).

## 10. Проверка

1. Запустите сервер (`tsx server/index.ts`) и клиент (`vite`), откройте страницу чата.
2. Напишите «Привет». Сообщение сразу в ленте, ответ растёт по частям, над ним «Думал N сек».
3. Попросите длинный ответ и нажмите «Остановить». Ответ перестаёт расти и помечен
   «Остановлено». После обновления страницы всё на месте. Если в `instructions` агенту велено
   отвечать коротко, он может отказаться писать длинно: на время проверки ослабьте инструкцию.
4. Спросите то, для чего нужен ваш инструмент. В ответе строка вызова: «выполняется» → «готово».
5. Откройте адрес чата под другим пользователем: сервер отвечает 404, в чате надпись
   «Чат не найден».

### Как проверить сбои и обрывы связи

В самом модуле имитации сбоев нет: приложение подставляет их у себя. Готовые образцы — в `apps/demo/server`
(`failure-simulation.ts`, `connection-simulation.ts`). Схема такая.

**Сбой модели** (ядро само повторяет временные ошибки и показывает постоянные). Оберните модели каталога
промежуточным слоем (`wrapLanguageModel` из `ai`, тип `LanguageModelV4Middleware` из `@ai-sdk/provider`), который бросает
`APICallError`:

- `statusCode: 503`, `isRetryable: true` — «модель перегружена». Ядро тихо повторяет запрос сначала через 1, потом
  через 3 и 6 секунд, собеседник ничего не видит, пока попытки не кончатся.
- `statusCode: 401`, `isRetryable: false` — постоянная ошибка. Чат сразу показывает сообщение и кнопку «Повторить»,
  повторов нет.

Выбирайте сбой в запросе (cookie или заголовок) и передавайте его в слой через `AsyncLocalStorage`: так сбой получает
именно ход агента, начатый этим запросом.

**Сервер молчит.** Промежуточный слой Hono, который после `await next()` заменяет тело ответа `text/event-stream`
потоком, придерживающим байты (в том числе пинги). Вкладка через 30 с тишины (при пингах реже раза в 10 с — через три их интервала) покажет
«Переподключаемся…».

**Сервер недоступен.** Оборвите соединение: в Hono с `@hono/node-server` это
`(c.env as { incoming?: { socket?: { destroy(): void } } }).incoming?.socket?.destroy()`. Клиент получает сетевую ошибку,
и после трёх попыток чат показывает «Нет связи с сервером». Через Vite-прокси так не проверить: он ответит `500`
(см. шаг 6), поэтому открывайте страницу с самого сервера.

## 11. Обновление

Все пакеты SDK обновляются одной командой (версия у них общая):

```bash
pnpm update "@ykurilov/agent-chat-*" --latest
```

Затем прочитайте журнал изменений: `CHANGELOG.md` лежит в каждом пакете, например
`node_modules/@ykurilov/agent-chat-react/CHANGELOG.md`. Для каждой версии между старой и новой там написано, что
изменилось, а у ломающих изменений есть раздел «Как обновить приложение» с кодом «было/стало» и шагами. Выполните
их и проверьте `pnpm typecheck` и сборку. Скин Тандема тянет за собой свежий `@ykurilov/tandem-ui`: проверьте, что
в `package.json` приложения псевдоним `@tandem/ui` не остался на старой версии. Как пишется и выпускается журнал —
в [RELEASING.md](../RELEASING.md).

## Если что-то не так

| Что видно | Причина |
|---|---|
| Все адреса чата отвечают `401` | `resolveUser` вернул `null`: сессия не дошла до сервера или не распознана |
| `404` на своём чате | `resolveUser` вернул другой `id`, чем при создании чата |
| «Ключ провайдера не подходит» сразу после отправки, в журнале сервера «Нет ключа провайдера … задайте переменную окружения …» | нет нужной переменной (`DEEPSEEK_API_KEY`, `FIREWORKS_API_KEY` или `TOGETHER_API_KEY`) в окружении сервера |
| «Ключ провайдера не подходит», в журнале сервера пусто | ключ есть, но провайдер его не принимает |
| Вместо причины отказа вашей обёртки — «Что-то пошло не так» | текст должен лежать в `error` (строка) или `error.message` ответа 4xx с телом JSON; 5xx и HTML-страницы показываются общей надписью |
| «Что-то пошло не так», сервер ответил `500 { error: { kind: "other" } }` | непредвиденный сбой: подробность — в журнале сервера (`console.error` или ваш `logError`) |
| `better-sqlite3` не находит `.node`-файл | для вашей платформы нет готовой сборки (или Node старше 22): разрешите сборку (шаг 2) |
| `pnpm install` отвечает `401`/`404` на `@ykurilov/…` | в `.npmrc` проекта или в `~/.npmrc` осталась строка `@ykurilov:registry=https://npm.pkg.github.com` от старой установки: удалите её |
| Чат без оформления или без пузырей и кнопок | Tailwind не видит файлы скина или Тандема: `@source` на `@tandem/ui/dist` и на `@ykurilov/agent-chat-skin-tandem/dist` (шаг 5) |
| Ошибка типов у `tools` | версия `ai` в приложении отличается от версии в ядре (шаг 2) |
| `createPostgresChatStorage` бросает «Не удалось подключиться к PostgreSQL (хост:порт/база)» | база недоступна, неверный адрес или пароль; сам адрес в ошибку не попадает |
| «Не удалось применить миграции PostgreSQL» | у пользователя базы нет права создавать схему `agent_chat` и таблицы в ней |
| Чтение чата работает, а отправка — 403, клиент пишет «Сервер чата не принимает сообщения с этой страницы» | фронт и API на разных адресах: впишите адрес фронта в `allowedOrigins` (или шаблон `https://*.example.com`) — раздел «Фронт и API на разных адресах» в шаге 4 |
| 403, в журнале сервера «Origin не совпал с Host … за прокси передайте Host/X-Forwarded-Host» | прокси подменяет `Host`: `proxy_set_header Host $host; proxy_set_header X-Forwarded-Host $host;` (шаг 4, «За прокси») |
| Next.js: ответ на `POST …/messages` приходит целиком в конце | в файле маршрута нет `dynamic = "force-dynamic"`, либо перед приложением стоит прокси, буферизующий ответ (для nginx — `proxy_buffering off`) |
| Next.js: `404` на всех адресах чата | путь файла маршрута не совпадает с `basePath` (в том числе с `basePath` из `next.config`) |
| Next.js: после правки кода в `next dev` идущий ответ пропал | обработчик создаётся заново при перезагрузке модуля: держите его в `globalThis` |
