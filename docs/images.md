# Картинки от агента

Агент сам делает картинки: человек просит «нарисуй логотип», модель вызывает инструмент `generate_images`, картинки появляются
в ленте и лежат в чате как вложения. Это отдельный пакет `@ykurilov/agent-chat-images`, провайдеры — Runware и KIE.ai. Нужен пакет
вложений `@ykurilov/agent-chat-attachments`: в нём файлы хранятся и отдаются.

Без пакета ничего не меняется.

## Включить

```bash
pnpm add @ykurilov/agent-chat-images
```

В `.env` сервера — ключ провайдера тех моделей, что выбраны (в браузер он не уходит, в журнал и ошибки тоже):

```bash
RUNWARE_API_KEY=…   # GPT Image, Seedream у Runware
KIE_API_KEY=…       # z-image, Seedream у KIE, разделение на слои
```

```ts
// сервер
import { createImageGeneration } from "@ykurilov/agent-chat-images";

const images = createImageGeneration({
  attachments, // тот же объект createAttachments, что отдан обработчику чата
  env: process.env,
  spending: { storage, limits }, // расход в лимиты; без этого картинки не учитываются
});

createChatHandler({
  …,
  attachments,
  agent: {
    instructions: appInstructions,
    tools: (model) => ({ ...appTools(model), ...images.tools(model) }),
  },
});
```

Свой срок ожидания (210 с: генерация и скачивание) инструмент сообщает серверу сам, общий `toolTimeoutMs` его не оборвёт. Своя настройка `toolTimeoutMs.byTool.generate_images` главнее.

```tsx
// страница
import { imagesClient } from "@ykurilov/agent-chat-images/react";
<AgentChat … attachments={attachmentsClient} images={imagesClient} />;
```

Ошибка настройки (нет модели, провайдера или ключа) — исключение сразу при `createImageGeneration`, а не при первой просьбе человека.

## Что умеет инструмент

`generate_images({ prompt, count, aspectRatio })` (с [назначениями](#назначения) — ещё `purpose`): описание 2–2000 знаков, от 1 до 8 картинок за раз, пропорции `1:1`, `3:2`, `2:3`, `16:9`, `9:16`.

- Картинки делаются параллельно: пачка из трёх укладывается во время одной (около 12 секунд в живой проверке).
- Каждая готовая картинка скачивается, проверяется по содержимому (PNG, JPEG, WebP, не больше 10 МБ) и сохраняется вложением чата.
  Отдаёт её тот же адрес, что у вложений, только владельцу; удаляется вместе с чатом.
- Упала часть — удачные остаются в чате, модель получает итог «создано 2 из 3» и причины упавших, чтобы честно ответить человеку.
  Упали все — это тоже результат, а не сбой хода.
- «Стоп» обрывает ожидание: картинки, пришедшие позже, не сохраняются; на экране «Создание остановлено».
- Лимит расходов проверяется до генерации: исчерпан — результат «лимит расходов исчерпан», картинок нет.
- Описание и схема инструмента постоянные, кэш модели цел.

## Модели и цена

По умолчанию — GPT Image 2 в низком качестве: около полцента за картинку (живая проверка: $0.005 одна, $0.009 три в 16:9). Выбор модели — `model: "…"`.

| Модель | `model` |
|---|---|
| GPT Image 2 (по умолчанию) | `gpt-image-2` |
| GPT Image 2.5 Flare | `gpt-image-2.5-flare` |
| GPT Image 2.5 Sunburst | `gpt-image-2.5-sunburst` |
| Seedream 5.0 Flash | `seedream-5-flash` (около $0.019) |
| Seedream 5.0 Lite | `seedream-5-lite` |
| Z-Image у KIE — дешёвая картинка без текста | `z-image` ($0.004) |
| Seedream 5.0 Flash у KIE — держит надписи | `seedream-5-flash-kie` ($0.016) |
| Разделение на слои у KIE — только для [`removeBackground`](#назначения) | `seedream-5-flash-layers` ($0.032) |

Размер у каждой модели наименьший из допустимых (GPT Image — от 655 360 пикселей, 1:1 — 816×816; Seedream — 1K). Цену провайдер
присылает в ответе (у KIE — кредиты, 1 кредит = $0.005). Нет её в ответе или человек нажал «Стоп» после отправки — берётся цена из каталога
с запасом. По ней же заказ бронируется в лимитах, пока картинка рисуется. Цена учитывает размер и качество: у GPT Image medium вчетверо
дороже low, high и auto — в 16 раз. Замер Runware 5 октября 2026 (1024×1024, low): GPT Image 2 и 2.5 Flare — $0.00602,
2.5 Sunburst — $0.00599, с прозрачным фоном так же. Цены KIE — живая проверка того же дня.

## Размер 1K

`size: "1k"` — длинная сторона около 1024: 1:1 — 1024×1024, 16:9 — 1088×608, 3:2 — 1008×672. Стороны кратны 16, площадь не меньше
655 360 (1024×576 Runware отвергает). Без настройки — наименьший размер. Задаётся рядом с `model` или в назначении.
Seedream и z-image рисуют в 1K и так. Своя модель без `sizes["1k"]` в каталоге с `size: "1k"` — ошибка настройки при создании.

## Качество и прозрачный фон

GPT Image 2, 2.5 Flare и 2.5 Sunburst у Runware умеют выбирать качество, прозрачный фон — только 2.5 Flare и 2.5 Sunburst
(GPT Image 2 у Runware отвечает ошибкой `invalidOpenAiBackground`):

```ts
createImageGeneration({
  attachments, env: process.env,
  model: "gpt-image-2.5-sunburst",
  quality: "medium",            // low (по умолчанию), medium, high, auto
  transparentBackground: true,  // файл PNG с настоящей прозрачностью
});
```

Модель, которая этого не умеет (Seedream, z-image, у GPT Image 2 — прозрачный фон), с `quality` или `transparentBackground` — ошибка
настройки при создании.

## Постобработка

`output` переводит готовую картинку в другой формат и уменьшает её перед сохранением:

```ts
createImageGeneration({ …, output: { format: "webp", maxSide: 1024 } }); // большая сторона не длиннее 1024
```

Меньшая картинка не увеличивается, прозрачность в PNG и WebP сохраняется, `jpeg` с прозрачным фоном — ошибка настройки.
Обработку делает sharp (он уже стоит вместе с пакетом вложений); без `output` он не загружается.

## Назначения

Приложение задаёт назначения, агент выбирает нужное параметром `purpose`. Описание инструмента собирается из них один раз
при создании и дальше не меняется — кэш модели цел.

```ts
createImageGeneration({
  attachments, env: process.env,
  purposes: {
    picture: { description: "картинка без текста", model: "z-image" },
    "with-text": { description: "картинка с надписью, вывеска, постер", model: "seedream-5-flash-kie" },
    "no-background": {
      description: "предмет без фона: иконка, стикер",
      model: "z-image",
      removeBackground: { model: "seedream-5-flash-layers" },
    },
  },
});
```

- По умолчанию `purpose` — первое назначение. С `purposes` поля `model` и `provider` не задаются.
- У назначения свои `quality`, `size`, `transparentBackground` и `output`; общие поля рядом с `purposes` — значения по умолчанию для всех.
- `removeBackground`: сначала картинка, потом модель разделения на слои по её адресу. Сохраняется слой предмета (PNG с прозрачностью),
  расход пишется за оба шага. Подсказку разделению можно заменить полем `prompt`.

## KIE.ai: очередь, повтор и поздний результат

KIE работает очередью: задача отправляется, а сервер проверяет её, пока она не готова (первая проверка через 2 с, дальше реже, до 10 с).

- Не успела к сроку вызова (`requestTimeoutMs`) — модель получает у картинки ошибку с пометкой `готовится: true` и просьбой повторить позже.
- Опрос продолжается в фоне ещё `lateResultWindowMs` (по умолчанию 10 минут). Готовая картинка сохраняется в чат, расход пишется.
- Повтор того же вызова (тот же человек, чат, назначение, описание, пропорция) не создаёт новую платную задачу: ждёт старую,
  проверяет её или сразу отдаёт уже сохранённую. За одну задачу расход пишется ровно один раз, в том числе после «Стопа».
- Задачи в фоне лимит видит как заказанное, но не оплаченное.
- Реестр задач — в памяти процесса: после перезапуска сервера повтор создаст новую задачу. Чтобы задачи переживали
  перезапуск, нужен [фоновый режим](#фоновый-режим-ход-не-ждёт-картинку) с хранилищем задач.

Готовый результат вызова инструмента в истории чата сервер изменить не может. Поэтому о поздней картинке приложение узнаёт
в `onLateImage` и само решает, что сделать, например написать человеку или показать вложение:

```ts
createImageGeneration({
  …,
  onLateImage: async ({ ownerId, chatId, attachmentId, prompt }) => notifyUser(ownerId, chatId, attachmentId),
});
```

Ошибка обработчика уходит в `logError`, на работу сервера она не влияет.

## Свой приёмник

По умолчанию картинка ложится во вложения чата. `deliver` отдаёт её приложению: записать файл, обновить экран.

```ts
createImageGeneration({
  …,
  deliver: async (image, { ownerId, chatId, turnId, number, prompt, modelId }, ctx) => {
    if (!(await ctx.isCurrent())) return false; // задачу заменили или остановили — не записывать
    await saveSomewhere(ownerId, image.bytes, image.mediaType);
    return { saved: true }; // модель видит это у картинки в поле `результат`
  },
});
```

- `image`: байты, тип (`image/png` и т.п.), ширина, высота и модель.
- Вернул `false` — картинка не нужна: у модели она в ошибках, расход всё равно записан (картинка оплачена).
- Приёмник упал — у модели «Приложение не приняло картинку», подробности в `logError`.
- Со своим приёмником `onLateImage` не зовётся: поздняя картинка тоже приходит в `deliver`.
- `ctx.isCurrent()` — картинка ещё нужна (в фоне задачу могут заменить новым заказом, пока приёмник работает);
  `ctx.signal` — срабатывает при замене и остановке. Запись делайте условной: сначала `isCurrent()`, потом файл.

## Фоновый режим: ход не ждёт картинку

`mode: "background"` — инструмент отвечает модели, как только задача ушла провайдеру. Модель получает
`{ заказано, принято, задачи: [{ номер, id }], сообщение }` и продолжает ответ. Картинка приходит позже: во вложения
чата и в `onLateImage` или в свой `deliver`.

```ts
import { sqliteImageJobStore } from "@ykurilov/agent-chat-images/sqlite";   // или postgresImageJobStore(pool) из "/postgres"

const images = createImageGeneration({
  attachments, env: process.env, spending: { storage, limits },
  mode: "background",
  jobStore: sqliteImageJobStore("./data/chat.db"),
  pollIntervalMs: 3_000,     // шаг проверки у провайдера с очередью
  requestTimeoutMs: 90_000,  // одна попытка
  attempts: 2,               // вторая попытка ждёт ту же задачу, новой оплаты нет
  onQueued: (job) => ({ подсказка: "картинка появится в чате" }), // свои поля в ответ модели
  onLateImage: ({ chatId, attachmentId }) => showInChat(chatId, attachmentId),
});

// остановка сервера, до закрытия базы
await images.stop();
```

- Задачи лежат в `jobStore` (SQLite или PostgreSQL; без него — в памяти). После перезапуска сервер сам допроверяет
  незаконченные, пишет расход ровно один раз и доставляет картинку.
- Несколько копий сервера на одной базе: задачу ведёт одна (аренда на 30 с). Упала — через 30 с её подхватит другая.
  Часы копий не должны расходиться больше чем на срок аренды.
- Попытки кончились, а задача у провайдера ещё идёт — её ждут ещё `lateResultWindowMs` (10 минут). Не пришла — расход по цене модели.
- Описание инструмента в фоне своё и постоянное: «картинки придут сами, не заказывай заново».
- Для своих инструментов (картинки в файлы приложения, кнопка «Повторить») — `createImageQueue`, пример в
  [README пакета](../packages/images/README.md#картинки-в-файлы-приложения).

## Предел за ход

`maxImagesPerTurn: 3` — не больше трёх картинок за один ход агента. Счёт идёт по номеру хода (`turnId`), который ядро
передаёт в `agent.tools(model)`: повтор хода после сбоя и запасной провайдер счёт не обнуляют. Лишние картинки —
у модели в ошибках, без заказа и оплаты. Отказ лимита расходов место не занимает.

## Расход

Каждая отправленная задача пишет расход `source: "images"` с `modelId` модели картинок и `providerId` провайдера (`runware`, `kie`). Задача, которую провайдер
отклонил до работы (неверный ключ, нет денег, неверные параметры), расхода не пишет. Расход входит в лимиты `@ykurilov/agent-chat-limits` наравне с ответами.
Если у вас свой код с `switch` по `UsageSource`, добавьте значение `"images"`.

## Свой каталог, провайдер и прокси

```ts
import { createImageGeneration, extendImageCatalog, standardImageCatalog } from "@ykurilov/agent-chat-images";

const catalog = extendImageCatalog(standardImageCatalog, {
  removeModels: ["seedream-5-lite"],
  addModels: [myModel],
  addProviders: [myProvider],
  // сервер в России: Runware через свой прокси, как провайдеры моделей
  connectProviders: { runware: { baseURL: "https://proxy.example/runware/v1", headers: { "x-proxy-token": token } } },
});
createImageGeneration({ attachments, env: process.env, catalog, model: "my-model" });
```

Ключ и значения `headers` вычищаются из причин сбоя и журнала. Остальные настройки `createImageGeneration`: `maxImageBytes` (по умолчанию 10 МБ),
`requestTimeoutMs` (одна генерация, по умолчанию 150 с), `lateResultWindowMs`, `onLateImage`, `provider`, `fetch`, `logError`;
`deliver`, `mode`, `jobStore`, `pollIntervalMs`, `attempts`, `maxImagesPerTurn`, `onQueued` — разделы выше.

Свой провайдер с очередью описывает `queue: { submit, check }` рядом с `generate`: тогда и у него будут фоновый опрос и безопасный повтор.

## На экране

Пока картинки делаются, в ленте заглушки нужной пропорции; готовые открываются в [окне просмотра](media-viewer.md) вместе с остальными картинками чата.
Упавшие помечены, остановленные — «Создание остановлено». Без `images` или без части скина `GeneratedImages` вызов виден обычной строкой инструмента.
Скин версии 13: `GeneratedImages` получает `GeneratedImagesView` ([договор](contracts/agent-widgets/react-and-skin.md)); надписи — группа `images`.

Для чата с агентом на сервере без экрана React не нужен: у пакета `react` и `@ykurilov/agent-chat-react` необязательные.

Пример — `apps/demo` (в тестах Runware подменён; живьём — только при `RUNWARE_API_KEY`). Живая проверка: `IMAGES_LIVE_BATCH=1 pnpm test:live images`
включает пачку из трёх картинок (стоит центы), без переменной идёт одна картинка, Sunburst с прозрачным фоном и по одной картинке
каждого назначения KIE (нужен `KIE_API_KEY`, вместе около $0.06).


Конечные сбои фоновой очереди: [сохраняемые события, классификация и восстановление](image-failure-events.md).
