# Агент внутри продукта

Агент живёт внутри вашего продукта и работает с его объектами: уроком, заказом, документом, заявкой. Приложение решает, можно
ли сейчас говорить с агентом, получает итог каждого хода и показывает на экране свои события. У каждого объекта свой чат, агент
может начать разговор первым, а старую переписку можно перенести из прежней системы.

Всё здесь — по желанию. Без новых настроек чат работает как раньше, запрос к модели не меняется ни на байт.

Рабочий пример — страница `/lesson` демо-стенда (`apps/demo`): чат урока с приветствием, отказ «Урок закрыт», плашка «Урок
зачтён», кнопка «Проверить работу».

## Пример: чат урока

Сервер:

```ts
const chat = createChatServer({
  storage, catalog, agent, resolveUser,
  // Чат урока: приложение по ключу даёт данные, название и приветствие нового чата — или отказ.
  subjectChats: async ({ user, key }) => {
    const lesson = await lessons.find(key.replace("lesson:", ""));
    if (!lesson || !(await lessons.hasAccess(user.id, lesson.id))) return { code: "lesson_locked", message: "Нет доступа к уроку" };
    return { data: { lessonId: lesson.id }, title: lesson.title, greeting: { text: lesson.greeting } };
  },
  // Перед каждым ходом: урок закрыт — агент не отвечает, человек видит текст.
  beforeTurn: async ({ userId, chat }) => {
    const lessonId = chat.subjectData?.lessonId;
    if (lessonId && (await lessons.isClosed(userId, lessonId))) return { code: "lesson_closed", message: "Урок закрыт" };
  },
  // После каждого хода: записать итог к себе и показать событие на экране.
  afterTurn: async (turn) => {
    if (turn.status !== "complete") return;
    const passed = await lessons.recordAnswer({ turnKey: `${turn.messageId}:${turn.status}`, userId: turn.ownerId, text: turn.text });
    if (passed) return { events: [{ type: "lesson_passed", data: { score: passed.score } }] };
  },
});
```

Клиент:

```tsx
<AgentChat
  api="/api/chat"
  subject={`lesson:${lessonId}`}
  skin={tandemSkin}
  appEvents={{ lesson_passed: ({ event }) => <Badge>Урок зачтён</Badge> }}
  onAppEvent={(event, { live }) => live && event.type === "lesson_passed" && refreshProgress()}
  onTurnRefused={({ code }) => code === "lesson_closed" && showLessonClosedBanner()}
  composerActions={(composer) => (
    <Button disabled={!composer.canSend} onClick={() => composer.send("Проверь мою работу")}>Проверить работу</Button>
  )}
/>
```

## 1. Проверка перед ходом

`beforeTurn({ userId, chat, action, text?, messageId? })` зовётся до того, как агент начнёт отвечать. `messageId` — id
сообщения человека (у `send` и `edit`): по нему удобно связать резерв приложения с ходом. Вернули `{ code, message }` —
ход не начинается и ничего не записывается. Человек видит `message`, а приложение получает `code`.

- **Где зовётся.** Отправка (`send`), правка (`edit`), «Повторить» (`retry`), «Переделать» (`regenerate`), ответ на
  подтверждение (`approval`) и на виджет (`widget`), служебные сообщения (`notice`). Ещё — продолжение фоновой задачи после
  «да» и сообщение из мессенджера до расшифровки голоса и приёма файлов (там без `text`).
- **Порядок.** Свой чат → проверка сообщения → права (`chatCapabilities`, [9](#9-права-человека-в-чате)) → закрытие
  ([10](#10-закрытый-чат)) → `beforeTurn` → занятость чата и лимиты → запись. Поэтому в занятом чате отказ приложения придёт
  раньше «занято»: 403, а не 409. Запрещённое действие и закрытый чат до `beforeTurn` не доходят.
- **Код и текст.** Код — `[a-z0-9_.-]`, 1–64 знака. Неверный код — ошибка приложения: ход не начат, ответ 500 `other`, строка в
  `logError`. Текст — до 300 знаков, длиннее обрезается. Исключение из хука — тоже 500, ход не начат.
- **Ответ сервера.** 403 `{ error: { kind: "turn_refused", code, message } }`.
- **Служебные сообщения** (`deliverNotices`, итог фоновой задачи) не показывают отказ: сообщение записывается без хода.
- **Песочница** `beforeTurn` приложения не зовёт: её владелец — админ, а не человек приложения.
- **Позвать вручную** — `service.assertTurnAllowed(userId, chatId, action, text?)`: для своей работы, которая тратит деньги.
- **Ход не начался после пропуска** — хук `turnNotStarted({ userId, chat, action, messageId?, text?, reason })`. Пример: хук
  зарезервировал попытку урока, а чат оказался занят. Каждый пропуск `beforeTurn` закрывается ровно одним: `afterTurn`
  начатого хода или `turnNotStarted`. Причины: `busy` (чат занят или сервер останавливается), `too_many_turns`,
  `spending_limit`, `duplicate_message` (повтор id сообщения), `invalid` (неверный запрос), `chat_closed` (чат закрыли,
  пока шла проверка: хук приложения или другая вкладка), `no_turn` (хода и не будет:
  `assertTurnAllowed`, ответ ждёт ещё решений, служебное сообщение без хода), `error` (сбой). Ответ клиенту прежний;
  бросок хука — строка в `logError`.

  ```ts
  beforeTurn: async ({ userId, messageId }) => { await reserveAttempt(userId, messageId); },
  turnNotStarted: async ({ userId, messageId }) => { await releaseAttempt(userId, messageId); },
  ```

- **Какие ответы уходят с ветки.** У «Переделать» (`regenerate`), правки вопроса (`edit`) и «Повторить» (`retry`) хук
  получает `abandonedAnswerIds` — ответы агента, которые уйдут с текущей ветки, сверху вниз, — и `previousAnswerId` — ответ,
  который заменит новый (переделываемый, ответ на правленый вопрос или оборванный ответ, который «Повторить» заменяет
  соседом). У «Повторить» вопроса без ответа полей нет: заменять нечего. Пример: агент заполнял форму, человек нажал «Переделать» —
  приложение откатывает правки формы, сделанные брошенными ответами. Сообщения нет на ветке — полей нет (ход и так не
  начнётся). Пока ход не начался, ветка прежняя: если после пропуска пришёл `turnNotStarted`, ничего не ушло, а хук
  получает те же поля — верните откат по ним. Надёжный порядок: в `beforeTurn` откатить и запомнить, в `turnNotStarted`
  вернуть. Ещё проще — держать правки формы в состоянии ветки (`model.state`, [12](#12-состояние-чата-на-ветке)): тогда
  «Переделать», правка и выбор ветки переключают его сами, а копию у приложения сводит `onStateChanged`.
  Выбор ветки (`selectBranch`) хода не начинает и `beforeTurn` не зовёт: для него — `onStateChanged` с причиной
  `selectBranch`.

**Отказ в доступе.** `resolveUser` может вернуть `{ refused: { code, message, status? } }` вместо `null`. Тогда на любом адресе
чата ответ `status` (401 или 403, по умолчанию 403) `{ error: { kind: "access_refused", code, message } }`. Так же отвечают
адреса голоса, голосового режима и привязки мессенджеров; WebSocket голосового режима закрывается кодом 4401. Песочница на
отказ отвечает 404, как будто её нет.

**В браузере.** `AgentChat` показывает текст отказа, а не «нет связи», и не предлагает «Повторить». Текст сообщения
возвращается в поле. `onTurnRefused({ kind, code, message })` получает каждый отказ. Отказ в доступе при открытии чата
показывается вместо ленты, с кнопкой «Повторить»: удачная загрузка истории его снимает. Отказ открыть чат объекта
(`subjectChats` вернул `{ code, message }`) тоже приходит в `onTurnRefused`. Мессенджеры отвечают человеку текстом отказа.

## 2. Итог хода и события приложения

`afterTurn(turn)` зовётся после каждого хода и ждётся: человек получает конец ответа только после хука. Пока хук идёт, чат
занят.

- **Что получает** (`TurnResult`): `ownerId`, `actorId` (кто сделал ход: владелец, а в копии у сотрудника — сотрудник),
  `chatId`, `messageId`, `status`, `text` (текст ответа подряд), `parts`, `usage`, `costUsd`, `error?`, `trigger` (каким
  действием начат ход), `channel` (веб или мессенджер), `subject?` (ключ и данные объекта чата), `staff?`, `recovered`.
- **Кто остановил** (`stopReason`, только у `status: "stopped"`): `user` — «Стоп» человека, `timeout` — общий срок хода
  (`agent.turnTimeoutMs`), `shutdown` — остановка сервера (`flush`). У итога, доделанного после перезапуска, его нет.
- **Обрыв по длине** (`lengthCut: true`): ответ упёрся в предел токенов (`agent.maxOutputTokens`) и оборван.
- **Предел шагов** (`stepLimit: true`): ход упёрся в `agent.maxSteps`. Статус обычный (`complete`): последний шаг был
  итоговым, без инструментов, и модель подвела итог, но дело могло остаться недоделанным. В журнале SDK — строка
  `[предел шагов] чат=… ответ=… модель=… шагов=…`. Человеку на экране ничего не показывается; показать своё — по этому
  полю или по части `data-step-limit` в ответе.
- **Любой итог:** законченный, остановленный, с ошибкой, прерванный. Ответ, который ждёт «да» человека (`awaiting_approval`),
  после решения продолжается тем же сообщением — хук позовут второй раз с новым статусом.
- **Копия у сотрудника.** В копии чата человека в песочнице хук зовётся с `ownerId` человека, его объектом, `staff` и
  `actorId` админа. **При `turn.staff` в данные человека не писать** — иначе проверка сотрудника засчитается человеку. В
  обычном песочном чате хук не зовётся.
- **Хук может прийти повторно** (повтор после сбоя, доделка после перезапуска). Пишите идемпотентно: ключ повтора —
  `messageId` + `status`.
- **Срок и повторы.** `afterTurnTimeoutMs` (по умолчанию 30 000) — на все попытки вместе. `afterTurnAttempts` (по умолчанию 3,
  паузы 1 и 3 с). Не вышло — `logError`, событие чата `after-turn-failed`, отметка в сообщении. Ответ человека цел, чат
  освобождается.
- **Перезапуск сервера.** Состояние хука хранится в сообщении (`pending` → `done` или `failed`). Хук, который не успел
  отработать, доделывается при старте (`recoverInterruptedAnswers`) или проверкой брошенных ответов — когда с его начала прошло
  больше срока плюс 60 с: так две копии сервера не зовут его одновременно. Ответы, прерванные перезапуском, тоже получают хук
  (`recovered: true`, статус `interrupted`). Приветствие и импорт хук не зовут.
- **«Стоп» во время хука.** Ход перестаёт ждать хук: человек сразу получает конец ответа, чат свободен. Хук доделывается в
  фоне, его события ложатся в ответ и приходят на экран через канал наблюдения.
- **Хранилище.** Нужны `setAfterTurnState` и `listPendingAfterTurn`; они есть у встроенных хранилищ (миграция SQLite `0015`,
  PostgreSQL `0014`). Своё хранилище без них с `afterTurn` — ошибка при создании службы.

**События приложения** — `{ type, data? }`: тип до 100 знаков, `data` — JSON до 16 КБ. Модели они не отправляются.

- **Из хука:** `return { events: [...] }` — события ложатся в конец ответа и приходят на экран живьём.
- **Из инструмента:** `model.emitAppEvent(event)` — событие сразу пишется в ответ и уходит в поток.
- **Вне хода:** `service.publishAppEvent({ ownerId, chatId, event })` — живьём через канал наблюдения, без записи в историю.
- **На экране:** `appEvents={{ lesson_passed: View }}` рисует событие внутри ответа (`View` получает `{ event, messageId }`).
  `onAppEvent(event, { live, messageId? })` зовётся по разу на событие: `live: true` — пришло живьём, `false` — лежало в
  истории при открытии чата. События из ответа переживают перезагрузку страницы.

### Свои данные чата

У любого чата есть `chat.data` (JSON-объект до 16 КБ; `subjectData` — тот же объект). Новый чат: `service.createChat(userId, { data })` или, из браузера, `createChatServer({ newChatData: ({ user, request }) => data })`. Правка: `service.updateChatData(userId, chatId, patch)` сливает верхние ключи (`undefined` удаляет ключ). Чтение без записи: `service.getChatData(userId, chatId)` — копия, без событий, нет данных — `{}`; чужой чат — `ChatNotFoundError`. Список: `service.listChats(userId, { data: { formId: "f1" } })` — равенство верхних ключей (строка, число, булево, `null`). Данные видят `beforeTurn`, `chatInstructions`, инструменты (`model.chat.data`) и `afterTurn` (`turn.chatData`); в браузер и к модели они не уходят. `turn.chatData` — данные на момент итога. Ключ `__proto__` не принимается. Событие `chat-data-changed` вкладке не пересылается. Нужно хранилище с `updateChatData` (SQLite и PostgreSQL SDK его имеют).

## 3. Чат объекта

У чата есть необязательный ключ объекта (`subjectKey`, 1–200 знаков) и данные объекта (`subjectData`, JSON-объект до 16 КБ). У
одного человека — один чат на ключ: это держит уникальный индекс базы, поэтому два одновременных открытия дают один чат.

- **Сервер.** `subjectChats({ user, key, request })` в обработчике чата открывает адрес `POST {base}/subject { key }` →
  `{ id, created }`. Приложение возвращает `{ data?, title?, greeting? }` или отказ `{ code, message }` (403 `turn_refused`, чат
  не создан). Нужно хранилище с `findChatBySubject`: без него — ошибка при создании обработчика.
- **Служба.** `service.openSubjectChat({ ownerId, key, data?, title?, greeting? })` → `{ chat, created }`. Данные, название и
  приветствие пишутся только при создании: у найденного чата они не меняются.
- **Клиент.** `<AgentChat subject="lesson:42" />` при открытии спрашивает id чата у сервера и дальше работает как обычный чат.
  `chatId` и `subject` вместе не задавайте.
- **Данные объекта в браузер и модели не уходят.** Их видят `beforeTurn` (в `chat`), инструменты (`model.subject = { key, data? }`,
  одно значение на весь ход, его же получают помощники) и `afterTurn` (`turn.subject`).
- **Список чатов.** Чаты объектов в общем списке не видны. `chatList: { subjectChats: true }` — видны, с полем `subjectKey`.
  В службе — `listChats(userId, { subjects: "include" | "only" })`.

## 4. Приветствие

`greeting: { text }` (1–10 000 знаков) в `createChat(userId, { greeting })`, `openSubjectChat` или ответе `subjectChats`.
Агент пишет первым: в новом чате сразу лежит его ответ с этим текстом. Модель не вызывается, токены не тратятся. Экран
показывает приветствие, а модель видит его в истории.

Некоторые провайдеры не принимают разговор, который начинает агент. Поэтому перед ведущим ответом агента ядро ставит в запрос
одну постоянную служебную строку от имени человека (`GREETING_LEAD`). Она одинаковая всегда и не мешает кэшу. У чатов, которые
начинает человек, запрос прежний. Проверено на всех моделях стандартного каталога у всех провайдеров.

Вместо готового текста можно дать указание: `greeting: { instruction }` (1–10 000 знаков, ровно одно из `text` и
`instruction`). Тогда при создании чата SDK один раз будит агента служебным сообщением `conversation_started`, и агент
пишет первым сам. Это обычный ход: модель вызывается, токены тратятся. Найденный чат не будится. Сбой побудки уходит в
`logError`, а чат всё равно отдаётся.

«Переделать» у приветствия нет: переделать можно только ответ на сообщение человека. Пока человек не написал, экран кнопку
не показывает, а `regenerate` такого ответа — `InvalidMessageError` (HTTP 400 `invalid`), ничего не записано.

## 5. Лимит сообщений

Окно лимитов (пакет `@ykurilov/agent-chat-limits`) считает доллары (`limitUsd`) или сообщения человека (`limitMessages`) —
ровно одно из двух. Остальное — как у денег: сутки, неделя, месяц, «N часов от первого сообщения», на всё время; личные
лимиты, сброс, пороги.

```ts
createSpendingLimits({
  storage, catalog,
  windows: [{ id: "day-messages", scope: "user", kind: "calendar", unit: "day", limitMessages: 20 }],
  exemptUsers: ({ userId }) => staff.has(userId),
  onMessageThreshold: ({ remaining, userId }) => remaining === 3 && notify(userId, "Осталось 3 сообщения"),
});
```

- **Что считается:** отправка и правка сообщения. Переделка, «Повторить», служебные сообщения, ответы на подтверждения и
  виджеты, импорт и песочница — нет.
- **Отказ:** 429 `spending_limit_reached` с `unit: "messages"`. Экран: «Осталось 1 сообщение», «Лимит сообщений исчерпан,
  обновится 7 октября».
- **Удаление чата счёт не сбрасывает:** он хранится в состоянии лимитов. Два сообщения на последнее место — проходит одно.
- **Пороги:** `onMessageThreshold({ windowId, threshold, used, limit, remaining, userId, … })` — по разу на порог в окне
  (`thresholds`, по умолчанию 80% и 100%). Денежный `onThreshold` окна сообщений не видит.
- **`exemptUsers`** снимает все окна, денежные тоже. Потолок хода (`maxCostUsd`, `maxToolCalls`) остаётся: он защищает от
  бесконечного хода.
- Подробно — [README пакета](../packages/limits/README.md#окна-лимитов).

## 6. Импорт старой переписки

`service.importChat({ ownerId, chat, messages })` → `{ chatId }`. Адреса HTTP нет: импорт зовёт только сервер.

```ts
await chat.service.importChat({
  ownerId: "user-7",
  chat: { title: "Урок 3", subjectKey: "lesson:3", createdAt: "2025-03-01T09:00:00Z", state: { step: 2 } },
  messages: [
    { role: "assistant", createdAt: "2025-03-01T09:00:00Z", parts: [{ type: "text", text: "Привет! Начнём урок." }] },
    { role: "user", createdAt: "2025-03-01T09:05:00+03:00", parts: [{ type: "image", bytes, mediaType: "image/png", filename: "work.png" }] },
  ],
});
```

- **Сообщения:** 1–5000, одна ветка, по порядку. Роли `user` и `assistant`, первое может быть от агента. Даты ISO 8601 с
  часовым поясом, не убывают. Дата чата — `chat.createdAt` (не позже первого сообщения) или дата первого сообщения;
  «последнее изменение» — дата последнего.
- **Без хода, памяти, расхода и лимитов.** Ответы агента — законченные, без модели.
- **Картинки** — байты; их сохраняет пакет вложений (`attachments.importFile`) до записи чата. Не больше 500 картинок и 200 МБ
  за импорт. Запись чата не удалась — файлы убираются. Без вложений картинки — ошибка до записи.
- **Картинка в ответе агента** видна на экране, а модели уходит текстом «[картинка: имя]»: провайдеры не принимают файлы от
  агента.
- **Состояние и закрытие:** `chat.state` — то, что отдаёт `getChatState().values` (верхние ключи без `$`, пределы как у
  `model.state`); `chat.closed` — `{ code, message }`, как у `closeChat`. `getChatState`, `model.state` и экран видят
  состояние сразу, закрытый чат закрыт сразу. Состояние лежит в служебном сообщении перед перенесённой историей:
  «Переделать» и правка любого сообщения его не теряют. Экран этого сообщения не показывает (состояние приходит в
  начале первого сообщения истории), модель его не получает. Вызовы инструментов
  не переносятся.
- **Ошибки:** данные не подходят — `TypeError`, ничего не записано; чат с таким id есть — `ChatAlreadyExistsError`; ключ объекта
  занят — `DuplicateChatSubjectError`.

## 7. Сотрудник проверяет чат человека

Админ песочницы видит чаты человека только на чтение и проверяет ответы агента в копии в своей песочнице. Человек ничего не
видит, его чат не меняется. Включается опцией `people` у `createSandboxHandler` (`{ find }` — поиск людей, `true` — ввод id) и
у `<AgentSandbox people />`.

- В копии агент читает память человека, но не пишет в неё. Расход и лимиты — на админа.
- Инструменты и `afterTurn` видят человека, его объект (`model.subject`, `turn.subject`) и сотрудника (`model.staff`,
  `turn.staff`, `turn.actorId`). **При `staff` в данные человека не писать** — ядро такие записи не перехватывает.
- Подробности — [песочница, раздел «Чаты людей»](sandbox.md#чаты-людей).

## 8. Свои кнопки у поля ввода

`composerActions` у `AgentChat` — готовый узел или функция от помощника поля:

- `value`, `setValue(text)` — текст в поле;
- `send(text?)` — отправить по тем же правилам, что «Отправить»: с `text` уходит он, без — то, что в поле (с файлами);
- `addFiles(files)` — положить файлы в поле, как скрепка;
- `busy`, `blocked`, `canSend` — идёт ответ, отправка остановлена (лимит или закрытый чат), отправка сейчас пройдёт.

Пока `canSend` ложно, `send` отказывает сразу и ничего не откладывает: гасите кнопку. Функция вызывается при каждом рендере —
делайте её быстрой, помощника не сохраняйте. Скин рисует кнопки через `Composer.actions` (договор скина v19,
[docs/skin-v19.md](skin-v19.md)); Тандем ставит их рядом с голосом и оставляет видными в голосовом режиме. Широкие элементы он прижимает влево и обрезает
на узком экране, а кнопка-значок (`Button size="icon"`) остаётся по центру без обёрток.

## 9. Права человека в чате

Публичный посетитель видит только переписку и поле ввода, а сотрудник может всё. Кто что может, решает приложение функцией
`chatCapabilities` у сервера. В SDK нет правил «публичный» или «тестовый» чат.

```ts
createChatServer({
  …,
  chatCapabilities: ({ userId, chat }) =>
    isVisitor(userId) ? { edit: false, regenerate: false, branches: false, modelChoice: false } : {},
});
```

- **Права.** `edit` — правка своего сообщения, `regenerate` — «Переделать» готовый ответ, `retry` — «Повторить» оборванный
  ответ (отдельно от `regenerate`), `branches` — переключение веток, `modelChoice` — выбор модели, `answerEditing` — правка
  ответа агента, `chatList` — переименование, удаление и список чатов на экране, `compact` — сжатие вручную, `attachments` —
  файлы в сообщении и загрузка вложений, `voice` — голосовые сообщения, микрофон и режим разговора, `reasoning` — мысли
  модели на экране, `toolDetails` — служебные инструменты на экране, `steer` — поправка к идущему ответу (`POST …/steer`; при запрете
  экран не предлагает поправку и ждёт конца ответа, как при `steering={false}`), `modelDetails` — модель, провайдер и
  расход ответа (при запрете выключает и `modelChoice`), `errorDetails` — подробности сбоя провайдера (выключено по умолчанию;
  см. ниже), `appNotices` — служебные пометки приложения на экране (выключено по умолчанию: «Агент написал первым —
  человек молчал 1 ч 7 мин» в тестовом чате сценария; `modelDetails: false` выключает и его). Пометки уходят без
  текста для модели и только через белый список `createChatService({ appNoticeViews })`: имя пометки → функция,
  которая из `data` делает безопасные данные для экрана. Пометка без функции (или функция вернула `undefined`) в браузер
  не уходит. Сценарии (`flow.withChat`) добавляют свои функции сами. Строки даёт `noticeLines` у `AgentChat`.
- **Права — для людей через HTTP.** Сервер приложения, который сам удаляет чат или ставит модель, передаёт
  `{ by: "app" }`: `service.deleteChat(userId, chatId, { by: "app" })`, `service.setModel(userId, chatId, choice, { by: "app" })`.
  Права экрана тогда не проверяются, владение чатом — как всегда. Адреса HTTP (`DELETE {chat}`, `PUT {chat}/model`)
  проверяют права всегда. `getChatData`, `updateChatData` и `createChat` прав экрана не проверяют и без опции.
- **Мысли и служебные инструменты** при `reasoning: false` и `toolDetails: false` не уходят в браузер: ни в историю, ни в
  поток ответа, ни в повтор кусков после переподключения. Модель, хранилище и `afterTurn` получают всё. Виджеты и браузерные
  инструменты видны всегда. Свой инструмент с карточкой на экране пометьте в описании:
  `tool({ …, metadata: { showOnScreen: true } })`. Метка записывается в каждый вызов (`toolMetadata`) и работает и для
  набора инструментов функцией от модели; модели она не уходит. Вызовы, записанные до пометки, метки не имеют и при
  запрете скрыты. Права считаются на того, кто открыл поток, в момент открытия. Вызов, который спросил подтверждения
  (`needsApproval`), виден сам, без пометки: иначе человек не увидит вопроса и ход зависнет.
- **Модель, провайдер и расход** при `modelDetails: false` не уходят в браузер: у чата истории нет `ownerId`, `modelId`,
  `providerId`, `reasoning`; у сообщений — `metadata.modelId`, `providerId`, `usage`; у частей и кусков потока —
  `providerMetadata`, `callProviderMetadata` и `resultProviderMetadata`; кусок `start`, итог ответа и отметка перехода на
  запасную модель (`data-step-reset`) — без модели и расхода. Разделитель сжатия идёт без текста сводки (`summary: ""`)
  — в истории и в `GET …/compactions`: сводка пересказывает выходы служебных инструментов. То же при переподключении и
  смене ветки. Запрет выключает и выбор модели (`PUT …/model` — 403). Модель, хранилище, хуки и лимиты
  получают всё. Меню моделей (`GET …/models`) чата не знает: закройте его опцией сервера
  `modelMenu: ({ userId }) => !isVisitor(userId)` (иначе 403 `action_forbidden`, `action: "modelDetails"`). Экран меню
  без выбора модели не запрашивает; видит ли модель картинки, вложения узнают из истории (`modelAcceptsImages`).
- **Подробности сбоя для админа** — право `errorDetails`, по умолчанию `false`. Ход, упавший на провайдере, хранит в
  ответе `error.details`: провайдер, модель, код ответа, причину одной строкой (сообщение провайдера до 300 знаков; ключи
  из окружения, `Bearer` в любом регистре, значения после `key=`/`token`/`api-key`/`password`, маски ключей со `*`,
  параметры адресов, `org-…`/`proj_…` и e-mail вычищены) и `resetsAt` — когда провайдер снимет предел, если сообщил (у
  OpenRouter «resets 2026-11-01» → `2026-11-01T00:00:00.000Z`; только будущее не дальше двух лет, без пояса — UTC). Ответ
  модерации может повторять текст человека — его видит только тот, кому открыто право. Всё, что ушло в браузер, видно любому через инструменты разработчика,
  поэтому подробности уходят только тому, кому приложение их открыло: `chatCapabilities: ({ userId }) => isAdmin(userId) ?
  { errorDetails: true } : {}`. Остальным — только `error.kind`, и в истории, и в потоке, и при переподключении. При
  `modelDetails: false` выключено и оно (одна строка в журнал). `afterTurn` получает подробности всегда. Подпись на экране — `labels.errorText`
  (раздел о надписях в README пакета React).
- **Публичный чат** (посетитель без входа): `chatCapabilities` → `{ modelDetails: false, toolDetails: false, reasoning: false, … }`,
  `modelMenu` для посетителей → `false`, служебные id в состоянии — `privateStateKeys`. Память (`memory`) — по человеку, а
  не по чату: посетителям её не подключайте.
  Посетитель без входа — человек со своим `userId` от `resolveUser` (например, `visitor:<id сессии из cookie>`);
  `isVisitor = (userId) => userId.startsWith("visitor:")`.
- **В мессенджере** голосовое при `voice: false` и файлы при `attachments: false` не скачиваются и не распознаются: человек
  получает текст «недоступно, напишите текстом». `/chats` и выбор чата из списка смотрят на `chatList` текущего чата.
- **По умолчанию всё разрешено.** Функция возвращает только запреты; нет функции — всё как раньше.
- **Вход тот же, что у `beforeTurn`:** человек и чат с данными объекта. Функция зовётся, только когда действию нужно право:
  простое сообщение без файлов её не зовёт. За один запрос она зовётся не больше раза. Не булево значение, неизвестное
  право (опечатка вроде `edits`) или исключение — ошибка приложения (500, строка в `logError`): опечатка не даёт доступ молча.
- **Проверка на сервере, а не только на экране.** Запрещённое действие в обход экрана получает 403
  `{ error: { kind: "action_forbidden", action, code: action, message: "Это действие в этом чате недоступно." } }`,
  ничего не записано. Мессенджер отвечает человеку тем же текстом. Экран после такого ответа перечитывает права.
- **История несёт права** (`capabilities`, все права). `<AgentChat>` сам прячет кнопки, стрелки веток, выбор модели,
  скрепку и микрофон. `<ChatWorkspace>` при `chatList: false` показывает только чат, без списка. Права и закрытие страница
  узнаёт из `onChatAccessChange({ capabilities, closed })`.
- **Песочница** права приложения не применяет: там админ.
- **Вручную** — `service.assertCapability(userId, chatId, "attachments")` (бросает `ActionForbiddenError`).
- **`editAnswer`** (правка ответа агента) бросает `ActionForbiddenError` при `answerEditing: false` и `ChatClosedError` в
  закрытом чате.

## 10. Закрытый чат

Заявка отправлена, урок сдан, форму сняли с публикации — разговор окончен. Переписка видна, но писать дальше нельзя.

```ts
// Из инструмента: чат закроется, когда ход закончится.
agent: {
  …,
  tools: (model) => ({
    submit_form: tool({
      …,
      execute: async (input) => {
        await submitForm(input);
        model.closeChat?.({ code: "form_submitted", message: "Заявка отправлена. Спасибо!" });
        return { ok: true };
      },
    }),
  }),
},

// Из своего кода приложения:
await chat.service.closeChat({ ownerId, chatId, code: "form_unpublished", message: "Форма снята с публикации" });
await chat.service.reopenChat({ ownerId, chatId });
```

- **Код и текст** — те же правила, что у отказа `beforeTurn`: код `[a-z0-9_.-]` до 64 знаков, текст до 300.
- **Что нельзя в закрытом чате:** отправка, «Повторить», ответ на подтверждение и виджет. Ответ сервера — 409
  `{ error: { kind: "chat_closed", code, message } }`, ничего не записано. Мессенджер отвечает человеку текстом закрытия.
  Права проверяются раньше: запрещённое действие в закрытом чате — `action_forbidden`.
- **Закрытие — запись на ветке.** Как любое состояние чата (раздел 12), оно лежит в сообщениях: из инструмента — в ответе
  агента, из кода — служебной записью в конце ветки. Поэтому правка, «Переделать», выбор ветки и правка ответа до точки
  закрытия открывают чат: на новой ветке закрытия нет. Вернулся стрелкой на старую ветку — чат снова закрыт.
- **Закрыть навсегда** — правами (раздел 9): `chatCapabilities` видит `chat.closed`.

  ```ts
  chatCapabilities: ({ chat }) => (chat.closed ? { edit: false, regenerate: false, branches: false, answerEditing: false } : {}),
  ```

- **Из инструмента** `model.closeChat` записывает закрытие сразу, при вызове: если сервер упадёт посреди хода, чат после
  перезапуска уже закрыт. Ход доводится до конца при любом итоге: «Стоп», сбой, срок хода. Дело инструмента уже сделано.
  Экран и события узнают о закрытии, когда итог хода записан. Вызов после конца хода не закрывает чат, только строка в
  `logError`.
- **Из кода посреди хода** закрытие ждёт конца хода и ложится записью после ответа. Проверки, история и список видят чат
  закрытым сразу. `reopenChat` на открытом чате ничего не пишет.
- **Закрытие побеждает паузу.** Ход закрыл чат, а в нём ждёт подтверждение или виджет. Или чат закрыли из кода, пока ответ
  ждёт человека. Тогда ждущие запросы закрываются отказом, как при «Стопе», и ответ считается законченным. Ответить на них
  уже нельзя, и ход не повиснет навсегда.
- **Гонки.** Чат закрыли, пока шла проверка перед ходом (`beforeTurn` или другая вкладка): ход не начнётся, ответ 409
  `chat_closed`, резерв приложения закрывается `turnNotStarted` с причиной `chat_closed`.
- **Экран узнаёт сразу:** куском потока ответа, событием наблюдения `chat-closed` (и `chat-reopened`) и из истории
  (`chat.closed`). Поле ввода неактивно, над ним текст закрытия. Скин рисует его через `ChatClosedNotice` (договор v20,
  [docs/skin-v20.md](skin-v20.md)); скин v19 покажет `ErrorNotice` с тем же текстом. `onTurnRefused` получает отказы
  `chat_closed` и `action_forbidden`.
- **Служебные сообщения** (`deliverNotices`) в закрытый чат пишутся без хода.
- **Чаты, закрытые в 0.27** (только флаг чата, записи нет), закрыты по флагу. Перенос ленивый: перед первой правкой,
  «Переделать», выбором ветки или правкой ответа ядро переносит флаг записью в конец текущей ветки. Миграции нет, делать
  ничего не нужно.
- **Список чатов** (`listChats`) отдаёт `closed`: на экране у закрытого чата пометка «Закрыт», в `/chats` мессенджера — «закрыт».
  Это копия закрытия текущей ветки в записи чата: ядро обновляет её при закрытии, открытии и смене ветки (событие
  `chat-closed` или `chat-reopened`). Права (`chatCapabilities`) и история берут закрытие с ветки, а не из копии. Не
  записалась копия — строка в `logError`; следующее открытие истории дописывает её.
- **Песочница** закрывает чат так же, как приложение: админ видит, что закрытие работает. Продолжить тест можно двумя путями:
  новая копия чата человека открыта всегда, а кнопка «Открыть чат снова» (`POST {sandboxBase}/chats/:chatId/reopen`, только
  админ) снимает закрытие с чата песочницы.
- **Своё хранилище** реализует необязательный `setChatClosed(chatId, closed | null)` и отдаёт `closed` в `getChat`: это копия
  для списка и прав. Без метода закрытие работает, но список и `chatCapabilities` его не видят.

## 11. Новый чат

Можно ли человеку завести ещё один чат, решает приложение хуком `beforeCreateChat({ userId, origin? })` у сервера. `origin` —
мессенджер, из которого заводят чат; нет — веб.

```ts
createChatServer({
  …,
  beforeCreateChat: async ({ userId }) =>
    (await countChats(userId)) >= 3 ? { code: "chat_limit", message: "Можно не больше трёх чатов." } : undefined,
});
```

- **Где зовётся.** `POST {base}` (новый чат на экране), `/new`, `/start` с меткой и первый чат в мессенджере. Чаты объектов
  приложения (`openSubjectChat`) и импорт его не спрашивают: их заводит приложение, а не человек.
- **Код и текст** — те же правила, что у `beforeTurn`. Неверный отказ или исключение — ошибка приложения (500, строка в
  `logError`).
- **Ответ сервера** — 403 `{ error: { kind: "chat_creation_refused", code, message } }`. Экран получает отказ в
  `onTurnRefused` (вид `chat_creation_refused`), мессенджер отвечает человеку текстом.
- **Песочница** хук не зовёт: там админ.
- **Нет хука** — чат заводится как раньше.

## 12. Состояние чата на ветке

Инструмент записывает данные не только в свою таблицу, но и в ответ агента, рядом с результатом вызова. Состояние чата —
сумма записей всех сообщений текущей ветки. Пример: посетитель сказал «почта a@x.ru», агент записал поле. Потом посетитель
исправил своё первое сообщение — ответ с записью ушёл с ветки, почты в состоянии больше нет. Переключился стрелкой на старую
ветку — почта вернулась. Приложению для этого ничего делать не нужно.

```ts
createChatServer({
  …,
  agent: {
    tools: (model) => ({
      update_form: tool({
        description: "Записать поле заявки",
        inputSchema: z.object({ field: z.string(), value: z.string() }),
        execute: async ({ field, value }) => {
          model.state?.set(`fields.${field}`, value);   // ляжет частью ответа рядом с результатом вызова
          return { ok: true, saved: model.state?.get("fields") };
        },
      }),
    }),
  },
});

// Сервер приложения: что сейчас в заявке
const { values, atMessageId } = await chat.service.getChatState(ownerId, chatId);
```

- **`model.state`**: `get(path?)` — копия значения (без пути — всё состояние), `set(path, value)`, `unset(path)`. Путь —
  ключи через точку (`fields.email`), до 200 знаков. **Ключи без точек, массивы целиком**: путь через строку или массив
  (`fields.report.pdf` при строке в `fields.report`, `items.0`) — `TypeError`, а не тихая замена объектом. Недостающие
  объекты по пути создаются. Значение — простой JSON: объекты, массивы, строки, конечные числа, `true`/`false`, `null`.
  `Map`, `Set`, `Date`, экземпляры классов, `NaN`, `Infinity`, `undefined` — `TypeError`. Убрать значение — `unset`.
- **Только значения, без прибавок.** Повтор вызова после сбоя ставит то же значение и ничего не задваивает. Запись, которая
  ничего не меняет, в ответ не ложится.
- **Где лежит.** Часть ответа `data-app-state` вида `{ set: { "fields.email": "a@x.ru" } }` или `{ unset: ["fields.phone"] }`
  — по одной на вызов `set` или `unset`. Модели не отправляется, на экране не рисуется, запрос к модели и кэш не меняет.
  Новых таблиц и миграций нет.
- **Свёртка** — по всей ветке из хранилища, а не по сжатой истории модели: сжатие состояние не теряет. Записи сообщений
  при любом итоге хода («Стоп», сбой) остаются: дело инструмента уже сделано. «Повторить» оборванного ответа переносит
  их в новый ответ вместе с выполненными вызовами.
- **«Править ответ»** (`editAnswer`) переносит записи в копию ответа как есть.
- **Пределы.** Запись — JSON до 16 КБ, всё состояние — до 256 КБ. Больше — `AppStateTooLargeError` внутри инструмента:
  модель видит её текстом. Большие данные (текст документа) — в свою таблицу, а в состояние — ссылку или номер версии.
- **После конца хода** запись не принимается: не бросает, строка в `logError`. Инструмент, не услышавший «Стоп», не испортит
  новую ветку.
- **Вне хода** (сжатие, фоновая задача) `model.state` нет: то, что приложение знает само, пишите в данные чата
  (`updateChatData`). В состоянии — то, что дал разговор.
- **Служебные ключи SDK** — верхние ключи на `$`: приложение их не пишет (`TypeError`) и не видит в `get`,
  `getChatState`, `onStateChanged`, истории и потоке ответа.
- **Закрытые ключи приложения** — `privateStateKeys: ["booking"]` в опциях обработчика или службы. Служебные номера
  брони и ревизии не уходят в браузер: ни в историю, ни в поток ответа, ни в `state-changed` наблюдения, так что
  `useChatState` их не видит. Модель (`model.state`), `getChatState`, `onStateChanged`, `subscribeEvents` и хранилище
  видят их как обычно. Ключ — верхний, без точки и не на `$` (иначе `TypeError` при создании). Закрыто только само
  состояние: не возвращайте закрытое значение в выходе инструмента (его прячет лишь `toolDetails: false`) и не давайте
  модели называть его в ответе (текст ответа не прячется никак). Например, инструмент брони возвращает модели
  «забронировано на 12 октября», а номер брони кладёт только в `model.state`.
- **Своя таблица** (брони, слоты, общие для многих чатов): пишите в неё своей транзакцией с ключом `(chatId, messageId,
  toolCallId)`, а в состояние кладите номер записи — `model.state.set("booking.holdId", hold.id)`.
- **Сохранение.** Ответ записывается в базу сразу после итога каждого инструмента: запись состояния не ждёт конца хода и
  переживает падение сервера. Промежуточные результаты (`preliminary`) пишутся обычным окном в 500 мс.
- **Чтение дешёвое.** `getChatState` и проверка закрытия читают только связи сообщений и записи состояния, без текстов. Своё
  хранилище может дать для этого необязательный метод `listMessagePartsOfTypes(chatId, types)` (флаг общих тестов
  `partsOfTypes`); без него ядро читает сообщения целиком.

### Копия состояния у приложения: `onStateChanged`

Приложению нужна своя таблица заявок: искать, строить отчёты. Хук зовётся каждый раз, когда состояние сменилось.

```ts
createChatServer({
  …,
  onStateChanged: async ({ ownerId, chatId, reason, state, previousState, atMessageId }) => {
    // Полная замена: повтор с тем же состоянием ничего не ломает.
    await db.upsertForm({ chatId, fields: state.fields ?? {} });
  },
});
```

- **Когда зовётся:** после хода, правки (`editMessage`), «Переделать» (`regenerate`), «Повторить» (`retry`), выбора ветки
  (`selectBranch`), правки ответа (`editAnswer`) и записи проверки ответа виджета (`widgetAnswer`, `ctx.state` в
  `checkAnswer`) — это `reason`, после хода — `turn`. Только если состояние сменилось.
  `state` и `previousState` — без служебных ключей. Закрытие чата хук не зовёт: для него события `chat-closed` и
  `chat-reopened`.
- **Ход его не ждёт.** Сбой — повторы с паузами 1 и 3 с в своём сроке (`onStateChangedAttempts`, 3; `onStateChangedTimeoutMs`,
  30 000). Не вышло — строка в `logError` и событие `state-changed-failed`.
- **По порядку.** Вызовы одного чата идут друг за другом: следующий ждёт конца предыдущего вместе с его повторами. Старое
  состояние не ляжет поверх нового. Разные чаты друг друга не ждут.
- **Только пока сервер жив.** Очередь хуков живёт в памяти. Сервер упал между записью ответа и хуком — хук не позовётся,
  копия отстанет до следующей смены. Сверка — по `getChatState`: например, при старте или раз в сутки пройти по чатам с
  незакрытыми заявками.

  ```ts
  const { values } = await service.getChatState(ownerId, chatId);
  await db.upsertForm({ chatId, fields: values.fields ?? {} });
  ```

- **`flush`** дожидается всех вызовов, в том числе вставших в очередь во время ожидания. После него хуки идут как обычно.
- **Вкладка** получает событие `state-changed` `{ chatId, reason, state, atMessageId }` через канал наблюдения: экран
  другой вкладки того же чата обновляет состояние сразу.

### Состояние на экране

```tsx
<AgentChat api="/api/chat" chatId={id} skin={skin} onStateChange={(state) => setFormPreview(state.fields)} />
```

- `onStateChange(state)` — после загрузки истории и при каждой смене: запись по ходу ответа, смена ветки, правка, смена в
  другой вкладке (событие `state-changed`). То же значение повторно не приходит.
- Внутри ленты (компоненты скина, виджеты) — хук `useChatState()`. С `useAgentChat` — поле `chatState`.
- Панель рядом с чатом, вне `AgentChat` — `useChatState(chatId)`:

  ```tsx
  function ApplicationPanel({ chatId }: { chatId: string }) {
    const state = useChatState(chatId);
    return <FormPreview fields={state.fields} />;
  }
  ```

  Значения те же, что у `AgentChat` (или `useAgentChat`) этого чата на странице: своих запросов нет, обновления живые —
  ход ответа, ответ виджета, смена в другой вкладке. Служебных ключей нет. Чата на странице нет или история ещё грузится —
  `{}`. Ловить `onStateChange` ради такой панели больше не нужно.

### Выбор модели человеком

Приложение может подставлять модель по умолчанию, пока человек сам не выбрал её в меню. Узнать о выборе человека:

```ts
createChatServer({
  …,
  // Человек выбрал модель или уровень в меню (`PUT {chat}/model`), выбор записан.
  onModelChosen: ({ userId, chatId }) => service.updateChatData(userId, chatId, { modelChosenByPerson: true }),
});
// Подстановка своей модели сервером — не выбор человека: без права modelChoice, без хука и без запоминания.
await service.setModel(userId, chatId, appDefault, { by: "app" });
```

- `onModelChosen({ userId, chatId, choice })` — после записи выбора человека. Подстановка выбора при открытии пустого
  чата и `setModel(…, { by: "app" })` его не зовут. Сбой хука — строка в журнал, выбор остаётся.
- На странице — `AgentChat.onModelChosen(choice)` (или `useModelChoice({ onModelChosen })`): после того как сервер
  сохранил выбор из меню. Выбор по умолчанию, выбор из истории и отказ сервера его не зовут.

### Снимок перед каждым шагом

Модель видит состояние, только если ей его показать. `agent.stepContext` собирает текст перед каждым шагом модели, и он
ложится сообщением человека в самый конец запроса — после результатов инструментов. Пример: на шаге 1 инструмент записал
почту, на шаге 2 модель уже видит её в снимке и не спрашивает ещё раз.

```ts
createChatServer({
  …,
  agent: {
    instructions,                         // постоянная, первой в запросе
    stepContext: async ({ state, chat, stepNumber }) =>
      `Служебный снимок сервера:\n${JSON.stringify({ saved: state.fields ?? {}, missing: missingFields(state, chat.data) })}`,
  },
});
```

- **Что видит функция:** `state` (живое состояние ветки без служебных ключей: записи прошлых шагов этого хода уже в нём),
  `stepNumber` (номер шага во всём ответе, с нуля: после подтверждения или виджета счёт продолжается), `chatId`,
  `ownerId`, `messageId`, `chat.data`, `subject`, `channel`, `audience`, `staff`, `modelId`, `providerId`, `abortSignal`.
  Те же «кто и где», что у инструментов. `state`, `chat`, `subject` и `staff` — копии: правка не доходит до хода. Текст
  снимка целиком ваш: SDK ничего к нему не дописывает.
- **В группе личного не показывайте.** В групповом чате мессенджера (`audience: "group"`) ответ модели видят все
  участники: снимок с почтой или телефоном владельца модель может пересказать при всех. Смотрите на `audience` и в группе
  оставляйте только общее.
- **Срок — `agent.stepContextTimeoutMs`,** по умолчанию 5 с; 0 или `Infinity` — без срока. Не ответила — шаг без снимка,
  `abortSignal` функции отменён, в `logError` строка `[снимок шага] … не ответил за N мс`. «Стоп» отменяет её сразу.
  Передавайте `abortSignal` в свои запросы к базе и API.
- **Кэш модели.** Снимок на шаге один и всегда в конце: прошлый снимок из запроса убирается, а всё до него — те же байты,
  что на прошлом шаге. Метки кэша стоят там же, где без снимка. Держите в снимке только меняющееся, постоянное — в
  инструкции.
- **В историю не пишется,** в запросы сжатия, памяти и помощников не идёт. Последний шаг хода: снимок, а после него
  пометка «шаги кончились».
- **Скажите модели в инструкции,** что снимок присылает сервер, и начинайте его постоянным заголовком. Снимок идёт от
  имени человека: осторожная модель без такой строки может решить, что человек его подделал, и не поверить (живая
  проверка: один раз из двенадцати на DeepSeek × Fireworks).
- `null`, `undefined` или пустая строка — шаг без снимка. Бросок — шаг без снимка, строка `[снимок шага]` в `logError`;
  ход не падает.
- Не задано — запрос побайтно прежний.

## 13. Блоки контекста в вопросе хода

Иногда агенту на весь ход нужны сведения, которые меняются редко: список скиллов, роль человека, правила раздела. В
инструкцию их класть нельзя: инструкция одна на всех и стоит первой, любая правка сбрасывает кэш модели. Снимок шага
(`stepContext`) тоже не годится: он меняется на каждом шаге. Для этого есть `agent.contextBlocks`.

```ts
createChatServer({
  …,
  agent: {
    instructions,
    contextBlocks: async ({ ownerId, audience, abortSignal }) => [
      { key: "skills", text: `Скиллы агента: ${await skillsOf(ownerId, { signal: abortSignal })}` },
      { key: "role", text: `Роль человека: ${await roleOf(ownerId)}`, private: true },
    ],
  },
});
```

- **Как это работает.** Функция зовётся один раз в начале хода. Блоки вписываются в вопрос человека после памяти и даты
  и больше не меняются. На следующем ходе ядро сравнивает блоки с прошлыми по тексту: в новый вопрос идут только
  изменившиеся и строка `[Больше не действует: «ключ»]` про пропавшие. Ничего не поменялось — вопрос без приписки.
- **Не влезло — не значит удалено.** Если блок есть, но вы не показываете его ради места, верните вместо него
  `{ key, hidden: true }`. Модель, которая блок уже видела, получит строку
  `[Не показано ради места, но по-прежнему действует: «ключ»]`, а не «Больше не действует». Память пользуется этим
  же, но только когда читается заново (новый чат, сжатие истории): в идущем чате она не перечитывается, и такой строки
  про память там не бывает.
- **Почему так.** Прошлые вопросы остаются байт в байт прежними, и следующий ход читает всю переписку из кэша модели.
  Так же устроены сегодняшняя дата и место на экране. Память строже: она читается один раз на чат (в первом ходе, после
  сжатия истории и в редких случаях вроде правки первого сообщения) и в идущем чате не досылается вовсе.
- **Что видит функция:** `chatId`, `ownerId`, `messageId`, `chat.data`, `state`, `subject`, `channel`, `audience`, `staff`,
  `modelId`, `providerId`, `abortSignal`. `state` — состояние текущей ветки на начало хода, то же, что `model.state.get()`
  у инструментов на первом шаге (читать его через `getChatState` не нужно). Данные, состояние и объект чата — копии.
- **Ключи.** `key` — постоянное имя блока, по нему ядро понимает, что блок изменился. Ключи `memory`, `memory:*`, `today`,
  `screen_place` заняты ядром. Блок с таким ключом, повтором ключа или пустым текстом отбрасывается со строкой
  `[блоки контекста] … отброшен` в `logError`.
- **`private: true`** — блок не показывается в групповом чате мессенджера (`audience: "group"`).
- **Срок — `agent.contextBlocksTimeoutMs`,** по умолчанию 5 с; 0 или `Infinity` — без срока, иначе не меньше 1000 мс.
  Не ответила или бросила — блоки приложения берутся из прошлого ответа чата, в `logError` строка `[блоки контекста] …`.
  «Стоп» отменяет функцию сразу.
- **Ответ человека на паузе хода** (кнопка виджета, «Разрешить» в карточке подтверждения) продолжает тот же ответ, но
  это новый вход: функция зовётся снова, место берётся со страницы ответа. Изменившееся встаёт заметкой сразу после
  ответа человека — последним сообщением запроса, а не в давнем вопросе хода. Всё, что раньше, остаётся байт в байт
  прежним. Ничего не поменялось — заметки нет. Страница не прислала `place` — место прежнее. У подтверждения заметка
  идёт после результата разрешённого инструмента.
- **Повтор того же запроса** (автопродолжение, запасной провайдер, «Повторить») берёт блоки из ответа и функцию второй
  раз не зовёт. Заметки продолжения остаются на своих местах.
- **Где лежат.** Набор хода хранится служебной частью ответа `data-frozen-context` (`FROZEN_CONTEXT_PART_TYPE`); каждая
  заметка продолжения — ещё одна такая часть в том месте ответа, где был ответ человека. На экран, в историю, `afterTurn`
  и поиск по истории они не уходят. Читаете ответы из хранилища сами — пропускайте все такие части.
- Текст блока целиком ваш: ядро его не оборачивает. Начинайте блок понятным заголовком.

## 14. Конец хода сразу после инструмента

Обычно после инструмента модель делает ещё шаг: читает результат и пишет ответ. Когда ответ известен заранее («Заявка
принята»), этот шаг — лишние деньги и задержка. Инструмент возвращает `endTurn(output, { text? })` из ядра:

```ts
import { endTurn } from "@ykurilov/agent-chat-core";

submit_form: tool({
  description: "Отправить заявку",
  inputSchema: z.object({}),
  execute: async () => endTurn({ saved: true }, { text: "Заявка принята, мы позвоним завтра." }),
}),
```

- **Что происходит.** Шаг кончается как обычно, следующего шага модели нет. Готовый `text` идёт в поток и в запись
  обычной текстовой частью ответа (в `afterTurn` — в `turn.text`, в мессенджер — как обычный ответ). Без `text` ответ —
  только вызов инструмента.
- **Только после пользовательского текста (с 0.73.0).** Инструмент, который сохраняет данные и ожидает реплику модели перед вызовом:

  ```ts
  execute: async (input) => {
    const output = await saveSection(input);
    return endTurn(output, { requireText: true });
  },
  ```

  Если в текущем ответе есть непустой пользовательский `text`-part, ход кончается без следующего запроса к провайдеру. Иначе возвращается обычный `output`: сохранение не отменяется и не повторяется из-за guard, модель продолжает штатным следующим шагом. SDK не сочиняет подтверждение за агента. `requireText: false` или отсутствие опции сохраняет прежний silent `endTurn`.

  **Что считается текстом.** Проверяется принятый в пользовательские части текущего ответа текст после исключения whitespace, Unicode-категории `Cf` и `Default_Ignorable_Code_Point`. Это проверка наличия символов, а не полезности или готовности ответа: Markdown/HTML не интерпретируются. Рассуждения, результат инструмента, служебные части, ошибки и предыдущие сообщения не считаются. Уже поступившие части учитываются и при незавершённом текстовом блоке. Проверка использует снимок внутреннего сборщика потока с fence, не читает хранилище и не ждёт flush. Это не подтверждение доставки/отрисовки браузером; режим отложенной проверки ответа по-прежнему может придерживать текст.

  **Повторы и подтверждения.** На повторной попытке учитываются лишь оставшиеся части этого ответа: стёртый текст или результат вызова не сохраняют guarded-остановку, поздний результат старой попытки новую не завершает. После approval проверяется тот же активный ответ до паузы и продолжение, а не весь входной prompt. Нет текста — модель получает результат одобренного инструмента и продолжает. Нет безусловной гарантии реплики при отмене, ошибке, лимите шагов/денег или другом ожидающем подтверждении.

  **Явные опции и несколько вызовов.** `endTurn(output, { text: "Текст приложения", requireText: true })` сохраняет старый путь явно переданного текста: если в нём есть символы по правилу выше, он выполняет условие и идёт в ответ без запроса модели. Это явное решение приложения, а не автоматический ACK. Чисто невидимый готовый текст сам по себе условие не выполняет. Guard относится к просьбе своего вызова; параллельный обычный `endTurn` по-прежнему может закончить ход без текста. Остальные вызовы шага доделываются по прежним правилам.

  **Как обновить приложение.** Обновить все пакеты SDK одной версией до 0.73.0 и заменить `return endTurn(output)` на `return endTurn(output, { requireText: true })` в инструментах, которым запрещён silent ответ. Настройку модели «сказать перед вызовом» сохранить. `model.messageId` идентифицирует ответ, но чтение его текста через БД не заменяет снимок потока; `execute` options.messages — сообщения запроса, который породил вызов; они не включают system prompt и сам ответ assistant с этим вызовом, поэтому это не getter накопленного текста. Схемы данных и остальные инструменты не меняются.

- **Результат на месте.** Модель, запись и наблюдатель видят `output` как обычный результат; на следующем ходе модель
  получает его как всегда. Для типов `endTurn` отдаёт тот же `output`.
- **Деньги.** Готовый текст пишется без запроса к провайдеру: в расход, лимиты и `turnObserver.modelCall` он не идёт.
- **Несколько инструментов в шаге.** Шаг доделывает все вызовы; тексты — по порядку вызовов, через пустую строку.
- **Без `text`.** На следующих ходах модель видит после результата постоянную пометку ответа «[Ход окончен инструментом]»:
  строгие провайдеры не принимают вопрос человека сразу после результата инструмента. В записи ответа — служебная часть
  `data-end-turn` (`END_TURN_PART_TYPE`), её текст рождается только в запросе; клиенту, в историю и в `afterTurn` она
  не идёт. Байты всегда те же — кэш модели цел. Другие ответы (поправка на лету, «Стоп») пометки не получают.
- **Подтверждение.** Инструмент с `needsApproval` кончает ход после «Разрешить»: модель после него не спрашивается. Если в
  том же шаге ещё ждёт решение человека, ход ждёт, а пометка не действует; потерянный готовый текст — строка
  `[endTurn] … готовый текст не показан` в `logError`.
- **Потолок шагов** готовый текст не теряет.
- **Сбой связи.** Инструменты шага запускаются после конца ответа модели: упал ответ — инструмент не выполнялся, пометки
  нет, ответ дописывает модель (автопродолжение или запасной провайдер). Новая попытка хода учитывает только пометки
  вызовов, чей результат записан в ответ: инструмент, запущенный заново после падения или стирания шага, текст не задвоит.
- **Не действует** у виджетов (ответ даёт человек) и у инструментов помощников: там пометка снимается, а помощник
  доводит свою работу до итога.

## 15. Права человека на ход

Права часто лежат в базе приложения: админ ли человек, какой у него тариф. Спрашивать базу в каждом инструменте долго,
а набор инструментов строится синхронно. Для этого есть `agent.viewer`: приложение один раз в начале хода отвечает,
кто смотрит, а ядро раздаёт ответ всем.

```ts
createChatServer({
  …,
  agent: {
    viewer: async ({ ownerId, abortSignal }) => ({ isAdmin: await users.isAdmin(ownerId, { signal: abortSignal }), plan: await users.planOf(ownerId) }),
    tools: (model) => {
      const app = { ...appTools, ...(model.viewer?.plan === "pro" && proTools) };
      return { ...mcp.tools(model, app), ...app };
    },
    contextBlocks: ({ viewer }) => [{ key: "plan", text: `Тариф человека: ${viewer?.plan}` }],
  },
});
```

- **Один раз на ход.** Функция зовётся в начале хода, до блоков контекста и сборки инструментов. Повторная попытка,
  автопродолжение и запасной провайдер её не зовут снова: права на весь ход одни. Ответ заморожен.
- **Куда идёт.** Полем `viewer` в `contextBlocks` и в модель инструментов (`AgentToolsModel.viewer`). Инструменты
  запроса сжатия и фонового помощника получают права так же: с тем же каналом и `audience`, что у хода (в группе —
  `"group"`), и со сроком ответа 10 с — «Стопа» там нет. В запрос к модели сам ответ не попадает: кэш модели от
  него не зависит. Меняются права — меняется только то, что вы из них построили (набор инструментов, блок контекста).
- **`isAdmin`** — общий признак для пакетов SDK: серверы MCP и навыки «только админы» видны, когда он `true`. Остальные
  поля — ваши.
- **Что видит функция:** `userId` (сотрудник в копии чата человека, иначе владелец), `ownerId`, `chatId`, `messageId`,
  `chat.data`, `subject`, `channel`, `audience`, `staff`, `abortSignal`. Объекты — копии.
- **Права — по `ownerId`.** В копии чата человека `userId` — сотрудник, а `ownerId` — сам человек. Права по `ownerId`
  дают сотруднику то, что увидел бы человек; по `userId` сотрудник увидел бы свои админские навыки и серверы.
- **Ошибка — ход падает.** Функция бросила или вернула не объект — ход кончается ошибкой, человек видит обычное «не
  получилось», в `logError` строка `[agent.viewer] …` с причиной. Молча считать человека «не админом» ядро не будет.
- **Песочница.** В тестовом чате админа права считаются по владельцу чата: обычный тестовый чат — по самому админу,
  копия чата человека — по человеку (`ownerId` — человек, `userId` и `staff` — админ). Так сотрудник видит то же, что
  увидел бы человек.
- Не задано — `viewer` нет нигде, всё работает как раньше.

## Своё хранилище

Встроенные хранилища (память, SQLite, PostgreSQL) умеют всё сами, миграции применяются при открытии. Своему хранилищу нужны
необязательные методы — только для тех возможностей, которые вы включаете:

| Возможность | Методы | Флаг общих тестов `describeChatStorageContract` |
|---|---|---|
| Чат объекта | `findChatBySubject`, `createChat` с `subjectKey`/`subjectData`/`title`/`createdAt`, `listChats(ownerId, { subjects })` | `subjectChats` |
| Данные чата | `updateChatData`, `createChat`/`importChat` с `data`, `listChats(ownerId, { data })` | `chatData` |
| Импорт, приветствие одной записью | `importChat` | `importChat` |
| Итог хода | `setAfterTurnState`, `listPendingAfterTurn` | `afterTurnState` |
| Лимит сообщений | `getSpendingLimitState`, `saveSpendingLimitState` | `spendingLimitState` |

### Проверка ответа виджета с записью состояния

Свой виджет или общая `agent.widgets.checkAnswer` проверяют ответ человека с доступом к базе, могут отказать текстом,
подменить ответ и записать состояние: `ctx.state.set("booking.holdId", hold.id)` ложится в ответ вместе с результатом
виджета и попадает в `getChatState`. Отказ — 409 `widget_answer_refused`, виджет остаётся открытым. Полностью — `docs/widgets.md`,
раздел «Проверка ответа на сервере».
