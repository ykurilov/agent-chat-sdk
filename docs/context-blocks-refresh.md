# Блоки приложения до смены начала истории

Настройка доступна с SDK 0.80.0. Исправление размещения снимка после сжатия описано в разделе [«Граница сжатия и контекст»](compaction-context.md); готовящийся выпуск указан в CHANGES.md.

```ts
agent: {
  instructions,
  contextBlocksRefresh: "history-start",
  contextBlocks: async ({ ownerId, chatId, abortSignal }) => [
    { key: "profile", text: await profileText(ownerId, chatId, abortSignal), private: true },
  ],
  prepareTurn: async (context) => {
    const event = await appEventForTurn(context);
    return event ? { notices: [{ kind: "app", title: event.text }] } : undefined;
  },
}
```

`contextBlocksRefresh?: "turn" | "history-start"`. Без настройки, а также при `"turn"`, остаётся прежнее поведение: источник читается для нового хода и обновлений продолжения, модели передаётся разница блоков. Настоящее продолжение с сохранёнными шагами использует их застывший контекст в обоих режимах; кнопка retry без завершённых шагов может создать новый ответ и новую сборку.

В режиме `"history-start"` используется тот же механизм источника и fallback, что у памяти SDK. Снимок и отметка начала истории лежат в служебной части frozen context ответа текущей ветки. Это не глобальный кэш и не состояние, доступное инструментам модели. SQL-схемы и формат данных приложения не меняются. Приложению не требуется кэшировать источник по `chatId` или получать новый `historyStart` в callback.

| Событие | Что происходит с источником приложения |
| --- | --- |
| Первый ответ, нет подходящего снимка | Читается; принятые блоки сохраняются |
| Следующий ход с тем же началом видимой истории | Не вызывается; используются прежние блоки без новой разницы |
| Сжатие изменило начало видимой истории | Читается заново; успешный полный снимок приложения размещается рядом со сводкой, старые app-снимки хвоста не выводятся |
| Правка позднего вопроса при прежнем начале | Сама по себе источник не обновляет |
| Правка первого вопроса изменила начало | Источник читается заново для новой ветки |
| Возврат на другую ветку | Используется её собственный снимок из видимых предков, а не будущий снимок соседней ветки |
| Перезагрузка приложения или перезапуск службы | Снимок восстанавливается из хранилища чата |
| Retry/continuation с сохранёнными завершёнными шагами и frozen context | Источник этого ответа повторно не вызывается |
| Retry без завершённых шагов / «Переделать» | SDK создаёт новый соседний ответ; если базового снимка нет или после ошибки нет отметки, это новая сборка источника |
| Approval/widget resume при прежнем начале | Используется снимок; дата, место, notices и права обрабатываются прежним путём |
| Включение настройки в старом чате | При следующей новой сборке источник читается один раз, даже если старые тексты совпали |
| Отключение, ход в `"turn"`, повторное включение | Обычный ход убирает отметку; при включении требуется новое чтение |

Начало определяется первым сообщением эффективной истории, переданной для ответа; при пустой истории — идентификатором самого ответа. Это существующий триггер памяти `memoryFrom`. Если в видимой истории не осталось базового ответа со снимком, источник читается заново, даже если приложение считает разговор тем же. Базой служит видимый ответ с содержимым и frozen context; пустые ответы и исключённые недоставленные сообщения не служат основанием для reuse.

Снимок переживает перезапуск после записи ответа в хранилище. Если процесс упал после чтения источника, но до сохранения снимка, следующая сборка прочитает источник снова. Это политика повторного использования контекста, а не exactly-once гарантия внешних действий callback.

Успешные `[]`, `null` и `undefined` фиксируют пустой снимок: он не перечитывается до следующей смены начала. Неверные отдельные блоки отбрасываются по прежним правилам уникальных ключей и текста. Исключение, неверный результат вместо списка или timeout сохраняют прежние блоки как fallback, но **не отмечают новое начало успешно прочитанным**. Следующая новая сборка снова попробует источник. Continuation с сохранёнными завершёнными шагами воспроизводит frozen fallback без повторного вызова источника. Retry без таких шагов создаёт новый ответ: отсутствие отметки после ошибки позволяет повторить источник сразу. Поздний результат уже истёкшей функции не заменяет снимок. «Стоп» отменяет ожидание; отмена не считается успешным чтением. Срок `contextBlocksTimeoutMs` и журналирование прежние.

При одинаковых ключах и текстах новая разница модели не отправляется. Удаление ключа или `hidden: true` при разрешённом обновлении сохраняет прежний смысл. Между сбросами `"history-start"` источник вообще не вызывается, поэтому изменения его данных не могут сами породить разницу. Снимок с теми же текстами при resume сохраняется служебно, без дополнительного текста, видимого сообщения или разделения ответа для модели.

Права и доступ проверяются сервером на каждом соответствующем действии. Настройка не кэширует авторизацию и не отключает `viewer`, права инструментов или фильтрацию `private` в группе. Приложение помечает личные тексты `private: true`; callback в этом режиме не вызывается заново только потому, что изменились канал, аудитория, страница, роль или данные приложения. Не используйте застывший профиль как проверку доступа.

Изменения, которые агент не видел в разговоре, передавайте через `prepareTurn.notices`. Порядок текущего сообщения модели прежний: исходные части человека → блоки или их разница → notices. Notice добавляется в свой ход и остаётся в прошлом prefix следующих запросов; прошлые байты не переписываются. Не возвращайте одно событие как новую notice на каждом ходе: выбор и повторная доставка событий принадлежат приложению. При настоящем продолжении SDK воспроизводит сохранённый контекст. Для retry без завершённых шагов действует описанная граница новой сборки. Продолжения после approval располагают заметку после ответа человека и результатов одобренного инструмента, как прежде.

Для подсказки JEV по каждому новому вопросу используйте `prepareTurn` и его notices либо сохраняйте режим `"turn"` с `contextBlocks.userMessage`. `"history-start"` намеренно не запускает классификацию нового вопроса на каждом ходе.


## Только актуальные карточки для модели

`agent.contextBlocksHistory: { latest: ["flow:state"] }` оставляет в запросе модели только последнее выданное обновление выбранного блока. Настройка работает и с `flow.withChat`: передайте её в `agent` при создании службы. Для карточки клиента к списку добавляется `flow:client`. Другие app-блоки сохраняют прежнюю историю, а служебные дата, память и место не подчиняются этому фильтру.

После изменения инструкции новый снимок карточки заменяет предыдущий в проекции запроса. Прежние `data-frozen-context` остаются в серверном хранилище и raw истории: перезаписывать `listMessages`/`getMessage` обёрткой не требуется. Сохраняются сообщения человека, инструменты, notices, приватность группового чата, паузы и подтверждения. Удаление/скрытие выбранного блока тоже учитывается. При возобновлении ответа актуальная заметка остаётся после соответствующего подтверждения.

По умолчанию опция выключена. Проекция меняет старый префикс запроса при каждом новом обновлении выбранного блока; это может сбрасывать кэш провайдера. Между обновлениями байты остаются стабильными. Настройка не переписывает обычный текст старых ответов или результаты инструментов и не заменяет миграцию закреплённой версии сценария.

Для обновления карточки после правки инструкций оставьте `contextBlocksRefresh: "turn"` (значение по умолчанию). Новое сообщение, `editMessage` с новой веткой и `regenerate` завершённого ответа заново вызывают источник. `retry` завершённого пустого ответа тоже создаёт новый ответ. У законченного непустого ответа действие переделки — `regenerate`, а не `retry`. Повтор прерванного ответа с сохранёнными выполненными шагами продолжает их с прежним frozen context и не перечитывает карточку. `contextBlocksHistory.latest` управляет проекцией истории и не отменяет политику reuse, если приложение явно выбрало `history-start`.
