# Мультиагентный аудит SDK от 25.10.2026

Независимые аудиторы Kimi K3.1 Pro, Codex, Claude Sonnet и Gemini Argon проверили SDK на базе 0.80.1. Из 22 исходных пунктов после объединения дублей подтверждены 16 групп ошибок. Исправления прошли отдельные регрессионные проверки на iMac и независимое ревью; общая проверка объединённого выпуска выполняется отдельно.

## Исправленные границы

- [Клиент, песочница и вложения](audit-client.md): состояние незавершённых действий принадлежит одному открытию чата; песочница изолирована от хуков записи; условное удаление файла согласовано с прикреплением.
- [Ядро, сценарии и мессенджеры](audit-runtime.md): групповые ограничения сохраняются в производных ходах, удаление чата требует общей аренды, подтверждение файлов предшествует записи сообщения, версия сценария проверяется до изменения данных, привязка аккаунта и завершение обновлений атомарны.
- [Сеть и фоновые задачи](audit-network.md): проверенный адрес закрепляется за соединением, включая числовые адреса и переадресации; запуск и продолжение фоновой задачи занимают место одной атомарной операцией. Отказ проверки адреса не расходует просмотр; битая кодировка адреса админки возвращает 404.

В ходе ревью исправлены также общая очередь голосовой замены, обход предела при продолжении фоновой задачи и числовые адреса в закреплённом транспорте. Новые тесты сначала воспроизводили ошибку на прежнем коде.

## Что не подтвердилось

Гипотеза о повторном выполнении подзапроса захвата PostgreSQL не подтвердилась: планы на 10, 1000 и 100 000 строк выполняли LockRows один раз; 1600 захватов на восьми соединениях не дали дублей и превышений предела. Запрос сохранён.

«Стоп» старого Chat не меняет сообщения нового при закреплённой версии AI SDK. Реальная ошибка была в общих state/ref React-хука; она исправлена. Страховочный тест самого AI SDK проходит и на старом коде.

## Обновление своих хранилищ

Встроенные память, SQLite и PostgreSQL обновлены. Пользовательские реализации обязаны поддержать новые договоры, а не только добавить имена методов:

| Хранилище | Обязательное изменение |
| --- | --- |
| AttachmentStorage | removeUnattached атомарно с markAttached; та же политика для удаления просроченных |
| TaskStore | admitWithinLimit: create/resume и подсчёт активных задач одной транзакцией с общей блокировкой владельца |
| MessengerStore | saveLinkIfFree; guarded: true; условные finishUpdate, renewal и release по держателю |
| FlowStore | swapDelivery: CAS версии доставки, срока и захвата; условия endedAt/freeAt/leaseOwner; guarded: true |

Точные сигнатуры и договорные тесты находятся в пакетах. Отсутствие методов или признака guarded приводит к отказу запуска. Схемы SQL не менялись. Все установленные пакеты SDK обновляются согласованно до одной версии.

## Дополнительный контракт доставки

По запросу приложения добавлены `await_repair` и `resumeDelivery` для собственной `attach({ deliver })`. Это отдельная возможность, включаемая приложением. Ожидание переживает перезапуск; после починки SDK повторяет тот же messageId через свой таймер. Метод resumeDelivery возвращает строку, а не объект статуса. Приложение отвечает за окно допустимой повторной отправки, прогресс частей и свою идемпотентность.

Новая реплика человека делает repaired-ответ устаревшим. Проверка выполняется непосредственно перед отправкой под резервом, но не является транзакцией с историей и внешним каналом. Уже начатое внешнее действие может завершиться после отмены или потери аренды. Гарантии «ровно один раз» нет. Успешный явный конец отменяет ожидание; прощание по сроку может доставляться после конца без переоткрытия сценария. Пока ожидается починка, сроки сценария стоят.
