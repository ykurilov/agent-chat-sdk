# История только в браузере

Опциональный режим для обычного `AgentChat` и скина «Одуванчик». Список локальных чатов и IndexedDB принадлежат приложению. SDK не заводит серверный чат между запросами: каждый POST создаёт отдельные службу и хранилище в памяти, восстанавливает переданный снимок и освобождает их после ответа, отмены или ошибки. У обработчика нет аргумента `ChatStorage`, подключения к SQL и адресов обычных чатов.

## Сервер

`createBrowserChatHandler` из `@ykurilov/agent-chat-server` возвращает `{ fetch(request): Promise<Response>, activeRequests, close(): Promise<void> }`. Подключите отдельный POST-адрес. В Next route передайте запрос в `handler.fetch`; в Hono — `c.req.raw`. Node/Express может использовать `toNodeListener({basePath, fetch: handler.fetch})` из `@ykurilov/agent-chat-server/node`. Адаптер обязан передавать отмену соединения в Request.signal и не буферизовать поток.

Опции:

| Поле | Контракт |
| --- | --- |
| `namespace` | Стабильное имя области приложения. Другой namespace не принимает снимок. |
| `snapshotKey` | `Uint8Array` из 32 случайных байт либо его base64url-строка. Отдельный постоянный секрет сервера, никогда не клиентская переменная. |
| `resolveUser` | `(request: Request) => Promise<ResolvedUser>`: обычная авторизация приложения, в том числе Auth V3. Владелец определяется только здесь. |
| `configure` | `(ownerId: string) => BrowserChatSettings \| Promise<BrowserChatSettings>`, вызывается на каждом запросе, включая каталог. Не получает снимок или текст чата. |
| `allowedOrigins` | Дополнительные разрешённые origins, как у обычного обработчика. По умолчанию только свой origin. |
| `onError` | Коды `configuration/snapshot/turn/usage/limit`, без текста разговора и объектов ошибок провайдера. |

`BrowserChatSettings`: `catalog`, `agent`, необязательные `defaultChoice`, `env`, `compaction`, `capabilities`, `assertWithinLimit(ownerId, signal): Promise<void>` и `onUsage(usage, signal): Promise<void>`. Типы экспортируются из того же пакета. Инструкции, инструменты, модели и права задаёт сервер. Поля клиента не становятся system messages, состоянием приложения или разрешениями инструментов.

`configure` видит обновлённый каталог на следующем запросе. Уже начатый ход использует каталог своего запроса. Меню браузера кэшируется на время экземпляра транспорта: после изменения каталога пересоздайте транспорт. Новый выбор из snapshot.choice проверяется на каждом запросе: недоступная модель даёт отказ без очистки истории. Для пары, сохранённой внутри sealed-истории, действуют обычные правила ядра: если модель/провайдер недоступны, используется настроенный defaultChoice, а удалённый уровень заменяется уровнем по умолчанию. При обновлении каталога согласуйте defaultChoice и пересоздайте клиентский транспорт, чтобы меню соответствовало серверу.

Лимиты по умолчанию: тело запроса 8 MiB (`maxRequestBytes`, 4 KiB–64 MiB); распакованный снимок 32 MiB (`maxSnapshotBytes`, 4 KiB–128 MiB); запрос 180 секунд (`maxTurnMs`, 100–900000 мс); checkpoint не чаще чем раз в 100 мс (`checkpointIntervalMs`, 10–1000); три одновременных хода владельца на экземпляр обработчика (`maxConcurrentTurnsPerUser`, 1–20). Все числовые значения целые. Поток может закончиться раньше при достижении предела снимка; уже сохранённый текст остаётся. Большой снимок идёт реже: следующий checkpoint ждёт, пока прошлый уйдёт со скоростью 512 KiB/с (снимок 1 MiB — раз в 2 секунды), и пока браузер не дочитал прежние записи. Медленная связь не обрывает ход: промежуточные снимки пропускаются, накопленные части уходят со следующим, конец доходит целиком. Настоящий предел снимка — `maxRequestBytes`: браузер присылает снимок обратно следующим запросом. Браузерный адаптер принимает всё, что разрешают наибольшие серверные пределы: envelope до 64 MiB и распакованную публичную проекцию до 128 MiB. Это ограниченный снимок, а не неограниченное хранилище всей жизни.

Сжатие контекста по умолчанию начинается с 250000 токенов (не выше 80% окна модели), как у обычного SDK; приложение меняет `compaction`. Полная история для UI и веток остаётся в локальном снимке, поэтому сжатие контекста не отменяет предел размера снимка.

## Браузер

`createBrowserChatTransport` и типы `BrowserChatTransportOptions`, `BrowserChatSnapshot` экспортируются из `@ykurilov/agent-chat-react`. Серверное ядро в клиентский bundle не импортируется.

Параметры:

- `endpoint: string`: отдельный POST-адрес обработчика;
- `ownerId: string`, `chatId: string`: идентификатор вошедшего человека и локальной записи;
- `loadSnapshot: () => unknown | Promise<unknown>`: снимок этой записи либо `null`;
- `saveSnapshot: (snapshot: BrowserChatSnapshot) => void | Promise<void>`: сохраняет весь объект непрозрачно; Promise завершается только после локальной транзакции;
- `fetch?: typeof globalThis.fetch`: транспорт приложения для авторизации; без него обычный fetch с `credentials: include`;
- `onError?: (code: "storage" | "snapshot" | "network" | "unsupported") => void`.

Результат: `chatProps` передаётся в обычный `<AgentChat {...transport.chatProps} skin={oduvanchikSkin} onBusyChange={setBusy} />`. `getSnapshot()` возвращает копию последнего сохранённого снимка либо `null`; `dispose()` отменяет запросы. Создавайте стабильный экземпляр на пару ownerId/chatId и вызывайте dispose при его замене/закрытии, без вызова во время каждой перерисовки. Для смены владельца нужен другой экземпляр.

Приложение сохраняет снимок атомарно с проверкой revision и существования записи. Старая вкладка не должна перезаписывать новую версию либо воскрешать удалённый чат. Отклоните `saveSnapshot` при конфликте: поток остановится до показа неподтверждённых частей. Снимки разных владельцев не смешиваются. Если история хранится до ручного удаления, приложение также отвечает за политику выхода из аккаунта и возможное вытеснение IndexedDB самим браузером.

Не передавайте обычный attachments/voice/voiceDialog/appBridge/subject или `history="compact"`: AgentChat отклонит их для этого режима. Не подменяйте api/transport из возвращённых chatProps обычным серверным адресом. Незнакомые виртуальные маршруты отклоняются, запросы никогда не переключаются на обычный ChatStorage.

## Stop, reload и обрыв

Перед показом очередной пачки потока адаптер ждёт сохранения полного checkpoint. Отдельная проекция включает сохранённый текущий ответ, сохраняя обычные права видимости. Поэтому показанный текст есть в последнем локальном снимке даже при Stop или обрыве соединения. Исходящее сообщение также сохраняется локально до первого запроса; при раннем обрыве остаётся ждущим подтверждения.

После reload история читается локально, текущий ответ показывается как `interrupted`. Ничего не продолжается автоматически. «Повторить» или новое сообщение начинает отдельный запрос с новым хранилищем в памяти. Незаконченные серверные вызовы не возобновляются старым процессом. Незавершённую отправку адаптер повторяет с прежним id; незавершённую правку следует сначала повторить, сохранив её ветку. Допустимы обычная правка сообщения человека, переделка ответа и переключение сохранённых веток. Редактирование текста ответа ассистента пока не поддержано.

Ключ snapshotKey шифрует и удостоверяет внутреннюю историю (AES-256-GCM), связывая её с владельцем, локальным чатом, namespace и публичной проекцией. Клиент хранит объект целиком и не исправляет его поля. Потеря/смена ключа или namespace оставляет читаемую локальную проекцию, но старый снимок больше нельзя продолжить на сервере. Планируйте сохранность секрета заранее; автоматической ротации/миграции в этой версии нет.

## Граница первой версии и приватность

Поддержаны текст, каталог моделей/уровней, поток, Stop, ветки, правка/повтор и обычные серверные инструменты с execute, включая веб-поиск/чтение Firecrawl. Сам внешний провайдер получает запросы по своему договору; SDK не обещает удаление данных у провайдера.

Не поддержаны файлы/вложения, голос, долговременная память, фон, helpers, browser RPC, widgets и инструменты с needsApproval. Последние отклоняются, а не исполняются без подтверждения. Обычный дисковый attachments plugin сюда не подключается. Создавайте наборы инструментов внутри configure на запрос, без общего кэша результатов между запросами; для Firecrawl достаточно search/reader из createFirecrawlServices и createWebTools. Не передавайте обычный ChatStorage в spending расширения: для стоимости веб-вызовов используйте числовой адаптер insertUsageRecord, который отбрасывает chatId/messageId перед своим ledger, либо отдельный биллинг приложения. onUsage обработчика покрывает расход его transient-службы, а не внешних расширений с собственным storage. Внешние инструменты и callbacks приложения обязаны соблюдать отмену и не писать контекст в свои базы, файлы, telemetry или журналы; SDK не может отменить уже совершённый внешний эффект.

Сам обработчик держит контекст только в памяти запроса, отключает собственное логирование ошибок провайдера/промахов кэша и отдаёт диагностике только коды. Отключите body/response capture в reverse proxy, APM и middleware приложения. Числовой биллинг допускается через onUsage: объект не содержит chatId/messageId, тексты и аргументы инструментов. onUsage вызывается также при Stop с отдельным сигналом срока в 5 секунд: отмена HTTP не должна отменять учёт уже потраченных денег. Записи, уже лежащие в снимке, onUsage повторно не получают. Расход, который восстановление дописывает к прерванному ответу, в onUsage не уходит: после Stop он уже учтён, а снимок в браузере мог остаться прежним. Повтор неучтённой записи приходит с тем же `id`; внешний ledger должен быть идемпотентным по нему. Если onUsage отказал или не уложился в 5 секунд, запись остаётся в зашифрованном снимке как неучтённая и повторяется в начале следующего запроса этого чата, пока onUsage её не примет. Отложенная фоновая сверка расхода генерации отключена: после Stop остаётся оценка с `estimated`, без удержания transient-хранилища для последующих запросов провайдеру. Лимиты оплаты между запросами проверяйте во внешнем assertWithinLimit; transient storage не является постоянным ledger.

Строгая stateless-модель не обеспечивает глобальную блокировку между процессами, запрет повторного проигрывания старого собственного снимка или exactly-once для внешних действий. Для инструментов с последствиями приложению требуется отдельная идемпотентность без хранения текста разговора; read-only поиск не меняет этот контракт. Результат внешнего действия, завершившегося после последнего доставленного checkpoint, может отсутствовать в локальном снимке. Повтор — явное действие человека, а не автоматический replay действий.

## Как обновить приложение

Обычные серверные чаты остаются без изменений. Для локального режима подключите отдельный handler и постоянный секрет; список чатов/IndexedDB оставьте приложению. Передавайте неизвестный snapshot через load/save, соблюдайте атомарный commit/revision, а в AgentChat используйте возвращённые chatProps. Скрывайте недоступные вложения и голос. Авторизация и оплата API сохраняются, серверный chat id или subject к этому режиму не присоединяется.
