# Выпуск обновлений SDK

Здесь описано, как выпускать новые версии пакетов `@ykurilov/agent-chat-*` и как писать журнал изменений.
Журнал читают агенты, которые обновляют чужие приложения: по одной записи они должны понять, что
изменилось и что сделать в приложении.

## Как устроены версии

- Все пакеты из `.changeset/config.json` (группа `fixed`) выходят **вместе и с одной версией**:
  «SDK 0.3.0» = каждый пакет группы 0.3.0.
- Пока версия `0.x`: `minor` — новая возможность или ломающее изменение, `patch` — исправление.
- Пакеты публикуются в общий каталог npm (registry.npmjs.org), открыто, лицензия MIT.
- Дизайн-система `@ykurilov/tandem-ui` в эту группу **не входит**: у неё своя версия (см. ниже).

## Как выпустить обновление SDK

1. Вместе с кодом добавьте запись: `pnpm changeset` (или файл в `.changeset/` руками, шаблоны — в
   [.changeset/README.md](.changeset/README.md)). Закоммитьте вместе с кодом.
2. Запушьте `main` (рабочая папка чистая, локальный `main` совпадает с `origin/main`) и запустите:

   ```bash
   pnpm release
   ```

   Команда сама ничего не публикует: она запускает выпуск на GitHub Actions (`.github/workflows/release.yml`),
   печатает ссылку на прогон, ждёт итога и при сбое показывает конец журнала. Там, на чистой машине, тот же
   `scripts/release.mjs` по порядку: проверка открытой выгрузки → юнит-тесты и проверки правил → проверка типов →
   сборка → `changeset version` (поднимает версию у всех пакетов, дописывает `CHANGELOG.md`, удаляет записи) →
   коммит `chore(release): vX.Y.Z` → публикация в npm → ожидание, пока npm покажет новую версию → тег `vX.Y.Z` → push.
   После выпуска сделайте `git pull`: коммит выпуска и тег появились в `origin/main`.

   `pnpm release --dry-run` — сухой прогон в Actions (на текущей ветке, если она запушена, иначе на `main`):
   показывает, что выпуск сделал бы, и останавливается до `changeset version`, ничего не меняя и не публикуя.
   Тот же запуск есть кнопкой **Run workflow** у Release на вкладке Actions (галочка «Сухой прогон» стоит по умолчанию).

   **Запасной путь — выпуск с этой машины:** `pnpm release --local` (прежний порядок, ключ npm — см. ниже).
   Здесь проверки пропускаются, если `pnpm verify` уже прогнал их на этом же коде (см. «Проверки перед сдачей»);
   `pnpm release --local --full` проверяет заново принудительно, `pnpm release --local --dry-run` — сухой прогон.

- Записей в `.changeset` нет — команда остановится с пояснением, ничего не опубликовав.
- Первым делом выпуск проверяет открытую выгрузку на HEAD: `node scripts/export-public.mjs HEAD --check-only`
  (запретный список и gitleaks, если установлен; без сборки и клона, секунды). Нашлось запретное — стоп до новой версии.
- Сбой на публикации (сеть, токен): исправьте причину и снова `pnpm release`. Версия уже подготовлена,
  команда доведёт публикацию, тег и push до конца, не создавая новую версию.
- На GitHub Actions ключ npm — секрет хранилища `NPM_TOKEN`; когда настроена доверенная публикация npm
  (см. «Прогоны на GitHub Actions»), ключ не нужен.
- Для `--local` нужен ключ npm (Granular Access Token с правом записи в пакеты `@ykurilov`). Выпуск ищет его по порядку:
  переменная `NPM_TOKEN`, файл `~/.config/agent-chat-sdk/npm-token` (другой путь — `NPM_TOKEN_FILE` в окружении
  или строкой `NPM_TOKEN_FILE=…` в `~/.config/agent-chat-sdk/release.env`; этот файл — настройка своей машины, вне репозитория),
  строка `//registry.npmjs.org/:_authToken=…` в `~/.npmrc`. Ключ из переменной или файла попадает в публикацию
  через временный `.npmrc` со ссылкой `${NPM_TOKEN}`, который удаляется сразу после; сам ключ не печатается.
  В репозиторий ключ не кладётся.
- Полный браузерный прогон и замеры скорости в `pnpm release` не входят. Перед выпуском изменений,
  которые их касаются, запустите `pnpm test:e2e` (проверки поведения), а после правок, влияющих на скорость, —
  ещё и `pnpm test:e2e:perf` (замеры скорости, отдельной группой).

## Проверки перед сдачей

Перед сдачей (и перед выпуском) вместо трёх команд по отдельности запускайте одну:

```bash
pnpm verify    # pnpm test → pnpm typecheck → pnpm build
```

Всё зелёное — `verify` пишет отметку «код проверен» в `node_modules/.cache/agent-chat-verified.json`
(вне git). В отметке отпечаток кода: хеш содержимого всех файлов под git, включая незакоммиченные и новые,
плюс старшая версия Node. Хеша коммита нет. `pnpm release` считает отпечаток заново: совпал — пишет
«код уже проверен» и не повторяет test, typecheck и build; не совпал или отметки нет — гоняет как раньше.

- В отпечаток **не входят** только `CHANGES.md` и `.changeset/*.md`: их правят уже после проверки, на test,
  typecheck и build они не влияют. Всё остальное (код, тесты, конфиги, `.changeset/config.json`,
  `pnpm-lock.yaml`, документация, которую читают тесты) входит: правка любого такого файла после `verify` —
  и отметка не совпадёт.
- Отметка лежит в папке, где запускали `verify`. Выпуск идёт из `main`, поэтому `pnpm verify` запускайте
  в `main` после вливания ветки, а не только в рабочей ветке.
- Код менялся во время самой проверки — отметка не ставится.
- Сборка после `changeset version` (в ветке «версия подготовлена, но не опубликована») отметкой не
  пропускается: версия и журнал в `package.json` и `CHANGELOG.md` уже изменились.

## Сводка «Что нового по версиям»

В корне лежит [CHANGES.md](CHANGES.md): по одной-две строки на версию простыми словами и ссылки на журналы пакетов.
**При каждом выпуске** дописывайте в него новую версию сверху (тем же коммитом, что и `chore(release)`, или сразу перед
`pnpm release`). Подробности живут в `CHANGELOG.md` пакетов, в сводку они не копируются.

## Как писать запись об изменении

Читатель записи — агент, который обновляет чужое приложение и видит только текст записи. Пишите так,
чтобы ему не пришлось открывать код SDK.

1. **Что изменилось — простыми словами**, для человека: одно-два предложения. Не «рефакторинг X», а «ответ
   агента теперь появляется сразу, а не после первого токена».
2. **Пакеты в шапке** — только те, чей код изменился. Приложение читает `CHANGELOG.md` тех пакетов, которые
   поставило. Если изменение задевает несколько пакетов сразу, перечислите все.
3. **Ломающее изменение** (старый код приложения перестанет собираться или работать иначе):
   - первой строкой пометка **«Ломает приложения:»** и суть;
   - обязательный раздел **`### Как обновить приложение`**: нумерованные шаги, у каждого — в каком файле
     искать и что сделать; для кода — блоки «Было» и «Стало»;
   - последним шагом — как проверить (`pnpm typecheck`, что открыть, что должно получиться);
   - если поменялись имена, параметры, адреса или переменные окружения — перечислить их точно, не «и т. п.».
4. **Требуется действие без поломки** (новая обязательная настройка, новый пакет, миграция базы): тоже раздел
   «Как обновить приложение».
5. Запись без действий для приложения (внутренние правки, скорость, исправление) — раздела «Как обновить» не
   нужно, но строка «Обновление ничего не требует» обязательна: по ней агент понимает, что искать нечего.

Шаблоны — в [.changeset/README.md](.changeset/README.md).

## Где читать журнал

- В репозитории: `CHANGELOG.md` в папке каждого пакета (`packages/*/CHANGELOG.md`, `skins/tandem/CHANGELOG.md`).
- В приложении, которое поставило пакеты: `node_modules/@ykurilov/agent-chat-react/CHANGELOG.md` и так
  далее для каждого пакета (`CHANGELOG.md` входит в публикуемые файлы).
- Версия поднимается у всех пакетов сразу, но запись в журнале есть только у пакетов, которых она
  касалась. Нет записи о версии в журнале пакета — в нём для этой версии ничего не менялось.

## Как обновить приложение (для агента)

```bash
pnpm update "@ykurilov/agent-chat-*" --latest
```

Затем прочитать записи в `node_modules/@ykurilov/agent-chat-*/CHANGELOG.md` между старой и новой версией,
выполнить шаги из «Как обновить приложение», проверить `pnpm typecheck` и сборку.
Если в приложении стоит `@ykurilov/agent-chat-skin-tandem`, вместе с ним обновляется и `@ykurilov/tandem-ui`
(алиас `@tandem/ui`): его версию проверить в `package.json` приложения.

## Выпуск дизайн-системы Тандем (`@ykurilov/tandem-ui`)

Тандем живёт в своём репозитории, пакет публикуется в npm отдельно, со своей версией. Папку репозитория Тандема
скрипт берёт из переменной `TANDEM_REPO`:

```bash
TANDEM_REPO=<папка Тандема> scripts/publish-tandem.sh            # версия из packages/ui/package.json Тандема
TANDEM_REPO=<папка Тандема> scripts/publish-tandem.sh 0.3.0      # или версия, заданная вручную
```

Скрипт берёт **последний коммит** Тандема (`git archive HEAD`, незакоммиченные правки в выпуск не попадают) во
временную папку, ставит зависимости (`npm ci`, при этом собирается `dist`), переименовывает пакет в
`@ykurilov/tandem-ui`, прописывает npm и репозиторий и делает `npm publish`. Ключ npm — так же, как у
`pnpm release`. Репозиторий Тандема скрипт не меняет. Если такая версия уже в npm — остановится. Если в
`packages/ui/package.json` Тандема нет поля `license` — тоже остановится: лицензию Тандема выбирает автор.

После выпуска Тандема:

1. В `skins/tandem/package.json` и `apps/demo/package.json` поднять `"@tandem/ui": "npm:@ykurilov/tandem-ui@^X.Y.Z"`, `pnpm install`.
   Поправить ту же версию в инструкциях по установке: `skins/tandem/README.md` и `docs/getting-started.md` (две строки `pnpm add` и «Тандем 0.X.x»).
2. Добавить запись `.changeset` для `@ykurilov/agent-chat-skin-tandem` (что изменилось во внешнем виде и что
   нужно приложению) и сделать `pnpm release`.


## Что проверять перед выпуском вручную

`pnpm release` сам гоняет юнит-тесты, типы и сборку (если их не проверил `pnpm verify` на этом же коде). Дополнительно, когда меняются условия экспорта,
сборка или состав пакетов: `pnpm --filter @ykurilov/agent-chat-core pack` (в архиве должны быть `dist`,
README, CHANGELOG и не должно быть `src` и тестов) и `pnpm test:e2e:quick`. У `storage-postgres` в архиве
ещё папка `drizzle` (миграции). Если менялось подключение Next.js или сервер — `pnpm test:next`; если менялись
запросы или миграции PostgreSQL — прогон набора на настоящей базе: `AGENT_CHAT_TEST_POSTGRES_URL=… pnpm vitest run --project unit packages/storage-postgres`.
